```
QUESTION 01

What is a Load Balancer?

⭐⭐⭐⭐⭐ MOST FREQUENTLY ASKED

A load balancer distributes incoming application traffic across multiple backend targets such as EC2 instances, containers or IP addresses. Its main purpose is to improve:

→ Availability
→ Scalability
→ Fault tolerance
→ Traffic distribution

👤 Users → ⚖️ Load Balancer → 🖥️ EC2-A
↓ 🖥️ EC2-B
↓ 🖥️ EC2-C
💡 Real-Time Example

Suppose an application has three EC2 instances. Instead of users connecting directly to one EC2 instance, they connect to the Load Balancer. The Load Balancer distributes requests among healthy backend instances.

🎤 Interview Answer

"A Load Balancer distributes incoming traffic across multiple healthy backend targets. It improves application availability, scalability and fault tolerance by preventing traffic from depending on a single server."

QUESTION 02

What are the types of AWS Load Balancers?

⭐⭐⭐⭐⭐ VERY COMMON

AWS Elastic Load Balancing provides several load balancing options. The major ones to know are:

1. Application Load Balancer (ALB)
Layer 7 HTTP/HTTPS load balancing.

2. Network Load Balancer (NLB)
Layer 4 TCP/UDP/TLS load balancing.

3. Gateway Load Balancer (GWLB)
Used to deploy and scale network virtual appliances.

4. Classic Load Balancer (CLB)
Older generation load balancer. For new architectures, ALB or NLB is generally preferred depending on the requirement.

🎤 Interview Answer

"The main AWS Elastic Load Balancing options are Application Load Balancer, Network Load Balancer, Gateway Load Balancer and the older Classic Load Balancer. ALB is mainly used for HTTP/HTTPS applications, NLB for high-performance Layer 4 traffic, and GWLB for network appliances."

QUESTION 03

What is an Application Load Balancer (ALB)?

⭐⭐⭐⭐⭐ MUST KNOW FOR DEVOPS

An Application Load Balancer operates at Layer 7 of the OSI model. It is designed for HTTP and HTTPS applications. ALB can make routing decisions based on application-level information such as:

→ Hostname
→ URL path
→ HTTP headers
→ Query parameters

User → ALB : 443 → Target Group → EC2 : 8080
💡 Path-Based Routing Example

`/api/*` → API target group

`/web/*` → Web target group

🎤 Interview Answer

"Application Load Balancer is a Layer 7 load balancer designed for HTTP and HTTPS traffic. It supports advanced application-level routing such as host-based and path-based routing."

QUESTION 04

What is a Network Load Balancer (NLB)?

⭐⭐⭐⭐⭐ VERY COMMON

A Network Load Balancer operates primarily at Layer 4. It is designed for high-performance network traffic such as TCP, UDP and TLS use cases. NLB is useful when very high throughput, low latency, static IP requirements or non-HTTP protocols are needed.

Client → NLB → TCP / UDP → Target
💡 Example

If an application uses a custom TCP protocol rather than HTTP, NLB can be a better fit than ALB.

🎤 Interview Answer

"Network Load Balancer is a Layer 4 load balancer designed for high-performance TCP, UDP and TLS traffic. It is useful when low latency, high throughput or network-level load balancing is required."

QUESTION 05

What is the difference between ALB and NLB?

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE
Feature ALB NLB
OSI Layer Layer 7 Layer 4
Main Traffic HTTP / HTTPS TCP / UDP / TLS
Path Routing Yes No HTTP path routing
Host Routing Yes No HTTP host routing
Typical Use Web applications / APIs High-performance network traffic
💡 Easy Memory Trick

ALB = Application-level decisions
"Which URL or hostname?"

NLB = Network-level decisions
"Which TCP/UDP target?"

🎤 Interview Answer

"ALB works at Layer 7 and is mainly used for HTTP/HTTPS applications with features such as host and path based routing. NLB works at Layer 4 and is designed for high-performance TCP, UDP and TLS traffic."

QUESTION 06

What is a Target Group?

⭐⭐⭐⭐⭐ MUST KNOW

A Target Group is a logical group of backend targets that a load balancer sends traffic to. Depending on the load balancer and configuration, targets can include:

→ EC2 instances
→ IP addresses
→ Containers through supported integrations
→ Lambda functions for ALB use cases

ALB → Target Group → EC2-1
↓ EC2-2
↓ EC2-3
💡 Example

An ALB receives HTTPS traffic on port 443. The target group may forward that traffic to application servers listening on port 8080.

🎤 Interview Answer

"A target group is a logical collection of backend targets that receive traffic from a load balancer. It also contains settings such as the target port and health check configuration."

QUESTION 07

What is a Listener?

⭐⭐⭐⭐⭐ VERY COMMON

A Listener checks for incoming connection requests on a configured protocol and port. For example: 

```

HTTPS : 443
HTTP  : 80
```

The listener then uses listener rules to determine where the request should go.

Client → Listener : 443 → Listener Rule → Target Group
🎤 Interview Answer

"A listener checks for incoming connection requests on a configured protocol and port. For an ALB, listener rules can then route requests to the appropriate target group."

QUESTION 08

What is a health check in a Load Balancer?

⭐⭐⭐⭐⭐ VERY FREQUENT

A health check allows the load balancer to determine whether a registered target is healthy enough to receive traffic. For an HTTP application, an example health check might be: 

```

Protocol: HTTP
Port: 8080
Path: /health
```

If the target fails health checks, the load balancer stops routing new traffic to that unhealthy target.

💡 Real-Time Example

Suppose we have:

EC2-A → healthy
EC2-B → unhealthy
EC2-C → healthy

The Load Balancer sends traffic only to the healthy targets.

🎤 Interview Answer

"A load balancer health check periodically verifies whether a registered target is healthy. If a target fails the configured health checks, the load balancer stops sending new traffic to it until it becomes healthy again."

QUESTION 09

What is path-based routing?

⭐⭐⭐⭐⭐ ALB FAVORITE

Path-based routing allows an ALB to route requests to different target groups depending on the URL path.

/api/* → API Target Group

/payment/* → Payment Target Group

/web/* → Web Target Group
💡 Microservices Example

A single ALB can expose:

example.com/api → API service
example.com/payment → Payment service
example.com/orders → Order service

🎤 Interview Answer

"Path-based routing allows an ALB to route HTTP or HTTPS requests to different target groups based on the URL path. It is commonly used in microservices architectures."

QUESTION 10

What is host-based routing?

⭐⭐⭐⭐⭐ COMMON

Host-based routing allows an ALB to route requests based on the hostname in the HTTP request.

api.example.com → API Target Group

web.example.com → Web Target Group

admin.example.com → Admin Target Group
🎤 Interview Answer

"Host-based routing allows an Application Load Balancer to route HTTP or HTTPS requests to different target groups based on the requested hostname."

QUESTION 11

How does an ALB distribute traffic?

⭐⭐⭐⭐⭐

The ALB receives client requests through its listener, evaluates listener rules and forwards matching requests to a target group. The target group contains registered targets and health-check information. Only healthy targets are eligible to receive new traffic.

Client ↓ ALB ↓ Listener ↓ Listener Rule ↓ Target Group ↓ Healthy Targets
🎤 Interview Answer

"The ALB accepts client requests through a listener, evaluates its listener rules, selects the relevant target group and forwards the request to eligible healthy targets."

QUESTION 12

Why do we use a Load Balancer with Auto Scaling?

⭐⭐⭐⭐⭐ DEVOPS FAVORITE

Auto Scaling changes the number of backend instances according to demand. The Load Balancer provides a stable entry point and distributes traffic across the currently healthy instances.

Users ↓ Load Balancer ↓ Auto Scaling Group ↓ EC2-1 EC2-2 EC2-3 ↕ Scale Out / Scale In
💡 Example

During normal traffic:
2 EC2 instances

During high traffic:
Auto Scaling launches additional instances.

The Load Balancer automatically routes traffic to the healthy registered instances.

🎤 Interview Answer

"Auto Scaling manages the number of backend instances, while the Load Balancer distributes traffic among healthy instances. Together they provide scalability and high availability."

⭐⭐⭐⭐ High Priority

QUESTION 13

What is cross-zone load balancing?

⭐⭐⭐⭐ IMPORTANT

Cross-zone load balancing allows load balancing across targets in different Availability Zones rather than restricting distribution to targets associated with only the receiving zone. Exact behavior and configuration details depend on the load balancer type.

💡 Example

AZ-A has 2 healthy targets.
AZ-B has 5 healthy targets.

Cross-zone behavior can help distribute traffic more evenly across available targets according to the load balancer's configuration.

🎤 Interview Answer

"Cross-zone load balancing allows a load balancer to distribute traffic across targets in multiple Availability Zones. The exact default and configuration behavior depends on the load balancer type."

QUESTION 14

What is connection draining / deregistration delay?

⭐⭐⭐⭐ COMMON

When a target is being removed from service, the load balancer can allow existing connections or requests to complete instead of immediately terminating traffic. This helps prevent users from experiencing interrupted requests during deployments or scale-in events.

💡 DevOps Deployment Example

During deployment, an old application server is removed. Instead of killing active requests immediately, deregistration delay allows existing traffic to finish while new traffic is sent to healthy targets.

🎤 Interview Answer

"Deregistration delay allows existing connections or requests to finish when a target is being removed from service. It helps provide graceful deployments and reduces interrupted requests."

QUESTION 15

Can an ALB route traffic to different ports?

⭐⭐⭐⭐

Yes. The Load Balancer listener can accept traffic on one port and the target group can forward it to a configured target port.

Client → HTTPS : 443 → ALB → Target Group → EC2 : 8080
💡 Example

Users access:
HTTPS : 443

Application servers listen on:
HTTP : 8080

🎤 Interview Answer

"Yes. A load balancer can listen on one port and forward traffic to a target group configured for another target port, depending on the protocol and load balancer configuration."

QUESTION 16

Where should an internet-facing ALB be deployed?

⭐⭐⭐⭐⭐ VERY COMMON

An internet-facing ALB is associated with subnets that have network connectivity suitable for internet-facing access, typically public subnets in multiple Availability Zones. The ALB itself provides the public-facing entry point; backend application instances can remain in private subnets.

🌐 Internet ↓ Public Subnets ↓ ALB ↓ Private App Subnets ↓ Application Servers
🎤 Interview Answer

"An internet-facing ALB is placed across appropriate public subnets in multiple Availability Zones. Backend application servers can remain in private subnets and receive traffic from the ALB."

QUESTION 17

What is an internal Load Balancer?

⭐⭐⭐⭐

An internal load balancer is reachable through private network connectivity rather than being directly internet-facing. It is useful for internal applications and service-to- service communication.

💡 Microservices Example

Public ALB:
Internet → Frontend

Internal ALB:
Frontend → Internal API services

🎤 Interview Answer

"An internal Load Balancer provides a private entry point for applications inside a VPC or connected networks. It is commonly used for internal service communication."

QUESTION 18

What is SSL/TLS termination at the Load Balancer?

⭐⭐⭐⭐ VERY IMPORTANT

SSL/TLS termination means the Load Balancer handles the HTTPS encryption/decryption from the client. For example:

Client → HTTPS : 443 → ALB → HTTP : 8080 → Application

This can reduce the TLS processing burden on backend servers. The exact architecture should be selected based on security requirements.

🎤 Interview Answer

"TLS termination means the load balancer terminates the client's HTTPS connection. It decrypts the request and can forward it to backend targets using the configured protocol and port."

⭐⭐⭐ Medium Priority

QUESTION 19

What is weighted routing in ALB?

⭐⭐⭐

ALB listener rules can use weighted forwarding to send different proportions of traffic to multiple target groups. This is useful for controlled releases and testing.

💡 Canary Deployment

Version 1:
90% traffic

Version 2:
10% traffic

If version 2 is stable, the percentage can be increased gradually.

🎤 Interview Answer

"Weighted forwarding allows an ALB listener rule to distribute traffic across multiple target groups using configured weights. It can be useful for canary or controlled deployments."

QUESTION 20

What happens when all targets become unhealthy?

⭐⭐⭐ TROUBLESHOOTING

If the target group has no healthy targets, requests cannot be successfully served by normal healthy-target routing. The exact response and behavior depend on the load-balancer configuration and failure scenario. The first troubleshooting step is to determine why the health checks are failing.

💡 What to check

→ Health check path
→ Health check port
→ Application process
→ Security Group
→ NACL
→ Route table
→ Application response code

🎤 Interview Answer

"If all targets are unhealthy, the load balancer has no healthy backend target to serve normal traffic. I would immediately troubleshoot the health check path, port, application response and network security configuration."

QUESTION 21

Can a Load Balancer distribute traffic across multiple Availability Zones?

⭐⭐⭐ VERY COMMON

Yes. For high availability, load balancers are commonly configured across multiple Availability Zones. Backend targets can also be distributed across multiple Availability Zones.

Internet ↓ ALB ↙ ↘ AZ-A AZ-B ↓ ↓ EC2 EC2
🎤 Interview Answer

"Yes. AWS load balancers can be configured across multiple Availability Zones. This improves availability and helps applications continue operating if one Availability Zone has a problem."

QUESTION 22

What is sticky session / session persistence?

⭐⭐⭐

Sticky sessions allow a client's requests to be routed to the same target for a period of time, when the relevant load balancer feature is enabled and supported. This can be useful for applications that maintain session state locally on a backend server.

💡 Better architecture: Whenever possible, design applications to be stateless and store session state in shared services such as databases or caches rather than relying on one specific backend instance.
🎤 Interview Answer

"Sticky sessions keep a client's requests associated with the same backend target for a configured period. They can help legacy stateful applications, but stateless application design is generally preferred."

QUESTION 24

What is Gateway Load Balancer?

⭐⭐

Gateway Load Balancer is designed for deploying, scaling and managing virtual network appliances such as firewalls, intrusion detection systems and other security appliances. It operates using network-level technologies suited for transparent appliance insertion.

💡 Example

Traffic can be inspected by a security appliance fleet before reaching application workloads.

🎤 Interview Answer

"Gateway Load Balancer is used to deploy and scale third-party and custom virtual network appliances, such as firewalls and inspection systems."

QUESTION 25

Can we use an ALB for non-HTTP traffic?

⭐

ALB is designed for HTTP and HTTPS application traffic. If the application requires general TCP or UDP load balancing, an NLB is normally considered instead.

🎤 Interview Answer

"ALB is designed for HTTP and HTTPS application traffic. For TCP or UDP network-level load balancing, NLB is generally the appropriate choice."

🎯 Real-Time Load Balancer Scenarios

SCENARIO 01

ALB is reachable, but it returns 503. How do you troubleshoot?

⭐⭐⭐⭐⭐ VERY COMMON

A common cause is that the target group does not have healthy targets. I would check:

1. Target group health status
2. Health check path
3. Health check port
4. Application is running
5. Security group allows ALB → target traffic
6. NACLs
7. Application response
8. Target registration

Client → ALB ✅ → Target Group ❌ → No Healthy Target
🎤 Interview Answer

"I would first check the target group's health status. Then I would verify the health check path, port, application process, target registration and security group and NACL rules between the ALB and the backend."

SCENARIO 02

Target is registered but showing unhealthy. What do you check?

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE

I follow the traffic path.

Step 1: Check health check protocol.

Step 2: Check health check port.

Step 3: Check health check path.

Step 4: Test the application locally on the EC2 instance. 

```

curl http://localhost:8080/health
``` Step 5: Check the EC2 security group. It should allow traffic from the Load Balancer's security group on the application port.

Step 6: Check NACL and routing.

🎤 Interview Answer

"I would verify the health check configuration first, then test the endpoint directly from the instance. After that I would check the target security group, NACLs, routing and application logs."

SCENARIO 03

ALB works but users cannot reach the application. What will you check?

⭐⭐⭐⭐

I would check the complete request path:

DNS → ALB → Listener → Target Group → Health Check → Application

Specifically:

→ DNS record
→ ALB listener
→ Security Group
→ Target group
→ Target health
→ Application port
→ Application logs

SCENARIO 04

You deploy a new version and suddenly all targets become unhealthy. What could be wrong?

⭐⭐⭐⭐⭐ DEVOPS SCENARIO

Possible reasons:

→ New application is listening on a different port
→ Health check path changed
→ Application startup takes longer
→ Security group changed
→ Environment variable/configuration issue
→ Application returns an unexpected status code
→ Deployment broke the health endpoint

💡 Production Approach

First check target health details. Then check application logs. Test the health endpoint directly. If necessary, rollback the deployment.

🎤 Interview Answer

"After a deployment I would first compare the new version's port and health endpoint with the target group configuration. Then I would check application logs and target health details. If the new release is confirmed as the cause, I would rollback or shift traffic back to the previous healthy version."

SCENARIO 05

How would you design a highly available ALB architecture?

⭐⭐⭐⭐⭐ ARCHITECTURE
🌐 Users ↓ ⚖️ ALB ↙ ↘ AZ-A AZ-B ↓ ↓ App-1 App-2 ↓ ↓ Private Database Tier

I would:

→ Use multiple Availability Zones
→ Place the ALB across multiple subnets/AZs
→ Run backend instances across multiple AZs
→ Configure health checks
→ Use Auto Scaling where appropriate
→ Keep application servers private where possible
→ Use security groups with least privilege

🎤 Interview Answer

"I would deploy the ALB across multiple Availability Zones and place backend application instances across multiple AZs. I would configure health checks and Auto Scaling, keep backend instances private where possible and use security groups to allow only the required traffic."
```
