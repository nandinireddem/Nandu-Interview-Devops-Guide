QUESTION 01

What is AWS Auto Scaling?

⭐⭐⭐⭐⭐ MOST FREQUENTLY ASKED

AWS Auto Scaling is the ability to automatically adjust application capacity according to demand. In EC2-based architectures, an Auto Scaling Group (ASG) can automatically launch or terminate EC2 instances based on configured scaling policies.

Low Traffic → Fewer Instances
High Traffic → More Instances
💡 Real-Time Example

Suppose an application normally needs 2 EC2 instances. During a sale, traffic suddenly increases. The ASG can launch additional instances so the application can handle the increased load. When traffic decreases, unnecessary instances can be terminated.

🎤 Interview Answer

"AWS Auto Scaling automatically adjusts application capacity based on demand. With EC2 Auto Scaling Groups, instances can be launched or terminated according to scaling policies while maintaining the desired capacity."

QUESTION 02

What is an Auto Scaling Group?

⭐⭐⭐⭐⭐ TOP INTERVIEW QUESTION

An Auto Scaling Group is a logical group of EC2 instances that AWS manages as a unit. It maintains the desired number of instances and can automatically scale the group based on policies.

Launch Template ↓ Auto Scaling Group ↓ EC2 Instances ↓ Load Balancer
The three important ASG capacity values are:

Minimum Capacity → Lowest number of instances ASG should maintain.

Desired Capacity → Target number of instances ASG tries to maintain.

Maximum Capacity → Highest number of instances ASG can launch.
🎤 Interview Answer

"An Auto Scaling Group manages a collection of EC2 instances and maintains the configured desired capacity. It can scale between the minimum and maximum capacity based on scaling policies."

QUESTION 03

What are minimum, desired and maximum capacities?

⭐⭐⭐⭐⭐ VERY COMMON
Setting Meaning
Minimum Lowest number of instances the ASG should maintain.
Desired Number of instances the ASG attempts to maintain normally.
Maximum Upper limit of instances the ASG can launch.
💡 Example

If:

Min = 2
Desired = 3
Max = 6

The ASG normally maintains 3 instances and can scale down to 2 or up to 6.

🎤 Interview Answer

"Minimum defines the lowest capacity, desired is the normal target capacity, and maximum defines the highest number of instances the Auto Scaling Group can launch."

QUESTION 04

What is a Launch Template?

⭐⭐⭐⭐⭐ MUST KNOW

A Launch Template contains the configuration required to launch EC2 instances. It can define:

→ AMI
→ Instance type
→ Key pair
→ Security groups
→ IAM instance profile
→ Storage configuration
→ User data
→ Network configuration

💡 Why is it important?

When an ASG needs to launch a new instance, it needs to know what configuration the new EC2 instance should have. The Launch Template provides that configuration.

🎤 Interview Answer

"A Launch Template defines the configuration used to launch EC2 instances. Auto Scaling Groups can use the template to consistently create instances with the required AMI, instance type, security groups, IAM role and user data."

QUESTION 05

How does Auto Scaling work with a Load Balancer?

⭐⭐⭐⭐⭐ EXTREMELY IMPORTANT

The Load Balancer distributes incoming traffic across healthy EC2 instances. The Auto Scaling Group manages the number of EC2 instances.

Users ↓ Load Balancer ↓ ┌─────────────┐ │ EC2 Instance │ ├─────────────┤ │ EC2 Instance │ ├─────────────┤ │ EC2 Instance │ └─────────────┘ ↑ Auto Scaling Group
🔥 Real-Time Scenario

Traffic increases → ASG launches instances.
New instances pass health checks → LB begins sending traffic to them.
Traffic decreases → ASG terminates unnecessary instances.

🎤 Interview Answer

"The Load Balancer distributes traffic across healthy instances, while the Auto Scaling Group dynamically adjusts the number of instances based on demand. Together they provide scalability and high availability."

QUESTION 06

What are the different Auto Scaling policies?

⭐⭐⭐⭐⭐ MUST KNOW

Important scaling approaches include:

1. Target Tracking Scaling
Maintains a target metric value.

2. Step Scaling
Changes capacity by different amounts depending on how far a metric moves beyond thresholds.

3. Simple Scaling
Older policy approach using a single adjustment and cooldown behavior.

4. Scheduled Scaling
Scales based on a known schedule.

5. Predictive Scaling
Uses historical patterns to forecast future demand for supported workloads.

🎤 Interview Answer

"Common Auto Scaling strategies include target tracking, step scaling, scheduled scaling and predictive scaling. Target tracking is commonly used when I want the ASG to maintain a target metric such as average CPU utilization."

QUESTION 07

What is Target Tracking Scaling?

⭐⭐⭐⭐⭐ VERY FREQUENT

Target tracking automatically adjusts capacity to maintain a selected metric close to a target value.

💡 Example

Suppose target CPU utilization is configured as 50%.

CPU stays significantly above the target → ASG can add capacity.

CPU stays below the target → ASG can reduce capacity.

🎤 Interview Answer

"Target tracking scaling adjusts the number of instances to maintain a target value for a selected metric, such as average CPU utilization."

QUESTION 08

What is the difference between vertical and horizontal scaling?

⭐⭐⭐⭐⭐ COMMON
Horizontal Scaling Vertical Scaling
Add more instances Increase resources of one instance
Scale out / scale in Scale up / scale down
Common with Auto Scaling Groups Changes instance size/resources
🧠 Easy Example

2 EC2 → 5 EC2 = Horizontal Scaling

t3.medium → larger instance type = Vertical Scaling

🎤 Interview Answer

"Horizontal scaling means adding or removing instances, also called scale out and scale in. Vertical scaling means increasing or decreasing resources of an individual instance."

QUESTION 09

What is scale out and scale in?

⭐⭐⭐⭐⭐ MUST KNOW

Scale Out means adding more instances.

Scale In means removing instances.

Scale Out:
2 EC2 → 3 EC2 → 4 EC2 → 5 EC2

Scale In:
5 EC2 → 4 EC2 → 3 EC2
🎤 Interview Answer

"Scale out increases the number of instances to handle higher demand, while scale in decreases the number of instances when demand falls."

QUESTION 10

How does Auto Scaling maintain high availability?

⭐⭐⭐⭐⭐ TOP QUESTION

Auto Scaling can maintain instances across multiple Availability Zones. If an instance becomes unhealthy, the ASG can terminate it and launch a replacement according to the group's configuration.

AZ-A → EC2
AZ-B → EC2
AZ-C → EC2

Auto Scaling Group
🎤 Interview Answer

"I can configure an Auto Scaling Group across multiple Availability Zones. If an instance becomes unhealthy, the ASG can replace it, helping maintain application availability."

QUESTION 11

What happens if an EC2 instance in an ASG becomes unhealthy?

⭐⭐⭐⭐⭐ VERY COMMON

The ASG uses health checks to determine instance health. If an instance is considered unhealthy, the ASG can terminate the unhealthy instance and launch a replacement to maintain the desired capacity.

EC2 Unhealthy → ASG Detects → Terminate → Launch Replacement → Healthy Capacity Restored
🎤 Interview Answer

"When an instance in the Auto Scaling Group is detected as unhealthy, the ASG can terminate it and launch a replacement so that the group returns toward its desired capacity."

QUESTION 12

What are EC2 and ELB health checks in Auto Scaling?

⭐⭐⭐⭐⭐ IMPORTANT

An ASG can use EC2 instance health status. When integrated with a Load Balancer, the ASG can also use ELB health checks to determine whether an instance is actually serving traffic correctly.

💡 Example

An EC2 instance may be running normally at the operating-system level, but the application may be returning HTTP 500 errors. A Load Balancer health check can detect that the application is unhealthy.

🎤 Interview Answer

"EC2 health checks determine whether the instance is considered healthy, while ELB health checks can evaluate whether the instance is successfully serving application traffic. For load-balanced applications, I can configure the ASG to use ELB health checks."

⭐⭐⭐⭐ High Priority

QUESTION 13

What is cooldown in Auto Scaling?

⭐⭐⭐⭐

A cooldown period was designed to prevent an ASG from immediately performing additional scaling actions while the previous scaling action was still taking effect. Modern Auto Scaling generally relies heavily on policy-specific behavior and warm-up settings, so in interviews it is important to distinguish classic cooldown from instance warm-up.

🎯 Remember:

Cooldown → helps avoid rapid repeated scaling actions.
Instance Warmup → gives a newly launched instance time to initialize before metrics are used for scaling decisions.
🎤 Interview Answer

"Cooldown historically helped prevent repeated scaling actions immediately after a scale event. In modern ASG configurations, instance warm-up and policy-specific behavior are also important for controlling scaling decisions."

QUESTION 14

What is instance warm-up?

⭐⭐⭐⭐

Instance warm-up gives a newly launched EC2 instance time to initialize before its metrics are fully used in scaling calculations.

💡 Example

Suppose a new instance needs 3 minutes to install dependencies, start Docker containers and become ready. The scaling configuration should account for this startup period rather than immediately treating the instance as fully contributing capacity.

🎤 Interview Answer

"Instance warm-up allows newly launched instances time to initialize before their metrics are fully considered for scaling decisions. This helps avoid unnecessary repeated scaling."

QUESTION 15

What is Scheduled Scaling?

⭐⭐⭐⭐

Scheduled scaling changes ASG capacity according to a predefined schedule.

💡 Real-Time Example

An e-commerce application receives heavy traffic every evening. You can schedule additional capacity before the expected traffic period and reduce capacity after the traffic window.

🎤 Interview Answer

"Scheduled scaling is useful when demand follows a predictable pattern. I can configure the ASG to change its capacity at predefined times."

QUESTION 16

What is a Lifecycle Hook?

⭐⭐⭐⭐

A lifecycle hook pauses an instance during an Auto Scaling lifecycle transition so that custom actions can be performed. Important transitions include:

→ Launching
→ Terminating

💡 Example

Before terminating an instance, a lifecycle hook can provide time to perform a custom action such as collecting logs or completing cleanup.

🎤 Interview Answer

"An Auto Scaling lifecycle hook temporarily pauses an instance during launch or termination so that custom initialization, cleanup or other automation can run before the lifecycle transition continues."

QUESTION 17

What is a termination policy?

⭐⭐⭐⭐

A termination policy influences which instance the ASG selects when scaling in. The goal is to make the termination decision consistent with the configured policy and group state.

💡 Interview Thinking

When scaling from 5 instances to 4, the ASG needs to decide which instance should be removed. Termination policies influence that decision.

🎤 Interview Answer

"A termination policy determines how Auto Scaling selects instances to terminate when the group scales in. It can help control which instance is removed."

QUESTION 18

What is a Mixed Instances Policy?

⭐⭐⭐⭐

A Mixed Instances Policy allows an Auto Scaling Group to use multiple EC2 instance types and purchasing options. It is commonly used with:

→ On-Demand Instances
→ Spot Instances
→ Multiple instance types

🎤 Interview Answer

"A Mixed Instances Policy allows an ASG to use multiple instance types and can combine On-Demand and Spot capacity. It helps improve flexibility, availability and potentially cost efficiency."

⭐⭐⭐ Medium Priority

QUESTION 19

What is Predictive Scaling?

⭐⭐⭐

Predictive Scaling uses historical usage patterns to forecast future demand and proactively adjust capacity for supported workloads.

💡 Example

If an application consistently experiences high traffic every weekday at 10 AM, predictive scaling can use historical patterns to prepare capacity ahead of the expected demand.

🎤 Interview Answer

"Predictive scaling uses historical patterns to forecast future demand and proactively adjust capacity. It is useful when workload patterns are predictable."

QUESTION 20

What is Step Scaling?

⭐⭐⭐

Step scaling changes capacity by different amounts depending on how far a CloudWatch alarm metric is from its threshold.

💡 Example

CPU slightly above the threshold: → Add 1 instance

CPU significantly above the threshold: → Add 3 instances

🎤 Interview Answer

"Step scaling adjusts capacity by different amounts depending on the size of the metric deviation from the alarm threshold."

QUESTION 21

What is the relationship between CloudWatch and Auto Scaling?

⭐⭐⭐⭐⭐ IMPORTANT

CloudWatch provides metrics and alarms that can be used by Auto Scaling policies.

EC2 → CloudWatch Metrics → Alarm / Scaling Policy → Auto Scaling Group → Launch / Terminate EC2
💡 Example

Average CPU remains above a configured target.
CloudWatch metrics reflect the workload.
Scaling policy determines the required capacity adjustment.
ASG launches additional instances.

🎤 Interview Answer

"CloudWatch provides monitoring metrics and alarms that Auto Scaling policies can use to make scaling decisions. The ASG then adjusts EC2 capacity based on those policies."

⭐⭐ Less Frequently Asked

QUESTION 22

What is a warm pool?

⭐⭐

An Auto Scaling warm pool keeps pre-initialized EC2 instances in a stopped or hibernated state so they can be moved into service more quickly when additional capacity is needed.

💡 Use Case

If application instances require a long startup process, a warm pool can reduce the time needed to bring additional capacity into service.

QUESTION 23

Can an Auto Scaling Group use multiple Availability Zones?

⭐⭐⭐

Yes. This is a common architecture for improving availability and resilience.

ASG ↓ ┌──────────┬──────────┬──────────┐ │ AZ-A │ AZ-B │ AZ-C │ │ EC2 │ EC2 │ EC2 │ └──────────┴──────────┴──────────┘
🎤 Interview Answer

"Yes. An Auto Scaling Group can span multiple Availability Zones. This helps distribute capacity and improves application availability."

🎯 Real-Time Interview Scenarios

SCENARIO 01

Traffic suddenly increases from 1,000 users to 50,000 users. What happens?

⭐⭐⭐⭐⭐ VERY IMPORTANT

In a properly configured architecture:

1. Load increases on the application.
2. CloudWatch metrics reflect the increased workload.
3. Auto Scaling policy detects the scaling condition.
4. ASG launches additional EC2 instances.
5. New instances initialize.
6. Load Balancer health checks verify them.
7. Healthy instances start receiving traffic.

🎤 Strong Interview Answer

"I would use an ALB in front of an Auto Scaling Group. CloudWatch metrics and the configured scaling policy would trigger scale-out when demand increases. Newly launched instances would pass health checks before receiving production traffic."

SCENARIO 02

CPU is 90%, but Auto Scaling is not launching instances. What do you check?

⭐⭐⭐⭐⭐ TROUBLESHOOTING

I would check step by step:

1. Is the ASG scaling policy attached?
2. Is the policy using the expected metric?
3. Is the desired capacity already equal to maximum capacity?
4. Is there an active alarm or scaling condition?
5. Is the Launch Template valid?
6. Are there EC2 capacity/quota issues?
7. Is instance warm-up or another scaling constraint affecting the decision?

🎤 Strong Interview Answer

"I would first verify the ASG min, desired and max capacity, then check the scaling policy and its CloudWatch metric or alarm. I would also inspect scaling activity history, launch template configuration, EC2 capacity errors and quotas."

SCENARIO 03

ASG keeps launching instances and terminating them repeatedly. What could be wrong?

⭐⭐⭐⭐⭐ TROUBLESHOOTING

This can happen when instances fail health checks or initialization repeatedly. Check:

→ Application startup
→ User data script
→ Security groups
→ Load Balancer health checks
→ Target group configuration
→ Application port
→ AMI configuration
→ Instance warm-up
→ ASG activity history

🎤 Strong Interview Answer

"I would check the ASG activity history and determine why instances are being marked unhealthy. Then I would verify the application startup, user data, target group health checks, ports, security groups and AMI configuration."

SCENARIO 04

How would you design a highly available EC2 application?

⭐⭐⭐⭐⭐ ARCHITECTURE QUESTION
Users ↓ Route 53 ↓ Application Load Balancer ↓ Auto Scaling Group ↓ EC2 Instances ↓ Multiple Availability Zones

I would distribute EC2 instances across multiple Availability Zones using an Auto Scaling Group and put an Application Load Balancer in front of them.

🎤 Strong Interview Answer

"I would deploy an ALB across multiple Availability Zones and place EC2 instances in an Auto Scaling Group spanning those zones. Health checks would remove unhealthy instances from traffic and the ASG would replace failed capacity."
