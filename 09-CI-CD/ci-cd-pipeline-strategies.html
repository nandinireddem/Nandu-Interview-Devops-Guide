⭐⭐⭐⭐⭐ 2. Build Once, Deploy Many

The preferred approach is to build and validate an application once, create a versioned artifact, and promote that same artifact through different environments.

Avoid rebuilding the application separately for every environment when the goal is to promote the same tested artifact. Environment- specific configuration should be supplied separately.

⭐⭐⭐⭐⭐ 3. Environment Promotion

Environment Purpose
Development Early integration and developer validation.
QA / Testing Functional, integration and regression testing.
Staging Production-like final validation.
Production Serve real users.
A release should normally progress through controlled gates rather than directly moving every untested change into production.

⭐⭐⭐⭐⭐ 4. Rolling Deployment

A Rolling Deployment gradually replaces old application instances with new instances instead of replacing everything at once.

Advantages

  • Usually no need for a completely separate environment.
  • Gradual rollout.
  • Can reduce deployment risk.
  • Common in Kubernetes.

Disadvantages

  • Old and new versions may temporarily coexist.
  • Rollback can be more complicated for stateful changes.

Blue-Green deployment maintains two environments or versions. Traffic is directed to one version while the other is prepared.

Advantages

  • Fast traffic switch.
  • Easy conceptual rollback.
  • Full new version can be tested before switching traffic.

Disadvantages

  • Can require additional infrastructure.
  • Database compatibility must be handled carefully.

⭐⭐⭐⭐⭐ 7. Rolling vs Blue-Green vs Canary

Strategy Core Idea Main Benefit
Rolling Gradually replace instances. Controlled incremental rollout.
Blue-Green Maintain old and new versions and switch traffic. Fast switch and rollback.
Canary Send a small amount of traffic to the new version. Small blast radius.
Easy memory:

Rolling → Replace gradually
Blue-Green → Switch environments
Canary → Release to a small percentage

Important requirements

  • Multiple application instances.
  • Load balancing.
  • Health checks.
  • Graceful shutdown.
  • Backward-compatible changes.
  • Safe database migration strategy.

⭐⭐⭐⭐⭐ 9. Rollback Strategy

Rollback means returning the application to a previously known-good version after a failed or unsafe release.
v1.0 ✅
↓
v1.1 🚀
↓
Production Error ❌
↓
Detect
↓
Rollback
↓
v1.0 ✅

Good rollback practices

  • Keep previous versions available.
  • Use immutable/versioned artifacts.
  • Automate rollback where appropriate.
  • Monitor deployment health.
  • Test rollback procedures.
Application rollback does not automatically mean database rollback. Database changes require separate compatibility and migration planning.

⭐⭐⭐⭐⭐ 10. Manual Approval Gates

An approval gate pauses the pipeline before a sensitive action, such as production deployment, until an authorized person approves it.

⭐⭐⭐⭐ 11. Feature Flags

A feature flag allows application functionality to be enabled or disabled through configuration without necessarily deploying a new application version.
Example: A new payment feature is deployed but initially disabled. After validation, the team enables it for a small group of users and then gradually increases exposure.
Feature flags should be managed securely and cleaned up when they are no longer needed. Old flags can create unnecessary application complexity.

⭐⭐⭐⭐ 12. Release vs Deployment

Deployment means installing or making a version available in an environment. Release means making functionality available to users. These can be separated using techniques such as feature flags.
A new application version can be deployed to production while a new feature remains disabled. The deployment happened, but the feature has not yet been released to users.

⭐⭐⭐⭐⭐ 13. Immutable Artifacts

An immutable artifact should not be modified after it is built and validated. 
payment-app:1.8.0
payment-app:git-a82f31c
payment-app:build-245
Avoid overwriting the same production artifact tag with different content. Immutable versioning improves traceability and rollback.

⭐⭐⭐⭐⭐ 15. Production Release Strategy

A safe production workflow can look like:

1. Build artifact.
2. Run automated tests.
3. Perform security checks.
4. Publish immutable artifact.
5. Deploy to staging.
6. Validate staging.
7. Obtain approval if required.
8. Deploy using Rolling, Blue-Green or Canary.
9. Monitor health and business metrics.
10. Roll back if defined failure thresholds are reached.

⭐⭐⭐⭐⭐ 16. Real-Time Scenario: Production Deployment Failed

Problem: A new version is deployed and error rates increase sharply.

Response: 1. Confirm the issue through monitoring and logs.
2. Stop further rollout.
3. Assess impact.
4. Roll back or shift traffic to the known-good version.
5. Investigate the root cause.
6. Fix and validate the new version.
7. Retry deployment through the normal pipeline.
The priority is to restore service safely first, then investigate the root cause.

⭐⭐⭐⭐⭐ 17. Real-Time Scenario: Zero Downtime

Question: "How would you deploy a new version without downtime?"

Answer approach: Use multiple healthy instances behind a load balancer, deploy the new version gradually, configure readiness/health checks, wait for new instances to become healthy, then remove old instances.

⭐⭐⭐⭐⭐ 18. Real-Time Scenario: Canary Failure

Suppose 10% of traffic is sent to version 2.0. Monitoring shows: 
Error Rate: 0.5% → 8%
Latency:    200ms → 900ms
The rollout should be paused and the traffic can be shifted back to the stable version while the issue is investigated.

⭐⭐⭐⭐⭐ 19. How to Choose a Deployment Strategy?

Requirement Possible Choice
Simple gradual replacement Rolling
Fast switch between complete versions Blue-Green
Small initial user exposure Canary
Very high-risk release Canary + strong monitoring
Need quick traffic reversal Blue-Green can be suitable
There is no universally best deployment strategy. The choice depends on application architecture, traffic, infrastructure cost, data compatibility, monitoring maturity and business risk.

🎯 If Interviewer Says: "Explain Deployment Strategies"

"In CI/CD, deployment strategies define how a new application version is introduced into an environment. With Rolling Deployment, old instances are gradually replaced with new ones. With Blue-Green Deployment, we maintain the old and new versions and switch traffic between them, which can make rollback quick. With Canary Deployment, we expose the new version to a small percentage of users first, monitor metrics such as error rate and latency, and gradually increase traffic if the release is healthy. For zero-downtime deployment, I would use multiple instances, load balancing, health checks and a controlled rollout. I also prefer building an immutable versioned artifact once and promoting that same artifact across environments. If a deployment causes a production issue, monitoring should detect it and we can pause or roll back to the known-good version."
