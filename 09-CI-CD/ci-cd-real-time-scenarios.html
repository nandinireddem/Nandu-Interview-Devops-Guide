CI/CD Real-Time Scenarios

Production-focused DevOps interview scenarios covering Jenkins, Git, Docker, registries, Kubernetes, GitOps, deployments, rollback, security and troubleshooting.

⭐⭐⭐⭐⭐ How to Approach Any CI/CD Scenario

1. Identify the failure
↓
2. Find the affected layer
↓
3. Check logs / status / metrics
↓
4. Fix or mitigate
↓
5. Verify
↓
6. Prevent recurrence
In interviews, don't immediately jump to random commands. First identify where the failure is occurring, then troubleshoot layer by layer.

⭐⭐⭐⭐⭐ 1. Jenkins Pipeline Suddenly Fails

Question: "Your Jenkins pipeline was working yesterday but suddenly started failing. What will you do?"

Approach

  1. Check which stage failed.
  2. Read Jenkins console output.
  3. Identify whether the failure is code, dependency, credential, agent, network or infrastructure related.
  4. Compare with the last successful build.
  5. Check recent changes.
  6. Fix the root cause and rerun safely.
Jenkins
→ Build History
→ Failed Build
→ Console Output
→ Failed Stage
→ Root Cause
Interview-ready: "I would first identify the exact failed stage rather than assuming Jenkins itself is broken. Then I would inspect console logs, compare the failed build with the last successful build, check recent code or environment changes, validate credentials and dependencies, fix the root cause and rerun the pipeline."

⭐⭐⭐⭐⭐ 2. Jenkins Agent Is Offline

A pipeline cannot start because the Jenkins agent is offline.

Check

  • Agent status in Jenkins.
  • Machine availability.
  • Network connectivity.
  • Jenkins agent process/service.
  • Disk space.
  • CPU and memory.
  • Java/runtime compatibility.
The key is to distinguish between a Jenkins controller problem and an agent execution problem.

⭐⭐⭐⭐⭐ 3. Git Webhook Is Not Triggering Jenkins

Developer pushes code to Git, but Jenkins does not start.
Git Push
↓
Webhook
❌
Jenkins

Troubleshooting

  1. Check whether the webhook exists.
  2. Check webhook delivery history.
  3. Verify Jenkins URL.
  4. Check webhook secret if configured.
  5. Check Jenkins job trigger configuration.
  6. Check network/firewall accessibility.
  7. Check branch/filter configuration.
A successful Git push does not guarantee that the webhook reached Jenkins successfully.

⭐⭐⭐⭐⭐ 4. Docker Build Fails in Jenkins

The pipeline reaches the Docker build stage and fails. 
docker build -t myapp:1.0.0 .

Check

  • Dockerfile syntax.
  • Build context.
  • Missing files.
  • Base image availability.
  • Network access.
  • Docker daemon availability.
  • Agent permissions.
  • Disk space.
I would inspect the exact Docker build error first. Common causes include an invalid Dockerfile, missing files in the build context, base-image pull failures or Docker daemon/permission problems.

⭐⭐⭐⭐⭐ 5. Docker Image Push Fails

Image builds successfully but the push to the registry fails.
Docker Build
✅
↓
Docker Image
✅
↓
Registry Push
❌

Check

  1. Registry URL.
  2. Authentication.
  3. Repository name.
  4. Image tag.
  5. Network connectivity.
  6. Registry permissions.
  7. Credential configuration.
docker images

docker login <registry>

docker push <registry>/myapp:1.0.0

⭐⭐⭐⭐⭐ 6. Kubernetes Cannot Pull the Image

Pod status: 
ImagePullBackOff
ErrImagePull

Check

  1. Image name.
  2. Image tag.
  3. Registry availability.
  4. Image existence.
  5. Registry authentication.
  6. Image pull secret if required.
  7. Node network access.
kubectl describe pod <pod-name>

kubectl get events
The most useful first command is often kubectl describe pod because Kubernetes events can reveal why the image pull failed.

⭐⭐⭐⭐⭐ 7. Pod Goes Into CrashLoopBackOff

The image is pulled successfully, but the container repeatedly exits.

Check

kubectl get pods

kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>

Common causes

  • Application startup error.
  • Wrong environment variables.
  • Missing configuration.
  • Database connection failure.
  • Incorrect command or arguments.
  • Application exits immediately.
  • Resource problems.

⭐⭐⭐⭐⭐ 8. Kubernetes Deployment Is Stuck

The pipeline succeeds, but the new deployment never becomes healthy.
Deployment
↓
ReplicaSet
↓
Pods
↓
❌ Not Ready

Commands

kubectl get deployment

kubectl rollout status deployment/myapp

kubectl get pods

kubectl describe pod <pod-name>

kubectl get events
Check whether the issue is image pulling, scheduling, startup, readiness probes, configuration, resources or networking.

⭐⭐⭐⭐⭐ 9. Readiness Probe Is Failing

The application is running, but Kubernetes keeps the Pod out of service because the readiness probe fails.

Check

  • Probe path.
  • Probe port.
  • Application startup time.
  • Service binding address.
  • Application health endpoint.
  • Network policy if applicable.
kubectl describe pod <pod-name>

kubectl logs <pod-name>
Readiness means "can this Pod receive traffic?" Liveness means "is this container still healthy enough to keep running?"

⭐⭐⭐⭐⭐ 10. Production Deployment Causes Errors

After deploying version 2.0, HTTP 5xx errors increase.
Deploy v2
↓
5xx ↑
↓
Stop Rollout
↓
Assess Impact
↓
Rollback / Shift Traffic
↓
Restore Service
↓
Root Cause Analysis
My first priority would be restoring service. I would stop further rollout, verify the impact through monitoring, roll back or shift traffic to the known-good version, and then investigate the root cause.

⭐⭐⭐⭐⭐ 11. How Do You Roll Back Kubernetes?

Kubernetes Deployments maintain rollout history that can be used to return to a previous revision. 
kubectl rollout history deployment/myapp

kubectl rollout undo deployment/myapp

kubectl rollout status deployment/myapp
Rollback of the application version does not automatically solve an incompatible database migration. Application and database changes must be designed for safe compatibility.

⭐⭐⭐⭐⭐ 12. Terraform Stage Fails in CI/CD

Pipeline reaches Terraform and terraform plan fails.

Check

  1. Terraform syntax.
  2. Provider configuration.
  3. Credentials/identity.
  4. Backend configuration.
  5. State locking.
  6. Variable values.
  7. Cloud permissions.
  8. Provider/resource changes.
terraform fmt -check

terraform init

terraform validate

terraform plan

⭐⭐⭐⭐⭐ 13. Terraform State Lock Error

Two CI jobs attempt to modify the same Terraform state.
Terraform state locking prevents concurrent operations from modifying the same state simultaneously when the backend supports locking.
Do not blindly force-unlock a state. First confirm whether another Terraform operation is actually running.

⭐⭐⭐⭐⭐ 14. ArgoCD Shows OutOfSync

ArgoCD reports: 
OutOfSync

Possible causes

  • Git desired state differs from cluster state.
  • Manual kubectl changes.
  • Application configuration drift.
  • Manifest generation differences.
  • Synchronization is disabled or pending.
Git Desired State
≠
Cluster Actual State
↓
ArgoCD Detects Drift
↓
Sync
↓
Desired State Restored

⭐⭐⭐⭐⭐ 15. ArgoCD Application Is Degraded

ArgoCD successfully synchronizes the manifests, but the application is marked degraded.
This means Git synchronization itself may have succeeded, but the resulting Kubernetes resources are not healthy.

Check

kubectl get pods

kubectl get deployment

kubectl describe pod <pod-name>

kubectl logs <pod-name>
ArgoCD can report the Kubernetes application health, but the actual root cause may be inside Kubernetes resources or the application.

⭐⭐⭐⭐⭐ 16. Pipeline Is Slow

A pipeline that previously took 8 minutes now takes 25 minutes.

Approach

  1. Identify the slowest stage.
  2. Compare current and previous build durations.
  3. Check dependency downloads.
  4. Check Docker build caching.
  5. Check test execution.
  6. Check Jenkins agent resources.
  7. Check external service latency.
Optimize the bottleneck instead of blindly adding more parallel stages.

⭐⭐⭐⭐ 17. Pipeline Works Manually but Fails Automatically

The developer runs the same command manually and it works, but the Jenkins pipeline fails.

Common reasons

  • Different environment variables.
  • Different working directory.
  • Different user permissions.
  • Different PATH.
  • Missing credentials.
  • Different runtime version.
  • Different agent environment.
I would compare the runtime environment between the successful manual execution and the Jenkins agent rather than assuming the command is wrong.

⭐⭐⭐⭐ 18. Secret Accidentally Appears in Jenkins Logs

A cloud credential appears in build output.

Immediate response

  1. Stop exposing the secret.
  2. Rotate/revoke the compromised credential.
  3. Check whether logs were accessible externally.
  4. Remove insecure logging.
  5. Move credentials into secure secret storage.
  6. Review pipeline permissions.
Treat an exposed credential as compromised even if the log was generated accidentally.

⭐⭐⭐⭐⭐ 19. Zero-Downtime Deployment Scenario

Question: "How would you deploy a new version without downtime?"

Answer: "I would run multiple application instances behind a load balancer. I would deploy the new version gradually, use readiness and health checks, wait until the new instances are healthy, and then remove the old instances. Depending on the application, I could use Rolling, Blue-Green or Canary deployment."

⭐⭐⭐⭐⭐ 20. Canary Deployment Failure

10% of users receive version 2.0. Monitoring shows: 
Error Rate: 0.4% → 7%
Latency:    180ms → 850ms
Action: Pause the rollout, reduce or stop traffic to version 2.0, restore the stable version if necessary, investigate the issue and only continue after validation.

⭐⭐⭐⭐⭐ 21. Database Migration Breaks Deployment

A new application version requires a database schema change. After deployment, the old application version can no longer work with the new schema.
This is a compatibility problem. A safer strategy is often to use backward-compatible database changes first, deploy application changes that work with both schema versions, migrate data if needed, and remove old compatibility later.
Never assume application rollback automatically makes a destructive database migration safe to reverse.

⭐⭐⭐⭐ 22. Build Passed but Production Failed

"All CI tests passed. Why can production still fail?"
CI tests may not cover every production condition. Possible causes include:
  • Environment-specific configuration.
  • Missing production secrets.
  • Different infrastructure.
  • External dependency failure.
  • Production traffic patterns.
  • Database differences.
  • Resource limits.
  • Networking or DNS issues.

⭐⭐⭐⭐⭐ 24. Production Is Down After Deployment

Situation: Users report that the application is unavailable immediately after a release. Response: 1. Confirm the incident through monitoring.
2. Identify whether the release caused the problem.
3. Stop further deployment.
4. Check application, Pod, Service and Ingress health.
5. Roll back if required.
6. Verify recovery.
7. Preserve logs and evidence.
8. Perform root-cause analysis after stabilization.
Priority: Restore service → stabilize → investigate → prevent recurrence.

⭐⭐⭐⭐⭐ 25. Complete End-to-End Failure Scenario

Scenario: Developer pushes code. Jenkins succeeds. Docker image is pushed to ECR. ArgoCD syncs successfully. But users receive HTTP 503.

Layer-by-layer investigation:

Git → Code exists
Jenkins → Build succeeded
Docker → Image exists
Registry → Image available
ArgoCD → Desired state synchronized
Kubernetes → Check Pods
Service → Check endpoints
Ingress → Check routing
Application → Check logs and health 
kubectl get pods

kubectl get svc

kubectl get endpoints

kubectl get ingress

kubectl describe ingress <name>

kubectl logs <pod-name>
This is a strong troubleshooting approach because each layer is validated independently instead of blaming the last tool in the pipeline.

🎯 Master Interview Answer: CI/CD Troubleshooting

"When troubleshooting a CI/CD issue, I first identify the exact stage where the failure occurred. I don't assume that the last tool used is necessarily the root cause. I check the logs and status of the affected component and compare the failed execution with the last successful execution. For example, if the pipeline fails during Docker push, I check the registry URL, authentication, repository, image tag and permissions. If Kubernetes deployment fails, I check Pod status, events, image pulling, application logs, readiness probes and resource issues. For a production failure after deployment, my first priority is to restore service. I would stop the rollout, assess the impact and rollback or shift traffic to a known-good version if appropriate. After recovery, I investigate the root cause and add preventive controls such as better testing, monitoring, validation or automated deployment gates."
