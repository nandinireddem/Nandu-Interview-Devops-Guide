CI/CD Basics

Core CI/CD concepts for DevOps interviews — Continuous Integration, Continuous Delivery, Continuous Deployment, pipeline stages, automation, benefits and real-world workflow.

⭐⭐⭐⭐⭐ 1. What is CI/CD?

CI/CD is a software delivery approach that automates the process of integrating code, validating changes, building artifacts and delivering or deploying applications.
👨‍💻 Developer
↓
📦 Git Repository
↓
⚙️ CI
↓
🧪 Build + Test + Scan
↓
📦 Artifact / Image
↓
🚀 CD
↓
☸️ Deployment
Real-time example: A developer pushes code to GitHub. A pipeline automatically builds the application, runs tests and security checks, creates a Docker image and deploys it to Kubernetes.

⭐⭐⭐⭐⭐ 2. What is Continuous Integration?

Continuous Integration (CI) is the practice of frequently integrating code changes into a shared repository and automatically validating those changes through builds and tests.

Typical CI Flow

Code Commit
↓
Build
↓
Unit Tests
↓
Code Quality
↓
Security Scan
↓
Artifact
Interview answer:

"Continuous Integration means developers frequently merge their changes into a shared repository, where an automated pipeline builds and tests the code to detect problems early."

⭐⭐⭐⭐⭐ 3. What is Continuous Delivery?

Continuous Delivery means the application is automatically built, tested and prepared for release so that it is always in a deployable state. The production deployment may require a manual approval.
Code
↓
CI
↓
Build + Test
↓
Package
↓
Staging
↓
Manual Approval
↓
Production
The key idea is: Software is always ready to be deployed, but production release may still require human approval.

⭐⭐⭐⭐⭐ 4. What is Continuous Deployment?

Continuous Deployment automatically deploys changes to production after they successfully pass the required automated checks. There is no manual production approval in the normal successful path.
Code
↓
Build
↓
Test
↓
Security
↓
Deploy Production
↓
Monitor
If a company has strong automated testing, security controls, deployment verification and monitoring, it may use Continuous Deployment to release changes automatically.

⭐⭐⭐⭐⭐ 5. CI vs Continuous Delivery vs Continuous Deployment

Concept Main Focus Production Deployment
CI Integrate, build and test code frequently Not the main purpose
Continuous Delivery Keep software ready for release Usually requires approval
Continuous Deployment Automatically release validated changes Automatically deployed
Easy interview trick:

CI = Integrate + Validate
Continuous Delivery = Always Ready to Deploy
Continuous Deployment = Automatically Deploy

⭐⭐⭐⭐⭐ 7. Why do we automate CI/CD?

  • Reduce manual errors.
  • Get faster feedback.
  • Release software more frequently.
  • Standardize deployment processes.
  • Detect bugs earlier.
  • Improve release consistency.
  • Support repeatable deployments.
  • Reduce operational effort.
Instead of manually copying application files to servers after every release, the pipeline performs the same validated deployment process consistently.

⭐⭐⭐⭐⭐ 8. Benefits of CI/CD

Benefit Explanation
Faster Releases Automation reduces manual release effort.
Early Bug Detection Automated tests run soon after code changes.
Consistency The same pipeline process can be reused for deployments.
Better Quality Testing and quality checks are integrated into delivery.
Lower Risk Small, frequent changes are generally easier to validate and roll back.

⭐⭐⭐⭐ 10. What is an Artifact?

An artifact is a versioned output produced by the build process that can be stored and used later for deployment.

Examples

  • JAR file
  • WAR file
  • ZIP package
  • Docker image
  • Compiled application package
For example, a Java pipeline may build: 
payment-service-1.5.0.jar
That artifact can then be promoted through different environments.

⭐⭐⭐⭐⭐ 11. CI/CD Across Environments

Development
↓
Testing
↓
QA
↓
Staging
↓
Production
A mature pipeline promotes a validated build through environments using controlled configuration and deployment policies.
Avoid rebuilding different application binaries for every environment when the goal is to promote the same tested artifact. Environment- specific configuration should normally be handled separately.

⭐⭐⭐⭐ 12. What triggers a CI/CD pipeline?

A pipeline can be triggered by different events.

  • Git push
  • Pull request
  • Merge to a branch
  • Tag creation
  • Scheduled execution
  • Manual execution
  • API or webhook events
Common example: A developer pushes code to the main branch → Git provider sends a webhook → CI/CD server starts the pipeline.

⭐⭐⭐⭐⭐ 13. What happens when a pipeline fails?

The pipeline should normally stop at the failed stage and prevent the invalid build from progressing to later deployment stages.
Build
↓
Test ❌
↓
Pipeline Stops
↓
Developer Investigates
↓
Fix
↓
New Pipeline Run
A failed pipeline is useful because it provides fast feedback before a bad change reaches later environments.

⭐⭐⭐⭐⭐ 14. Why is rollback important?

Rollback allows the team to return to a previously known-good version when a deployment introduces a serious problem.
Version 1.4
↓
Version 1.5 🚀
↓
Production Issue ❌
↓
Rollback
↓
Version 1.4 ✅

Rollback strategies are discussed in more detail in the CI/CD Pipeline Strategies module.

⭐⭐⭐⭐⭐ 15. Real-Time End-to-End Example

A developer modifies a payment application.

1. Code is pushed to GitHub.
2. CI pipeline is triggered.
3. Application is built.
4. Unit and integration tests execute.
5. Code and dependencies are scanned.
6. Docker image is created.
7. Image is pushed to a container registry.
8. Deployment is triggered.
9. Kubernetes deploys the new version.
10. Health checks and monitoring verify the deployment.
Interview-ready summary:

"I would design the CI/CD pipeline so that every code change is validated through automated build, testing and security stages. After producing a versioned artifact or container image, the validated version is promoted through environments and deployed using a controlled deployment strategy. Monitoring and health checks then verify the release."

🎯 If Interviewer Says: "Explain CI/CD"

"CI/CD is an approach used to automate and improve the software delivery lifecycle. Continuous Integration means developers frequently integrate code changes into a shared repository and automatically build and test those changes. Continuous Delivery keeps the application in a deployable state, usually with an approval before production. Continuous Deployment goes one step further by automatically deploying successfully validated changes to production. A typical pipeline includes source control, build, testing, security checks, artifact creation, deployment and monitoring. In a real DevOps environment, tools such as Git, Jenkins, Docker, Kubernetes and cloud services can work together to create an automated and repeatable delivery process."
