Last-minute interview revision covering CI/CD concepts, pipeline flow, Jenkins, GitHub Actions, Docker, Kubernetes, GitOps, security, deployment strategies and troubleshooting.

⭐⭐⭐⭐⭐ 1. What is CI/CD?

CI — Continuous Integration Developers frequently integrate code into a shared repository. Automated builds and tests validate the changes.

CD — Continuous Delivery / Continuous Deployment Continuous Delivery keeps validated changes ready for release. Continuous Deployment automatically releases validated changes to production.

Integrates code frequently Delivers/releases code
Builds application Deploys application
Runs automated tests Runs deployment processes
Finds integration problems early Reduces release effort/risk

⭐⭐⭐⭐⭐ 5. Continuous Delivery vs Deployment

Continuous Delivery: The application is automatically built, tested and prepared for release, but production release may require approval or another controlled step.

Continuous Deployment: Every change that passes the required automated checks can be automatically deployed to production.

⭐⭐⭐⭐⭐ 8. Docker in CI/CD

Docker packages the application and its runtime dependencies into a container image. This helps create consistent environments between development, testing and deployment. 
docker build -t myapp:1.0 .

docker tag myapp:1.0 registry/myapp:1.0

docker push registry/myapp:1.0

⭐⭐⭐⭐⭐ 9. Why Use Image Tags?

Tags identify different versions of an image. A strong CI/CD practice is to use immutable identifiers such as commit SHA or release version. 
myapp:1.0.0
myapp:1.1.0

myapp:git-a83f91c
Avoid relying only on latest for production deployments because it does not clearly identify the exact application version.

⭐⭐⭐⭐⭐ 17. Rollback

Rollback returns the application to a known-good version when a release causes unacceptable problems. 
kubectl rollout history deployment/myapp

kubectl rollout undo deployment/myapp

kubectl rollout status deployment/myapp
Application rollback does not automatically make a destructive database migration reversible.

⭐⭐⭐⭐⭐ 18. Pipeline Security

  • Never hard-code credentials.
  • Use secret management.
  • Apply least privilege.
  • Scan source and dependencies.
  • Scan container images.
  • Protect production environments.
  • Use short-lived/federated credentials where possible.
  • Do not expose secrets in logs.

⭐⭐⭐⭐⭐ 21. Common CI/CD Failures

Problem First Things to Check
Git checkout failure Repository, branch, credentials, network.
Build failure Dependencies, runtime, source changes.
Test failure Test logs and recent code changes.
Docker build failure Dockerfile, build context, base image.
Docker push failure Registry, authentication, permissions, tag.
ImagePullBackOff Image name, tag, registry credentials.
CrashLoopBackOff Application logs, configuration, startup command.
Readiness failure Probe path, port, application health.
ArgoCD OutOfSync Git desired state vs cluster state.
Production 5xx Application, Pods, Service, Ingress, recent release.

🎯 25. Best Interview Answer: Explain Your CI/CD Pipeline

"In my CI/CD approach, developers push code to GitHub, which triggers the CI pipeline. The pipeline checks out the code, builds the application and runs automated tests. I can integrate code-quality and security scanning before creating the Docker image. The Docker image is tagged with a unique version such as the commit SHA and pushed to a container registry such as Amazon ECR. For deployment, Kubernetes runs the application, while GitOps tools such as ArgoCD can continuously reconcile the desired deployment state from Git. Finally, monitoring with Prometheus and Grafana helps detect application and infrastructure issues. If a production deployment causes problems, I prioritize restoring service, stop the rollout or rollback to a known-good version, and then perform root-cause analysis."
