🔥 ⭐⭐⭐⭐⭐ 2. Why Should Containers Not Run as Root?

By default, some containers may run processes as root inside the container. Running applications as a dedicated non-root user follows the principle of least privilege and can reduce the impact of a container compromise.

Dockerfile example

FROM node:22-alpine

WORKDIR /app

COPY . .

RUN addgroup -S appgroup \
    && adduser -S appuser -G appgroup

USER appuser

CMD ["node","server.js"]
Non-root containers are an important defense, but they do not replace other security controls.

⭐⭐⭐⭐⭐ 3. USER Instruction

USER appuser
The Dockerfile USER instruction specifies the user that will run subsequent commands and, unless overridden, the main container process.

Check the running user

docker exec <container> id
Interview scenario: An application does not require root privileges. I would create a dedicated application user and switch to it with USER before starting the application.

Container images can contain vulnerable operating-system packages, application dependencies or libraries.

Common causes

  • Old base images
  • Unpatched OS packages
  • Outdated application dependencies
  • Unused packages
  • Unmaintained libraries
  • Untrusted third-party images

⭐⭐⭐⭐⭐ 6. Vulnerability Severity

Security scanners commonly classify vulnerabilities by severity, for example:

Severity Typical Interpretation
CRITICAL Very high potential impact; usually requires immediate attention.
HIGH Significant risk requiring prompt remediation.
MEDIUM Moderate risk evaluated according to environment and exposure.
LOW Lower-risk finding that should still be tracked.
A scanner finding does not automatically mean the application is exploitable in your exact environment. Teams should assess severity, exposure, exploitability and business impact.

⭐⭐⭐⭐⭐ 7. Why Use Minimal Base Images?

A smaller runtime image generally contains fewer packages and components, which can reduce the attack surface and image size.

Example

FROM python:3.13-slim

Minimal does not automatically mean secure. The image must still be maintained and scanned.

⭐⭐⭐⭐⭐ 8. Use Trusted Base Images

Base images should come from trusted sources and should be regularly updated and scanned.

Bad practice

FROM random-image:latest

Better practice

FROM python:3.13-slim

In enterprise environments, organizations may also maintain approved internal base images.

⭐⭐⭐⭐ 9. Why Avoid latest in Production?

FROM nginx:latest
The latest tag is mutable. A future build can therefore use a different image than an earlier build.

Prefer controlled versions:

FROM nginx:1.29-alpine

For stronger reproducibility, an image digest can be pinned.

🔥 ⭐⭐⭐⭐⭐ 10. How Should Secrets Be Handled?

Never hardcode passwords, API keys, cloud credentials or private keys into Dockerfiles or source code.

Do not do this

ENV AWS_SECRET_ACCESS_KEY=supersecret

Better options

  • Cloud secret managers
  • CI/CD secret stores
  • Runtime secret injection
  • Docker/Swarm secrets where applicable
  • Kubernetes Secrets with appropriate protection
"I would keep secrets outside the image and inject them at deployment or runtime using the platform's secret-management mechanism."

⭐⭐⭐⭐⭐ 11. Why Deleting a Secret From Dockerfile Is Not Enough

Suppose a secret was accidentally included in an image layer. Later you remove the line from the Dockerfile. That does not necessarily make the previously built image or its layers safe.

Correct response

  1. Immediately rotate/revoke the exposed credential.
  2. Stop using the compromised credential.
  3. Remove the secret from source/history where appropriate.
  4. Rebuild the image.
  5. Scan the new image.
  6. Review registry and CI/CD exposure.
Treat an exposed credential as compromised. Do not assume deleting the visible file makes the credential safe.

🔥 ⭐⭐⭐⭐⭐ 12. Why Is /var/run/docker.sock Sensitive?

-v /var/run/docker.sock:/var/run/docker.sock
The Docker socket provides access to the Docker daemon API. Giving a container access to the host Docker socket can effectively grant very powerful control over Docker-managed resources.
Do not mount the Docker socket into containers unless there is a specific, well-understood requirement and the security implications have been accepted.

Interview question

Why is Docker socket access dangerous?

Because access to the Docker daemon can allow powerful operations against containers, images, volumes and potentially the host.

🔥 ⭐⭐⭐⭐⭐ 13. What Does --privileged Do?

docker run --privileged myimage
Privileged mode significantly expands the capabilities available to a container and reduces many of Docker's normal isolation restrictions.
Avoid --privileged unless there is a legitimate, documented requirement. It should not be used as a default solution for permission problems.

🔥 ⭐⭐⭐⭐⭐ 14. Linux Capabilities

Linux capabilities divide traditional root privileges into smaller privilege sets. Docker can add or drop capabilities for containers.

Drop unnecessary capabilities

docker run \
  --cap-drop=ALL \
  myimage

Add only what is required

docker run \
  --cap-drop=ALL \
  --cap-add=NET_BIND_SERVICE \
  myimage
Principle: Give the container only the privileges it actually needs.

⭐⭐⭐⭐⭐ 15. Read-Only Root Filesystem

docker run \
  --read-only \
  myimage
A read-only root filesystem prevents normal writes to the container's root filesystem.

If the application needs writable storage, explicitly provide the required writable volume or temporary filesystem.

Example

docker run \
  --read-only \
  --tmpfs /tmp \
  myimage

⭐⭐⭐⭐⭐ 16. Container Network Security

Containers should only communicate with the services they actually need to reach.

Good practices

  • Use dedicated Docker networks.
  • Do not expose unnecessary ports.
  • Publish only required host ports.
  • Separate application tiers where appropriate.
  • Restrict external access with firewalls/security groups.

⭐⭐⭐⭐ 17. EXPOSE vs Published Ports

EXPOSE -p / --publish
Documents the container port in image metadata. Publishes a container port through the host.
Does not make the port externally reachable by itself. Creates host-to-container port mapping. 
EXPOSE 8080
docker run -p 8080:8080 myimage

⭐⭐⭐⭐⭐ 18. Resource Limits

Resource limits can reduce the impact of runaway or compromised containers consuming excessive host resources.

Memory

docker run --memory=512m myimage

CPU

docker run --cpus="1.0" myimage
Production scenario: A container has a memory leak and continuously consumes host memory. A suitable memory limit can prevent that single container from consuming unlimited memory and affecting other workloads.

⭐⭐⭐⭐ 19. PID Limits

docker run --pids-limit=100 myimage
A PID limit restricts the number of processes that a container can create. This can help reduce the impact of process-exhaustion attacks or runaway applications.

⭐⭐⭐⭐ 20. Seccomp

Seccomp is a Linux kernel security mechanism that can restrict the system calls a process is allowed to make. Docker uses a default seccomp profile unless configured otherwise.
The goal is to reduce the available kernel attack surface by limiting unnecessary system calls.

⭐⭐⭐ 21. AppArmor and SELinux

Technology Purpose
AppArmor Mandatory access-control mechanism based on application profiles.
SELinux Mandatory access-control framework using security labels and policies.

Both can provide additional host-level controls around what processes and containers are allowed to access.

🔥 ⭐⭐⭐⭐⭐ 22. Why Protect the Docker Daemon?

The Docker daemon has powerful control over containers, images, networks, volumes and host resources. Therefore, unauthorized access to the daemon is highly sensitive.

Best practices

  • Restrict access to the Docker socket.
  • Do not expose the daemon unnecessarily.
  • Use appropriate access controls.
  • Protect the host operating system.
  • Keep Docker components updated.

⭐⭐⭐⭐ 25. Secure Container Registry Practices

  • Use private repositories for sensitive images.
  • Restrict push/pull permissions.
  • Enable vulnerability scanning.
  • Use immutable/versioned image tags where possible.
  • Remove obsolete vulnerable images according to policy.
  • Protect registry credentials.
  • Use image signing/provenance where supported.
A CI pipeline should authenticate to the registry using a short-lived or securely stored credential rather than exposing a developer's personal password.

⭐⭐⭐⭐⭐ 27. Scenario — Container Is Running as Root

Problem: A production container runs its application as UID 0.

Approach: Create a dedicated user, ensure the application files have the correct ownership, switch to that user with USER, then test the application.

⭐⭐⭐⭐⭐ 28. Scenario — Trivy Finds Critical Vulnerabilities

Do not simply ignore the scan.

First identify which package is vulnerable and whether a fixed version is available. Then update the base image or dependency, rebuild the image and scan again.

⭐⭐⭐⭐⭐ 29. Scenario — Container Requests Docker Socket

Question: A monitoring or automation container asks for: 
/var/run/docker.sock
Would you approve it immediately?

Answer: No. I would first understand why the access is required, assess the security implications, look for alternatives and restrict access as much as possible.

⭐⭐⭐⭐⭐ 30. Scenario — Developer Uses --privileged

Do not treat --privileged as a general fix for permission errors.
"I would identify the exact operation requiring additional privileges and grant only the necessary capability or device access, instead of enabling full privileged mode."

⭐⭐⭐⭐⭐ 31. Scenario — Secret Found in Docker Image

Immediate actions:
  1. Revoke or rotate the secret.
  2. Determine where it was exposed.
  3. Remove it from source and image build process.
  4. Clean repository history if necessary.
  5. Rebuild the image.
  6. Scan the rebuilt image.
  7. Check logs, registries and CI systems for exposure.
The first priority is credential rotation, not merely deleting the secret from a file.

🎯 Explain Docker Security in 1 Minute

"Docker security starts from the image build process and continues through container runtime and deployment. I would use trusted and appropriately minimal base images, scan images for vulnerabilities using tools such as Trivy, and keep dependencies updated. Containers should run as non-root users whenever possible, and I would avoid unnecessary privileges such as privileged mode or excessive Linux capabilities. Secrets should never be hardcoded into Dockerfiles or images. They should be injected securely through the deployment platform or a secret-management solution. I would also restrict Docker socket access, control network exposure, use resource limits, and consider read-only filesystems and security profiles. In CI/CD, I would scan images before pushing or promoting them and apply security policies before production deployment. The overall principle is least privilege, minimal attack surface, secure supply chain and defense in depth."
