Interview definition: Docker Compose is a tool for defining and running multi-container applications using a YAML file that describes services, networks, volumes and configuration.

⭐⭐⭐⭐⭐ 1. Why Do We Need Docker Compose?

Running multiple containers manually can become difficult. Compose allows the entire application stack to be described as configuration and started with a small number of commands.

Example application

  • Frontend
  • Backend API
  • MySQL
  • Redis
Frontend ↓
Backend ↓
MySQL
+
Redis

Instead of maintaining many separate docker run commands, these services can be defined in one Compose file.

⭐⭐⭐⭐⭐ 2. What is docker-compose.yml?

The Compose YAML file defines how the application's services should be built, configured, connected and run.

Basic structure

services:

  backend:
    image: my-backend:1.0
    ports:
      - "8080:8080"

  database:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: example

Modern Docker Compose uses the docker compose command. The older docker-compose command is also seen in older projects.

⭐⭐⭐⭐⭐ 3. What is a Service in Docker Compose?

A service represents a containerized application component defined inside the Compose configuration. 
services:

  frontend:
    image: nginx

  backend:
    image: my-backend

  database:
    image: mysql:8
Here: frontend → service backend → service database → service Compose uses these definitions to create and manage the corresponding containers.

⭐⭐⭐⭐⭐ 4. image vs build

image build
Uses an existing Docker image. Builds an image from a Dockerfile/context.
Useful for official or prebuilt images. Useful for your application source code.

Using an image

services:
  nginx:
    image: nginx:latest

Using build

services:
  backend:
    build: ./backend

Build with Dockerfile

services:
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile

⭐⭐⭐⭐ 5. Ports in Compose

services:

    ports:
      - "8080:8080"
The left side is the host port and the right side is the container port.

Port publishing is mainly needed when the service must be reached from outside the Compose network.

⭐⭐⭐⭐⭐ 6. Environment Variables

services:

  backend:
    image: my-backend
    environment:
      DB_HOST: database
      DB_PORT: 3306
      APP_ENV: production

Using .env

services:

  backend:
    image: my-backend
    environment:
      DB_HOST: ${DB_HOST}
      DB_PORT: ${DB_PORT}

.env

DB_HOST=database
DB_PORT=3306
Do not put real passwords, API keys or cloud credentials directly into source-controlled Compose files.

⭐⭐⭐⭐⭐ 8. Networks in Compose

Compose can create networks that allow services to communicate. 

services:

  backend:
    image: my-backend
    networks:
      - app-network

  database:
    image: mysql:8
    networks:
      - app-network

networks:
  app-network:
Services on the same Compose network can normally communicate using their service names.

⭐⭐⭐⭐⭐ 9. Service Name as Hostname

services:

  backend:
    image: my-backend

  database:
    image: mysql:8

The backend can normally reach the database using: 

DB_HOST=database
Do not use the container IP as the application's permanent database hostname. Service names provide a more stable Compose-level communication mechanism.

⭐⭐⭐⭐⭐ 10. depends_on

Why use depends_on?

It expresses a startup/shutdown dependency between Compose services. 
services:

  backend:
    image: my-backend
    depends_on:
      - database

  database:
    image: mysql:8
Important interview point: depends_on controls service dependency/startup ordering, but it does not automatically guarantee that the database is ready to accept connections.

⭐⭐⭐⭐⭐ 11. Healthchecks

A healthcheck can be used to determine whether a service is actually ready or healthy. 

services:

  database:
    image: mysql:8
    environment:
      MYSQL_ROOT_PASSWORD: example

    healthcheck:
      test:
        - CMD-SHELL
        - mysqladmin ping -h localhost -pexample
      interval: 10s
      timeout: 5s
      retries: 5

Healthchecks are useful when an application depends on another service becoming operational rather than merely starting.

⭐⭐⭐⭐ 12. Restart Policies

services:

  backend:
    image: my-backend
    restart: unless-stopped
Policy Meaning
no Do not automatically restart.
always Restart the container according to Docker's restart behavior.
on-failure Restart when the container exits with a failure.
unless-stopped Restart unless it has been explicitly stopped.

⭐⭐⭐⭐⭐ 14. docker compose up vs down

Command Purpose
docker compose up Creates/starts the application services.
docker compose up -d Runs services in detached mode.
docker compose up --build Builds images and starts services.
docker compose down Stops and removes Compose-created containers and networks.
Be aware of persistent volumes before using destructive cleanup options. Do not remove database storage accidentally.

⭐⭐⭐⭐⭐ 15. Real-Time Backend + MySQL Example

docker-compose.yml

services:

  backend:
    build: ./backend
    ports:
      - "8080:8080"
    environment:
      DB_HOST: database
      DB_PORT: 3306
      DB_NAME: appdb
      DB_USER: appuser
      DB_PASSWORD: example

⭐⭐⭐⭐⭐ 16. Three-Tier Application Using Compose

services:

  frontend:
    build: ./frontend
    ports:
      - "3000:3000"

  backend:
    build: ./backend
    ports:
      - "8080:8080"
    depends_on:
      - database

  database:
    image: mysql:8
    volumes:
      - db-data:/var/lib/mysql

volumes:
  db-data:
Architecture: Frontend handles user requests. Backend handles business logic. Database stores persistent data. Compose manages the complete local multi-container stack.

⭐⭐⭐⭐ 18. Development vs Production Configuration

Teams may use different Compose configurations for different environments. 

docker-compose.yml
docker-compose.dev.yml
docker-compose.prod.yml
For example, development might mount source code into the container for rapid iteration, while production should generally use a versioned image rather than a developer's local source directory.

⭐⭐⭐⭐⭐ 19. Secrets in Docker Compose

Never commit production passwords, AWS credentials, private keys or API tokens into a Git repository.

Better approaches

  • Environment-specific secret injection
  • CI/CD secret stores
  • Cloud secret managers
  • Docker/Swarm secrets where applicable
  • Kubernetes Secrets for Kubernetes deployments
Interview answer: "I would avoid hardcoding secrets in Compose files. For production, I would inject secrets through the CI/CD or deployment platform and prefer a dedicated secret-management solution."

Check:

  • Network configuration
  • Volume mounts
  • Healthchecks
  • Application logs

⭐⭐⭐⭐⭐ 21. Common Interview Scenarios

Scenario 1 — Backend cannot connect to database

Check whether both services are running, whether they share the appropriate network, whether the backend uses the database service name as hostname, and whether the database is actually ready.

Scenario 2 — Port already in use

docker compose ps

docker ps

Choose another host port or stop the process/container occupying the required port.

Scenario 3 — Database data disappeared

Check whether the database was using a persistent named volume. Containers should not be treated as the durable storage layer for database data.

Scenario 4 — Configuration changed but container still uses old value

docker compose up -d --build

Also verify the effective Compose configuration and environment variables.

🎯 Explain Docker Compose in 1 Minute

"Docker Compose is used to define and run multi-container applications from a YAML configuration file. For example, a typical application may contain frontend, backend and database services. Instead of running each container manually, I can define these services in a Compose file. Each service can specify an image or build context, ports, environment variables, volumes, networks and dependencies. Services can communicate using their Compose service names, and named volumes can be used to persist database data. I can start the complete stack using docker compose up -d, check logs with docker compose logs, inspect the services with docker compose ps, and stop the stack using docker compose down. In a DevOps workflow, Compose is useful for local development, integration testing and consistent multi-container environments."
