⭐⭐⭐⭐⭐ 1. What is Docker?

Docker is a containerization platform used to package an application together with its dependencies into a portable container image.

Why Docker?

  • Consistent application environments
  • Lightweight compared with traditional VMs
  • Fast application startup
  • Isolation between applications
  • Portable deployment
  • Useful for CI/CD and microservices
Interview answer:

"Docker packages an application and its dependencies into a container image so that the application can run consistently across different environments."

⭐⭐⭐⭐⭐ 2. Docker vs Virtual Machine

Docker Container Virtual Machine
Shares host OS kernel Includes a guest OS
Lightweight Heavier
Starts quickly Usually slower to start
Uses fewer resources Uses more resources
Application-level isolation Full OS-level virtualization
Hardware → Host OS → Docker Engine → Containers
Hardware → Hypervisor → Virtual Machines → Guest OS → Application

⭐⭐⭐⭐⭐ 3. Docker Architecture

Docker CLI
↓
Docker Daemon
↓
Images / Containers / Networks / Volumes
↓
Docker Registry

Main components

  • Docker Client: Sends commands to Docker.
  • Docker Daemon: Manages Docker objects and container lifecycle.
  • Docker Engine: Provides the Docker runtime environment.
  • Docker Image: Read-only template used to create containers.
  • Container: Running instance of an image.
  • Registry: Stores and distributes images.

⭐⭐⭐⭐⭐ 4. Image vs Container

Image Container
Immutable template Running instance of an image
Used to create containers Runs the application
Stored locally or in registry Runs on Docker host
Simple memory trick:

Image = blueprint
Container = running object created from the blueprint

⭐⭐⭐⭐⭐ 6. Dockerfile — Must Know Instructions

Instruction Purpose
FROM Defines base image
WORKDIR Sets working directory
COPY Copies files into image
RUN Executes commands while building image
ENV Defines environment variables
EXPOSE Documents intended container port
CMD Provides default runtime command
ENTRYPOINT Defines the main executable

Example

FROM nginx:alpine

WORKDIR /app

COPY . .

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

⭐⭐⭐⭐⭐ 7. CMD vs ENTRYPOINT

CMD ENTRYPOINT
Default command/arguments Main executable
Can be easily overridden More strongly defines container purpose
Often used for defaults Often used for executable behavior
A common pattern is using ENTRYPOINT for the main application and CMD for default arguments.

⭐⭐⭐⭐⭐ 8. Docker Image Layers & Caching

Docker images are built from layers. Docker can reuse unchanged layers from previous builds, which can make builds faster.

Best practices

  • Use a suitable small base image
  • Order Dockerfile instructions carefully
  • Copy dependency files before application source when appropriate
  • Use .dockerignore
  • Avoid unnecessary packages
  • Use multi-stage builds
If application source changes frequently but dependencies rarely change, placing dependency installation before copying the frequently changing source can improve build-cache reuse.

⭐⭐⭐⭐⭐ 9. Multi-Stage Docker Build

A multi-stage build uses multiple stages in one Dockerfile so that build dependencies can be separated from the final runtime image. 
FROM node:20 AS builder

WORKDIR /app

COPY package*.json ./
RUN npm install

COPY . .
RUN npm run build


FROM nginx:alpine

COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
Why? Smaller final images, fewer unnecessary build dependencies and a cleaner production runtime.

⭐⭐⭐⭐⭐ 12. Port Mapping

Containers have their own network namespace. Port publishing maps a host port to a container port. 
docker run -d -p 8080:80 nginx
Host Port 8080 ↓ Docker Port Mapping ↓ Container Port 80
EXPOSE in a Dockerfile does not itself publish the port. Use -p or an appropriate Compose configuration to publish a port.

⭐⭐⭐⭐⭐ 13. Docker Networking

Network Typical Use
bridge Common default network for containers
host Container shares host networking
none No normal network connectivity

Container-to-container communication

On a user-defined Docker network, containers can communicate using container/service names rather than relying on hard-coded IP addresses. 
docker network create app-net

docker run -d --name db --network app-net postgres

docker run -d --name app --network app-net myapp

⭐⭐⭐⭐⭐ 14. Volumes vs Bind Mounts

Docker Volume Bind Mount
Managed by Docker Uses a host filesystem path
Good for persistent application data Useful when host path control is needed
Portable Docker-managed storage Tightly connected to host filesystem 
docker volume create app-data

docker run -d \
  -v app-data:/var/lib/data \
  myapp
Containers are generally ephemeral, so persistent application data should not depend only on the container's writable layer.

⭐⭐⭐⭐⭐ 15. Docker Compose

Docker Compose is used to define and run multi-container applications using a declarative YAML configuration. 
services:

  app:
    image: myapp:1.0
    ports:
      - "8080:8080"

  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: example
docker compose up -d

docker compose ps

docker compose logs

docker compose down
Typical example: application container + database + cache + reverse proxy running together as one development/test environment.

⭐⭐⭐⭐⭐ 16. Docker Registry

A Docker registry stores and distributes container images. Docker Hub is one example; organizations can also use private registries such as Amazon ECR or other enterprise registries.
Developer ↓ docker build ↓ Image ↓ docker tag ↓ docker push ↓ Registry ↓ docker pull ↓ Deployment Environment 
docker login

docker tag myapp:1.0 username/myapp:1.0

docker push username/myapp:1.0

docker pull username/myapp:1.0

⭐⭐⭐⭐⭐ 17. Docker Security

  • Use trusted/minimal base images
  • Scan images for vulnerabilities
  • Do not store secrets in Dockerfiles
  • Do not bake credentials into images
  • Run containers as non-root where practical
  • Keep images and dependencies updated
  • Use read-only filesystems where appropriate
  • Limit Linux capabilities
  • Use private registries for sensitive workloads
Never put passwords, API keys, AWS credentials or private keys directly inside a Dockerfile or image.

⭐⭐⭐⭐⭐ 18. Dockerfile Secrets — Common Trap

Do NOT do this:

ENV AWS_SECRET_ACCESS_KEY=secret

The secret can become part of the image configuration/history.

Better approach

  • Inject secrets at runtime
  • Use CI/CD secret management
  • Use cloud secret managers
  • Use Docker/BuildKit secret mechanisms when build-time secrets are required

⭐⭐⭐⭐⭐ 19. HEALTHCHECK

A Docker health check allows Docker to determine whether a container's application is responding as expected. 
HEALTHCHECK --interval=30s --timeout=5s \
  CMD curl -f http://localhost:8080/health || exit 1
A container can be running while the application inside it is unhealthy. That is why process status and application health are not always the same thing.

⭐⭐⭐⭐ 20. Resource Limits

Containers can be constrained so one workload does not consume unbounded host resources. 
docker run -d \
  --memory="512m" \
  --cpus="1.0" \
  myapp
In production, resource requests/limits should be designed according to workload behavior and the orchestration platform being used.

⭐⭐⭐⭐⭐ 21. Docker Troubleshooting — Container Exits Immediately

Problem: Container starts and immediately stops.

Investigation

docker ps -a

docker logs <container>

docker inspect <container>

docker image inspect <image>

Common causes

  • Main process exited
  • Incorrect CMD/ENTRYPOINT
  • Application crashed
  • Missing environment variable
  • Incorrect configuration
  • Port/configuration issue

⭐⭐⭐⭐⭐ 22. Troubleshooting: Container Cannot Reach Another Container

Check whether both containers are attached to the same user-defined network and whether the application is listening on the expected port. 
docker network ls

docker network inspect app-net

docker inspect <container>
Use service/container names on a user-defined network rather than hard-coding dynamic container IP addresses.

⭐⭐⭐⭐⭐ 23. Troubleshooting: Image Build Is Too Large

  • Check the Dockerfile layers
  • Use a smaller runtime base image
  • Use multi-stage builds
  • Add a proper .dockerignore
  • Remove unnecessary build artifacts
  • Avoid installing unnecessary packages
docker images

docker history myapp:1.0

⭐⭐⭐⭐⭐ 24. Real-Time Scenario: Application Works Locally but Not in Docker

Approach:

I would compare the local and container environments, inspect logs, verify environment variables, check exposed/listening ports, inspect the container filesystem and verify dependencies. 
docker logs <container>

docker exec -it <container> sh

docker inspect <container>

⭐⭐⭐⭐⭐ 25. Real-Time Scenario: Container Is Using Too Much CPU

docker stats

Then investigate the application process, workload pattern, memory usage and logs. Resource limits can be configured where appropriate. 

docker update --cpus="1.0" <container>

⭐⭐⭐⭐⭐ 26. Real-Time Scenario: Image Has a Vulnerability

Do not simply ignore the finding. Identify the vulnerable package or base image, update the dependency/base image, rebuild the image and scan again before deployment.
Image ↓ Security Scan ↓ Vulnerability ↓ Update Dependency/Base Image ↓ Rebuild ↓ Rescan ↓ Deploy

⭐⭐⭐⭐⭐ 27. Docker + CI/CD

Git Push ↓ CI Pipeline ↓ Build ↓ Unit Tests ↓ Docker Build ↓ Security Scan ↓ Tag Image ↓ Push Registry ↓ Deploy ↓ Health Check
Interview answer:

"In a DevOps pipeline, Docker provides a consistent packaging format. After code is pushed, CI can build the image, run tests and security scans, tag the image, push it to a registry and deploy the immutable image to the target environment."

⭐⭐⭐⭐⭐ 28. Image Tagging Strategy

Avoid relying only on mutable tags such as latest for production deployments. Prefer immutable or traceable version tags. 
myapp:1.4.2
myapp:2026-08-12
myapp:<commit-sha>
A CI pipeline can build an image tagged with the Git commit SHA. That makes it easier to identify exactly which source revision was deployed.

⭐⭐⭐⭐⭐ 29. Docker vs Kubernetes

Docker Kubernetes
Containerization platform Container orchestration platform
Builds and runs containers Manages containers/workloads across clusters
Useful for local development and container runtime workflows Provides scheduling, scaling, service discovery and orchestration
Docker and Kubernetes are not simply replacements for each other. Docker focuses on container workflows, while Kubernetes orchestrates containerized workloads across a cluster.

🎯 If the Interviewer Says: "Explain Docker in 1 Minute"

" Docker is a containerization platform used to package applications and their dependencies into portable images. A Dockerfile defines how the image is built, and a container is a running instance of that image. Docker provides networking for container communication and volumes for persistent data. Docker Compose can be used to define multi-container applications. In a DevOps pipeline, I can build a Docker image from source code, run tests and security scans, tag the image with a traceable version such as a Git commit SHA, push it to a container registry and deploy that image to a platform such as Kubernetes or ECS. For production, I would focus on small and secure images, multi-stage builds, vulnerability scanning, secret management, resource limits, health checks and immutable image versions."
