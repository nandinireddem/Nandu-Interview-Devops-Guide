Dockerfile Interview Guide

Important Dockerfile concepts, instructions, optimization, multi-stage builds, security, troubleshooting and DevOps interview questions.

⭐⭐⭐⭐⭐ Dockerfile — Must Know

A Dockerfile is a text file containing instructions used by Docker to build a container image.

Dockerfile
↓
docker build
↓
Docker Image
↓
docker run
↓
Container

⭐⭐⭐⭐⭐ 1. What is a Dockerfile?

A Dockerfile is a text-based file containing instructions that Docker uses to automatically build a container image.

Example

FROM nginx:alpine

COPY index.html /usr/share/nginx/html/

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

⭐⭐⭐⭐⭐ 2. Basic Dockerfile Structure

FROM base-image

WORKDIR /app

COPY application-files /app/

RUN installation-command

EXPOSE port

ENV VARIABLE=value

CMD ["command"]
Interview point:

The Dockerfile describes how the image should be built and what should happen when a container starts.

⭐⭐⭐⭐⭐ 3. Important Dockerfile Instructions

Instruction Purpose
FROM Defines the base image.
WORKDIR Sets the working directory inside the image/container.
COPY Copies files from the build context into the image.
ADD Copies files and provides additional features such as archive extraction.
RUN Executes commands while building the image.
CMD Provides the default command for starting a container.
ENTRYPOINT Defines the main executable for the container.
ENV Defines environment variables.
ARG Defines build-time variables.
EXPOSE Documents the port the application listens on.
USER Specifies the user used to run subsequent commands/container process.
LABEL Adds metadata to an image.
HEALTHCHECK Defines a container health check.

⭐⭐⭐⭐⭐ 4. FROM

FROM specifies the base image from which the Docker image is built. 
FROM ubuntu:24.04

FROM python:3.12-slim

FROM nginx:alpine

Why use small base images?

  • Smaller image size
  • Faster downloads
  • Smaller attack surface
  • Faster deployments

⭐⭐⭐⭐⭐ 5. RUN

RUN executes commands during image build time. 
FROM ubuntu:24.04

RUN apt-get update

RUN apt-get install -y curl

Better approach

RUN apt-get update \
    && apt-get install -y curl \
    && rm -rf /var/lib/apt/lists/*

Combining related commands can reduce unnecessary image layers and clean package metadata in the same layer.

⭐⭐⭐⭐⭐ 6. CMD vs RUN

RUN CMD
Runs during image build. Provides the default command when the container starts.
Creates image layers. Does not execute during build. 
RUN npm install

CMD ["npm", "start"]
Easy way to remember:

RUN = Build time
CMD = Container start time

⭐⭐⭐⭐⭐ 7. CMD vs ENTRYPOINT

CMD ENTRYPOINT
Default command or arguments. Defines the main executable.
Can be replaced by a docker run command. Normally remains the executable unless overridden with appropriate options.

Example

ENTRYPOINT ["python"]

CMD ["app.py"]

Docker effectively starts the container with the executable and its default arguments.

Override CMD

docker run image other.py

⭐⭐⭐⭐⭐ 8. COPY vs ADD

COPY ADD
Simple file/directory copying. Provides extra functionality.
Usually preferred for clarity. Can automatically extract local tar archives. 
COPY package.json /app/

ADD package.tar.gz /app/
Best practice:

Prefer COPY unless you specifically need functionality provided by ADD.

⭐⭐⭐⭐⭐ 9. WORKDIR

WORKDIR sets the working directory for subsequent Dockerfile instructions and the default working directory of the container. 
WORKDIR /app

COPY . .

RUN npm install

CMD ["npm", "start"]

It is generally preferable to WORKDIR over repeatedly using cd.

⭐⭐⭐⭐⭐ 10. COPY and Docker Build Context

docker build -t myapp:1.0 .

The final . represents the build context. Docker can copy files only from within the build context, subject to Dockerfile and ignore rules.

.dockerignore

node_modules/
.git/
*.log
.env
terraform.tfstate
DevOps scenario: If the build context is huge because it contains Git history, dependencies or logs, builds can become slower. Use .dockerignore to exclude unnecessary files.

⭐⭐⭐⭐⭐ 11. ENV vs ARG

ARG ENV
Primarily available during image build. Available to processes running in the container.
Can be supplied using --build-arg. Can be set using -e at runtime.
Not automatically a runtime environment variable. Persists as image configuration. 
ARG APP_VERSION=1.0

ENV APP_ENV=production
Do not use Dockerfile ARG or ENV as a safe place for secrets. Build arguments and image configuration can become visible through image metadata/history depending on how they are used.

⭐⭐⭐⭐⭐ 12. EXPOSE

EXPOSE documents the port on which the application inside the container listens. 
EXPOSE 8080
Important: EXPOSE does not publish the port to the host.

To publish a port, use docker run -p. 

docker run -p 8080:8080 myapp

⭐⭐⭐⭐⭐ 13. USER

The USER instruction specifies which user should run subsequent Dockerfile commands and, by default, the container process. 
FROM nginx:alpine

RUN adduser -D appuser

USER appuser
Running applications as a non-root user is generally preferred for better container security when the application supports it.

⭐⭐⭐⭐ 14. HEALTHCHECK

HEALTHCHECK --interval=30s --timeout=5s \
    CMD curl -f http://localhost:8080/health || exit 1
A health check allows Docker to determine whether the application inside a container is responding as expected.
In production, an application process may still exist while the application itself is unhealthy. A health check helps distinguish these situations.

⭐⭐⭐⭐⭐ 15. Docker Image Layers

Many Dockerfile instructions create filesystem layers in the image. Docker can reuse unchanged layers through its build cache. 
FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["python", "app.py"]

Why COPY requirements first?

If application source code changes but the dependency file does not, Docker can often reuse the dependency installation layer.

⭐⭐⭐⭐⭐ 16. Docker Build Cache

docker build -t myapp:1.0 .
Docker attempts to reuse previously built layers when the relevant instruction and inputs have not changed.

Bad ordering

COPY . .

RUN pip install -r requirements.txt

Better ordering

COPY requirements.txt .

RUN pip install -r requirements.txt

COPY . .

This improves cache reuse when only application source code changes.

⭐⭐⭐⭐⭐ 17. Multi-Stage Builds

Multi-stage builds use multiple FROM instructions so that build dependencies can remain in an intermediate stage while only the required runtime artifacts are copied into the final image. 
FROM node:22 AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM nginx:alpine

COPY --from=builder /app/dist /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]
Benefit: The final image contains the runtime application instead of all the Node.js build dependencies.

⭐⭐⭐⭐⭐ 18. Why use Multi-Stage Builds?

  • Smaller production images
  • Lower attack surface
  • Separate build and runtime environments
  • Cleaner production containers
  • Reduced unnecessary dependencies
Interview answer:

"I use multi-stage Docker builds to separate the build environment from the runtime environment. The builder stage contains compilers and development dependencies, while the final stage contains only the artifacts and runtime dependencies required by the application."

⭐⭐⭐⭐⭐ 19. Dockerfile Best Practices

  • Use trusted and appropriately small base images.
  • Pin important dependency versions where appropriate.
  • Use .dockerignore.
  • Use multi-stage builds.
  • Run as a non-root user.
  • Keep images minimal.
  • Combine related package installation and cleanup.
  • Order instructions for cache efficiency.
  • Do not store secrets in images.
  • Scan images for vulnerabilities.
  • Use clear and maintainable Dockerfiles.

⭐⭐⭐⭐⭐ 20. Dockerfile Security

Never do this

ENV AWS_ACCESS_KEY_ID=xxxxx
ENV AWS_SECRET_ACCESS_KEY=xxxxx
Secrets can become part of image configuration or history. Never bake cloud credentials, passwords or API keys into an image.

Better approach

docker run \
  -e AWS_ACCESS_KEY_ID \
  -e AWS_SECRET_ACCESS_KEY \
  myapp

For production, use the secret-management mechanism provided by the platform, such as AWS Secrets Manager, Kubernetes Secrets with appropriate controls, or CI/CD secret stores.

⭐⭐⭐⭐⭐ 22. ENTRYPOINT + CMD Real Example

FROM python:3.12-slim

WORKDIR /app

COPY app.py .

ENTRYPOINT ["python"]

CMD ["app.py"]

The entrypoint defines the executable and CMD supplies the default argument. 

docker run myapp

docker run myapp another.py

The second command replaces the default CMD argument while keeping the entrypoint.

⭐⭐⭐⭐ 23. Shell Form vs Exec Form

Shell form

CMD python app.py

Exec form

CMD ["python", "app.py"]
Exec form is generally preferred because it executes the process directly and provides more predictable signal handling.

⭐⭐⭐⭐⭐ 24. Dockerfile Troubleshooting

Problem: Build is very slow

  • Check build context size.
  • Use .dockerignore.
  • Optimize layer ordering.
  • Reuse build cache.
  • Use multi-stage builds where appropriate.

Problem: Image is very large

  • Use a smaller suitable base image.
  • Remove unnecessary packages.
  • Use multi-stage builds.
  • Clean package caches.

Problem: Application works locally but not in container

  • Check application listening address.
  • Check exposed/published ports.
  • Check environment variables.
  • Check filesystem paths.
  • Check logs.
  • Check dependencies.

⭐⭐⭐⭐⭐ 25. Real-Time Scenario: Image Size is Huge

Problem: A Java/Node/Python application produces a 1.5 GB Docker image.

Approach: 1. Inspect image layers.
2. Remove unnecessary dependencies.
3. Use a suitable slim runtime image.
4. Use multi-stage builds.
5. Add a proper .dockerignore.
6. Scan and verify the final image.

⭐⭐⭐⭐⭐ 26. Real-Time Scenario: Secret Accidentally Added

A developer accidentally adds an AWS access key to a Dockerfile.

Immediate response: Treat the credential as compromised and rotate/revoke it immediately. Then remove the secret from the Dockerfile and review image and repository history as appropriate.
Simply deleting the line from the latest Dockerfile does not guarantee that the credential is absent from previous image layers or Git history.

⭐⭐⭐⭐⭐ 27. Real-Time Scenario: Container Starts and Immediately Exits

A container normally remains alive while its main process is running. If that process exits, the container stops.

Debug

docker ps -a

docker logs <container>

docker inspect <container>

Check the Dockerfile's CMD/ENTRYPOINT, logs, environment variables and application startup command.

⭐⭐⭐⭐⭐ 28. Real-Time Scenario: Build Works but Application Cannot Be Reached

Check:

1. Application listening port
2. EXPOSE
3. Host-to-container port mapping
4. Application binding address
5. Container status
6. Container logs 
docker ps

docker logs <container>

docker port <container>

docker inspect <container>

⭐⭐⭐⭐⭐ 29. Important Docker Build Commands

# Build image
docker build -t myapp:1.0 .

# Build without cache
docker build --no-cache -t myapp:1.0 .

# Build with argument
docker build --build-arg APP_VERSION=2.0 -t myapp:2.0 .

# List images
docker images

# Inspect image
docker inspect myapp:1.0

# View image history
docker history myapp:1.0

# Run container
docker run -d --name myapp -p 8080:8080 myapp:1.0

🎯 Explain Dockerfile in 1 Minute

"A Dockerfile is a text file containing instructions used to build a Docker image. I normally start with a suitable base image using FROM, set the working directory using WORKDIR, copy the required application files, install dependencies using RUN, and define the startup behavior using ENTRYPOINT and CMD. I use .dockerignore to reduce the build context and optimize instruction ordering to improve Docker layer caching. For production images, I prefer multi-stage builds so that build-time dependencies are not included in the final runtime image. From a security perspective, I avoid storing secrets in Dockerfiles, use trusted minimal base images, scan images for vulnerabilities and prefer running applications as a non-root user. The final image can then be pushed to a registry and deployed through the CI/CD pipeline."
