Dockerfile Advanced

Production-focused Dockerfile concepts, instructions, image layers, build cache, multi-stage builds, security, optimization and high-frequency DevOps interview scenarios.

⭐⭐⭐⭐⭐ DOCKERFILE — FINAL INTERVIEW REVISION

A Dockerfile is a text file containing instructions used by Docker to build an image.

Dockerfile
↓
docker build
↓
Docker Image
↓
Container
↓
Application
Interview definition: A Dockerfile is a declarative set of instructions used to build a Docker image containing an application, its dependencies and the runtime configuration required to execute it.

⭐⭐⭐⭐⭐ 1. Basic Dockerfile Structure

FROM node:22-alpine

WORKDIR /app

COPY package*.json ./

RUN npm install

COPY . .

EXPOSE 3000

CMD ["npm", "start"]

Flow

FROM → Base Image
↓
WORKDIR → Working Directory
↓
COPY → Application Files
↓
RUN → Build/Install Dependencies
↓
EXPOSE → Document Application Port
↓
CMD → Default Runtime Command

⭐⭐⭐⭐⭐ 2. FROM

FROM defines the base image from which the Docker image is built. 
FROM ubuntu:24.04

FROM python:3.13-slim

FROM node:22-alpine

Why is FROM important?

  • Provides the operating-system/runtime foundation.
  • Determines available tools and libraries.
  • Influences final image size.
  • Can affect security and compatibility.
Prefer trusted, maintained and appropriately sized base images. Avoid using latest when deterministic builds are important.

⭐⭐⭐⭐ 3. Why Pin Image Versions?

Instead of:

FROM node:latest

Prefer a controlled version:

FROM node:22-alpine
Pinning a meaningful image version improves build reproducibility because the base image does not unexpectedly change just because the tag latest was updated.

For stronger supply-chain reproducibility, organizations can also pin images by immutable digest when appropriate.

⭐⭐⭐⭐⭐ 4. WORKDIR

WORKDIR sets the working directory for subsequent Dockerfile instructions and the default working directory of the container. 
WORKDIR /app

COPY . .

RUN npm install

Using WORKDIR is preferable to repeatedly using RUN cd /app.

⭐⭐⭐⭐⭐ 5. COPY

COPY copies files from the Docker build context into the image. 
COPY package.json /app/

COPY . .

COPY --from=builder /app/dist ./dist

Most important use

The --from option is heavily used in multi-stage builds to copy artifacts from one build stage into another.

⭐⭐⭐⭐ 6. COPY vs ADD

COPY ADD
Simple file/directory copying. Provides additional behavior such as archive extraction for supported local archives and URL handling.
Usually preferred for clarity. Use only when its additional behavior is intentionally needed.
Interview answer: "I generally prefer COPY because it has simpler and more explicit behavior. I use ADD only when I specifically need its additional features."

⭐⭐⭐⭐⭐ 7. RUN

RUN executes commands while the image is being built. Its result becomes part of an image layer. 
RUN apt-get update && apt-get install -y curl

RUN npm ci

RUN pip install -r requirements.txt

Important distinction

RUN CMD
Build-time instruction. Default runtime command.
Creates image-layer changes. Runs when a container starts.

⭐⭐⭐⭐⭐ 8. CMD

CMD specifies the default command or arguments for a container. 
CMD ["nginx", "-g", "daemon off;"]

A Dockerfile normally has one effective CMD instruction; if multiple CMD instructions exist, the last one takes effect.

Override CMD

docker run myimage
docker run myimage sh

The command supplied at container runtime can replace the default CMD command.

⭐⭐⭐⭐⭐ 9. ENTRYPOINT

ENTRYPOINT defines the primary executable of a container. 
ENTRYPOINT ["python"]

CMD ["app.py"]

Conceptually this runs:

python app.py

Override ENTRYPOINT

docker run --entrypoint sh myimage

🔥 ⭐⭐⭐⭐⭐ 10. CMD vs ENTRYPOINT

CMD ENTRYPOINT
Provides a default command/arguments. Defines the main executable.
Can be replaced by a runtime command. Usually remains the main executable unless explicitly overridden.
Often used for default arguments. Useful when the container should behave like a specific executable.

Common pattern

ENTRYPOINT ["python"]

CMD ["app.py"]
Interview answer: "ENTRYPOINT defines the main executable, while CMD commonly provides default arguments or a default command. They can also be used together."

⭐⭐⭐⭐ 11. Shell Form vs Exec Form

Exec form

CMD ["node", "server.js"]

ENTRYPOINT ["python", "app.py"]

Shell form

CMD node server.js

RUN echo hello
For application ENTRYPOINT/CMD definitions, exec form is generally preferred because it gives clearer process behavior and signal handling.

⭐⭐⭐⭐⭐ 12. ENV

ENV sets environment variables in the image and makes them available to processes running in containers created from it. 
ENV APP_ENV=production
ENV PORT=8080

Values can be overridden at runtime: 

docker run -e APP_ENV=staging myimage
Do not use ENV to bake passwords, API keys or other sensitive credentials into an image.

⭐⭐⭐⭐⭐ 13. ARG

ARG defines a build-time variable that can be supplied to docker build. 
ARG NODE_VERSION=22

FROM node:${NODE_VERSION}-alpine

Build with:

docker build --build-arg NODE_VERSION=22 -t myapp .

🔥 ⭐⭐⭐⭐⭐ 14. ARG vs ENV

ARG ENV
Mainly build-time. Available to processes in the resulting image/container.
Can influence image construction. Defines runtime environment variables.
Not automatically available as a runtime environment variable. Persists as image configuration. 
ARG APP_VERSION=1.0

ENV APP_ENV=production
Do not treat ARG or ENV as a secure secret-storage mechanism. Build arguments can be exposed through build metadata/history in some workflows.

⭐⭐⭐⭐ 15. EXPOSE

EXPOSE 8080
EXPOSE documents the port on which the application listens inside the container. It does not publish the port to the host by itself.

Host publishing happens at runtime, for example:

docker run -p 8080:8080 myimage

⭐⭐⭐⭐⭐ 16. USER — Run as Non-Root

Running an application as root inside a container can increase the impact of a container compromise. 
FROM node:22-alpine

WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .

USER node

CMD ["npm", "start"]
Using a non-root user is an important container security practice when the application supports it.

⭐⭐⭐⭐ 17. LABEL

LABEL maintainer="devops-team"
LABEL version="1.0"
LABEL description="Production API"

Labels add metadata to images and can help with organization, automation and image management.

⭐⭐⭐⭐⭐ 18. .dockerignore

.dockerignore prevents unnecessary files from being sent as part of the Docker build context. 
.git
.gitignore
node_modules
.env
*.log
coverage
Dockerfile*

Why is it important?

  • Reduces build context size.
  • Improves build performance.
  • Prevents unnecessary files from entering build context.
  • Helps avoid accidentally copying local files.
Do not rely on .dockerignore as your only security control. Never put secrets into a Docker build context in the first place.

⭐⭐⭐⭐⭐ 19. Docker Image Layers

Many Dockerfile instructions contribute filesystem changes that can be represented as image layers. 

FROM node:22-alpine
        ↓
COPY package.json
        ↓
RUN npm ci
        ↓
COPY source
        ↓
CMD
Docker can reuse unchanged build layers through its build cache. This is one reason Dockerfile instruction order matters.

🔥 ⭐⭐⭐⭐⭐ 20. Docker Build Cache

Bad ordering

COPY . .

RUN npm ci

Any source-code change may invalidate the COPY layer and cause dependency installation to run again.

Better ordering

COPY package*.json ./

RUN npm ci

COPY . .
Dependency files change less frequently than application source in many projects, so separating them can allow Docker to reuse the dependency-installation layer.

⭐⭐⭐⭐ 21. Package Installation Best Practice

Less efficient

RUN apt-get update

RUN apt-get install -y curl

Better

RUN apt-get update \
    && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
Combining related package-management commands helps avoid stale package indexes and unnecessary intermediate filesystem data.

🔥 ⭐⭐⭐⭐⭐ 22. Multi-Stage Builds

Multi-stage builds use multiple FROM stages so build tools and intermediate artifacts can be separated from the final runtime image.

Example — Node.js

FROM node:22-alpine AS builder

WORKDIR /app

COPY package*.json ./

RUN npm ci

COPY . .

RUN npm run build


FROM nginx:alpine

COPY --from=builder /app/dist /usr/share/nginx/html
Builder Image
↓
Install Dependencies
↓
Build Application
↓
dist/
↓
Final Runtime Image
↓
Nginx

⭐⭐⭐⭐⭐ 23. Why Use Multi-Stage Builds?

  • Smaller final images.
  • Build tools stay out of runtime image.
  • Reduced attack surface.
  • Cleaner production images.
  • Better separation between build and runtime.
Example: A Java application may need Maven and JDK to compile, but the production container may only need a smaller JRE/runtime environment.

⭐⭐⭐⭐⭐ 24. Production Java Multi-Stage Example

FROM maven:3.9-eclipse-temurin-21 AS builder

WORKDIR /app

COPY pom.xml .

RUN mvn dependency:go-offline

COPY src ./src

RUN mvn clean package -DskipTests


FROM eclipse-temurin:21-jre

WORKDIR /app

COPY --from=builder /app/target/app.jar app.jar

USER 10001

EXPOSE 8080

ENTRYPOINT ["java","-jar","app.jar"]
The first stage contains Maven and build dependencies. The final stage contains only the runtime required to execute the JAR.

⭐⭐⭐⭐ 25. Python Production Pattern

FROM python:3.13-slim

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir -r requirements.txt

COPY . .

RUN useradd --create-home appuser

USER appuser

EXPOSE 8000

CMD ["python", "app.py"]

The exact production setup depends on the Python framework and application architecture, but the important concepts are dependency installation, minimal runtime image and non-root execution.

⭐⭐⭐⭐ 26. HEALTHCHECK

HEALTHCHECK --interval=30s \
            --timeout=5s \
            --retries=3 \
            CMD wget --spider -q http://localhost:8080/health || exit 1
A healthcheck defines a command Docker can use to determine whether a container is healthy.
A healthcheck does not magically fix an unhealthy application. It only reports health status to the container runtime/orchestrator.

⭐⭐⭐ 27. STOPSIGNAL

STOPSIGNAL SIGTERM

Specifies the system call signal sent to the container's main process when Docker requests the container to stop.

Correct signal handling becomes particularly important for graceful shutdown of web servers and applications.

⭐⭐⭐ 28. VOLUME

VOLUME ["/data"]
The VOLUME instruction declares a mount point intended for persistent or externally managed data.

In modern deployments, the actual storage mechanism is usually chosen by the runtime or orchestrator rather than relying only on the Dockerfile.

⭐⭐⭐⭐ 29. Docker Build Context

docker build -t myapp .
The final . specifies the build context sent to the Docker builder.

The Dockerfile can only access files available in the build context unless another supported build mechanism is used.

A huge project directory can make builds slower because the build context itself becomes large. A good .dockerignore helps reduce unnecessary context.

⭐⭐⭐⭐⭐ 30. Build and Tag an Image

docker build -t myapp:1.0 .

docker images

docker run myapp:1.0

Use meaningful version tags for controlled deployments.

For production release workflows, avoid treating mutable tags such as latest as your only deployment identifier.

🔥 ⭐⭐⭐⭐⭐ 31. Dockerfile Security Best Practices

  • Use trusted and maintained base images.
  • Prefer minimal runtime images where practical.
  • Pin meaningful versions or immutable digests.
  • Run as a non-root user.
  • Do not bake secrets into images.
  • Use .dockerignore.
  • Use multi-stage builds.
  • Scan images for vulnerabilities.
  • Keep dependencies updated.
  • Use read-only filesystems where appropriate.
  • Drop unnecessary Linux capabilities at runtime.
  • Keep the final image focused on runtime requirements.

🔥 ⭐⭐⭐⭐⭐ 32. Why Should Secrets Not Be in Dockerfiles?

Never do this:

ENV AWS_ACCESS_KEY_ID=xxxxx
ENV AWS_SECRET_ACCESS_KEY=xxxxx
Even if the container is later removed, secrets embedded in an image may remain accessible through image metadata, layers or registries.

Better approach

docker run \
  -e API_KEY="$API_KEY" \
  myapp:1.0

For production, prefer the secret-management facilities provided by the deployment platform or cloud provider.

⭐⭐⭐⭐⭐ 33. Why Run Containers as Non-Root?

If an attacker compromises an application process, running it as a non-root user can reduce the privileges available inside the container.

Example

RUN addgroup -S appgroup \
    && adduser -S appuser -G appgroup

USER appuser

The exact commands depend on the Linux distribution used by the base image.

⭐⭐⭐⭐⭐ 34. Interview Scenario — CMD vs ENTRYPOINT

Question: You have: 
ENTRYPOINT ["python"]
CMD ["app.py"]
What happens with: 
docker run myimage
Answer: It effectively starts: 
python app.py
If the user supplies another argument: 
docker run myimage test.py
The CMD arguments are replaced, resulting conceptually in: 
python test.py

⭐⭐⭐⭐⭐ 35. Interview Scenario — Build Became Slow

Problem: Every source-code change causes dependency installation to run again.

Solution: Separate dependency files from frequently changing source files. 
COPY package*.json ./
RUN npm ci

COPY . .
This allows Docker to reuse the dependency layer when only source files change.

⭐⭐⭐⭐⭐ 36. How to Reduce Docker Image Size?

  • Use an appropriately small base image.
  • Use multi-stage builds.
  • Remove build tools from runtime.
  • Use .dockerignore.
  • Install only required packages.
  • Clean package-manager caches when appropriate.
  • Copy only required runtime artifacts.
  • Avoid unnecessary files.
Interview answer: "I would first identify what is contributing to the image size, then use a suitable base image, multi-stage builds, .dockerignore, dependency optimization and a runtime-only final stage."

⭐⭐⭐⭐ 37. Debugging a Dockerfile Build

docker build -t myapp:debug .

docker history myapp:debug

docker inspect myapp:debug

Useful questions

  • Which Dockerfile instruction failed?
  • Is the build context correct?
  • Does the file being copied exist?
  • Are dependency versions compatible?
  • Did a cache layer cause unexpected behavior?
  • Is the final image actually containing the application?

🎯 Explain Dockerfile in 1 Minute

"A Dockerfile contains instructions used to build a Docker image. I normally start with a trusted base image using FROM, set the working directory using WORKDIR, copy dependency files and install them with RUN, then copy the application source. For runtime configuration I can use ENV, while ARG is mainly used for build-time variables. EXPOSE documents the application's container port. For production images I prefer multi-stage builds so build tools do not remain in the final runtime image. I also use .dockerignore, appropriate image versions, non-root users and image scanning. For the application process, I use ENTRYPOINT and CMD depending on whether I want to define a fixed executable, default arguments or both. The goal is to create a reproducible, secure, small and production-ready image."
