ArgoCD RBAC & Security

Authentication, authorization, RBAC policies, projects, repositories, Kubernetes permissions and important ArgoCD security practices.

⭐⭐⭐⭐⭐ 1. What is RBAC?

RBAC stands for Role-Based Access Control. It controls what actions a user or service account is allowed to perform based on assigned roles and permissions.

Interview Answer:
ArgoCD RBAC controls which users or groups can perform actions such as viewing, syncing, creating or deleting applications and projects.

⭐⭐⭐⭐⭐ 2. Authentication vs Authorization

Authentication Authorization
Who are you? What are you allowed to do?
Login / identity verification. Permissions and access control.
Example: SSO login. Example: Can this user sync an application?
👤 User
↓
Authentication
↓
Identity Verified
↓
Authorization / RBAC
↓
Allowed Actions

⭐⭐⭐⭐⭐ 3. ArgoCD RBAC Components

  • User / Group → Identity requesting access.
  • Role → Collection of permissions.
  • Policy → Defines allowed or denied actions.
  • Project → Restricts applications, repositories and destinations.

⭐⭐⭐⭐⭐ 4. Common ArgoCD RBAC Actions

Action Purpose
get View resources.
create Create resources.
update Modify resources.
delete Delete resources.
sync Synchronize an application.
override Override application source during supported operations.

⭐⭐⭐⭐⭐ 5. ArgoCD RBAC Policy Example

p, role:developer, applications, get, dev-project/*, allow
p, role:developer, applications, sync, dev-project/*, allow

g, alice, role:developer

The example gives the developer role permission to view and sync applications under the specified project scope.

Interview Tip:
Do not memorize only the syntax. Explain the principle: developers should receive only the permissions required for their job.

⭐⭐⭐⭐⭐ 6. Least Privilege

The principle of least privilege means giving users and systems only the permissions they actually need.

Developer
↓
View + Sync Dev Applications
↓
❌ No Production Delete Permission
Interview Answer:
In production, I would avoid giving broad admin permissions to every developer. I would use project-level RBAC and grant only the required actions.

⭐⭐⭐⭐⭐ 7. What is an ArgoCD Project?

An ArgoCD Project is a logical boundary used to organize applications and restrict what those applications can access.

A Project Can Control:

  • Allowed source repositories
  • Allowed destination clusters
  • Allowed destination namespaces
  • Allowed resource kinds
  • Project roles
Interview Answer:
Projects provide an additional security and organizational boundary for ArgoCD applications.

⭐⭐⭐⭐⭐ 8. Why Use Projects?

ArgoCD
↓
Project: Development
├── Dev Applications
├── Dev Repository
└── Dev Namespace

Project: Production
├── Prod Applications
├── Prod Repository
└── Prod Namespace

This separation helps prevent accidental deployment of applications into unauthorized environments.

⭐⭐⭐⭐⭐ 9. Project Security Example

apiVersion: argoproj.io/v1alpha1
kind: AppProject

metadata:
  name: production
  namespace: argocd

spec:
  sourceRepos:
    - https://github.com/example/prod-gitops.git

  destinations:
    - namespace: production
      server: https://kubernetes.default.svc
Meaning:
This project can be configured so applications use approved Git repositories and approved Kubernetes destinations.

⭐⭐⭐⭐⭐ 10. Kubernetes RBAC vs ArgoCD RBAC

ArgoCD RBAC Kubernetes RBAC
Controls access to ArgoCD resources and actions. Controls access to Kubernetes API resources.
Example: Can user sync an ArgoCD Application? Example: Can service account create Deployments?
Configured through ArgoCD RBAC policies. Uses Role, ClusterRole and bindings.
Interview Point:
They are separate authorization layers. A user being allowed to use ArgoCD does not automatically mean they have unrestricted Kubernetes permissions.

⭐⭐⭐⭐⭐ 11. What is SSO?

SSO stands for Single Sign-On. It allows users to authenticate through an external identity provider rather than maintaining separate credentials for every application.

ArgoCD can integrate with identity providers using supported authentication mechanisms such as OIDC.

👤 User
↓
Identity Provider
↓
Authentication
↓
ArgoCD
↓
RBAC
↓
Allowed Application Actions

⭐⭐⭐⭐ 12. Why Use SSO Instead of Local Users?

  • Centralized identity management.
  • Centralized access control.
  • Easier onboarding and offboarding.
  • Integration with organizational identity systems.
  • Reduced dependency on separate local credentials.

⭐⭐⭐⭐⭐ 13. How Should Production ArgoCD Be Secured?

  • Use SSO / centralized identity where appropriate.
  • Apply least-privilege RBAC.
  • Separate environments using Projects.
  • Restrict allowed Git repositories.
  • Restrict allowed destination clusters and namespaces.
  • Avoid giving admin permissions unnecessarily.
  • Protect repository credentials and secrets.
  • Use TLS for access to ArgoCD.
  • Monitor and audit administrative actions.
  • Control who can perform production sync or deletion.

⭐⭐⭐⭐⭐ 14. Real-Time Security Scenario

Scenario

A developer needs to deploy applications to the development namespace, but must not be able to modify production applications.

Solution

Developer
↓
SSO Group
↓
Developer RBAC Role
↓
Development Project
↓
Dev Namespace
↓
✅ Allowed

Production
↓
❌ Access Denied
Interview Answer:
I would use SSO groups with ArgoCD RBAC and AppProjects. The developer role would have access only to development applications and would not have production sync or delete permissions.

⭐⭐⭐⭐⭐ 15. What If Someone Gets ArgoCD Admin Access?

An ArgoCD administrator can potentially control a large portion of the applications managed by ArgoCD, depending on the configured permissions and cluster access.

Security Risk:
ArgoCD is a powerful control plane. Administrative credentials must be protected carefully and broad permissions should be minimized.

⭐⭐⭐⭐ 16. Repository Access Security

ArgoCD may need credentials to access private Git repositories. These credentials should be handled securely.

  • Use secure credential mechanisms.
  • Do not commit passwords or tokens to Git.
  • Limit repository access.
  • Rotate credentials when necessary.
  • Use dedicated credentials where possible.
