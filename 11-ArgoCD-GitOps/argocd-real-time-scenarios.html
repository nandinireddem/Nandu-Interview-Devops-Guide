ArgoCD Real-Time Scenarios

Production-style ArgoCD interview scenarios with practical troubleshooting approaches and interview-ready answers.

⭐⭐⭐⭐⭐ 1. Git Change Is Not Reflected in Kubernetes

Scenario:
A developer changed the Deployment image tag in Git, but the Kubernetes cluster is still running the old image.

What I Would Check

  1. Verify the correct repository.
  2. Verify the branch or revision.
  3. Verify the application path.
  4. Check whether ArgoCD detected the Git change.
  5. Check whether automated sync is enabled.
  6. Check Application events and sync status.
argocd app get my-app
argocd app diff my-app
argocd app sync my-app
Interview Answer:
I would first verify that ArgoCD is tracking the correct repository, revision and path. Then I would check whether the application is OutOfSync and whether automated synchronization is enabled. If the change is detected but not applied, I would inspect the sync error.

⭐⭐⭐⭐⭐ 2. Application Shows OutOfSync

Scenario:
The application suddenly changes from Synced to OutOfSync even though nobody changed Git.

Likely Cause

Someone may have manually modified a Kubernetes resource using kubectl, causing configuration drift.

Git
↓
Desired State
↓
ArgoCD
↕
Live Kubernetes State
↓
❌ Difference Detected
↓
OutOfSync
Interview Answer:
I would run an ArgoCD diff and identify the changed resource. If the change was made manually, I would either revert it or update Git if the change is actually required.

⭐⭐⭐⭐⭐ 3. Self-Healing Reverts a Manual Change

Scenario:
An engineer manually changes replicas from 3 to 1 using kubectl. Within a short time, ArgoCD changes them back to 3.
Git
replicas: 3
↓
Kubernetes
replicas: 1
↓
ArgoCD detects drift
↓
Self-Heal
↓
replicas: 3
Interview Answer:
This is expected when automated sync with self-healing is enabled. ArgoCD continuously reconciles the live state toward the desired state stored in Git.

⭐⭐⭐⭐⭐ 4. Sync Failed Because of an Invalid Manifest

Scenario:
A developer pushes a malformed Kubernetes YAML file. ArgoCD detects the change but synchronization fails.

Approach

argocd app get my-app

Read the error and identify the resource that failed. Validate the YAML and, depending on the source type, test Helm or Kustomize generation.

Interview Answer:
I would not repeatedly retry the sync. I would identify the exact manifest error, fix the configuration in Git, commit the correction and allow ArgoCD to reconcile again.

⭐⭐⭐⭐⭐ 5. Sync Succeeds but Pods Are Not Running

Scenario:
ArgoCD reports Synced, but the application is Degraded and Pods are failing. 
kubectl get pods -n production
kubectl describe pod <pod-name> -n production
kubectl logs <pod-name> -n production

Possible Causes

  • Application startup failure.
  • Missing environment variables.
  • Missing Secret or ConfigMap.
  • Image problem.
  • Readiness or liveness probe failure.
  • Insufficient resources.
Key Point:
Synced does not necessarily mean Healthy. Sync represents desired-state application, while health reflects the runtime state.

⭐⭐⭐⭐⭐ 6. Production Deployment Must Be Prevented

Scenario:
Developers should be able to deploy to Dev but must not be able to deploy or delete Production applications.
Developer
↓
SSO Group
↓
ArgoCD RBAC
↓
Development Project
↓
Dev Namespace

Production → ❌ Denied
Interview Answer:
I would use AppProjects and RBAC. The developer role would be restricted to development applications and destinations, while production access would be granted only to authorized teams.

⭐⭐⭐⭐ 7. Private Git Repository Cannot Be Accessed

Scenario:
The ArgoCD Application cannot fetch manifests from a private GitHub repository.

Check

argocd repo list

Possible Causes

  • Incorrect repository URL.
  • Invalid or expired credentials.
  • Insufficient repository permissions.
  • Network connectivity issue.
Interview Answer:
I would verify the repository URL and credentials configured in ArgoCD, confirm that the credential has access to the repository, and check the repository connection status.

⭐⭐⭐⭐⭐ 8. ImagePullBackOff After Successful Sync

Scenario:
ArgoCD successfully applies the Deployment, but the Pod enters ImagePullBackOff. 
kubectl describe pod <pod-name> -n production

Possible Causes

  • Wrong image name.
  • Wrong image tag.
  • Private registry authentication missing.
  • Image does not exist.
Interview Answer:
I would inspect the Pod events first. Since ArgoCD already synchronized the Deployment successfully, I would troubleshoot the Kubernetes image pull process rather than the GitOps controller itself.

⭐⭐⭐⭐⭐ 9. Rollback After a Bad Deployment

Scenario:
A new production version was deployed and the application became unhealthy.

GitOps Approach

Bad Commit
↓
Deployment
↓
Application Failure
↓
Revert Git Commit
↓
ArgoCD Detects Change
↓
Sync
↓
Previous Version Restored
Interview Answer:
With GitOps, I prefer reverting the problematic Git change so that Git again represents the desired state. ArgoCD then reconciles the cluster to that known-good configuration.

⭐⭐⭐⭐ 10. ArgoCD Application Is Stuck During Sync

Scenario:
The sync operation appears to remain in progress for a long time.

Investigation

argocd app get my-app

kubectl get events -A --sort-by=.lastTimestamp

kubectl get pods -A

Identify the resource that is waiting. It could be a Deployment, Job, Pod, Service, webhook or another dependency.

Interview Answer:
I would identify the exact resource holding up the sync rather than assuming the entire ArgoCD installation is unhealthy.

⭐⭐⭐⭐⭐ 11. ArgoCD Server Is Not Accessible

Scenario:
The ArgoCD UI suddenly becomes inaccessible.

Check ArgoCD Components

kubectl get pods -n argocd
kubectl get svc -n argocd
kubectl get events -n argocd

Important Components

  • argocd-server
  • argocd-repo-server
  • argocd-application-controller
  • argocd-redis
  • argocd-applicationset-controller
Interview Answer:
I would first verify that the ArgoCD pods are running and then check the Service, ingress or load balancer configuration used to expose ArgoCD.

⭐⭐⭐⭐⭐ 12. Application Controller Problem

Scenario:
Applications stop reconciling even though the ArgoCD UI is accessible. 
kubectl get pods -n argocd
kubectl logs deployment/argocd-application-controller -n argocd
Interview Answer:
The Application Controller is responsible for continuously comparing desired and live state and initiating reconciliation. I would inspect its logs, pod status and resource availability.

⭐⭐⭐⭐ 13. Repo Server Problem

Scenario:
ArgoCD cannot generate manifests from Git. 
kubectl get pods -n argocd
kubectl logs deployment/argocd-repo-server -n argocd
Interview Answer:
The Repo Server handles repository access and manifest generation. Therefore, if applications fail during manifest generation, I would check repository connectivity and Repo Server logs.

⭐⭐⭐⭐⭐ 14. Emergency Production Scenario

Production is down immediately after a deployment.

My Troubleshooting Sequence

  1. Check ArgoCD Application health.
  2. Check recent Git commit.
  3. Check sync history.
  4. Check Deployment and ReplicaSet.
  5. Check Pod status.
  6. Check application logs.
  7. Check Kubernetes events.
  8. Identify the root cause.
  9. Rollback by reverting the Git change if required.
  10. Verify application recovery.
Interview Answer:
During a production incident, I focus first on restoring service safely. I identify the failing layer, use the Git history to understand the change, and revert to a known-good version when necessary. After recovery, I investigate the root cause.

🧠 One-Minute Revision

OutOfSync → Desired and live state differ.

SyncFailed → ArgoCD could not apply a change.

Degraded → Resource/application health is bad.

Git Error → Check URL, credentials and connectivity.

Manifest Error → Check YAML, Helm or Kustomize.

Pod Error → Check describe, logs and events.

Production Failure → Identify change → restore service → revert Git if required → verify recovery.
