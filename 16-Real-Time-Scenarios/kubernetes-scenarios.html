1. Pod Is in CrashLoopBackOff

Question

A Pod keeps restarting and shows CrashLoopBackOff. How would you troubleshoot it?

First check the Pod: 
kubectl get pods
Then inspect it: 
kubectl describe pod <pod-name>
Check logs: 
kubectl logs <pod-name>
If the container restarted: 
kubectl logs <pod-name> --previous
I would investigate application errors, incorrect commands, missing configuration, failed health checks, permissions or resource problems.
⭐⭐⭐⭐⭐ VERY IMPORTANT

2. Pod Is in Pending State

kubectl get pods
kubectl describe pod <pod-name>
The Events section is very important. Common causes:
  • Insufficient CPU or memory
  • Node selector mismatch
  • Affinity/anti-affinity rules
  • Taints and tolerations
  • Unbound PersistentVolumeClaim
  • Scheduling constraints
I would identify the scheduler event explaining why the Pod cannot be placed on a node.
⭐⭐⭐⭐⭐

3. Pod Shows ImagePullBackOff

kubectl describe pod <pod-name>
I would check:
  • Image name
  • Image tag
  • Registry availability
  • ImagePullSecrets
  • Private registry authentication
  • Network connectivity
The Events section normally provides the immediate reason for the image pull failure.
⭐⭐⭐⭐⭐ VERY IMPORTANT

4. Pod Is Running but Application Is Not Accessible

Client
↓
Service
↓
Pod
↓
Container
↓
Application

Check

kubectl get pods -o wide
kubectl get svc
kubectl describe svc <service-name>
kubectl get endpoints <service-name>
I would verify that the Service selector matches the Pod labels and that the target application is listening on the expected container port.
⭐⭐⭐⭐⭐

5. Service Has No Endpoints

kubectl get endpoints <service-name>
kubectl describe svc <service-name>
kubectl get pods --show-labels
The most common issue is a mismatch between the Service selector and Pod labels. For example: 
Service selector:
app: nginx

Pod label:
app: apache
The Service will not select that Pod.
⭐⭐⭐⭐⭐ VERY IMPORTANT

6. Deployment Is Not Creating New Pods

kubectl get deployment
kubectl describe deployment <deployment-name>
kubectl get replicaset
kubectl get events --sort-by=.lastTimestamp
I would check the Deployment desired replicas, ReplicaSet status, Pod scheduling, resource constraints and image availability.
⭐⭐⭐⭐⭐

7. New Deployment Version Is Failing

I would compare the new ReplicaSet with the previous working ReplicaSet. Check:
  • Image version
  • Environment variables
  • ConfigMaps
  • Secrets
  • Probes
  • Resource limits
  • Application logs
Then, if necessary, perform a rollback. 
kubectl rollout history deployment/myapp

kubectl rollout undo deployment/myapp
⭐⭐⭐⭐⭐ VERY IMPORTANT

8. Readiness Probe Is Failing

kubectl describe pod <pod-name>
kubectl logs <pod-name>
A readiness probe determines whether the Pod should receive traffic. I would verify:
  • Probe path
  • Probe port
  • Application startup time
  • Initial delay
  • Timeout
  • Application health endpoint
A failed readiness probe removes the Pod from Service endpoints.
⭐⭐⭐⭐⭐

9. Liveness Probe Keeps Restarting the Container

A liveness probe determines whether the container should be restarted. If it is too aggressive, a healthy but slow-starting application may repeatedly restart. I would review the probe configuration and application startup behavior.
⭐⭐⭐⭐⭐ VERY IMPORTANT

10. Pod Is OOMKilled

kubectl describe pod <pod-name>
OOMKilled usually indicates that the container exceeded its memory limit. I would check: 
kubectl top pod
Then compare actual usage with the configured resource requests and limits. Possible solutions include fixing a memory leak, optimizing the application or adjusting the memory limit based on actual requirements.
⭐⭐⭐⭐⭐

11. Node Is NotReady

kubectl get nodes

kubectl describe node <node-name>
I would check:
  • Node conditions
  • Kubelet status
  • Container runtime
  • CPU and memory pressure
  • Disk pressure
  • Network connectivity
  • Node events
On the node: 
systemctl status kubelet
⭐⭐⭐⭐⭐ VERY IMPORTANT

12. Pods Are Stuck on One Node

I would investigate scheduling configuration:
  • Node selectors
  • Node affinity
  • Taints
  • Tolerations
  • Resource availability
Commands: 
kubectl describe pod <pod-name>
kubectl describe node <node-name>
⭐⭐⭐⭐⭐

13. DNS Is Not Working Inside Kubernetes

kubectl get pods -n kube-system

kubectl get svc -n kube-system

kubectl logs -n kube-system -l k8s-app=kube-dns

Test from a Pod:

nslookup kubernetes.default
I would investigate CoreDNS health, the DNS Service, Pod networking and DNS configuration.
⭐⭐⭐⭐⭐ VERY IMPORTANT

14. Ingress Is Not Working

kubectl get ingress

kubectl describe ingress <ingress-name>

kubectl get svc
I would check:
  • Ingress Controller
  • Ingress rules
  • Host/path configuration
  • Backend Service
  • Service endpoints
  • DNS
  • TLS certificate if HTTPS is used
⭐⭐⭐⭐⭐

15. ConfigMap Changes Are Not Reflected in Application

The behavior depends on how the ConfigMap is consumed. If configuration is injected as environment variables, existing containers generally need to be restarted to receive updated values. If mounted as files, updates can be reflected into the mounted volume depending on Kubernetes behavior and application handling. A common approach is to trigger a controlled rollout when configuration changes.
⭐⭐⭐⭐⭐

16. Secret Is Not Available Inside Pod

kubectl describe pod <pod-name>
kubectl get secret
I would verify:
  • Secret exists in the same namespace
  • Correct Secret name
  • Correct key
  • Volume or environment variable configuration
  • Pod specification
⭐⭐⭐⭐⭐ VERY IMPORTANT

17. Kubernetes Deployment Rollback

kubectl rollout history deployment/myapp

kubectl rollout status deployment/myapp

kubectl rollout undo deployment/myapp
I would first confirm the new deployment is unhealthy, identify the cause, and then roll back to the previous known-good revision if required.
⭐⭐⭐⭐

18. HPA Is Not Scaling Pods

kubectl get hpa

kubectl describe hpa <hpa-name>

kubectl top pods
I would check:
  • Metrics Server
  • CPU/memory resource requests
  • HPA configuration
  • Current and desired metrics
  • Minimum and maximum replicas
⭐⭐⭐⭐⭐ VERY IMPORTANT

19. Pod Cannot Mount PersistentVolume

kubectl get pvc
kubectl describe pvc <pvc-name>

kubectl get pv
I would check:
  • PVC status
  • StorageClass
  • PV availability
  • Access mode
  • Requested storage
  • CSI driver
  • Events
⭐⭐⭐⭐⭐

20. Cluster Has Insufficient Resources

kubectl top nodes

kubectl describe nodes
I would determine whether the problem is CPU, memory or another resource. Possible solutions:
  • Optimize Pod resource requests
  • Scale the node group
  • Add larger nodes
  • Use cluster autoscaling
  • Remove unnecessary workloads

21. Kubernetes Troubleshooting Cheat Sheet

Problem First Commands
CrashLoopBackOff get pods → logs → describe
Pending describe pod → Events
ImagePullBackOff describe pod → image/secret
Service unavailable get svc → endpoints → labels
Node NotReady get nodes → describe node → kubelet
OOMKilled describe pod → top pod → resources
DNS issue CoreDNS → DNS service → nslookup
Ingress issue Ingress → controller → service → endpoints
HPA issue get hpa → describe hpa → metrics
PVC issue get pvc → describe pvc → PV/StorageClass

🧠 Golden Kubernetes Interview Formula

Pod Problem → get pods → describe → logs

Scheduling Problem → Events → Nodes → Resources

Networking Problem → Service → Endpoints → DNS → Ingress

Storage Problem → PVC → PV → StorageClass

Performance Problem → top → Requests/Limits → HPA

Deployment Problem → Rollout → Logs → Rollback
