⭐⭐⭐⭐⭐ VERY IMPORTANT

1. Terraform Apply Fails

Question

Terraform plan succeeds but terraform apply fails. What would you do?

I would first read the exact provider error and identify whether the failure is related to permissions, configuration, quotas, dependencies or an existing cloud resource. Then I would fix the root cause and run: 
terraform plan
terraform apply
I would avoid randomly changing resources without understanding the error.
⭐⭐⭐⭐⭐ VERY IMPORTANT

2. Terraform State File Is Missing

The Terraform state tracks the relationship between configuration and infrastructure. If the state is missing, Terraform may believe resources do not exist. I would first check whether the state is stored locally or in a remote backend. For production, I would prefer a remote backend with appropriate locking and access control.
⭐⭐⭐⭐⭐

3. Terraform State and Real Infrastructure Are Different

Question

Someone manually changes an AWS resource. What happens when Terraform runs?

This is called configuration drift. I would run: 
terraform plan
Terraform refreshes its understanding of the infrastructure and the plan can show differences between the desired configuration and actual infrastructure. The correct solution is to bring the infrastructure back under controlled Terraform management rather than making random manual changes.
⭐⭐⭐⭐⭐ VERY IMPORTANT

4. Two Engineers Run Terraform at the Same Time

This can cause state consistency problems if both operations modify the same state concurrently. For production, I would use a remote backend with state locking where supported. Example AWS architecture:
Developer A      Developer B
↓          ↓
Terraform
↓
Remote Backend
↓
Shared State
The lock prevents conflicting state operations.
⭐⭐⭐⭐⭐

5. Terraform State Is Locked

Question

Terraform says the state is locked. What do you do?

First I would determine whether another Terraform operation is actually running. I would not immediately force-unlock the state. Only after confirming that the original operation is no longer running and the lock is stale would I consider: 
terraform force-unlock <LOCK_ID>
Important: Force-unlock can be dangerous if another Terraform operation is still running.
⭐⭐⭐⭐⭐ VERY IMPORTANT

6. Terraform Wants to Recreate an Important Resource

terraform plan
I would carefully inspect why Terraform wants to replace the resource. Possible causes include:
  • Immutable attribute changes
  • Configuration changes
  • State mismatch
  • Drift
  • Provider behavior
I would not run apply blindly against a production resource. I would understand the planned replacement first.
⭐⭐⭐⭐⭐

7. Resource Exists in AWS but Terraform Wants to Create It

This usually means Terraform does not have that resource correctly represented in its state. If the resource was created outside Terraform, I would consider importing it into state. Modern Terraform supports import blocks, for example: 
import {
  to = aws_instance.app
  id = "i-0123456789abcdef0"
}
The exact resource type and ID depend on the provider.
⭐⭐⭐⭐⭐ VERY IMPORTANT

8. Terraform Destroy Is Dangerous

Question

How would you safely destroy infrastructure?

First I would review: 
terraform plan -destroy
I would verify the resources being removed and ensure that production resources are protected through process and policy. Where appropriate, lifecycle rules can prevent accidental destruction: 
lifecycle {
  prevent_destroy = true
}
⭐⭐⭐⭐

9. Terraform Provider Authentication Fails

I would verify:
  • Credentials
  • IAM permissions
  • Environment variables
  • AWS profile
  • Region
  • Account
  • STS identity
For AWS: 
aws sts get-caller-identity
This quickly confirms which AWS identity Terraform may be expected to use.
⭐⭐⭐⭐⭐

10. Terraform Plan Shows Unexpected Changes

I would investigate:
  • Recent code changes
  • Variable values
  • State
  • Manual cloud changes
  • Provider version
  • Resource defaults
Then I would compare the plan carefully before applying it.
⭐⭐⭐⭐⭐ VERY IMPORTANT

11. Terraform Variables Are Not Getting the Expected Value

Check variable declaration:

variable "region" {
  type    = string
  default = "ap-south-1"
}

Check tfvars:

region = "ap-south-1"
I would verify variable precedence, variable names, tfvars files, environment variables and command-line values. I would also check whether Terraform is loading the expected workspace and configuration.
⭐⭐⭐⭐

12. Terraform Module Is Not Working

terraform init
terraform validate
terraform plan
I would check:
  • Module source
  • Module version
  • Required inputs
  • Outputs
  • Provider configuration
  • Module dependency
I would also inspect the module source itself if necessary.
⭐⭐⭐⭐⭐

13. Terraform Init Fails

Common causes include:
  • Provider download failure
  • Backend configuration problem
  • Authentication issue
  • Network/proxy problem
  • Invalid module source
I would inspect the exact error before changing the configuration.
⭐⭐⭐⭐

14. Terraform Configuration Has Syntax Errors

terraform fmt
terraform validate
terraform fmt formats the configuration. terraform validate checks whether the configuration is syntactically and internally valid. I would run both before creating infrastructure.
⭐⭐⭐⭐⭐ VERY IMPORTANT

15. Terraform Apply Fails Halfway Through

Terraform may have successfully created some resources before another resource failed. I would first inspect: 
terraform state list

terraform plan
I would identify what already exists, understand the failed resource and then safely continue after fixing the root cause. I would not automatically destroy everything and start again.
⭐⭐⭐⭐⭐

16. Terraform State Contains Sensitive Information

Terraform state can contain sensitive resource information. I would:
  • Use a secure remote backend
  • Restrict backend access
  • Encrypt state at rest
  • Control IAM permissions
  • Avoid committing state files to Git
  • Protect state backups
Example .gitignore: 
*.tfstate
*.tfstate.*
.terraform/
⭐⭐⭐⭐⭐ VERY IMPORTANT

17. Terraform Resource Was Deleted Manually

Someone deletes an EC2 instance manually from AWS.

Terraform still has the resource recorded in state. During the next plan, Terraform detects that the real resource is missing and may propose creating it again to match the desired configuration. I would review the plan and apply only after confirming that recreation is expected.
⭐⭐⭐⭐

18. Different Environments Need Different Values

For example, development and production need different instance sizes.

I would avoid hardcoding environment-specific values. A common approach is: 
terraform.tfvars
dev.tfvars
prod.tfvars
Or use workspaces/modules depending on the architecture. Example: 
instance_type = "t3.micro"
The exact approach should match the team's environment strategy.
⭐⭐⭐⭐⭐

19. How Would You Manage Terraform in a Team?

I would use:
  • Git for version control
  • Pull requests and code review
  • Remote state
  • State locking
  • Reusable modules
  • Separate environments
  • CI validation
  • Terraform plan before apply
  • Restricted production access
A typical pipeline:
Git Push
↓
terraform fmt
↓
terraform validate
↓
terraform plan
↓
Code Review
↓
terraform apply
⭐⭐⭐⭐⭐ VERY IMPORTANT

20. Terraform Changes Must Be Applied Automatically

I would integrate Terraform into CI/CD. The pipeline could run: 
terraform init
terraform fmt -check
terraform validate
terraform plan
After approval, a controlled process can execute: 
terraform apply
Production apply should have appropriate approval and access controls rather than allowing every developer to change infrastructure directly.
