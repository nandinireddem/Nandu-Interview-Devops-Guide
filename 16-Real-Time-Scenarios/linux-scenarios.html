1. Server CPU Usage Is 100%

Question

A production Linux server suddenly reaches 100% CPU. How would you troubleshoot it?

Step 1: Check overall CPU usage 
top
uptime
Step 2: Find the process consuming CPU 
ps aux --sort=-%cpu | head
Step 3: Determine whether the process is expected, a runaway process, application issue or traffic-related issue. Step 4: Check application logs. Step 5: Fix the root cause and monitor again.
⭐⭐⭐⭐⭐

2. Server Memory Is Almost Full

free -h
top
ps aux --sort=-%mem | head
I would identify which process is consuming memory and determine whether the system is under genuine memory pressure or whether Linux is using memory for cache. I would also check swap usage. 
swapon --show
Then I would investigate the application for a memory leak or increase capacity if required.
⭐⭐⭐⭐⭐ VERY IMPORTANT

3. Disk Space Is 100% Full

df -h

Then identify large directories:

du -sh /* 2>/dev/null
du -sh /var/* 2>/dev/null
Common causes include:
  • Large application logs
  • Temporary files
  • Old packages
  • Large application data
  • Log rotation failure
I would clean only safe files, fix log rotation if necessary, and increase disk capacity when required.
⭐⭐⭐⭐⭐

4. Application Is Running but Users Cannot Access It

Check

systemctl status application.service

ss -tulpn

curl localhost:8080
I would verify that the application process is running and listening on the expected port. Then I would check firewall, security rules and network connectivity.
⭐⭐⭐⭐⭐ VERY IMPORTANT

5. Service Is Not Running

systemctl status nginx

systemctl start nginx

systemctl enable nginx

For deeper investigation:

journalctl -u nginx
I would first check the service status, then inspect the service logs and configuration, fix the root cause and restart the service. After restarting, I would verify its status and application connectivity.
⭐⭐⭐⭐⭐

6. SSH Connection Is Failing

Check from client

ssh user@server-ip

Check on server

systemctl status sshd

ss -tlnp | grep :22
I would check:
  • Server availability
  • Port 22 connectivity
  • SSH service
  • Firewall rules
  • User account
  • SSH key / password
  • sshd configuration
  • Authentication logs
⭐⭐⭐⭐⭐

7. Permission Denied Error

ls -l file.txt

id

whoami

Check ownership:

chown user:group file.txt

Check permissions:

chmod 640 file.txt
I would first identify the user running the process and compare that user's permissions with the file or directory ownership. I would avoid blindly using chmod 777.
⭐⭐⭐⭐⭐ VERY IMPORTANT

8. Which Process Is Using a Port?

ss -tulpn

Or:

lsof -i :8080
This helps identify which process is listening on the required port and whether another application is causing a port conflict.
⭐⭐⭐⭐⭐

9. Application Logs Are Growing Rapidly

du -sh /var/log/*

tail -f /var/log/application.log
I would determine why the application is generating excessive logs, check log rotation configuration and prevent the filesystem from becoming full.
⭐⭐⭐⭐

10. How Do You Find a File?

find /var/log -name "*.log"

find / -name "app.conf" 2>/dev/null

Search inside files:

grep -R "ERROR" /var/log/
⭐⭐⭐⭐⭐

11. Server Load Average Is High

uptime

top
Load average indicates how much work is waiting for CPU or other system resources. I would correlate load average with CPU, memory, disk I/O and process information rather than assuming high load always means high CPU.
⭐⭐⭐⭐

12. Disk I/O Is Very High

iostat

iotop

vmstat
I would identify the process causing high disk activity and determine whether the workload is application-related, database-related or caused by insufficient disk performance.
⭐⭐⭐⭐⭐ VERY IMPORTANT

13. DNS Is Not Working

nslookup google.com

dig google.com

cat /etc/resolv.conf
I would determine whether the issue is DNS configuration, network connectivity, resolver availability or an application- specific DNS problem.
⭐⭐⭐⭐

14. Server Cannot Reach Another Server

ping server-ip

curl -v http://server-ip:8080

nc -vz server-ip 8080
I would troubleshoot layer by layer:
  • DNS
  • Routing
  • Firewall
  • Port availability
  • Target service
⭐⭐⭐⭐⭐

15. Process Is Stuck

ps aux | grep application

top

Inspect the process:

ps -p PID -f

If necessary, terminate gracefully:

kill PID

Force termination only when required:

kill -9 PID
Interview Point: Use SIGTERM first so the application has an opportunity to clean up. SIGKILL should be a last resort.
⭐⭐⭐⭐⭐ VERY IMPORTANT

16. Server Rebooted Unexpectedly

I would investigate:
  • System logs
  • Kernel messages
  • Cloud provider events
  • OOM events
  • Hardware / infrastructure events
  • Scheduled jobs
  • Manual administrative actions
Useful commands: 
journalctl -b -1
dmesg | tail -50
last reboot
⭐⭐⭐⭐⭐

17. OOM Killer Terminated an Application

dmesg | grep -i "out of memory"

journalctl -k | grep -i oom
I would identify which process consumed excessive memory, check application behavior and determine whether memory limits or instance capacity need adjustment.
⭐⭐⭐⭐

18. Cron Job Is Not Running

crontab -l

systemctl status cron

Check logs:

grep CRON /var/log/syslog
I would verify the cron syntax, correct user, executable permissions, absolute paths and environment variables. Cron runs with a limited environment, so commands that work interactively may fail in cron.
⭐⭐⭐⭐⭐

19. Find the Top CPU and Memory Processes

ps aux --sort=-%cpu | head

ps aux --sort=-%mem | head
These commands quickly help identify resource-heavy processes during production troubleshooting.
