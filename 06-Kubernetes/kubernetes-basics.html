⭐⭐⭐⭐⭐ 1. What is Kubernetes?

Q. What is Kubernetes?

Kubernetes is an open-source container orchestration platform used to deploy, manage, scale and maintain containerized applications across a cluster of machines.

Why do we need Kubernetes?

Running one or two Docker containers manually is simple. But in a production environment we may have hundreds of containers running across multiple servers.

We need automation for scheduling, scaling, service discovery, self-healing, rolling updates, configuration management and resource management.

Problem Kubernetes Solution
Container crashes Self-healing / container restart
Server has limited capacity Schedule workloads across nodes
Need more application instances Scale replicas
Application IP keeps changing Service provides stable networking
Need application update without downtime Rolling updates
Need to manage hundreds of containers Container orchestration
Real-time example: Suppose an e-commerce application runs as 10 container replicas. If one container crashes, Kubernetes can replace it. If traffic increases from 10,000 requests/minute to 50,000 requests/minute, the application can be scaled from 10 Pods to more replicas. If a node becomes unavailable, Kubernetes can reschedule workloads on available nodes depending on the workload configuration and cluster capacity.
Interview-ready answer:

"Kubernetes is an open-source container orchestration platform. It automates deployment, scaling, networking and management of containerized applications. In production, it helps us maintain application availability through mechanisms such as self-healing, replica management, service discovery and rolling deployments."

⭐⭐⭐⭐⭐ 2. Why Kubernetes when we already have Docker?

Q. Is Kubernetes a replacement for Docker?

Kubernetes and Docker solve different problems. Docker is primarily used to build, package and run containers. Kubernetes is used to orchestrate and manage containerized workloads across a cluster.
Docker Kubernetes
Build container images Manage containerized workloads
Run individual containers Manage workloads across multiple nodes
Container runtime / tooling ecosystem Container orchestration platform
Dockerfile Pod / Deployment / Service YAML
docker run kubectl apply
Real-time: A company has 50 microservices. Running each container manually would be difficult. Kubernetes can schedule these workloads across worker nodes, restart failed workloads, expose services and scale applications.
Do not say: " Kubernetes is used to create Docker containers." A better answer is: "Kubernetes orchestrates containerized workloads."

⭐⭐⭐⭐⭐ 3. Kubernetes Cluster

Q. What is a Kubernetes cluster?

A Kubernetes cluster is a group of machines that work together to run containerized workloads. It consists conceptually of a control plane and one or more worker nodes.
Kubernetes Cluster

┌───────────────────────────────┐
Control Plane
API Server | Scheduler | Controllers | etcd
└───────────────────────────────┘

↓

┌───────────────────────────────┐
Worker Nodes
Kubelet | Container Runtime | kube-proxy
Pods
└───────────────────────────────┘

Two major parts

  1. Control Plane — manages cluster state and makes control decisions.
  2. Worker Nodes — run application workloads.

Interview-ready answer:

"The control plane manages the Kubernetes cluster. The API server provides the Kubernetes API, etcd stores cluster state, the scheduler selects nodes for Pods, and controller components continuously work to maintain the desired state."

⭐⭐⭐⭐⭐ 5. What is kube-apiserver?

The kube-apiserver is the central API component of Kubernetes. It exposes the Kubernetes API and acts as the main entry point for cluster management operations.

Example

When you execute: 

kubectl get pods

kubectl communicates with the Kubernetes API server. The API server processes the request and returns the relevant cluster information.

kubectl
↓
API Server
↓
Cluster Data / Components
↓
Response
Real-time: A DevOps engineer wants to inspect application Pods in production. Instead of directly connecting to every worker node, the engineer uses kubectl to communicate with the Kubernetes API.

⭐⭐⭐⭐⭐ 6. What is etcd?

etcd is a distributed key-value store used by Kubernetes to store important cluster state and configuration data.

What kind of information?

  • Cluster configuration
  • Object metadata
  • Desired state information
  • Resource definitions
  • Other Kubernetes control-plane state
Real-time: If you create a Deployment with 3 replicas, Kubernetes needs to know the desired state. The cluster's state information is persisted through the Kubernetes control plane, with etcd serving as the backing store for that state.
etcd is critical infrastructure. In production clusters, etcd backup and recovery are important because loss of the required cluster state can affect the ability to recover the control plane.

⭐⭐⭐⭐⭐ 7. What is kube-scheduler?

The kube-scheduler watches for Pods that do not yet have a node assigned and selects an appropriate worker node for them.

What does it consider?

  • Available resources
  • CPU and memory requirements
  • Node constraints
  • Affinity / anti-affinity
  • Taints and tolerations
  • Other scheduling rules
Pod Created
↓
API Server
↓
Scheduler
↓
Select Suitable Node
↓
Pod Gets Scheduled
↓
Kubelet Runs Pod
Real-time example: Suppose Node A has only 200 MB memory available while Node B has 8 GB available. If a Pod requires significant memory, Kubernetes scheduling logic may select an appropriate node based on resource requirements and other scheduling constraints.

⭐⭐⭐⭐⭐ 8. What is kube-controller-manager?

The controller manager runs controllers that continuously compare the desired state with the current state and take actions to move the cluster toward the desired state.

Desired State vs Actual State

Desired State
"3 Pods should run"
↓
Controller observes cluster
↓
Actual State = 2 Pods
↓
Controller takes action
↓
3 Pods running
You define: 
replicas: 3
If one Pod disappears, the relevant controller detects that the actual state no longer matches the desired state and works toward restoring the required number of replicas.
This is one of the most important Kubernetes concepts: Kubernetes is declarative and continuously works toward the desired state.

⭐⭐⭐⭐⭐ 9. Worker Node

Q. What is a worker node?

A worker node is a machine in the Kubernetes cluster where application workloads, usually in the form of Pods, run.

Important node components

Component Purpose
Kubelet Agent running on the node that communicates with the API server and manages Pods assigned to the node.
Container Runtime Runs containers for Pods.
kube-proxy Provides node-level networking functionality for Kubernetes Services according to the cluster's networking implementation.
Worker Node

Kubelet
Container Runtime
kube-proxy
CNI / Networking

↓
Pods

⭐⭐⭐⭐⭐ 10. What is kubelet?

Kubelet is the primary node agent. It runs on every worker node and ensures that Pods assigned to that node are running and healthy according to their specifications.
Real-time: The scheduler assigns a Pod to Node-1. The kubelet on Node-1 receives the Pod specification through the Kubernetes control plane and works with the container runtime to ensure the required containers are running.
Interview answer: "Kubelet is the Kubernetes node agent. It runs on each worker node, communicates with the control plane and ensures that the containers specified for Pods assigned to that node are running."

⭐⭐⭐⭐⭐ 11. What is a Container Runtime?

A container runtime is the software responsible for running containers on a Kubernetes node. Modern Kubernetes uses the CRI (Container Runtime Interface) to communicate with supported container runtimes.

Important point

Docker Engine is not the required Kubernetes runtime itself. Kubernetes can use CRI-compatible runtimes such as containerd and CRI-O.

Interview trap: Do not simply say: "Kubernetes uses Docker to run containers." A better answer is: "Kubernetes uses a CRI-compatible container runtime such as containerd or CRI-O to run containers."

⭐⭐⭐⭐⭐ 12. What is a Pod?

A Pod is the smallest deployable and schedulable unit in Kubernetes. A Pod contains one or more containers that share networking and can share storage.

Why doesn't Kubernetes directly manage individual containers?

Kubernetes uses the Pod as its basic workload unit. A Pod provides the context in which one or more tightly coupled containers run.

Most common pattern

Pod
↓
Application Container

Multi-container Pod

Pod
├── Application Container
└── Sidecar Container
Real-time example: A Java application runs in one container. A sidecar container may collect or process data closely associated with that application. Both containers are part of the same Pod and can communicate over the Pod's network namespace.
Interview-ready answer: "A Pod is the smallest deployable and schedulable unit in Kubernetes. It can contain one or more tightly coupled containers. Containers in the same Pod share the Pod network namespace and can share volumes. Normally we run one main application container per Pod and use multiple containers when they need to work closely together."

⭐⭐⭐⭐⭐ 13. Pod Networking

Important concept

Containers inside the same Pod share the Pod network namespace. They can communicate with each other using localhost and different ports. 

Pod IP: 10.244.1.15

Container A → localhost:8080
Container B → localhost:9000
Containers in the same Pod do not normally receive separate Pod IPs. The Pod has the network identity.

⭐⭐⭐⭐⭐ 14. Pod Lifecycle

Common Pod phases

Phase Meaning
Pending Pod has been accepted but one or more containers are not yet running.
Running Pod has been scheduled and at least one container is running or starting.
Succeeded All containers terminated successfully.
Failed All containers terminated and at least one failed.
Unknown Pod state could not be obtained, usually due to communication issues.

Useful command

kubectl get pods

⭐⭐⭐⭐⭐ 16. Desired State vs Actual State

Q. What is desired state?

Desired state is the state that we declare we want Kubernetes to maintain.

Example

replicas: 3

This tells Kubernetes that the workload should have three replicas.

Actual state

The actual state is what is currently running in the cluster.

Desired State
3 replicas
↓
Kubernetes Controllers
↓
Actual State
3 replicas
If one Pod crashes:

Desired = 3
Actual = 2
Kubernetes works toward restoring:
Actual = 3
Very important interview statement: "Kubernetes continuously reconciles the actual state with the desired state."

⭐⭐⭐⭐⭐ 17. Declarative vs Imperative Approach

Declarative Imperative
Describe desired state Tell Kubernetes specific commands/actions
Usually YAML manifests Often kubectl commands
Good for version control and GitOps Useful for quick operational tasks

Declarative example

kubectl apply -f deployment.yaml

Imperative example

kubectl create deployment nginx --image=nginx
For production and GitOps, declarative configuration is especially important because Kubernetes manifests can be version controlled and reviewed through Git.

Interview answer: "Most Kubernetes manifests describe the API version, resource kind, metadata and desired specification. The spec is where we define what we want Kubernetes to maintain."

⭐⭐⭐⭐⭐ 19. Kubernetes Object

A Kubernetes object is a persistent representation of a resource that describes the desired state of part of the cluster.

Common objects

Pod Deployment Service ConfigMap Secret Namespace StatefulSet DaemonSet Job CronJob

Each object has its own purpose. Kubernetes controllers and other control-plane components use these object definitions to manage cluster state.

⭐⭐⭐⭐⭐ 20. What are Labels?

Labels are key-value pairs attached to Kubernetes objects. They are commonly used to identify and organize resources and to select related workloads. 
metadata:
  labels:
    app: payment
    environment: production

Why are labels important?

  • Identify applications
  • Group resources
  • Enable selectors
  • Connect Services to Pods
  • Support operational organization
A Deployment creates Pods with: 
app: payment
A Service can use a selector matching: 
selector:
  app: payment
The Service can then target the appropriate Pods.

⭐⭐⭐⭐⭐ 21. Labels vs Annotations

Labels Annotations
Used for identification and selection Used for storing additional metadata
Can be used by selectors Not normally used for selection
Important for Services and workload grouping Useful for tooling and extra information

Example

metadata:
  labels:
    app: payment

  annotations:
    owner: devops-team

⭐⭐⭐⭐⭐ 22. What is kubectl?

kubectl is the command-line tool used to communicate with the Kubernetes API and manage Kubernetes resources.

Most important commands

kubectl get pods

kubectl get nodes

kubectl get deployments

kubectl describe pod <pod-name>

kubectl logs <pod-name>

kubectl exec -it <pod-name> -- /bin/sh

kubectl apply -f file.yaml

Real-time troubleshooting: A production Pod is not working. A DevOps engineer might start with: 
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
These commands help identify scheduling, image, container, configuration and runtime-related problems.

⭐⭐⭐⭐⭐ 23. What is a Namespace?

A Namespace provides a logical scope for Kubernetes resources within a cluster. It helps organize and isolate groups of resources.

Example

Kubernetes Cluster

│ ├── Pods
│ ├── Services
│ └── Deployments
│
├── staging
│ ├── Pods
│ └── Services

Commands

kubectl get namespaces

kubectl create namespace dev

kubectl get pods -n dev

kubectl get all -n dev
A company may use separate namespaces for development, staging and production workloads within a cluster, together with appropriate RBAC and resource policies.

⭐⭐⭐⭐ 24. What is a Kubernetes Context?

A kubectl context defines which cluster, user/credentials and namespace kubectl should use by default for commands.

Useful commands

kubectl config get-contexts

kubectl config current-context

kubectl config use-context <context-name>
Always verify the current context before running destructive commands against production.

⭐⭐⭐⭐⭐ 27. What happens if a Pod crashes?

Kubernetes behavior depends on how the Pod is managed and the container's restart policy. For Pods managed by controllers such as Deployments, the controller also works to maintain the desired number of replicas.
Production example: Suppose a Deployment requires: 
replicas: 3
If one Pod becomes unavailable, the Deployment's controller works to restore the desired number of available replicas, subject to cluster capacity and the specific failure.
For production applications, we normally manage Pods through higher-level workload controllers such as Deployments rather than creating individual Pods manually.

⭐⭐⭐⭐⭐ 28. Why don't we normally create Pods directly?

A standalone Pod does not provide the same desired-state management and rollout capabilities as a Deployment or other workload controller.

If a standalone Pod is deleted, Kubernetes does not automatically create a replacement Pod simply because that Pod existed.

A Deployment, on the other hand, maintains a desired number of replicas and manages rollout behavior.

Deployment
↓
ReplicaSet
↓
Pods
↓
Containers

⭐⭐⭐⭐⭐ 29. Pod vs Deployment

Pod Deployment
Smallest deployable unit Workload controller
Runs containers Manages replicated Pods
No built-in rollout strategy Supports rolling updates and rollout management
Not ideal for production application management Common for stateless applications
Interview answer: "A Pod runs the application containers, while a Deployment manages the desired number of replicated Pods and provides rollout and rollback capabilities for stateless workloads."

⭐⭐⭐⭐ 30. Kubernetes Self-Healing

Self-healing means Kubernetes continuously works to maintain the desired state of workloads, including restarting failed containers according to the Pod's restart policy and recreating Pods when a controller such as a Deployment determines that replicas are missing.
Suppose: 
replicas: 3
Current state: 
Pod-1
Pod-2
Pod-3
If Pod-2 becomes unavailable, the workload controller can work toward restoring the desired replica count.

⭐⭐⭐⭐ 31. What is Kubernetes Service Discovery?

Kubernetes Services provide a stable network endpoint for reaching a set of Pods selected by labels. This is important because Pod IPs are not intended to be the stable application endpoint.
Frontend Pod
↓
Service
↓
Backend Pods
├── Pod 1
├── Pod 2
└── Pod 3

Services are covered in detail in the Kubernetes Services section, but this concept is essential to understand the Kubernetes basics.

⭐⭐⭐⭐ 32. Kubernetes Networking Basic Concept

At a high level, Kubernetes networking allows Pods to communicate with each other and allows Services to provide stable access to workloads.

Important interview points

  • Each Pod gets a network identity.
  • Containers in the same Pod share the network namespace.
  • Services provide stable virtual endpoints.
  • Kubernetes networking is implemented using a CNI plugin.
Do not confuse: Pod IP → individual Pod networking
Service IP → stable Service endpoint
Node IP → worker machine networking

⭐⭐⭐⭐⭐ 33. Kubernetes Resource Requests and Limits — Basic Idea

Resource requests indicate the amount of CPU or memory a container is requesting for scheduling purposes. Limits define an upper boundary for resource usage. 
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"

Why important?

  • Helps scheduler make placement decisions
  • Prevents uncontrolled resource consumption
  • Improves cluster capacity planning
  • Important for production workloads

⭐⭐⭐⭐⭐ 34. Kubernetes Health Checks — Basic Idea

Kubernetes supports probes that help determine whether a container is alive, ready to receive traffic, or has started successfully.

Probe Purpose
Liveness Probe Helps determine whether a container needs to be restarted.
Readiness Probe Determines whether the application should receive traffic.
Startup Probe Gives slow-starting applications time to initialize before other probes take over.
Real-time example: A Spring Boot application takes 60 seconds to start. A startup probe can prevent Kubernetes from treating the application as unhealthy too early. Once startup succeeds, readiness and liveness checks can take over.

⭐⭐⭐⭐⭐ 36. Real-Time Scenario — Pod is Pending

Problem: You deploy an application and the Pod remains in: 
Pending
What would you check? 
kubectl get pods

kubectl describe pod <pod-name>
Look at the Events section. Possible causes include:
  • Insufficient CPU or memory
  • Scheduling constraints
  • Node selectors
  • Taints and tolerations
  • Affinity rules
  • No suitable node available
Interview answer: "If a Pod is Pending, I would first run kubectl describe pod and check the Events section. I would verify node availability, resource requests, taints, tolerations, selectors and other scheduling constraints."

⭐⭐⭐⭐⭐ 37. Real-Time Scenario — Pod is CrashLoopBackOff

Problem: A Pod repeatedly starts and crashes.

First checks: 
kubectl get pods

kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>
Possible causes:
  • Application startup failure
  • Incorrect environment variables
  • Missing configuration
  • Incorrect command or arguments
  • Dependency unavailable
  • Probe failure
  • Application exits immediately
Important: CrashLoopBackOff is not the root cause itself. It means Kubernetes is repeatedly restarting a container and applying a backoff delay between restart attempts.

⭐⭐⭐⭐⭐ 38. Real-Time Scenario — ImagePullBackOff

Problem: Pod cannot start because the container image cannot be pulled. Check: 
kubectl describe pod <pod-name>
Look for image-related events. Possible causes:
  • Wrong image name
  • Wrong image tag
  • Private registry authentication issue
  • Image does not exist
  • Registry connectivity issue
  • Image pull credentials problem
Interview answer: "I would inspect the Pod events using kubectl describe pod. Then I would verify the image name and tag, registry availability and, for private registries, the image-pull credentials."

⭐⭐⭐⭐⭐ 39. Real-Time Scenario — Pod is Running but Application is Not Accessible

Do not assume that: 
STATUS = Running
means the application is reachable. Check: 
kubectl get pods -o wide

kubectl get svc

kubectl describe svc <service-name>

kubectl get endpoints

kubectl logs <pod-name>
Possible issues:
  • Service selector does not match Pod labels
  • Wrong targetPort
  • Application listening on wrong port
  • Readiness probe failing
  • Network policy or external networking issue

🎯 Explain Kubernetes in 1 Minute

"Kubernetes is an open-source container orchestration platform used to deploy, manage and scale containerized applications. A Kubernetes cluster consists mainly of a control plane and worker nodes. The control plane includes components such as the API server, etcd, scheduler and controllers, while worker nodes run application Pods using components such as kubelet and a container runtime. A Pod is the smallest deployable unit in Kubernetes and can contain one or more tightly coupled containers. Kubernetes follows a declarative model where we define the desired state, usually through YAML manifests. Controllers continuously reconcile the actual state with the desired state. For example, if a Deployment requires three application replicas and one becomes unavailable, Kubernetes works to restore the desired replica state. In DevOps, Kubernetes provides capabilities such as self-healing, scaling, service discovery, rolling deployments and resource management, making it suitable for running containerized applications in production."

🚨 Common Kubernetes Interview Traps

Question Correct Understanding
Is Kubernetes the same as Docker? No. Docker provides container tooling; Kubernetes orchestrates containerized workloads.
Is a Pod the same as a container? No. A Pod can contain one or more containers.
Does Kubernetes normally create containers directly? Kubernetes manages Pods through the control plane and node agents, which work with a container runtime.
Does a Pod always have multiple containers? No. The common pattern is one main application container per Pod.
Does Running mean the application is healthy? No. Readiness and application-level health must also be considered.
Does CrashLoopBackOff mean the image is wrong? Not necessarily. It indicates repeated container restart attempts with backoff.
Does Pending mean the application crashed? No. Pending commonly indicates scheduling or startup prerequisites have not been satisfied.
Is a Pod IP permanent? No. Pods are replaceable and their IPs should not be treated as permanent endpoints.
Does etcd run application containers? No. etcd stores Kubernetes cluster state.
Does scheduler run containers? No. Scheduler selects suitable nodes for Pods.
