Kubernetes Ingress, Helm & Monitoring

Interview-focused guide covering Ingress, Ingress Controllers, TLS routing, Helm, Charts, Releases, Values, Prometheus, Grafana, metrics, alerting, troubleshooting and real-time DevOps scenarios.

⭐⭐⭐⭐⭐ Big Picture

Ingress, Helm and Monitoring solve three different production problems in Kubernetes.

Ingress
External HTTP/HTTPS traffic → Kubernetes Services

↓ Helm
Package + install + upgrade Kubernetes applications

↓ Monitoring
Observe metrics → dashboards → alerts → troubleshoot
Real-time example: A company runs a web application on Kubernetes. Users access: 
https://shop.example.com
Ingress routes the request to the correct Service. Helm is used to install and upgrade the application. Prometheus collects metrics and Grafana displays dashboards for CPU, memory, request rate, latency and application health.

⭐⭐⭐⭐⭐ 1. What is Kubernetes Ingress?

Ingress is a Kubernetes API object used to define HTTP and HTTPS routing rules for traffic entering the cluster. It can route requests based on hostnames and URL paths to backend Services.
Internet
↓
Load Balancer
↓
Ingress Controller
↓
Ingress Rules
↓
Service
↓
Pods
Interview answer: "Ingress provides HTTP and HTTPS routing into Kubernetes Services. It allows us to expose multiple applications using host-based or path-based routing through a common entry point."

⭐⭐⭐⭐⭐ 2. What is an Ingress Controller?

An Ingress resource only defines routing rules. An Ingress Controller is the component that actually implements those rules and processes incoming traffic. Examples include:
  • NGINX Ingress Controller
  • Traefik
  • HAProxy
  • Cloud-provider ingress/load-balancer controllers
Creating an Ingress object without an appropriate Ingress Controller does not automatically make the application reachable.

⭐⭐⭐⭐⭐ 3. Basic Ingress YAML

apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: shop-ingress

spec:
  ingressClassName: nginx

  rules:
  - host: shop.example.com

    http:
      paths:
      - path: /
        pathType: Prefix

        backend:
          service:
            name: shop-service
            port:
              number: 80

Requests for shop.example.com are routed to shop-service.

⭐⭐⭐⭐⭐ 4. Path-Based Routing

apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: app-ingress

spec:
  ingressClassName: nginx

  rules:
  - host: example.com

    http:
      paths:

      - path: /api
        pathType: Prefix

        backend:
          service:
            name: api-service
            port:
              number: 80

      - path: /web
        pathType: Prefix

        backend:
          service:
            name: web-service
            port:
              number: 80
example.com/api → API Service

example.com/web → Web Service

⭐⭐⭐⭐⭐ 5. Host-Based Routing

rules:

- host: api.example.com

  http:
    paths:
    - path: /
      pathType: Prefix

      backend:
        service:
          name: api-service
          port:
            number: 80

- host: shop.example.com

  http:
    paths:
    - path: /
      pathType: Prefix

      backend:
        service:
          name: shop-service
          port:
            number: 80
Production example: 
api.example.com
        ↓
API Service

shop.example.com
        ↓
Shop Service
One cluster can serve multiple applications through the ingress layer.

⭐⭐⭐⭐⭐ 6. Ingress TLS

Ingress can terminate HTTPS/TLS traffic using a Kubernetes TLS Secret. 
spec:

  tls:
  - hosts:
    - shop.example.com

    secretName: shop-tls

  rules:
  - host: shop.example.com

    http:
      paths:
      - path: /
        pathType: Prefix

        backend:
          service:
            name: shop-service
            port:
              number: 80
Client: HTTPS ↓ Ingress Controller terminates TLS ↓ Service ↓ Pod

⭐⭐⭐⭐⭐ 7. Ingress vs Service

Service Ingress
Provides stable networking for Pods. Provides HTTP/HTTPS routing.
Can expose applications using ClusterIP, NodePort or LoadBalancer. Routes based on host/path rules.
Works at the Service/networking layer. Primarily handles HTTP/HTTPS application routing.
Simple answer: "Service provides stable access to Pods, while Ingress provides HTTP/HTTPS routing from outside the cluster to those Services."

⭐⭐⭐⭐ 8. Ingress troubleshooting

If an application is not reachable through Ingress, check: 
kubectl get ingress
kubectl describe ingress <ingress-name>

kubectl get ingressclass

kubectl get svc
kubectl get pods

kubectl get endpoints
kubectl get events

Verify the Ingress class, hostname, Service name, Service port, backend endpoints and Ingress Controller logs.

⭐⭐⭐⭐⭐ 9. What is Helm?

Helm is a package manager for Kubernetes. It helps package, install, upgrade, configure and manage Kubernetes applications using reusable Charts.
Helm Chart
↓ Templates + Values
↓ Helm
↓ Kubernetes Manifests
↓ Kubernetes API
↓ Resources
"Helm is commonly used to package Kubernetes applications and simplify repeatable deployments by using charts, templates and values."

⭐⭐⭐⭐⭐ 10. What is a Helm Chart?

A Helm Chart is a collection of files that describes a Kubernetes application. A typical chart contains templates, default values and chart metadata.

Typical structure

myapp/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    ├── ingress.yaml
    └── _helpers.tpl

⭐⭐⭐⭐⭐ 11. Important Helm files

File Purpose
Chart.yaml Chart metadata such as name and version.
values.yaml Default configurable values.
templates/ Kubernetes manifest templates.
_helpers.tpl Reusable Helm template helpers.

⭐⭐⭐⭐⭐ 12. Helm values.yaml

replicaCount: 2

image:
  repository: nginx
  tag: "1.27"

service:
  type: ClusterIP
  port: 80

Templates can consume these values using Helm template expressions. 

replicas: {{ .Values.replicaCount }}

image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

⭐⭐⭐⭐⭐ 13. Helm install

helm install myapp ./myapp

This creates a Helm release from the chart.

Specify values

helm install myapp ./myapp \
  --set replicaCount=3

⭐⭐⭐⭐⭐ 14. Helm upgrade

helm upgrade myapp ./myapp
Suppose production currently runs: 
replicas: 2
You change the values to: 
replicas: 4
Then: 
helm upgrade myapp ./myapp
Helm applies the updated release configuration.

⭐⭐⭐⭐⭐ 15. Helm rollback

Helm tracks release revisions, allowing you to roll back to a previous revision. 
helm history myapp

helm rollback myapp 2
Production deployment v3 causes an outage. If revision 2 was stable: 
helm rollback myapp 2
This provides a fast recovery mechanism.

⭐⭐⭐⭐⭐ 16. Helm release

A Helm release is a deployed instance of a Helm Chart. The same chart can have different releases. 
helm install dev-app ./myapp
helm install prod-app ./myapp

Here the same chart is used to create two different releases.

⭐⭐⭐⭐⭐ 17. Helm important commands

# Add repository
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts

# Update repositories
helm repo update

# Search charts
helm search repo prometheus

# Install
helm install myapp ./mychart

# List releases
helm list

# List all namespaces
helm list -A

# Show values
helm get values myapp

# Show release
helm get all myapp

# History
helm history myapp

# Upgrade
helm upgrade myapp ./mychart

# Rollback
helm rollback myapp 1

# Uninstall
helm uninstall myapp

⭐⭐⭐⭐⭐ 18. helm template

helm template renders Kubernetes manifests locally without actually installing the release. 
helm template myapp ./mychart
Very useful in CI/CD to inspect generated manifests before applying them to a cluster.

⭐⭐⭐⭐⭐ 19. Helm vs kubectl

kubectl Helm
Directly interacts with Kubernetes resources. Manages applications through reusable charts.
Works with individual manifests/resources. Provides templating, values and release management.
Excellent for troubleshooting and direct operations. Excellent for repeatable application packaging/deployment.

⭐⭐⭐⭐⭐ 21. What is Kubernetes Monitoring?

Kubernetes monitoring means collecting and analyzing information about cluster nodes, Pods, containers, applications and workloads. It helps teams detect failures, resource problems, performance issues and capacity requirements.
Applications
↓
Metrics
↓
Prometheus
↓
Grafana
↓
Dashboard
↓
Alert
↓
DevOps Engineer

⭐⭐⭐⭐⭐ 22. Prometheus

Prometheus is a monitoring and alerting system commonly used with Kubernetes. It collects time-series metrics and stores them for querying and alerting.

Examples of metrics

  • CPU usage
  • Memory usage
  • Request rate
  • HTTP errors
  • Latency
  • Pod/container metrics
  • Node metrics

⭐⭐⭐⭐⭐ 23. Grafana

Grafana is commonly used to visualize metrics through dashboards. It can connect to Prometheus and display Kubernetes and application metrics in graphs, tables and panels.
Example dashboard: 
Cluster CPU
Cluster Memory
Node Health
Pod Count
Pod Restarts
HTTP Request Rate
HTTP Error Rate
Application Latency

⭐⭐⭐⭐⭐ 24. Prometheus vs Grafana

Prometheus Grafana
Collects and stores metrics. Visualizes metrics.
Provides PromQL querying. Provides dashboards and panels.
Can perform alerting. Can visualize and route alerts depending on configuration.
Easy answer: "Prometheus is primarily the metrics collection and monitoring system, while Grafana is primarily used to visualize those metrics through dashboards."

⭐⭐⭐⭐⭐ 25. What is PromQL?

PromQL is Prometheus Query Language. It is used to query and analyze time-series metrics stored in Prometheus.

Example

up

Shows whether monitored targets are currently up.

Example

rate(http_requests_total[5m])

Calculates the per-second rate of increase over the selected five-minute range.

⭐⭐⭐⭐⭐ 27. Install monitoring stack using Helm

helm repo add prometheus-community \
https://prometheus-community.github.io/helm-charts

helm repo update

helm install monitoring \

-n monitoring \
--create-namespace

Check

kubectl get pods -n monitoring
kubectl get svc -n monitoring

⭐⭐⭐⭐⭐ 28. Why use monitoring in production?

Without monitoring, engineers may know that an application is down only after users report the problem. Monitoring provides visibility into:
  • Resource usage
  • Application performance
  • Errors
  • Latency
  • Pod restarts
  • Node failures
  • Capacity trends

⭐⭐⭐⭐⭐ 29. What should you monitor?

Layer Examples
Cluster Node health, CPU, memory, capacity
Pods Restarts, CPU, memory, status
Application Request rate, errors, latency
Network Traffic, failures, latency
Storage Capacity, I/O, volume health

⭐⭐⭐⭐⭐ 30. Pod CrashLoopBackOff monitoring

If a Pod repeatedly crashes: 
kubectl get pods
kubectl describe pod <pod-name>
kubectl logs <pod-name>
kubectl logs <pod-name> --previous
Monitoring can help identify:
  • Frequent restarts
  • Application errors
  • Memory pressure
  • Probe failures

⭐⭐⭐⭐⭐ 31. Alerting

Monitoring tells us what is happening. Alerting notifies engineers when defined conditions require attention.
Examples: 
High CPU
High memory
Pod repeatedly restarting
Node unavailable
High HTTP 5xx rate
High application latency
Low disk space

⭐⭐⭐⭐ 32. Metrics Server vs Prometheus

Metrics Server Prometheus
Provides basic resource metrics. Full-featured monitoring and time-series database.
Used by commands such as kubectl top. Used for extensive metrics collection, querying and alerting.
Commonly supports resource-based HPA. Can provide richer/custom metrics depending on setup.
Do not treat Metrics Server and Prometheus as interchangeable products. They solve overlapping but different monitoring needs.

🔥 ⭐⭐⭐⭐⭐ 34. Real-Time Scenario — Deployment fails after Helm upgrade

Suppose: 
helm upgrade myapp ./mychart
completes but the application is unhealthy. Check: 
helm history myapp

helm status myapp

kubectl get pods

kubectl describe pod <pod-name>

kubectl logs <pod-name>
If the previous release was stable: 
helm rollback myapp <revision>
Then investigate the failed chart/configuration before trying the upgrade again.

🔥 ⭐⭐⭐⭐⭐ 35. Real-Time Scenario — Ingress returns 404

Check: 
kubectl get ingress
kubectl describe ingress <ingress-name>

kubectl get ingressclass

kubectl get svc
kubectl get endpoints
Verify:
  • Hostname is correct.
  • Path is correct.
  • IngressClass is correct.
  • Service exists.
  • Service port matches.
  • Service has healthy endpoints.
  • Ingress Controller is running.

🔥 ⭐⭐⭐⭐⭐ 36. Real-Time Scenario — High CPU Alert

Prometheus detects high CPU usage. Grafana displays the affected Pods. Engineer checks: 
kubectl top pods
kubectl top nodes
kubectl describe pod <pod-name>
Then determine whether the cause is:
  • Traffic increase
  • Bad application behavior
  • Insufficient resource requests/limits
  • Missing autoscaling
If appropriate, HPA can increase replicas.

🎯 If Interviewer Says: "Explain Ingress, Helm and Monitoring"

"In Kubernetes, I use Ingress to expose HTTP and HTTPS applications through routing rules based on hostnames and paths. An Ingress Controller implements those rules and forwards traffic to Services. For application deployment and packaging, I use Helm. A Helm Chart contains templates and configurable values. Helm allows me to install, upgrade, inspect and rollback application releases consistently across environments. For monitoring, Prometheus collects time-series metrics from the cluster and applications, while Grafana provides dashboards and visualization. I monitor CPU, memory, Pod restarts, node health, request rate, errors and latency. In a production setup, these components work together: Ingress handles external traffic, Helm manages application deployments, and Prometheus with Grafana provides observability."
