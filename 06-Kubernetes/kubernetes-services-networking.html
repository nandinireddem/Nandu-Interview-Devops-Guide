Kubernetes Services & Networking

DevOps interview-focused revision covering Services, ClusterIP, NodePort, LoadBalancer, DNS, Service Discovery, Endpoints, Ingress, NetworkPolicy and real-time troubleshooting.

⭐⭐⭐⭐⭐ What You Must Know

⭐⭐⭐⭐⭐ 1. What is Kubernetes Networking?

Kubernetes networking provides communication between Pods, Services and external clients inside or outside the cluster. The main goal is to allow applications running in different Pods and services to communicate reliably.

Four important networking requirements

  • Pod-to-Pod communication
  • Pod-to-Service communication
  • Service-to-Service communication
  • External-to-Service communication
Real-time example: Suppose an application has:

Frontend Pod → Backend Pod → MySQL Pod

The frontend should not depend on the backend Pod's changing IP. Instead, it communicates with a Kubernetes Service that provides a stable endpoint.

⭐⭐⭐⭐⭐ 2. How does Pod-to-Pod communication work?

Every Pod normally receives its own IP address. Kubernetes networking is designed so that Pods can communicate with each other directly without requiring NAT between Pods.
Pod A
10.244.1.5
↓
Kubernetes Network
↓
Pod B
10.244.2.7

Important interview point

Interview answer: "Each Kubernetes Pod gets an IP address. Pods can communicate with other Pods across nodes through the cluster networking implementation, usually provided by a CNI plugin."

⭐⭐⭐⭐⭐ 3. Why do we need a Kubernetes Service?

Pod IP addresses are not stable. Pods can be deleted, recreated, rescheduled or scaled, causing their IP addresses to change. A Service provides a stable virtual IP and DNS name for accessing a group of Pods.
Pod → Pod → Pod

↓ Labels
Service

Stable IP + DNS
Real-time example: Suppose the backend has 3 Pods: backend-1 → 10.244.1.10 backend-2 → 10.244.2.12 backend-3 → 10.244.3.15 If backend-2 dies, Kubernetes creates another Pod with a different IP. The frontend should not track these changing IPs. Instead: backend-service provides a stable endpoint.

⭐⭐⭐⭐⭐ 4. What is a Kubernetes Service?

A Kubernetes Service is an abstraction that exposes a group of Pods through a stable network endpoint. The Service selects Pods using labels.

Example

apiVersion: v1
kind: Service
metadata:
  name: backend-service

spec:
  selector:
    app: backend

  ports:
    - port: 80
      targetPort: 8080

  type: ClusterIP

Important fields

Field Meaning
selector Selects Pods using labels.
port Port exposed by the Service.
targetPort Port where the application is listening inside the Pod.
type Determines how the Service is exposed.

⭐⭐⭐⭐⭐ 5. Kubernetes Service Types

Type Purpose
ClusterIP Internal cluster communication. Default Service type.
NodePort Exposes the Service through a port on each node.
LoadBalancer Exposes the Service externally using a cloud load balancer.
ExternalName Maps a Service name to an external DNS name.

⭐⭐⭐⭐⭐ 6. What is ClusterIP?

ClusterIP is the default Kubernetes Service type. It exposes the application internally inside the cluster and is normally not directly reachable from the public internet. 
apiVersion: v1
kind: Service
metadata:
  name: backend-service

spec:
  type: ClusterIP

  selector:
    app: backend

  ports:
    - port: 80
      targetPort: 8080
Real-time use: Frontend and backend are both running inside Kubernetes. Frontend: frontend-service communicates with: backend-service:80 No public IP is required for the backend.

⭐⭐⭐⭐⭐ 7. What is NodePort?

NodePort exposes a Service on a static port on each Kubernetes node. External traffic can reach: NodeIP:NodePort which is then forwarded to the Service and its backend Pods. 
apiVersion: v1
kind: Service
metadata:
  name: web-service

spec:
  type: NodePort

  selector:
    app: web

  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30080
User
↓
Node IP : 30080
↓
NodePort Service
↓
Pod : 8080
NodePort is useful for development, testing and some specific architectures, but production cloud environments commonly use LoadBalancer or Ingress for external access.

⭐⭐⭐⭐⭐ 8. What is LoadBalancer?

LoadBalancer exposes a Kubernetes Service externally using a cloud provider's load balancing capability. In cloud environments such as AWS, Azure or GCP, the cloud integration can provision the corresponding load balancer. 
apiVersion: v1
kind: Service
metadata:
  name: web-service

spec:
  type: LoadBalancer

  selector:
    app: web

  ports:
    - port: 80
      targetPort: 8080
Internet
↓
Cloud Load Balancer
↓
Kubernetes Service
↓
Pods

⭐⭐⭐⭐⭐ 10. What is targetPort vs port?

port is the port exposed by the Service. targetPort is the port on which the application inside the Pod is listening. 
ports:
  - port: 80
    targetPort: 8080
User connects to: backend-service:80 Kubernetes forwards the traffic to: Pod:8080

⭐⭐⭐⭐⭐ 11. How does Service select Pods?

A Service uses label selectors to identify the Pods that should receive traffic.

Pod

apiVersion: v1
kind: Pod

metadata:
  name: backend
  labels:
    app: backend

Service

spec:
  selector:
    app: backend

Because the labels match, the Service sends traffic to the Pod.

If the Service selector does not match the Pod labels, the Service may have no backend endpoints.

⭐⭐⭐⭐⭐ 12. What are Endpoints / EndpointSlices?

Kubernetes maintains the network destinations associated with a Service. Modern Kubernetes primarily uses EndpointSlices to represent these backend endpoints. They help Kubernetes track which Pod IPs are currently available behind a Service. 
kubectl get endpoints

kubectl get endpointslices

kubectl describe service backend-service
Troubleshooting: Service exists, but application is unreachable. First check: kubectl get endpoints backend-service If no backend endpoints are present, check the Service selector and Pod labels.

⭐⭐⭐⭐⭐ 13. What is Kubernetes DNS?

Kubernetes provides DNS-based service discovery. Services normally receive DNS records, allowing applications to communicate using Service names instead of hard-coded IP addresses.
backend-service
↓
Kubernetes DNS
↓
Service ClusterIP
↓
Backend Pods

Example

curl http://backend-service:80

A Pod in the same namespace can normally resolve the Service using its Service name.

⭐⭐⭐⭐⭐ 14. How do Pods communicate across namespaces?

A Service can be addressed using its DNS name. For example: backend-service.dev.svc.cluster.local
DNS Form Example
Service name backend-service
Service + namespace backend-service.dev
Full DNS backend-service.dev.svc.cluster.local
Frontend is in namespace: frontend Backend is in: backend Frontend can communicate with: backend-service.backend.svc.cluster.local

⭐⭐⭐⭐⭐ 15. What is kube-proxy?

kube-proxy is a node-level Kubernetes component responsible for implementing Service networking rules so traffic destined for Services can be directed toward the appropriate backend Pods.

Depending on the cluster configuration, these rules may be implemented using mechanisms such as iptables or IPVS.

Interview answer: "kube-proxy runs on nodes and helps implement Kubernetes Service networking by maintaining the rules required to forward Service traffic to backend Pods."

⭐⭐⭐⭐⭐ 16. What is Ingress?

Ingress is a Kubernetes API resource used to define HTTP and HTTPS routing rules for external traffic entering the cluster. It commonly provides host-based or path-based routing. An Ingress requires an Ingress Controller to actually implement the routing.
Internet
↓
Load Balancer
↓
Ingress Controller
↓
Ingress Rules
↓
Services
↓
Pods

⭐⭐⭐⭐⭐ 17. Ingress Example

apiVersion: networking.k8s.io/v1
kind: Ingress

metadata:
  name: app-ingress

spec:

  rules:

  - host: app.example.com

    http:

      paths:

      - path: /api
        pathType: Prefix

        backend:

          service:
            name: backend-service
            port:
              number: 80

      - path: /
        pathType: Prefix

        backend:

          service:
            name: frontend-service
            port:
              number: 80
Real-time architecture: app.example.com/ → frontend-service

app.example.com/api → backend-service

⭐⭐⭐⭐⭐ 18. Ingress vs LoadBalancer

Ingress LoadBalancer Service
HTTP/HTTPS routing Exposes a Service externally
Can route multiple applications Normally exposes one Service
Supports host/path rules Does not provide the same application-level routing model
Requires Ingress Controller Implemented through Service/cloud integration
Interview answer: "If I have multiple web applications and want centralized HTTP/HTTPS routing using host or path rules, I would commonly use Ingress with an appropriate Ingress Controller."

⭐⭐⭐⭐⭐ 19. What is a CNI plugin?

CNI stands for Container Network Interface. A CNI plugin provides the networking implementation used by the Kubernetes cluster for Pod networking.

Examples include implementations such as Calico, Cilium and cloud-specific networking solutions.

Important: Do not say Kubernetes itself provides the complete Pod networking implementation. The networking behavior is provided through the cluster's networking/CNI implementation.

⭐⭐⭐⭐⭐ 20. What is NetworkPolicy?

NetworkPolicy controls which network traffic is allowed to or from selected Pods. It can be used to implement network-level access restrictions such as allowing frontend Pods to access backend Pods while preventing other Pods from doing so.
Without proper restrictions: Frontend → Backend Test Pod → Backend Unknown Pod → Backend

With NetworkPolicy: Frontend → Backend ✅ Test Pod → Backend ❌ Unknown Pod → Backend ❌

⭐⭐⭐⭐⭐ 21. NetworkPolicy Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy

metadata:
  name: backend-policy

spec:

  podSelector:
    matchLabels:
      app: backend

  policyTypes:
  - Ingress

  ingress:

  - from:

    - podSelector:
        matchLabels:
          app: frontend

    ports:

    - protocol: TCP
      port: 8080
This policy selects backend Pods and allows ingress traffic on port 8080 only from Pods labeled app: frontend, assuming the cluster's networking implementation enforces the policy.

⭐⭐⭐⭐⭐ 22. What is Service Discovery?

Service discovery is the mechanism by which applications find and communicate with Services without manually knowing changing Pod IPs. Kubernetes commonly provides service discovery through DNS.

⭐⭐⭐⭐ 23. What is Headless Service?

A headless Service is created by setting: clusterIP: None Instead of providing a normal virtual ClusterIP, DNS can return the individual Pod addresses associated with the Service. 
apiVersion: v1
kind: Service

metadata:
  name: database

spec:
  clusterIP: None

  selector:
    app: database

  ports:
  - port: 3306
Headless Services are commonly useful for stateful applications where clients need to discover individual Pods, such as certain database or distributed-system architectures.

⭐⭐⭐⭐ 24. What is ExternalName?

ExternalName maps a Kubernetes Service name to an external DNS name. It does not create a normal ClusterIP. 
apiVersion: v1
kind: Service

metadata:
  name: external-db

spec:
  type: ExternalName
  externalName: database.example.com

⭐⭐⭐⭐⭐ 25. What happens when a Pod dies?

If the Pod is managed by a controller such as a Deployment, Kubernetes can create a replacement Pod. The replacement may receive a different IP. The Service continues to provide a stable endpoint and updates its backend endpoint information accordingly.

⭐⭐⭐⭐⭐ 26. Real-Time Scenario: Service has no traffic

Problem

Service exists, but requests are failing.

Step 1 — Check Service

kubectl get svc

Step 2 — Check Endpoints

kubectl get endpoints
kubectl get endpointslices

Step 3 — Check Pods

kubectl get pods --show-labels

Step 4 — Compare selector and labels

kubectl describe svc backend-service
Most common issue: Service: selector: app=backend Pod: app=backend-api Labels do not match → Service has no matching backend Pods.

⭐⭐⭐⭐⭐ 27. Real-Time Scenario: Pod cannot reach another Service

Troubleshooting flow

kubectl get svc

kubectl get endpoints

kubectl get pods

kubectl describe svc backend-service

kubectl describe pod frontend-pod

Then test DNS and connectivity from inside a temporary/debug Pod. 

kubectl exec -it frontend-pod -- sh

# Inside container
nslookup backend-service

# Or
curl http://backend-service:80
Interview approach: "I first verify that the Service exists, then verify that it has healthy endpoints, check DNS resolution, confirm the target port, and finally investigate NetworkPolicy or application-level issues."

⭐⭐⭐⭐⭐ 28. Real-Time Scenario: DNS not resolving

If a Pod cannot resolve a Service name, I would verify the Service, namespace, DNS configuration and DNS components. 
kubectl get svc

kubectl get pods -n kube-system

kubectl get svc -n kube-system
Example: Frontend is in namespace frontend. Backend Service is in namespace backend. Using: backend-service may not resolve to the intended Service. Use: backend-service.backend.svc.cluster.local

🎯 If Interviewer Says: "Explain Kubernetes Networking"

"Kubernetes networking allows Pods, Services and external clients to communicate with each other. Each Pod gets an IP address, but Pod IPs are not stable because Pods can be recreated or rescheduled. Therefore, Kubernetes Services provide a stable virtual endpoint and use label selectors to route traffic to the appropriate Pods. ClusterIP is mainly used for internal communication, NodePort exposes a Service through a port on each node, and LoadBalancer provides external exposure through cloud load balancing. For HTTP and HTTPS routing, we can use Ingress together with an Ingress Controller. Kubernetes also provides DNS-based service discovery, so applications can communicate using Service names instead of hard-coded IP addresses. For security, NetworkPolicies can restrict which Pods are allowed to communicate with each other. In a production troubleshooting scenario, I would check the Pod status, Service configuration, labels, endpoints, DNS resolution, ports, Ingress or LoadBalancer configuration and NetworkPolicies step by step."
