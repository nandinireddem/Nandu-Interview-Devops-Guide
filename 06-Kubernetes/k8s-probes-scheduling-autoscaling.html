Kubernetes Probes, Scheduling & Autoscaling

Interview-focused guide covering Liveness, Readiness and Startup Probes, resource requests and limits, QoS, scheduling, taints, tolerations, affinity, HPA, VPA, Cluster Autoscaler and real-time production scenarios.

⭐⭐⭐⭐⭐ Big Picture

Three important areas control how Kubernetes keeps applications healthy and places workloads efficiently:

Probes
"Is my application healthy and ready?"

↓ Scheduling
"Where should this Pod run?"

↓ Autoscaling
"How many Pods or nodes do I need?"
Real-time example: A production API suddenly receives heavy traffic. Readiness probes prevent unhealthy Pods from receiving traffic. The scheduler places Pods on suitable nodes. HPA increases the number of application replicas when the workload requires more capacity. If the cluster needs more nodes, Cluster Autoscaler can adjust node capacity when supported/configured.

⭐⭐⭐⭐⭐ 1. What are Kubernetes Probes?

Kubernetes probes are health checks used by the kubelet to determine the state of a containerized application. The three important probes are:

1. Liveness Probe → Is the application still alive?
2. Readiness Probe → Can the application receive traffic?
3. Startup Probe → Has the slow-starting application finished starting?
Application
↓
Startup → "Has startup completed?"
↓ Liveness → "Is it still alive?"
↓ Readiness → "Can it receive traffic?"

⭐⭐⭐⭐⭐ 2. Liveness Probe

A liveness probe determines whether a container is still functioning. If the liveness probe repeatedly fails, Kubernetes may restart the container according to the Pod's restart policy and probe behavior.

HTTP example

livenessProbe:
  httpGet:
    path: /health
    port: 8080

  initialDelaySeconds: 10
  periodSeconds: 10
  timeoutSeconds: 2
  failureThreshold: 3
Real-time: A Java application gets stuck internally and stops responding to health requests. The liveness probe detects the failure and Kubernetes can restart the affected container.

⭐⭐⭐⭐⭐ 3. Readiness Probe

A readiness probe determines whether a container is ready to serve traffic. When readiness fails, Kubernetes removes the Pod from the endpoints of Services that select it, so the Pod should not receive normal Service traffic.

Example

readinessProbe:
  httpGet:
    path: /ready
    port: 8080

  initialDelaySeconds: 5
  periodSeconds: 5
  timeoutSeconds: 2
  failureThreshold: 3
Real-time: A new application Pod starts successfully but is still loading configuration and establishing database connections. The container is alive, but not ready. Readiness probe remains failed, so the Pod does not receive application traffic until it becomes ready.

⭐⭐⭐⭐⭐ 4. Startup Probe

A startup probe is designed for applications that take a long time to initialize. While the startup probe has not succeeded, Kubernetes does not run the liveness and readiness probes in the normal way. This prevents a slow-starting application from being incorrectly restarted by an aggressive liveness probe.

Example

startupProbe:
  httpGet:
    path: /startup
    port: 8080

  periodSeconds: 10
  failureThreshold: 30
A legacy Java application takes several minutes to load a large application context. Without a startup probe, liveness could fail during startup and continually restart the application. Startup probe solves this type of problem.

⭐⭐⭐⭐⭐ 5. Liveness vs Readiness vs Startup

Probe Main Question Failure Effect
Liveness Is the application alive? Container may be restarted.
Readiness Can it receive traffic? Pod is removed from Service traffic.
Startup Has startup completed? Protects slow-starting applications during initialization.
Interview-ready answer: "Liveness checks whether the application is still healthy enough to continue running. Readiness checks whether it is ready to serve traffic. Startup is useful for slow-starting applications and gives them enough time to initialize before normal liveness and readiness checks take effect."

⭐⭐⭐⭐⭐ 6. Probe Types

Type Usage
httpGet Sends an HTTP request to an endpoint.
tcpSocket Checks whether a TCP connection can be established.
exec Runs a command inside the container.
grpc Performs a gRPC health check where supported/configured.

TCP example

readinessProbe:
  tcpSocket:
    port: 8080
  periodSeconds: 10

Exec example

livenessProbe:
  exec:
    command:
    - cat
    - /tmp/healthy

  periodSeconds: 10

⭐⭐⭐⭐ 7. Probe Timing Parameters

Parameter Meaning
initialDelaySeconds Wait before starting the probe.
periodSeconds How frequently the probe runs.
timeoutSeconds How long to wait for a probe response.
failureThreshold Number of consecutive failures before failure is acted upon.
successThreshold Number of successful checks required for recovery in supported probe contexts.

⭐⭐⭐⭐⭐ 8. Bad Probe Configuration

A common production mistake is configuring an aggressive liveness probe that fails while the application is still initializing. This can cause:

Pod starts → liveness fails → container restarts → application starts again → liveness fails → restart loop.
Use a Startup Probe for slow initialization and configure liveness and readiness according to real application behavior rather than using arbitrary values.

⭐⭐⭐⭐⭐ 9. CPU and Memory Requests

A resource request tells Kubernetes how much CPU or memory a container needs for scheduling purposes. The scheduler uses resource requests when deciding whether a Pod can fit on a node.

Example

resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
If a Pod requests: cpu: 500m the scheduler looks for a node with enough allocatable CPU according to the Pod's requested resources.

⭐⭐⭐⭐⭐ 10. Resource Limits

A resource limit defines the maximum amount of a resource a container is allowed to consume, subject to Kubernetes behavior and the resource type. 
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"
Memory is especially important. If a container exceeds its memory limit and is terminated due to memory pressure, you may see an OOMKilled state. CPU overuse is generally throttled rather than causing the same kind of OOM termination.

⭐⭐⭐⭐⭐ 11. Requests vs Limits

Requests Limits
Used mainly for scheduling. Defines an upper resource boundary.
Influences whether Pod fits on a node. Controls resource consumption according to Kubernetes semantics.
Important for capacity planning. Important for workload protection.
Simple answer: "Requests tell Kubernetes how much resource the Pod needs for scheduling, while limits define the maximum resource boundary for the container."

⭐⭐⭐⭐⭐ 12. What is CPU millicore?

CPU can be represented in millicores. 
1000m = 1 CPU core
500m  = 0.5 CPU
250m  = 0.25 CPU
100m  = 0.1 CPU

⭐⭐⭐⭐⭐ 13. QoS Classes

Kubernetes assigns Pods a Quality of Service class based on their resource requests and limits.
QoS Concept
Guaranteed Every container has CPU and memory requests and limits set, with matching values for the relevant resources.
Burstable Pod does not meet Guaranteed criteria but has at least some resource requests/limits.
BestEffort No CPU or memory requests/limits are specified.

Check QoS

kubectl get pod <pod-name> -o jsonpath='{.status.qosClass}'

⭐⭐⭐⭐⭐ 14. What is Kubernetes Scheduling?

The Kubernetes scheduler selects an appropriate node for a newly created Pod that is not yet assigned to a node. It considers factors such as resource availability, constraints, affinity, taints and tolerations, topology and other scheduling rules.
Pod Created
↓
Scheduler
↓
Filter unsuitable nodes
↓
Score eligible nodes
↓
Select node
↓
Kubelet starts Pod

⭐⭐⭐⭐⭐ 15. What happens if a Pod is Pending?

A Pod may remain Pending when Kubernetes cannot find a suitable node for it. Common causes include:
  • Insufficient CPU.
  • Insufficient memory.
  • Taints without matching tolerations.
  • Node affinity rules.
  • NodeSelector mismatch.
  • Storage topology constraints.
  • Resource requests are too large.

First troubleshooting command

kubectl describe pod <pod-name>

Check the Events section for scheduler messages explaining why nodes were rejected.

⭐⭐⭐⭐⭐ 16. nodeSelector

nodeSelector is a simple way to constrain a Pod to nodes having specific labels.

Label a node

kubectl label nodes worker-1 workload=backend

Pod

spec:
  nodeSelector:
    workload: backend
Use case: A team has dedicated nodes for backend workloads. The nodes are labeled: workload=backend Pods using nodeSelector are scheduled only onto nodes with that label.

⭐⭐⭐⭐⭐ 17. Taints

A taint is placed on a node to repel Pods that do not have a matching toleration.

Example

kubectl taint nodes worker-1 dedicated=backend:NoSchedule

Now normal Pods without a matching toleration should not be scheduled onto that node.

⭐⭐⭐⭐⭐ 18. Tolerations

A toleration allows a Pod to tolerate a matching node taint. It does not automatically force the Pod onto that node. 
tolerations:
- key: "dedicated"
  operator: "Equal"
  value: "backend"
  effect: "NoSchedule"
Important: Taint = node says "keep Pods away." Toleration = Pod says "I am allowed to run here." Toleration alone does not mean "schedule me here."

⭐⭐⭐⭐⭐ 19. Taint Effects

Effect Meaning
NoSchedule New Pods without a matching toleration are not scheduled.
PreferNoSchedule Scheduler tries to avoid placing Pods there when possible.
NoExecute Can prevent scheduling and can evict existing Pods that do not tolerate the taint.

⭐⭐⭐⭐⭐ 20. Node Affinity

Node affinity provides more expressive rules for selecting nodes based on labels. It is more flexible than a simple nodeSelector.

Example

affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: workload
          operator: In
          values:
          - backend
Use node affinity when scheduling rules become more complex than a simple exact label match.

⭐⭐⭐⭐ 21. required vs preferred affinity

requiredDuringScheduling... preferredDuringScheduling...
Hard requirement. Soft preference.
Pod cannot be scheduled if requirement is not satisfied. Scheduler tries to satisfy it but can use another node.

⭐⭐⭐⭐⭐ 22. Pod Affinity and Anti-Affinity

Pod affinity can encourage Pods to run near other Pods. Pod anti-affinity can encourage Pods to run away from other Pods.
High availability example: Suppose an application has three replicas. You do not want all replicas on the same node because a node failure could take all replicas down. Pod anti-affinity can help spread replicas across nodes.

⭐⭐⭐⭐⭐ 23. Real-Time Scheduling Design

Production application:
  • Backend nodes labeled workload=backend.
  • Backend nodes tainted with dedicated=backend:NoSchedule.
  • Backend Pods have a matching toleration.
  • Node affinity ensures they prefer/require backend nodes.
  • Pod anti-affinity spreads replicas across nodes.
This creates controlled workload placement and better failure distribution.

⭐⭐⭐⭐⭐ 24. What is Kubernetes Autoscaling?

Autoscaling automatically adjusts resources or capacity according to workload requirements. The major autoscaling mechanisms are:

HPA → Changes number of Pod replicas.
VPA → Adjusts resource requests/limits recommendations or updates according to its configured mode.
Cluster Autoscaler → Adjusts node-group capacity when configured and supported.
Traffic increases
↓
HPA
↓
More Pods
↓
Insufficient node capacity
↓
Cluster Autoscaler
↓
More Nodes

⭐⭐⭐⭐⭐ 25. HPA — Horizontal Pod Autoscaler

HPA automatically adjusts the number of Pod replicas based on configured metrics such as CPU, memory or custom/external metrics.

Basic HPA

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler

metadata:
  name: api-hpa

spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: api

  minReplicas: 2
  maxReplicas: 10

  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

⭐⭐⭐⭐⭐ 26. How HPA works

Metrics
↓
Metrics API / metrics source
↓
HPA Controller
↓
Compare current vs target
↓
Change Deployment replica count
↓
Scheduler
↓
New Pods
If average CPU utilization rises above the configured target, HPA can increase replicas, subject to its configured behavior and limits. When load decreases, HPA can scale down after stabilization and cooldown behavior as configured.

⭐⭐⭐⭐⭐ 27. Why are resource requests important for HPA?

For CPU utilization-based HPA, utilization is calculated relative to the container's requested CPU. Therefore, correctly configured resource requests are important for meaningful utilization-based scaling.
If requests are missing or badly sized, CPU utilization-based HPA behavior may not work as expected.

⭐⭐⭐⭐⭐ 28. VPA — Vertical Pod Autoscaler

VPA adjusts or recommends CPU and memory resource requests for Pods. It is focused on the resources assigned to individual Pods rather than changing the number of replicas.
HPA VPA
Changes number of Pods. Changes/recommends Pod resource sizing.
Horizontal scaling. Vertical scaling.
Useful when workload replica count should respond to demand. Useful when individual Pod resource sizing needs optimization.
HPA and VPA can interact in problematic ways if both attempt to use the same resource metric for scaling decisions. Design their configuration carefully.

⭐⭐⭐⭐ 29. Cluster Autoscaler

Cluster Autoscaler adjusts the number of nodes in a cluster or node group based on unschedulable Pods and underutilized capacity, according to its configuration and cloud integration.
Example: HPA increases replicas from 4 to 12. The current nodes do not have enough capacity for the new Pods. Some Pods remain Pending. Cluster Autoscaler can increase node-group capacity so the scheduler can place those Pods.

⭐⭐⭐⭐⭐ 30. HPA vs VPA vs Cluster Autoscaler

Tool What changes?
HPA Number of Pods
VPA Pod CPU/Memory sizing
Cluster Autoscaler Number of Nodes
Easy memory trick: HPA = More/Fewer Pods
VPA = Bigger/Smaller Pods
Cluster Autoscaler = More/Fewer Nodes

⭐⭐⭐⭐⭐ 31. HPA needs Metrics

Resource-based HPA depends on metrics being available through the cluster's metrics infrastructure. A common Kubernetes setup uses Metrics Server for basic resource metrics.

Check

kubectl top nodes
kubectl top pods
If kubectl top does not work, investigate the metrics pipeline before assuming HPA itself is broken.

⭐⭐⭐⭐⭐ 32. HPA not scaling — Troubleshooting

Possible reasons:
  • Metrics are unavailable.
  • Target workload is incorrect.
  • CPU requests are missing or poorly configured.
  • HPA min/max replicas prevent expected scaling.
  • Metric target is not being reached.
  • Custom metrics configuration is broken.

Commands

kubectl get hpa
kubectl describe hpa <hpa-name>

kubectl top pods
kubectl top nodes

kubectl get deployment <deployment-name>

⭐⭐⭐⭐⭐ 33. Real-Time HPA Scenario

An e-commerce application normally runs with 3 replicas. During a flash sale, traffic increases dramatically. CPU usage increases. HPA detects the increased metric and scales: 
3 Pods
↓
5 Pods
↓
8 Pods
↓
10 Pods
If the existing cluster does not have enough capacity, some new Pods may remain Pending. Cluster Autoscaler can then add nodes when its configuration and cloud provider integration allow it.

⭐⭐⭐⭐⭐ 34. Why Pods can remain Pending even after HPA scales?

HPA only changes the desired number of replicas. It does not automatically create node capacity. If the cluster has no available resources, newly requested Pods can remain Pending until capacity becomes available.
HPA → More Pods
↓
Scheduler → Needs Node Capacity
↓
No Capacity → Pods Pending
↓
Cluster Autoscaler → More Nodes
↓
Scheduler → Pods Placed

🔥 ⭐⭐⭐⭐⭐ 35. Production Scenario — Application becomes unhealthy

Situation: Application is running but is no longer responding correctly. Solution: Use liveness to detect a stuck application and allow Kubernetes to restart the affected container. Readiness should separately prevent unhealthy instances from receiving traffic.
Never use readiness as a replacement for liveness. They solve different problems.

🔥 ⭐⭐⭐⭐⭐ 36. Production Scenario — Slow startup

A Java application requires 2 minutes to start. A liveness probe begins too early and kills the application before startup completes. Fix: Use a startup probe or appropriately design initial startup timing, then allow liveness/readiness to perform their normal functions after startup.

🔥 ⭐⭐⭐⭐⭐ 37. Production Scenario — Pod won't schedule

Pod is Pending. First command: 
kubectl describe pod <pod-name>
Check Events. If the message says insufficient CPU/memory, inspect: 
kubectl describe nodes
If it mentions taints, inspect: 
kubectl describe node <node-name>
Then check Pod tolerations and scheduling rules.

🔥 ⭐⭐⭐⭐⭐ 38. Production Scenario — HPA not scaling

Check in this order: 
kubectl get hpa
kubectl describe hpa <hpa-name>

kubectl top pods
kubectl top nodes

kubectl get deployment <deployment-name>
Then verify resource requests, metric availability, target values and HPA min/max replica settings.

🎯 If Interviewer Says: "Explain Probes, Scheduling and Autoscaling"

"Kubernetes probes help maintain application availability. I use liveness probes to detect containers that are unhealthy and need restarting, readiness probes to control whether a Pod should receive traffic, and startup probes for applications that take a long time to initialize. For scheduling, Kubernetes uses the scheduler to select suitable nodes based on resources and constraints. I can use nodeSelector, node affinity, taints and tolerations, and pod anti-affinity to control workload placement. For resource management, I define CPU and memory requests for scheduling and limits to establish resource boundaries. For autoscaling, HPA adjusts the number of Pods based on metrics, VPA adjusts or recommends Pod resource sizing, and Cluster Autoscaler adjusts node capacity when configured. In a production environment, I combine these features carefully: probes protect application health, scheduling controls placement, and autoscaling handles changing workload demand."
