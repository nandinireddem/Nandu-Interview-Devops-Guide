Kubernetes Storage

PV, PVC, StorageClass, dynamic provisioning, access modes, StatefulSets, AWS storage examples, troubleshooting and real-time DevOps interview scenarios.

⭐⭐⭐⭐⭐ Kubernetes Storage Architecture

Containers are generally treated as ephemeral. If a container is deleted and recreated, data stored only inside the container's writable layer may disappear.

Kubernetes provides persistent storage abstractions so application data can survive Pod or container recreation.

Application Pod
↓
PersistentVolumeClaim (PVC)
↓
PersistentVolume (PV)
↓
Storage Backend

AWS EBS / EFS / Cloud Disk / SAN / NFS / etc.
Real-time example: A PostgreSQL database is running in Kubernetes. If the Pod crashes and Kubernetes recreates it, the database data must still exist. The database uses a PVC backed by persistent storage rather than depending only on the container filesystem.

⭐⭐⭐⭐⭐ 1. Why do we need persistent storage?

Container filesystems are normally tied to the lifecycle of the container. Kubernetes workloads can be restarted, recreated or rescheduled onto another node. Persistent storage separates important application data from the temporary container lifecycle.
Pod Created
↓
Application writes data
↓
Pod Deleted
↓
New Pod
↓
Persistent Volume still contains data

⭐⭐⭐⭐⭐ 2. What is a PersistentVolume (PV)?

A PersistentVolume is a Kubernetes storage resource representing storage available to workloads. A PV can be backed by infrastructure such as cloud block storage, file storage, NFS or another supported storage implementation.

Basic PV example

apiVersion: v1
kind: PersistentVolume
metadata:
  name: app-pv
spec:
  capacity:
    storage: 10Gi

  accessModes:
    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  hostPath:
    path: /data/app
hostPath is mainly useful for local/testing scenarios. It is generally not the preferred production storage solution for multi-node clusters.

⭐⭐⭐⭐⭐ 3. What is a PersistentVolumeClaim (PVC)?

A PersistentVolumeClaim is a request for storage made by a workload. The application normally asks for storage through a PVC instead of directly managing the underlying storage infrastructure.

PVC example

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc
spec:
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 5Gi
Developer / Application
↓
PVC
"I need 5Gi storage"
↓
PV / Storage Provisioner
↓
Actual Storage

⭐⭐⭐⭐⭐ 4. PV vs PVC

PV PVC
Represents available storage Requests storage
Cluster resource Namespace-scoped resource
Usually managed/provisioned by infrastructure or platform teams Usually requested by application teams
Describes capacity and storage properties Describes requested capacity and access requirements
Interview answer:

"PV is the storage resource available to the cluster, while PVC is the application's request for that storage. Pods normally consume the PVC rather than directly referencing the underlying storage."

⭐⭐⭐⭐⭐ 5. What is StorageClass?

A StorageClass defines a class of storage and allows Kubernetes to dynamically provision persistent volumes through a storage provisioner.
PVC
↓
StorageClass
↓
Provisioner
↓
Cloud / Storage Backend
↓
PV
↓
Pod

Example

apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-storage

provisioner: example.com/provisioner

reclaimPolicy: Delete

volumeBindingMode: WaitForFirstConsumer

The exact provisioner depends on the cluster and storage platform.

⭐⭐⭐⭐⭐ 6. Static vs Dynamic Provisioning

Static Provisioning Dynamic Provisioning
PV is created beforehand Storage is provisioned when requested
More manual management More automated
Useful for specific pre-created storage Common in cloud environments

Dynamic flow

PVC
  ↓
StorageClass
  ↓
Provisioner
  ↓
Cloud Storage
  ↓
PV automatically created
  ↓
PVC Bound
Dynamic provisioning is one of the most important concepts to understand for managed Kubernetes platforms such as Amazon EKS.

⭐⭐⭐⭐⭐ 7. Access Modes

Mode Meaning
ReadWriteOnce (RWO) Volume can be mounted read-write by a single node at a time.
ReadOnlyMany (ROX) Volume can be mounted read-only by many nodes.
ReadWriteMany (RWX) Volume can be mounted read-write by many nodes.
Do not assume every storage backend supports every access mode. Always verify what the underlying storage implementation supports.

⭐⭐⭐⭐⭐ 8. RWO vs RWX Real-Time Example

Scenario 1 — Database: A PostgreSQL database usually uses block storage such as an EBS-like volume and commonly needs single-node read/write attachment. RWO is a common access pattern.

Scenario 2 — Shared application files: Multiple application Pods running on different nodes need to read and write the same shared filesystem. A storage system supporting RWX, such as an appropriate network filesystem, may be required.

⭐⭐⭐⭐⭐ 9. Using PVC in a Pod

PVC

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc
spec:
  accessModes:
    - ReadWriteOnce

  resources:
    requests:
      storage: 5Gi

Pod

apiVersion: v1
kind: Pod
metadata:
  name: storage-demo
spec:
  containers:
  - name: app
    image: nginx

    volumeMounts:
    - name: app-storage
      mountPath: /data

  volumes:
  - name: app-storage
    persistentVolumeClaim:
      claimName: app-pvc

The application writes data under /data, which is backed by the PVC.

⭐⭐⭐⭐⭐ 11. PVC Pending

Problem: A PVC remains in: 
Pending
Possible reasons include:
  • No suitable PV exists for static provisioning.
  • Incorrect StorageClass.
  • No dynamic provisioner is available.
  • Requested access mode is unsupported.
  • Requested capacity cannot be satisfied.
  • Storage backend/provisioner has an error.

Troubleshooting

kubectl get pvc
kubectl describe pvc app-pvc

kubectl get pv
kubectl get storageclass

kubectl describe storageclass <storage-class>

⭐⭐⭐⭐⭐ 12. Reclaim Policy

The PV reclaim policy determines what Kubernetes should do with the underlying volume after the PVC is deleted.
Policy Meaning
Retain Keep the PV/storage so data can be preserved and handled manually.
Delete Delete the volume according to the provisioner's behavior.
Recycle Legacy behavior and generally not used for modern Kubernetes storage.
For important production data, understand the reclaim policy before deleting PVCs. A Delete policy can result in deletion of the underlying dynamically provisioned storage.

⭐⭐⭐⭐⭐ 13. Retain vs Delete

Production database: If accidental PVC deletion must not immediately destroy the data, a Retain strategy may be appropriate depending on the organization's backup and recovery design.

Temporary application environment: For disposable environments, Delete may be appropriate so that temporary storage is automatically cleaned up.

⭐⭐⭐⭐⭐ 14. What is volumeBindingMode?

volumeBindingMode controls when volume binding and dynamic provisioning occur. Two important modes are:
Immediate WaitForFirstConsumer
Provision/bind as soon as PVC is created. Delay provisioning/binding until a Pod using the PVC is created.
WaitForFirstConsumer can help the scheduler choose a storage location compatible with the Pod's placement and storage topology.

⭐⭐⭐⭐⭐ 15. emptyDir vs PVC

emptyDir PVC
Temporary Pod storage Persistent storage abstraction
Deleted when Pod is removed from the node Can survive Pod recreation according to storage lifecycle
Useful for temporary files/cache Useful for databases and persistent application data

emptyDir example

volumes:
- name: temp-storage
  emptyDir: {}

containers:
- name: app
  image: nginx
  volumeMounts:
  - name: temp-storage
    mountPath: /tmp/app

⭐⭐⭐⭐⭐ 16. StatefulSet + Persistent Storage

StatefulSets are commonly used for stateful applications that need stable identities and persistent storage. A StatefulSet can use volumeClaimTemplates to create a PVC for each Pod.

Example

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: database
spec:
  serviceName: database
  replicas: 2

  selector:
    matchLabels:
      app: database

  template:
    metadata:
      labels:
        app: database

    spec:
      containers:
      - name: database
        image: postgres:16

        volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data

  volumeClaimTemplates:
  - metadata:
      name: data

    spec:
      accessModes:
      - ReadWriteOnce

      resources:
        requests:
          storage: 10Gi
StatefulSet
↓
database-0 → PVC data-database-0
database-1 → PVC data-database-1

⭐⭐⭐⭐⭐ 17. Why StatefulSet instead of Deployment for databases?

A StatefulSet provides stable Pod identities, stable network identity when configured with the appropriate Service, and supports per-Pod persistent storage patterns. A Deployment is designed primarily for interchangeable replicas.
For a database cluster, each member may need its own persistent data volume. A StatefulSet can provide:

database-0 → its own PVC
database-1 → its own PVC
database-2 → its own PVC
A StatefulSet alone does not make a database highly available. The database itself must support replication, failover and recovery, and the storage/backup architecture must be designed appropriately.

⭐⭐⭐⭐⭐ 18. AWS EBS vs EFS in Kubernetes

AWS EBS AWS EFS
Block storage Managed network file system
Commonly associated with RWO workloads Commonly suitable for shared filesystem access such as RWX patterns
Good for many database/block-storage workloads Useful when multiple Pods/nodes need shared file access
EKS example: A database Pod needs block storage → EBS-backed storage class. Multiple application Pods need shared files across nodes → EFS-backed storage class, assuming the appropriate CSI driver and access mode support.

⭐⭐⭐⭐⭐ 19. CSI Driver

CSI stands for Container Storage Interface. CSI provides a standard mechanism for Kubernetes to communicate with storage systems. Cloud platforms commonly provide CSI drivers for their storage services.
Kubernetes
↓
CSI Driver
↓
Cloud Storage

Example:
EKS → EBS CSI / EFS CSI
The CSI driver is an important part of modern Kubernetes storage, especially in managed clusters such as EKS.

⭐⭐⭐⭐⭐ 22. Default StorageClass

A cluster can have a default StorageClass. If a PVC does not specify storageClassName, Kubernetes can use the default StorageClass for dynamic provisioning when the cluster is configured accordingly.

Check StorageClasses

kubectl get storageclass

kubectl get sc

Inspect

kubectl describe storageclass <name>
When troubleshooting a PVC stuck in Pending, checking whether the cluster has an appropriate default StorageClass is one of the first things to verify.

⭐⭐⭐⭐⭐ 23. PVC is Bound but Pod cannot start

Problem: PVC shows: 
Bound
But the Pod remains Pending or fails during volume attachment/mount. Possible reasons include:
  • Node does not satisfy storage topology.
  • CSI driver issue.
  • Volume attachment failure.
  • Mount permission problem.
  • Underlying storage unavailable.
  • Access mode or attachment limitation.

Commands

kubectl describe pod <pod-name>

⭐⭐⭐⭐⭐ 24. Real-Time Scenario: Pod deleted

A database Pod is deleted accidentally. Kubernetes creates a replacement Pod. If the database uses a correctly configured persistent volume, the new Pod can mount the existing storage and continue using the persisted data.
Old Pod
↓
Deleted
↓
PVC remains
↓
New Pod
↓
Same Persistent Storage
↓
Data Available

⭐⭐⭐⭐⭐ 25. Real-Time Scenario: Pod moves to another node

A node fails and Kubernetes schedules the workload onto another eligible node. Whether the persistent volume can be attached to the new node depends on the storage backend, access mode, topology and CSI implementation.
Do not simply say "the volume works on any node." Storage attachment and topology rules matter, especially with single-node-attached block storage.

⭐⭐⭐⭐⭐ 26. Database Production Storage Strategy

For a production database in Kubernetes, I would consider:

• Persistent storage through PVCs
• Appropriate StorageClass
• Correct access mode
• StatefulSet when appropriate
• Storage encryption
• Regular backups
• Snapshot strategy where supported
• Monitoring
• Tested restore procedures
• Reclaim policy
• Capacity planning
Persistent storage is not the same as backup. A persistent volume can still be lost because of infrastructure, operator error, corruption or deletion. Backups and tested restoration are essential for important data.

⭐⭐⭐⭐⭐ 27. Backup vs Persistent Storage

Persistent Storage Backup
Keeps application data available across Pod lifecycle changes. Provides a recoverable copy of data.
Supports normal application operation. Used for disaster recovery and accidental deletion.
Not automatically a backup. Should be stored according to recovery requirements.
If an interviewer asks "Does PVC provide backup?", the answer is: No. PVC provides persistent storage, not a complete backup and disaster-recovery solution.

⭐⭐⭐⭐ 28. Storage Security

  • Encrypt storage where supported.
  • Restrict access through RBAC.
  • Use appropriate filesystem permissions.
  • Protect sensitive data with application-level encryption where required.
  • Use secure StorageClasses and CSI drivers.
  • Monitor storage access and failures.
  • Use backups and tested recovery procedures.
  • Do not expose database storage unnecessarily.

🎯 If Interviewer Says: "Explain Kubernetes Storage"

"Kubernetes Pods are generally ephemeral, so for applications that need persistent data I use PersistentVolumes and PersistentVolumeClaims. A PersistentVolume represents available storage, while a PVC is the application's request for storage. For dynamic provisioning, I use a StorageClass. The PVC references the StorageClass, and the provisioner creates the appropriate persistent volume. Access modes such as ReadWriteOnce and ReadWriteMany determine how the storage can be mounted, depending on what the storage backend supports. For stateful applications such as databases, I can use StatefulSets with volumeClaimTemplates so each Pod can have its own persistent storage. In AWS EKS, I would commonly consider EBS for block-storage workloads and EFS for shared filesystem use cases, using the appropriate CSI drivers. Finally, I would configure reclaim policies carefully, monitor storage, encrypt sensitive data, and maintain backups because persistent storage itself is not a backup."
