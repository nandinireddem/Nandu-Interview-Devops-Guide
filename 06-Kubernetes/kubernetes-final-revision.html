⭐⭐⭐⭐⭐ 1. Kubernetes Architecture

Control Plane

API Server → Scheduler → Controller Manager → etcd

↓

Worker Nodes

kubelet → Container Runtime → Pods

kube-proxy / Networking
Component Purpose
API Server Entry point for Kubernetes API requests.
etcd Stores Kubernetes cluster state and configuration.
Scheduler Decides which node should run a newly scheduled Pod.
Controller Manager Runs controllers that continuously reconcile desired and actual state.
kubelet Runs on worker nodes and ensures assigned Pods are running.
Container Runtime Runs containers through the Kubernetes container runtime interface.
kube-proxy Provides node-level Service networking behavior.
Interview answer: "Kubernetes follows a control-plane and worker-node architecture. The API Server receives requests, etcd stores cluster state, the Scheduler assigns Pods to nodes and Controllers maintain the desired state. Worker nodes run Pods using kubelet and a container runtime."

⭐⭐⭐⭐⭐ 2. Desired State vs Actual State

Desired State
↓
Kubernetes Controllers
↓
Actual State
↓
Reconciliation
Kubernetes continuously compares the desired state defined by the user with the current state of the cluster and takes action to reduce the difference.
Example: Deployment requests: 
replicas: 3
If one Pod crashes, the Deployment/ReplicaSet mechanism works toward restoring the desired number of replicas.

⭐⭐⭐⭐⭐ 3. Pod

A Pod is the smallest deployable unit in Kubernetes. A Pod can contain one or more containers that share networking and can share storage volumes.
Pod
├── Container
├── Container
├── Shared Network
└── Shared Volumes
In production, applications are normally managed through higher-level workloads such as Deployments rather than manually creating Pods.

⭐⭐⭐⭐⭐ 4. Kubernetes Workloads

Workload Use Case
Deployment Stateless applications and rolling updates.
ReplicaSet Maintains desired number of matching Pods; usually managed by Deployment.
StatefulSet Stateful applications requiring stable identity and storage.
DaemonSet Runs a Pod on selected/all eligible nodes.
Job Runs a task until successful completion.
CronJob Runs Jobs according to a schedule.
Examples: Deployment → Web application StatefulSet → Database DaemonSet → Node monitoring agent Job → Database migration CronJob → Scheduled backup

⭐⭐⭐⭐⭐ 5. Deployment

A Deployment manages ReplicaSets and provides declarative updates for Pods, including rolling updates and rollback capabilities. 
kubectl get deployments

kubectl rollout status deployment myapp

kubectl rollout history deployment myapp

kubectl rollout undo deployment myapp
Production deployment: 
Version 1
↓
Rolling Update
↓
Version 2
↓
Health Checks
↓
Traffic continues
If Version 2 fails, rollback can restore the previous version.

⭐⭐⭐⭐⭐ 9. ConfigMap

ConfigMap stores non-sensitive configuration separately from the container image. 
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
Common uses:
  • Environment variables
  • Application settings
  • URLs
  • Feature flags
  • Configuration files

⭐⭐⭐⭐⭐ 10. Secret

Secret is designed for sensitive data such as passwords, tokens and credentials. 
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  username: admin
  password: example
Base64 encoding is NOT encryption. Production Secret management should include appropriate access control, encryption and rotation.

⭐⭐⭐⭐⭐ 11. Kubernetes Storage

Pod
↓
PVC
↓
PV
↓
Storage Backend
Object Meaning
PV Persistent storage resource available to the cluster.
PVC Request for persistent storage.

Application needs persistent data. Pod → PVC → dynamically provisioned PV → storage backend. If the Pod is recreated, the persistent data can remain available depending on the storage configuration.

⭐⭐⭐⭐⭐ 12. Health Probes

Probe Purpose
Liveness Checks whether the container should be restarted.
Readiness Checks whether the Pod should receive traffic.
Startup Helps handle slow-starting applications before normal probes take over.
Liveness Failure → Container Restart

Readiness Failure → Remove from Service Traffic

Startup Probe → Allow Slow Startup

⭐⭐⭐⭐⭐ 13. Requests and Limits

Request is the amount of CPU/memory Kubernetes uses when making scheduling decisions. Limit is the maximum resource amount enforced for the container according to the resource type. 
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"

  limits:
    cpu: "500m"
    memory: "512Mi"
If a Pod requests more resources than available on eligible nodes, the Scheduler may leave the Pod Pending. If a container exceeds its memory limit, it can be terminated with an OOMKilled status.

⭐⭐⭐⭐⭐ 14. Kubernetes Scheduling

Important concepts: Node Selector Node Affinity Pod Affinity Pod Anti-Affinity Taints Tolerations
The Scheduler evaluates whether a node satisfies the Pod's requirements and selects an appropriate node.
Example: A workload must run only on nodes labelled: 
workload=production
A nodeSelector or node affinity rule can be used to constrain placement.

⭐⭐⭐⭐⭐ 15. Autoscaling

Type Purpose
HPA Scales workload replicas based on metrics such as CPU/memory or configured custom metrics.
VPA Adjusts Pod resource requests/limits according to observed usage, depending on configuration.
Cluster Autoscaler Adjusts the number of cluster nodes based on scheduling/resource needs.
Traffic Increase
↓
HPA
↓
More Pods
↓
Cluster Capacity
↓
Cluster Autoscaler if needed

⭐⭐⭐⭐⭐ 16. RBAC

RBAC controls which identities can perform which actions on Kubernetes resources.
Object Purpose
Role Permissions within a namespace.
ClusterRole Cluster-scoped permissions or reusable permissions depending on binding.
RoleBinding Binds a Role or ClusterRole to subjects within a namespace.
ClusterRoleBinding Binds a ClusterRole at cluster scope. 
kubectl auth can-i get pods

kubectl auth can-i create deployments

kubectl get role
kubectl get rolebinding

⭐⭐⭐⭐⭐ 17. Kubernetes Security

  • Use least-privilege RBAC.
  • Protect Secrets.
  • Use NetworkPolicies where required.
  • Use trusted and scanned container images.
  • Run containers with appropriate security settings.
  • Avoid privileged containers unless required.
  • Keep Kubernetes and node components updated.
  • Restrict API access.
  • Use image scanning and admission controls where appropriate.
  • Monitor cluster activity.
DevSecOps example: Git push → CI scan → image build → vulnerability scan → registry → Kubernetes deployment → runtime monitoring.

⭐⭐⭐⭐ 18. Helm

Helm is a package manager for Kubernetes. It uses Charts to package Kubernetes resources and templates. 
helm create myapp

helm install myapp ./myapp

helm list

helm upgrade myapp ./myapp

helm rollback myapp 1

helm uninstall myapp
Instead of maintaining many almost-identical YAML files for Dev, QA and Production, Helm values can be used to provide environment specific configuration.

⭐⭐⭐⭐ 20. Namespace

Namespaces provide logical isolation within a Kubernetes cluster and are commonly used to separate teams, applications or environments. 
kubectl get namespaces

kubectl get pods -n dev

kubectl get svc -n production

kubectl create namespace dev
Example: 
dev
qa
production
The same application can exist in separate namespaces with environment-specific configuration.

⭐⭐⭐⭐⭐ 21. Labels and Selectors

Labels identify and organize Kubernetes objects. Selectors are used by resources such as Services and controllers to find matching objects. 
labels:
  app: frontend

selector:
  app: frontend
A very common troubleshooting issue is a mismatch between Service selectors and Pod labels.

🔥 ⭐⭐⭐⭐⭐ 23. Kubernetes Troubleshooting Cheat Sheet

Problem First Things to Check
Pending describe Pod → Events → resources → taints → affinity
CrashLoopBackOff logs → logs --previous → describe → probes/config
ImagePullBackOff image name/tag → registry → credentials → ImagePullSecret
OOMKilled memory usage → limits → application memory behavior
No Service endpoints selector → Pod labels → readiness → namespace
Connection refused Service → targetPort → endpoints → application listening port
DNS failure CoreDNS → Service → DNS name → network connectivity
PVC Pending StorageClass → PV → provisioner → events
Forbidden RBAC → Role → Binding → identity → auth can-i
Ingress 404 host/path → Ingress rules → controller → Service
Ingress 502/503 Service → endpoints → targetPort → Pod health
Node NotReady node conditions → kubelet → runtime → resources
Golden Troubleshooting Flow

get → describe → events → logs → dependencies → fix → verify

🔥 ⭐⭐⭐⭐⭐ 31. Project Interview Answer

"In my DevOps project, I used Kubernetes to deploy and manage the containerized application. I used Deployments to maintain application replicas and rolling updates. Services provided stable internal access to Pods, while Ingress handled external HTTP/HTTPS routing. I separated configuration using ConfigMaps and Secrets and used persistent storage through PV/PVC where required. I configured readiness and liveness probes for application health and resource requests and limits for predictable scheduling and resource management. For security, I used RBAC and followed least-privilege principles. For observability, I integrated monitoring using Prometheus and Grafana. For deployment automation, Kubernetes can be integrated with CI/CD and GitOps tools such as Argo CD. When troubleshooting, I use kubectl get, describe, events and logs to identify the root cause before applying a fix."

🎯 34. If Interviewer Says: "Explain Kubernetes"

"Kubernetes is a container orchestration platform used to automate the deployment, scaling and management of containerized applications. It follows a desired-state model. The control plane consists of components such as the API Server, etcd, Scheduler and Controller Manager, while worker nodes run application Pods through kubelet and the container runtime. I use Deployments for stateless applications, Services for stable network communication and Ingress for external HTTP/HTTPS routing. ConfigMaps and Secrets help separate configuration and sensitive data from application images. For persistent workloads, Kubernetes provides PV, PVC and StorageClass. Readiness, liveness and startup probes help manage application health. For scalability, I use resource requests and limits and HPA. RBAC and NetworkPolicies help control access and communication. In production, I combine Kubernetes with CI/CD, monitoring and GitOps practices. When issues occur, I troubleshoot systematically using kubectl get, describe, events and logs instead of making random changes."

🧠 36. Kubernetes Golden Rules

  • Pod is not the application architecture. Use appropriate workload controllers.
  • Service is not the same as Pod. Service provides stable networking.
  • Running does not always mean healthy. Use readiness and application health checks.
  • Base64 is not encryption. Protect Secrets appropriately.
  • Requests influence scheduling. Limits constrain resource usage.
  • Don't blindly restart Pods. Find the root cause.
  • Don't expose everything publicly. Use appropriate Services, Ingress and security controls.
  • Don't hard-code environment-specific configuration. Use configuration management.
  • Don't give excessive permissions. Follow least privilege.
  • Always verify after fixing.
