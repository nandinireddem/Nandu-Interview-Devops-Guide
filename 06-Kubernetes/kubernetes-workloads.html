Kubernetes Workloads

DevOps interview-focused guide covering Pods, Deployments, ReplicaSets, StatefulSets, DaemonSets, Jobs, CronJobs, rollout, scaling, self-healing and real-time workload scenarios.

⭐⭐⭐⭐⭐ What Are Kubernetes Workloads?

A workload is an application running on Kubernetes. Kubernetes provides workload resources such as Deployments, StatefulSets, DaemonSets, Jobs and CronJobs to manage Pods according to the application's requirements.
Application
↓
Workload Controller
↓
Pods
↓
Containers

The key interview point is that we normally don't manually manage individual application Pods in production. Controllers manage the desired state of those Pods.

⭐⭐⭐⭐⭐ 1. What is a Pod?

A Pod is the smallest deployable unit in Kubernetes. A Pod can contain one or more containers that share the same network namespace and can share storage volumes.

Simple architecture

Pod
│
├── Container
│
└── Container (optional)
Real-time example: A normal web application may have one application container in a Pod. A sidecar architecture may have: Application Container + Logging/Proxy Sidecar Both containers share the Pod's network namespace.

⭐⭐⭐⭐⭐ 2. Why don't we usually create Pods directly?

A standalone Pod is not automatically recreated by Kubernetes if it fails. For production workloads, controllers such as Deployments manage Pods and maintain the desired number of replicas.
Standalone Pod Deployment
Directly created Manages Pods through ReplicaSets
No automatic desired replica management Maintains desired replicas
Limited production use Common for stateless applications

⭐⭐⭐⭐⭐ 3. What is a Deployment?

A Deployment is a Kubernetes workload resource used mainly to manage stateless applications. It manages ReplicaSets, which in turn maintain the required number of Pods.
Deployment
↓
ReplicaSet
↓
Pods
↓
Containers

Deployment responsibilities

  • Maintain desired replicas
  • Rolling updates
  • Rollback
  • Scaling
  • Self-healing through ReplicaSets

⭐⭐⭐⭐⭐ 4. Deployment YAML

apiVersion: apps/v1
kind: Deployment

metadata:
  name: nginx-deployment

spec:

  replicas: 3

  selector:
    matchLabels:
      app: nginx

  template:

    metadata:
      labels:
        app: nginx

    spec:

      containers:

      - name: nginx
        image: nginx:1.27

        ports:
        - containerPort: 80
The Deployment declares that three Pods should normally exist, and the Pod template defines how those Pods should be created.

⭐⭐⭐⭐⭐ 5. What is ReplicaSet?

A ReplicaSet ensures that a specified number of Pod replicas are running. For example, if the desired replica count is 3 and one Pod fails, the ReplicaSet works to create a replacement Pod.
Desired = 3

Pod 1 ✅    Pod 2 ❌    Pod 3 ✅

↓

ReplicaSet creates replacement

↓

Pod 1 ✅    Pod 2 ✅    Pod 3 ✅
In normal application deployments, you generally create a Deployment rather than manually creating a ReplicaSet.

⭐⭐⭐⭐⭐ 6. Deployment vs ReplicaSet vs Pod

Resource Main responsibility
Pod Runs one or more containers.
ReplicaSet Maintains the desired number of matching Pods.
Deployment Manages ReplicaSets and provides rollout/rollback functionality.
Interview answer: "A Deployment manages ReplicaSets, and ReplicaSets maintain the desired number of Pods. The Pods actually run the containers."

⭐⭐⭐⭐⭐ 7. What is self-healing in Kubernetes?

Self-healing means Kubernetes controllers continuously compare the actual state with the desired state and take corrective action when they differ.
Deployment requires: 3 replicas Current state: 2 healthy Pods Kubernetes detects the difference and creates another Pod.
Desired State
3 Pods
↓
Actual State
2 Pods
↓
Controller
↓
Create Pod
↓
3 Pods

⭐⭐⭐⭐⭐ 8. What happens if a Pod crashes?

The exact behavior depends on how the Pod is managed. If it is managed by a Deployment/ReplicaSet, the controller ensures the desired replica count is maintained. Kubernetes may restart containers inside a Pod, and controllers may create replacement Pods when necessary.
Production example: A backend Deployment has 3 replicas. One Pod crashes. Kubernetes detects that the desired replica count is no longer met and creates a replacement so the application returns to the desired state.

⭐⭐⭐⭐⭐ 9. What is Rolling Update?

A rolling update gradually replaces old Pods with new Pods instead of stopping the entire application at once. This helps reduce downtime during application updates.
Old Version
3 Pods
↓
New Version starts
↓
Old Pods gradually removed
↓
New Pods become ready
↓
New Version
3 Pods

⭐⭐⭐⭐⭐ 10. How do you update a Deployment?

kubectl set image deployment/nginx-deployment \
nginx=nginx:1.28

Check rollout:

kubectl rollout status deployment/nginx-deployment

kubectl rollout history deployment/nginx-deployment
The Deployment creates a new ReplicaSet and gradually moves traffic/workload from the old version to the new version according to the rollout strategy.

⭐⭐⭐⭐⭐ 11. What is Rollback?

Rollback means returning a Deployment to a previous revision when a new deployment has a problem. 
kubectl rollout history deployment/nginx-deployment

kubectl rollout undo deployment/nginx-deployment

kubectl rollout status deployment/nginx-deployment
Real-time scenario: Version 2 of the application causes HTTP 500 errors after deployment. The DevOps engineer checks the rollout and quickly rolls back to the previously working version while investigating the issue.

⭐⭐⭐⭐⭐ 12. What is StatefulSet?

StatefulSet is a Kubernetes workload resource designed for stateful applications that require stable identity, stable network identity and/or persistent storage characteristics.

Typical examples

  • Databases
  • Kafka
  • ZooKeeper
  • Distributed stateful systems
StatefulSet
↓
pod-0
pod-1
pod-2
↓
Stable identities

⭐⭐⭐⭐⭐ 13. StatefulSet vs Deployment

Deployment StatefulSet
Primarily stateless workloads Stateful workloads
Pods are interchangeable Pods have stable identities
Usually does not require stable Pod identity Stable network identity
Storage is not inherently tied to Pod identity Can use stable persistent storage per Pod
Simple answer: "Deployment is normally preferred for stateless applications, while StatefulSet is used when Pods need stable identity or persistent state characteristics."

⭐⭐⭐⭐⭐ 14. StatefulSet Example

apiVersion: apps/v1
kind: StatefulSet

metadata:
  name: web

spec:

  serviceName: "web"

  replicas: 3

  selector:
    matchLabels:
      app: web

  template:

    metadata:
      labels:
        app: web

    spec:

      containers:

      - name: nginx
        image: nginx:1.27

The Pods can have stable ordinal identities such as: 

web-0
web-1
web-2

⭐⭐⭐⭐⭐ 15. What is DaemonSet?

A DaemonSet ensures that a Pod runs on each eligible node, or on each node matching the DaemonSet's scheduling constraints.

Common use cases

  • Node-level logging agents
  • Monitoring agents
  • Security agents
  • Node networking components
Node 1 → Agent Pod
Node 2 → Agent Pod
Node 3 → Agent Pod
Node 4 → Agent Pod
Real-time example: Suppose an organization runs a logging agent on every Kubernetes node to collect container logs. A DaemonSet can ensure each eligible node has one logging agent Pod.

⭐⭐⭐⭐⭐ 16. Deployment vs StatefulSet vs DaemonSet

Workload Best suited for
Deployment Stateless web applications and APIs
StatefulSet Stateful applications requiring stable identity/storage
DaemonSet One Pod per eligible node

⭐⭐⭐⭐⭐ 17. What is a Job?

A Job creates one or more Pods and ensures that the required successful completions are achieved. Jobs are intended for tasks that run to completion rather than long-running services.

Examples

  • Database migration
  • Batch processing
  • Data processing
  • One-time administrative task

⭐⭐⭐⭐⭐ 18. Job YAML

apiVersion: batch/v1
kind: Job

metadata:
  name: database-migration

spec:

  template:

    spec:

      restartPolicy: Never

      containers:

      - name: migration
        image: myapp:1.0
        command:
        - /bin/sh
        - -c
        - "python migrate.py"
The migration Pod runs the migration script. If the task completes successfully, the Job reaches completion.

⭐⭐⭐⭐⭐ 19. What is CronJob?

A CronJob creates Jobs on a repeating schedule using a cron expression.

Typical use cases

  • Scheduled backups
  • Cleanup tasks
  • Reports
  • Periodic data processing

Example

apiVersion: batch/v1
kind: CronJob

metadata:
  name: backup-job

spec:

  schedule: "0 2 * * *"

  jobTemplate:

    spec:

      template:

        spec:

          restartPolicy: OnFailure

          containers:

          - name: backup
            image: backup-image:1.0
            command:
            - /bin/sh
            - -c
            - "backup.sh"

This schedule runs approximately every day at 02:00 according to the CronJob's configured time interpretation.

⭐⭐⭐⭐⭐ 20. Job vs CronJob

Job CronJob
Runs a task to completion Creates Jobs on a schedule
One-time/batch execution Recurring execution
Example: migration Example: daily backup

⭐⭐⭐⭐⭐ 21. What is desired state?

Desired state is the configuration that we tell Kubernetes we want. Kubernetes continuously works to make the actual state match the desired state. 
replicas: 3
Desired state = 3 Pods Actual state = 2 Pods Controller action = create another Pod Final state = 3 Pods

⭐⭐⭐⭐⭐ 22. What is declarative configuration?

Declarative configuration describes the desired end state rather than specifying every individual operation required to reach it. Kubernetes controllers then work to achieve that state. 
spec:
  replicas: 3

  containers:
  - name: nginx
    image: nginx:1.28

This configuration describes what should exist. Kubernetes handles the reconciliation process.

⭐⭐⭐⭐⭐ 23. What is a Replica count?

The replica count specifies how many Pod replicas a workload should maintain. 
spec:
  replicas: 3

This is commonly used with Deployments and ReplicaSets.

⭐⭐⭐⭐⭐ 24. How do you scale a Deployment?

Imperative scaling

kubectl scale deployment nginx-deployment --replicas=5

Check

kubectl get deployment

kubectl get pods

Declarative scaling

spec:
  replicas: 5
Production example: Traffic increases during a sale. The application may need more replicas to handle increased demand. For long-term automated scaling, Horizontal Pod Autoscaler can be used when the application and cluster are configured appropriately.

⭐⭐⭐⭐⭐ 25. What is HPA?

Horizontal Pod Autoscaler automatically adjusts the number of Pod replicas based on observed metrics such as CPU utilization, memory or configured custom/external metrics.
Low Traffic
↓
2 Pods

Traffic increases
↓
HPA evaluates metrics
↓
5 Pods
HPA does not increase the CPU or memory of an individual Pod. It changes the number of replicas.

⭐⭐⭐⭐⭐ 26. HPA vs Vertical Scaling

Horizontal Scaling Vertical Scaling
Increase/decrease number of Pods Increase resources assigned to a Pod
More replicas More CPU/memory
HPA is commonly used VPA can be used in supported/configured environments

⭐⭐⭐⭐⭐ 27. What are readiness and liveness probes?

Readiness Probe

Determines whether a container is ready to receive traffic. If the readiness check fails, Kubernetes can remove the Pod from Service endpoints.

Liveness Probe

Determines whether a container is considered healthy enough to continue running. If the liveness probe repeatedly fails, kubelet can restart the container.
Application starts slowly. Without readiness: Traffic may reach the application before it is ready. With readiness: Traffic is sent only after the application passes its readiness check.

⭐⭐⭐⭐⭐ 28. Readiness vs Liveness vs Startup

Probe Purpose
Readiness Should this Pod receive traffic?
Liveness Should this container be restarted?
Startup Has a slow-starting application completed startup?
Easy memory trick:

Readiness → "Can I send traffic?"
Liveness → "Is it still alive?"
Startup → "Has it finished starting?"

⭐⭐⭐⭐ 29. Deployment Strategy

Kubernetes Deployments commonly support strategies such as:

  • RollingUpdate
  • Recreate

RollingUpdate

Gradually replaces old Pods with new Pods. This is commonly preferred when application availability should be maintained during updates.

Recreate

Existing Pods are terminated before the new Pods are created. This can cause downtime and is useful only when the application's requirements justify it.

⭐⭐⭐⭐⭐ 30. What are maxUnavailable and maxSurge?

During a RollingUpdate: maxUnavailable controls how many Pods can be unavailable during the update. maxSurge controls how many additional Pods can be created above the desired replica count during the update. 
strategy:

  type: RollingUpdate

  rollingUpdate:

    maxUnavailable: 1
    maxSurge: 1
If desired replicas = 3 and maxSurge = 1, Kubernetes can temporarily have up to 4 Pods during the rollout.

⭐⭐⭐⭐⭐ 31. Real-Time Scenario: New deployment is failing

Problem: A new application version is deployed, but Pods are failing.

Check Deployment

kubectl get deployment

kubectl describe deployment <deployment>

Check ReplicaSets

kubectl get rs

Check Pods

kubectl get pods

kubectl describe pod <pod>

kubectl logs <pod>

Rollback if required

kubectl rollout undo deployment/<deployment>

⭐⭐⭐⭐⭐ 32. Real-Time Scenario: Pods are in CrashLoopBackOff

CrashLoopBackOff means a container is repeatedly starting and crashing, and Kubernetes is backing off before restarting it again.

Investigation

kubectl get pods

kubectl describe pod <pod>

kubectl logs <pod>

kubectl logs <pod> --previous
Possible causes:
  • Application error
  • Wrong environment variable
  • Missing configuration
  • Incorrect command
  • Dependency unavailable
  • Permission problem
  • Probe configuration issue

⭐⭐⭐⭐⭐ 33. Real-Time Scenario: Pods are Pending

A Pending Pod has not successfully reached the running state. The scheduler may be unable to place it on a suitable node, or another condition may be preventing startup. 
kubectl get pods

kubectl describe pod <pod>

kubectl get nodes

kubectl describe node <node>
Common causes:
  • Insufficient CPU or memory
  • Node selector mismatch
  • Taints and tolerations
  • Affinity rules
  • Unbound persistent volume claim

⭐⭐⭐⭐⭐ 34. Real-Time Scenario: Deployment says Available replicas are low

I would inspect the Deployment, ReplicaSet and Pods to identify why the desired replicas are not becoming available. 
kubectl get deployment

kubectl get rs

kubectl get pods

kubectl describe deployment <deployment>

kubectl describe pod <pod>

kubectl logs <pod>

Readiness failures, image problems, resource issues and application startup failures are common areas to investigate.

🎯 If Interviewer Says: "Explain Kubernetes Workloads"

"Kubernetes workloads are resources used to run and manage applications in a Kubernetes cluster. A Pod is the smallest deployable unit and contains one or more containers. For stateless applications, I commonly use a Deployment. The Deployment manages ReplicaSets, and the ReplicaSet maintains the required number of Pods. Deployments also provide rolling updates, scaling and rollback. For stateful applications that need stable identity or persistent storage characteristics, I would use StatefulSet. DaemonSet is used when a Pod needs to run on each eligible node, for example a logging or monitoring agent. For tasks that need to run to completion, I would use a Job, and for scheduled recurring tasks, I would use a CronJob. Kubernetes continuously compares the actual state with the desired state and controllers work to maintain the desired state. This is one of the key reasons Kubernetes provides self-healing behavior. In production, I would also use readiness and liveness probes, appropriate resource configuration, controlled rolling updates and rollback mechanisms to maintain application availability."
