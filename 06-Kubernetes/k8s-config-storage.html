Kubernetes Config & Storage

Interview-focused revision covering ConfigMaps, Secrets, Volumes, Persistent Volumes, PVCs, StorageClasses and real-time production scenarios.

⭐⭐⭐⭐⭐ Why Config & Storage Matter

Kubernetes applications usually need two things outside the container image: configuration and persistent data.

Application Container
↓
ConfigMap / Secret → Application Configuration

Volume / PVC → Persistent Application Data
Real-time example: A Java application runs in Kubernetes. The application image contains the code, but database URLs, environment-specific configuration and passwords should not be hardcoded inside the image. ConfigMaps can store normal configuration, Secrets can store sensitive values, and PVCs can provide persistent storage for application data.

⭐⭐⭐⭐⭐ 1. What is a ConfigMap?

Interview Question

A ConfigMap is a Kubernetes object used to store non-sensitive configuration data separately from application code and container images.

Why do we use ConfigMaps?

  • Keep configuration outside the container image
  • Use different configuration for different environments
  • Avoid rebuilding images for configuration changes
  • Provide configuration as environment variables or files

Example

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: INFO
  APP_PORT: "8080"

Using ConfigMap as environment variables

apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  replicas: 2
  selector:
    matchLabels:
      app: app
  template:
    metadata:
      labels:
        app: app
    spec:
      containers:
      - name: app
        image: myapp:v1
        envFrom:
        - configMapRef:
            name: app-config
Interview answer:

"I use ConfigMaps to externalize non-sensitive application configuration from the container image. This allows the same image to be promoted across environments while configuration can vary between development, staging and production."

⭐⭐⭐⭐⭐ 2. What is a Secret?

A Secret is a Kubernetes object designed to hold sensitive data such as passwords, tokens, API keys and credentials.

Example

apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  DB_USERNAME: admin
  DB_PASSWORD: mypassword

Using Secret in a Pod

env:
- name: DB_USERNAME
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: DB_USERNAME

- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: DB_PASSWORD
Kubernetes Secrets are not automatically equivalent to a fully secure external secrets manager. In production, protect access using RBAC and encryption at rest, and consider external secret-management solutions when appropriate.

⭐⭐⭐⭐⭐ 3. ConfigMap vs Secret

ConfigMap Secret
Non-sensitive configuration Sensitive configuration
Environment variables Passwords / tokens / keys
Application settings Credentials
Not intended for secrets Designed for sensitive values
Easy interview line:

"ConfigMap is for non-sensitive configuration, while Secret is for sensitive configuration such as credentials and tokens."

⭐⭐⭐⭐⭐ 4. How can ConfigMap and Secret be consumed?

They can commonly be consumed in two ways:

1. Environment Variables

envFrom:
- configMapRef:
    name: app-config

- secretRef:
    name: db-secret

2. Mounted as Files

volumes:
- name: config-volume
  configMap:
    name: app-config

containers:
- name: app
  image: myapp:v1
  volumeMounts:
  - name: config-volume
    mountPath: /etc/config
Real-time example: An NGINX application may need a configuration file. Instead of rebuilding the Docker image whenever the configuration changes, the configuration can be stored in a ConfigMap and mounted inside the Pod.

⭐⭐⭐⭐⭐ 5. What is a Volume in Kubernetes?

A Kubernetes Volume provides storage that can be mounted into containers running inside a Pod.

A container's writable filesystem is tied to the container lifecycle. When a container is replaced, data stored only inside that writable layer may be lost.

Basic volume example

apiVersion: v1
kind: Pod
metadata:
  name: volume-demo
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: app-storage
      mountPath: /data

  volumes:
  - name: app-storage
    emptyDir: {}

⭐⭐⭐⭐⭐ 6. What is emptyDir?

emptyDir creates temporary storage when a Pod is assigned to a node. The storage exists for the lifetime of the Pod.
Real-time use case: A Pod has two containers. One container generates temporary files and another container processes them. Both containers can mount the same emptyDir volume and share those temporary files.
When the Pod is deleted from the node, the emptyDir data is deleted.

⭐⭐⭐⭐⭐ 7. What is PersistentVolume?

A PersistentVolume (PV) is a cluster-level storage resource provisioned for persistent application data.

A PV represents storage that exists independently of a particular Pod's lifecycle.

Concept

Pod
↓
PVC
↓
PV
↓
Storage Backend

The storage backend could be cloud block storage, network storage, or another Kubernetes-supported storage implementation.

⭐⭐⭐⭐⭐ 8. What is PersistentVolumeClaim?

A PersistentVolumeClaim (PVC) is a request for persistent storage made by a user or workload.

Instead of directly selecting a physical storage device, the application requests storage through a PVC.

Example PVC

apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-pvc
spec:
  accessModes:
  - ReadWriteOnce

  resources:
    requests:
      storage: 10Gi

Using PVC in a Pod

volumes:
- name: app-storage
  persistentVolumeClaim:
    claimName: app-pvc

containers:
- name: app
  image: nginx
  volumeMounts:
  - name: app-storage
    mountPath: /data

⭐⭐⭐⭐⭐ 9. PV vs PVC

PV PVC
Actual Kubernetes storage resource Request for storage
Cluster-level resource Requested by workload/user
Provides storage Consumes/claims storage
Usually associated with a storage backend Specifies required capacity/access characteristics
Simple interview answer:

"PV is the storage resource, while PVC is the request for that storage. Pods normally consume the PVC rather than directly managing the underlying storage."

⭐⭐⭐⭐⭐ 10. What is StorageClass?

A StorageClass defines classes of storage and enables dynamic provisioning of PersistentVolumes.

Without dynamic provisioning, administrators may need to create PVs manually. With a StorageClass, Kubernetes can provision storage through the configured storage provisioner when a PVC requests it.

PVC
↓
StorageClass
↓
Provisioner
↓
Persistent Volume
↓
Pod

⭐⭐⭐⭐⭐ 11. Dynamic vs Static Provisioning

Static Provisioning Dynamic Provisioning
Admin creates PV manually PV is provisioned automatically
More manual work Automation-friendly
Useful for predefined storage Common in cloud Kubernetes environments
Real-time AWS example: An application requests a 20Gi PVC. The configured StorageClass can dynamically provision the required cloud storage instead of the administrator manually creating every PV.

⭐⭐⭐⭐⭐ 12. Access Modes

Mode Meaning
ReadWriteOnce Volume can be mounted read-write by a node according to the storage backend's capabilities.
ReadOnlyMany Volume can be mounted read-only by multiple nodes where supported.
ReadWriteMany Volume can be mounted read-write by multiple nodes where supported.
Do not assume every storage backend supports every access mode. The actual capability depends on the storage implementation.

⭐⭐⭐⭐ 13. What happens when a Pod using a PVC is deleted?

Deleting a Pod does not automatically mean the persistent data is deleted. The PVC and the underlying storage can remain available for another Pod, depending on the storage lifecycle and reclaim configuration.
Real-time example: A database Pod crashes. Kubernetes creates a replacement Pod. The replacement Pod can mount the same PVC and continue using the persistent database data, assuming the storage can be attached to the new Pod.

⭐⭐⭐⭐ 14. What is a Reclaim Policy?

A PV reclaim policy determines what happens to the underlying storage after the PVC is deleted.
Policy Meaning
Retain Keep the PV/storage for manual recovery or cleanup.
Delete Delete the associated dynamically provisioned storage where supported.
Recycle Legacy behavior and generally not used in modern Kubernetes.
For production databases, storage lifecycle must be chosen carefully. Accidental deletion of a claim should not automatically destroy critical data without an intentional recovery strategy.

⭐⭐⭐⭐⭐ 15. Kubernetes Storage Troubleshooting

Scenario: PVC is stuck in Pending

First inspect the PVC:

kubectl get pvc
kubectl describe pvc <pvc-name>

Then inspect StorageClasses:

kubectl get storageclass
kubectl describe storageclass <storage-class-name>

Also inspect Pods and cluster events:

kubectl get pods
kubectl describe pod <pod-name>
kubectl get events --sort-by=.lastTimestamp

Common causes

  • No suitable StorageClass
  • StorageClass/provisioner problem
  • Insufficient storage capacity
  • Unsupported access mode
  • Storage backend problem
  • Topology or node constraints

⭐⭐⭐⭐⭐ 16. ConfigMap/Secret Troubleshooting

Check objects

kubectl get configmap
kubectl get secret

Inspect configuration

kubectl describe configmap app-config
kubectl describe secret db-secret

Check Pod

kubectl describe pod <pod-name>
kubectl logs <pod-name>
Example: The application starts but cannot connect to the database. I would verify:

1. Secret exists
2. Correct Secret key is referenced
3. Environment variable is injected correctly
4. Database hostname and port are correct
5. Pod logs show the actual application error

⭐⭐⭐⭐⭐ 17. Secret Security in Production

  • Use least-privilege RBAC
  • Restrict who can read Secrets
  • Enable encryption at rest where appropriate
  • Avoid committing secrets to Git
  • Rotate credentials
  • Use external secret-management systems when appropriate
  • Never print secrets in application logs
Base64 encoding is not the same thing as encryption. Do not describe Kubernetes Secret data as secure simply because it is base64-encoded.

⭐⭐⭐⭐⭐ 18. Real-Time Scenario: Database in Kubernetes

Situation: A PostgreSQL database is running inside Kubernetes. The Pod gets deleted because of a node failure.

Problem: If database files were stored only inside the container's writable layer, the replacement Pod could lose the data.

Solution: Use a PVC backed by persistent storage.
PostgreSQL Pod
↓
PVC
↓
PV / Dynamic Provisioning
↓
Persistent Storage
Interview answer: "I would not depend on the container writable layer for database persistence. I would use a PVC backed by an appropriate persistent storage system, define the storage lifecycle carefully, and also maintain backups because persistent storage alone is not a complete backup strategy."

⭐⭐⭐⭐ 19. ConfigMap vs Baking Configuration into Docker Image

Docker Image Configuration Kubernetes ConfigMap
Configuration becomes part of image Configuration is externalized
Often requires rebuilding image Same image can be used across environments
Less flexible for environment changes Better separation of application and configuration
DevOps principle: Build the application image once and inject environment-specific configuration during deployment.

Secret → Sensitive configuration

Volume → Storage mounted into Pod

emptyDir → Temporary Pod storage

🎯 If Interviewer Says: "Explain Kubernetes Storage"

"Kubernetes provides different mechanisms for configuration and storage. For non-sensitive application configuration, I use ConfigMaps, while sensitive values such as credentials are stored in Secrets. For storage, a Pod can use volumes. For temporary data, emptyDir can be used, but for persistent application data I use PersistentVolumeClaims. A PVC represents the application's request for storage and can be bound to a PersistentVolume. In dynamic provisioning, a StorageClass and its provisioner can automatically create the required storage. For production workloads such as databases, I would use persistent storage with an appropriate access mode and reclaim policy, secure Secrets using RBAC and encryption controls, and maintain backups because storage persistence is not a substitute for backups."
