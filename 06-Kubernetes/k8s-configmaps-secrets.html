Kubernetes ConfigMaps & Secrets

Interview-focused guide covering configuration management, Secrets, environment variables, volume mounts, security practices, troubleshooting and real-time DevOps scenarios.

⭐⭐⭐⭐⭐ Core Concept

Applications should not normally have environment-specific configuration hard-coded inside the container image. Kubernetes provides ConfigMap and Secret for separating configuration from application images.

Docker Image
↓
Application
+
ConfigMap → Non-sensitive configuration
Secret → Sensitive configuration
↓
Pod
Real-time example: The same application image is deployed to Dev, QA and Production. The application code remains unchanged, while values such as database host, application mode and API credentials are supplied through Kubernetes configuration.

⭐⭐⭐⭐⭐ 1. What is a ConfigMap?

A ConfigMap stores non-confidential configuration data as key-value pairs or configuration files. It helps keep environment-specific configuration separate from the container image.

Example

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  API_URL: https://api.example.com

View it

kubectl get configmap
kubectl describe configmap app-config

⭐⭐⭐⭐⭐ 2. What is a Secret?

A Secret stores sensitive information such as passwords, tokens, API keys or credentials. Kubernetes Secrets are intended for sensitive data, but simply storing a value in a Secret does not automatically make it strongly protected in every environment.

Example

apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  username: admin
  password: MyStrongPassword

View Secret metadata

kubectl get secret
kubectl describe secret db-secret
Do not commit real passwords, API keys or cloud credentials into Git repositories.

⭐⭐⭐⭐⭐ 3. ConfigMap vs Secret

ConfigMap Secret
Non-sensitive configuration Sensitive configuration
URLs, feature flags, log levels Passwords, tokens, credentials
Can be consumed as env variables Can be consumed as env variables
Can be mounted as files Can be mounted as files
Interview answer:

"I use ConfigMaps for non-sensitive configuration such as application settings and URLs. I use Secrets for sensitive values such as passwords, tokens and credentials. Both can be consumed by Pods through environment variables or mounted files."

⭐⭐⭐⭐⭐ 4. Using ConfigMap as Environment Variables

ConfigMap

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info

Pod

apiVersion: v1
kind: Pod
metadata:
  name: config-demo
spec:
  containers:
  - name: app
    image: nginx
    envFrom:
    - configMapRef:
        name: app-config

The keys from the ConfigMap become environment variables inside the container.

⭐⭐⭐⭐⭐ 5. Using Secret as Environment Variables

Secret

apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  DB_USERNAME: admin
  DB_PASSWORD: MyStrongPassword

Pod

apiVersion: v1
kind: Pod
metadata:
  name: database-client
spec:
  containers:
  - name: app
    image: nginx
    envFrom:
    - secretRef:
        name: db-secret
Environment variables can potentially be exposed through application debugging, process inspection, logs or other operational mechanisms. Use the consumption method appropriate for your security requirements.

⭐⭐⭐⭐⭐ 6. ConfigMap using individual environment variable

env:
- name: APP_ENV
  valueFrom:
    configMapKeyRef:
      name: app-config
      key: APP_ENV

This is useful when the container should receive only a specific configuration value instead of the entire ConfigMap.

⭐⭐⭐⭐⭐ 7. Secret using individual key

env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-secret
      key: DB_PASSWORD
Real-time use: An application needs only the database password. Instead of importing every Secret key into the container, expose only the required key.

⭐⭐⭐⭐⭐ 8. Mount ConfigMap as a Volume

ConfigMap

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  application.properties: |
    app.name=myapp
    log.level=INFO

Pod

apiVersion: v1
kind: Pod
metadata:
  name: config-volume-demo
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: config-volume
      mountPath: /etc/app

  volumes:
  - name: config-volume
    configMap:
      name: app-config

The ConfigMap data is exposed as files inside /etc/app.

⭐⭐⭐⭐ 9. Mount Secret as a Volume

Pod example

apiVersion: v1
kind: Pod
metadata:
  name: secret-volume-demo
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: secret-volume
      mountPath: /etc/secrets
      readOnly: true

  volumes:
  - name: secret-volume
    secret:
      secretName: db-secret

Each Secret key is exposed as a file inside the mounted directory.

⭐⭐⭐⭐⭐ 10. stringData vs data

data stringData
Values are represented as base64-encoded data in the manifest. Allows plain string values in the manifest.
Commonly seen when inspecting Secret manifests. Kubernetes converts the values into the Secret's data representation.

Example

apiVersion: v1
kind: Secret
metadata:
  name: example
type: Opaque
stringData:
  username: admin
  password: password123
Base64 is encoding, not encryption. Do not assume a base64-encoded Secret is safe to expose.

⭐⭐⭐⭐⭐ 11. Why not hard-code configuration in Docker image?

Hard-coding environment-specific values inside an image creates deployment and maintenance problems. For example, the same image should ideally be reusable across development, staging and production while configuration changes independently.
Same Image
↓
Dev Config
QA Config
Production Config
This follows the DevOps principle of separating application code from environment-specific configuration.

⭐⭐⭐⭐ 12. ConfigMap update behavior

How a Pod observes a ConfigMap update depends on how the ConfigMap is consumed. Mounted ConfigMap volumes can eventually reflect updates, while environment variables populated from ConfigMaps are not dynamically updated inside an already-running container.
If an application reads configuration from environment variables, you normally need to restart or recreate the Pod to load the updated environment values.

⭐⭐⭐⭐ 13. Secret update behavior

The same important distinction applies to Secrets. A Secret consumed as an environment variable does not automatically change inside a running process when the Secret object changes. Mounted Secret volumes can reflect updates according to Kubernetes' volume update behavior.
Even when Kubernetes updates a mounted Secret, the application must be designed to re-read or reload the file if it needs the new value without restarting.

⭐⭐⭐⭐⭐ 14. Immutable ConfigMap / Secret

Kubernetes supports immutable ConfigMaps and Secrets. This can prevent accidental modification of configuration after creation and is useful when configuration should remain fixed for the lifetime of a deployment.

ConfigMap example

apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
immutable: true
data:
  APP_ENV: production

Secret example

apiVersion: v1
kind: Secret
metadata:
  name: app-secret
immutable: true
type: Opaque
stringData:
  API_KEY: example
If configuration needs to change, create a new ConfigMap or Secret and update the workload reference as part of a controlled deployment.

⭐⭐⭐⭐⭐ 15. How to create ConfigMap using kubectl?

From literals

kubectl create configmap app-config \
  --from-literal=APP_ENV=production \
  --from-literal=LOG_LEVEL=info

From file

kubectl create configmap app-config \
  --from-file=application.properties

From env file

kubectl create configmap app-config \
  --from-env-file=.env

⭐⭐⭐⭐⭐ 16. How to create Secret using kubectl?

From literal

kubectl create secret generic db-secret \
  --from-literal=username=admin \
  --from-literal=password='MyStrongPassword'

From file

kubectl create secret generic app-secret \
  --from-file=credentials.txt

Check

kubectl get secrets
kubectl describe secret db-secret
Avoid putting real secrets directly into shell history or shared terminal sessions. Prefer a secure secret-management workflow.

⭐⭐⭐⭐⭐ 17. Troubleshooting: ConfigMap not found

Problem: Pod fails because it references a ConfigMap that does not exist in the Pod's namespace.

Check

kubectl get configmap -n dev

kubectl describe pod <pod-name> -n dev

kubectl get configmap app-config -n dev
ConfigMaps and Pods are namespace-scoped. The ConfigMap must normally exist in the same namespace as the workload referencing it.

⭐⭐⭐⭐⭐ 18. Troubleshooting: Secret not found

Problem: A Deployment references db-secret, but the Pod cannot start correctly because the Secret is missing. 
kubectl get secret -n production

kubectl describe pod <pod-name> -n production

kubectl get deployment <deployment-name> -n production -o yaml

Verify the Secret name, namespace and referenced key.

⭐⭐⭐⭐⭐ 19. Real-Time Scenario: Dev, QA and Production

Suppose the application image is: 
mycompany/payment-app:v1.5
The application is deployed into three environments.

Dev: LOG_LEVEL=debug
QA: LOG_LEVEL=info
Production: LOG_LEVEL=warn

The same application image can be reused while each environment provides its own ConfigMap.
This avoids rebuilding the Docker image just because environment configuration changed.

⭐⭐⭐⭐⭐ 20. Real-Time Scenario: Database Password Rotation

A production database password must be rotated. A good approach is to update the credential through the approved secret-management process, update the Kubernetes Secret, and ensure the application reloads or restarts as required.
New Credential
↓
Secret Management
↓
Kubernetes Secret
↓
Application Reload / Restart
↓
Verify Connection
Do not update credentials by manually editing application source code or committing the new password to Git.

⭐⭐⭐⭐⭐ 21. Real-Time Scenario: Secret accidentally committed to Git

Problem: An AWS access key or database password was accidentally committed.

Immediate response: 1. Treat the credential as compromised.
2. Revoke or rotate it immediately.
3. Remove it from active configuration.
4. Investigate repository history and exposure.
5. Clean repository history when appropriate.
6. Use secret scanning to prevent recurrence.
Deleting the file in a later commit does not automatically remove the secret from Git history.

⭐⭐⭐⭐⭐ 22. ConfigMap & Secret with Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: payment-app
spec:
  replicas: 2

  selector:
    matchLabels:
      app: payment

  template:
    metadata:
      labels:
        app: payment

    spec:
      containers:
      - name: payment
        image: mycompany/payment:v1.0

        envFrom:
        - configMapRef:
            name: payment-config

        - secretRef:
            name: payment-secret
This is a common production pattern: Image contains application code. ConfigMap provides normal configuration. Secret provides sensitive configuration.

⭐⭐⭐⭐ 23. ConfigMap vs Docker ENV

Docker ENV Kubernetes ConfigMap
Can be baked into the image definition Managed separately from the image
Less flexible for multiple environments Designed for Kubernetes configuration management
Image may contain environment-specific defaults Same image can be reused across environments
In Kubernetes deployments, I prefer externalizing environment-specific configuration through ConfigMaps and Secrets rather than rebuilding images for every environment.

⭐⭐⭐⭐⭐ 24. Security Best Practices

  • Never store production secrets in Git.
  • Use RBAC to limit Secret access.
  • Use encryption at rest where appropriate.
  • Rotate credentials.
  • Use external secret managers when required.
  • Do not print Secrets in application logs.
  • Use dedicated Secrets for different environments.
  • Use immutable Secrets when appropriate.
  • Give workloads only the permissions they need.
  • Scan repositories for leaked credentials.
For a production AWS workload, an organization may integrate Kubernetes with a dedicated cloud secret-management solution instead of manually managing long-lived credentials in Git.

🎯 If Interviewer Says: "Explain ConfigMaps and Secrets"

"ConfigMaps and Secrets allow us to separate configuration from the application container image. I use ConfigMaps for non-sensitive values such as environment settings, application URLs and log levels. For sensitive information such as passwords, tokens and API keys, I use Kubernetes Secrets and restrict access through RBAC. Both ConfigMaps and Secrets can be consumed through environment variables or mounted as files. For production, I avoid committing Secrets to Git, use appropriate encryption and access controls, rotate credentials and consider an external secret-management solution when required. This allows us to reuse the same application image across Dev, QA and Production while managing environment-specific configuration separately."
