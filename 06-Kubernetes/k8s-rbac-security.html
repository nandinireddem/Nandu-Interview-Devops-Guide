Kubernetes RBAC & Security

Interview-focused revision covering RBAC, ServiceAccounts, Roles, ClusterRoles, bindings, securityContext, least privilege, NetworkPolicies and real-time security scenarios.

⭐⭐⭐⭐⭐ Kubernetes Security Mindset

Kubernetes security is mainly about controlling who can do what, where they can do it, and what workloads are allowed to do.

Identity
↓
Authentication
↓
Authorization / RBAC
↓
Kubernetes API
↓
Resources

Workload Security
↓
securityContext + NetworkPolicy + Secrets Protection
Real-time example: A DevOps team has a production Kubernetes cluster. Developers should be able to view Pods and logs in the dev namespace, but they should not be allowed to delete production Deployments. RBAC can enforce this least-privilege access.

⭐⭐⭐⭐⭐ 1. What is Kubernetes RBAC?

RBAC stands for Role-Based Access Control. It controls which users, groups or ServiceAccounts can perform which actions on which Kubernetes resources.
Subject
User / Group / ServiceAccount
↓
Role / ClusterRole
↓
RoleBinding / ClusterRoleBinding
↓
Permission

Important verbs

get
list
watch
create
update
patch
delete
Interview answer:

"RBAC is Kubernetes' authorization mechanism. It defines permissions through Roles or ClusterRoles and assigns those permissions to users, groups or ServiceAccounts using RoleBindings or ClusterRoleBindings."

⭐⭐⭐⭐⭐ 2. Role vs ClusterRole

Role ClusterRole
Namespace-scoped Cluster-scoped
Permissions within a namespace Can define permissions for cluster-wide resources
Useful for application teams Useful for cluster-level access

Role example

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

This Role allows reading Pods only inside the dev namespace.

⭐⭐⭐⭐⭐ 3. RoleBinding vs ClusterRoleBinding

A RoleBinding grants permissions within a namespace. A ClusterRoleBinding grants the permissions of a ClusterRole across the cluster.

RoleBinding example

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods
  namespace: dev
subjects:
- kind: User
  name: developer
  apiGroup: rbac.authorization.k8s.io

roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
Avoid giving users cluster-admin unless it is genuinely required. Excessive permissions increase the blast radius of mistakes or compromised credentials.

⭐⭐⭐⭐⭐ 4. ServiceAccount

A ServiceAccount provides an identity for workloads running inside Kubernetes. Pods can use that identity when communicating with the Kubernetes API or other systems that integrate with Kubernetes identities.

Create ServiceAccount

apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: dev

Use it in a Pod

apiVersion: v1
kind: Pod
metadata:
  name: app
  namespace: dev
spec:
  serviceAccountName: app-sa

  containers:
  - name: app
    image: nginx
Real-time example: A Kubernetes workload needs permission to read specific Kubernetes resources. Instead of giving every Pod broad permissions, create a dedicated ServiceAccount and bind only the required Role.

⭐⭐⭐⭐⭐ 5. ServiceAccount + Role + RoleBinding

Pod
↓
ServiceAccount
↓
RoleBinding
↓
Role
↓
Allowed API Actions

Example

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "list", "watch"]

---

apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-read-access
  namespace: dev
subjects:
- kind: ServiceAccount
  name: app-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

The application can now use the ServiceAccount identity with only the permissions granted by the Role.

⭐⭐⭐⭐⭐ 6. Authentication vs Authorization

Authentication Authorization
Who are you? What are you allowed to do?
Verifies identity Checks permissions
Users / ServiceAccounts / external identity RBAC policies
Easy interview answer:

"Authentication verifies the identity, while authorization determines what that identity is allowed to access or perform."

⭐⭐⭐⭐⭐ 7. Least Privilege

Least privilege means giving an identity only the minimum permissions required to perform its job.

Bad approach

verbs: ["*"]
resources: ["*"]

Better approach

resources:
- pods

verbs:
- get
- list
- watch
A monitoring application only needs to read Pod information. Do not give it permission to create, update or delete Deployments, Secrets or Nodes. Give it only the permissions it actually needs.

⭐⭐⭐⭐⭐ 8. What is securityContext?

A Kubernetes securityContext defines security-related settings for a Pod or container, such as the user/group identity, Linux capabilities and privilege settings.

Example

apiVersion: v1
kind: Pod
metadata:
  name: secure-pod
spec:
  securityContext:
    runAsNonRoot: true

  containers:
  - name: app
    image: nginx
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop:
        - ALL

Important settings

  • runAsUser
  • runAsGroup
  • runAsNonRoot
  • allowPrivilegeEscalation
  • privileged
  • capabilities
  • readOnlyRootFilesystem

⭐⭐⭐⭐⭐ 9. Why should containers run as non-root?

Running an application as a non-root user reduces the impact of a container compromise. If an attacker gains control of the application process, the attacker does not automatically receive root privileges inside the container.

Example

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
Non-root execution is one security layer. It does not replace RBAC, network controls, image security or host-level security.

⭐⭐⭐⭐ 10. Privileged Container

A privileged container receives significantly elevated access to the host and should be avoided unless a legitimate infrastructure workload requires it.

Example to avoid for normal applications

securityContext:
  privileged: true
A normal web application should not require privileged access. If an application can run without it, keep the container unprivileged.

⭐⭐⭐⭐⭐ 11. Linux Capabilities

Linux capabilities split traditional root privileges into smaller permission units. Kubernetes can drop unnecessary capabilities from containers.

Example

securityContext:
  capabilities:
    drop:
    - ALL

This follows the principle of removing privileges that the application does not need.

⭐⭐⭐⭐ 12. readOnlyRootFilesystem

readOnlyRootFilesystem: true makes the container's root filesystem read-only. This can reduce the ability of a compromised application to modify files inside the image filesystem. 
securityContext:
  readOnlyRootFilesystem: true
If the application needs temporary writable space, provide a specific writable volume such as an emptyDir rather than making the entire root filesystem writable.

⭐⭐⭐⭐⭐ 13. NetworkPolicy

A NetworkPolicy controls network traffic to and/or from Pods when the cluster's networking implementation supports NetworkPolicy enforcement.
Pod A
↓
NetworkPolicy
↓
Allowed / Denied Traffic
↓
Pod B

Example

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-api
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: database

  policyTypes:
  - Ingress

  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: api
    ports:
    - protocol: TCP
      port: 5432

This expresses that traffic to the selected database Pods on port 5432 should be allowed from Pods matching the API label, subject to the cluster's NetworkPolicy behavior.

⭐⭐⭐⭐⭐ 14. Why use NetworkPolicy?

Imagine a production namespace containing:

Frontend → API → Database

The database should not accept traffic from every Pod in the cluster. A NetworkPolicy can restrict database access so that only the required application Pods can communicate with it.

Security principle

Do not assume that Pods are automatically isolated from each other. Define network access according to application requirements.

⭐⭐⭐⭐ 15. Pod Security Standards

Kubernetes Pod Security Standards provide security profiles that help define which Pod security configurations are permitted. The commonly discussed levels are:
Level Purpose
Privileged Unrestricted profile intended for trusted workloads.
Baseline Prevents known privilege-escalation patterns.
Restricted Strong security requirements for hardened workloads.
For normal production workloads, aim for a restrictive security posture while validating that the application's actual requirements are compatible with it.

⭐⭐⭐⭐⭐ 16. Kubernetes Secret Security

  • Never commit Secrets directly to Git repositories.
  • Use RBAC to restrict Secret access.
  • Enable encryption at rest where appropriate.
  • Rotate credentials regularly.
  • Avoid exposing secrets in logs.
  • Use external secret-management systems when required.
  • Use short-lived credentials where possible.
Base64 is encoding, not encryption. A Secret containing base64 data should still be treated as sensitive.

⭐⭐⭐⭐⭐ 17. RBAC Troubleshooting

Scenario

A developer receives: 

Error from server (Forbidden)

Check current identity

kubectl auth whoami

Check permission

kubectl auth can-i get pods -n dev

kubectl auth can-i delete deployments -n production

Inspect RBAC objects

kubectl get role -n dev
kubectl get rolebinding -n dev

kubectl get clusterrole
kubectl get clusterrolebinding
Interview approach: First identify the user or ServiceAccount, then check the relevant Role/ClusterRole and binding, verify the namespace and requested verb/resource, and use kubectl auth can-i to confirm the effective permission.

⭐⭐⭐⭐⭐ 18. Real-Time Scenario: Developer needs Pod logs

Requirement: Developer should be able to view Pods and logs in the dev namespace. They should not be able to delete workloads.

Solution: Create a namespace-scoped Role containing only the required read permissions and bind it to the developer. 
rules:
- apiGroups: [""]
  resources:
  - pods
  - pods/log
  verbs:
  - get
  - list
  - watch

Do not add delete unless the job actually requires it.

⭐⭐⭐⭐⭐ 19. Real-Time Scenario: Application needs Kubernetes API

A controller or application running inside Kubernetes needs to read ConfigMaps. Instead of using a highly privileged ServiceAccount, create a dedicated ServiceAccount with a minimal Role and RoleBinding.
Application Pod
↓
Dedicated ServiceAccount
↓
RoleBinding
↓
Minimal Role
↓
Read ConfigMaps
This is an example of the least-privilege principle.

⭐⭐⭐⭐⭐ 20. Real-Time Scenario: Pod Compromised

Situation: An attacker compromises a web application Pod.

Security layers that reduce impact:

1. Run the container as non-root.
2. Drop unnecessary Linux capabilities.
3. Disable privilege escalation.
4. Use a read-only root filesystem where possible.
5. Give the ServiceAccount minimal RBAC permissions.
6. Restrict network access with NetworkPolicies.
7. Keep Secrets tightly controlled.
8. Use trusted and scanned container images.
Key interview point: Kubernetes security should be layered. No single control should be treated as the complete security solution.

🎯 If Interviewer Says: "How Do You Secure Kubernetes?"

"I follow a layered security approach. First, I use RBAC and the principle of least privilege so users and workloads receive only the permissions they need. For workloads, I use dedicated ServiceAccounts and avoid excessive permissions such as cluster-admin. At the container level, I prefer non-root execution, disable unnecessary privilege escalation, drop unnecessary capabilities and use a read-only root filesystem where practical. I also use NetworkPolicies to restrict unnecessary Pod-to-Pod communication and protect Secrets with RBAC and appropriate encryption controls. Finally, I use secure images, vulnerability scanning, Pod security controls, monitoring and regular credential rotation. The main goal is to reduce the attack surface and limit the blast radius if a workload or credential is compromised."
