Kubernetes Troubleshooting & Real-Time Scenarios

Interview-focused troubleshooting guide covering Pod failures, CrashLoopBackOff, ImagePullBackOff, Pending Pods, Services, Networking, DNS, ConfigMaps, Secrets, Storage, Probes, Resources, Deployments, Nodes, Ingress and real-time production scenarios.

⭐⭐⭐⭐⭐ Kubernetes Troubleshooting Mindset

In production, do not randomly change Kubernetes resources. Troubleshoot from the outside toward the application and identify the exact failing layer.

1. Check Status
↓
2. Describe Resource
↓
3. Check Events
↓
4. Check Logs
↓
5. Check Dependencies
↓
6. Fix Root Cause
↓
7. Verify Recovery
Golden interview line: "I first identify which Kubernetes layer is failing, then I use status, describe, events and logs to narrow down the root cause before making a change."

⭐⭐⭐⭐⭐ 1. First Commands to Run

kubectl get pods
kubectl get pods -o wide

kubectl get svc
kubectl get deployments

kubectl get nodes

kubectl get events --sort-by=.lastTimestamp

These commands provide the initial health picture of the cluster and workload.

⭐⭐⭐⭐⭐ 2. Describe the Problem Resource

kubectl describe pod <pod-name>

kubectl describe deployment <deployment-name>

kubectl describe service <service-name>

kubectl describe node <node-name>
The describe output is especially useful for conditions, events, scheduling failures, mounts, probes and other Kubernetes control-plane information.

⭐⭐⭐⭐⭐ 3. Check Pod Logs

kubectl logs <pod-name>

kubectl logs <pod-name> -c <container-name>

kubectl logs <pod-name> --previous

kubectl logs -f <pod-name>
If a container crashed and restarted, use: 
kubectl logs <pod-name> --previous
This is often critical for finding the error from the previous container instance.

⭐⭐⭐⭐⭐ 4. Pod is Pending

A Pending Pod has not successfully reached the running state. Common causes include insufficient resources, scheduling constraints, taints, node availability or volume-related issues.

Check

kubectl get pod <pod-name>
kubectl describe pod <pod-name>
kubectl get nodes
kubectl get events --sort-by=.lastTimestamp
Example: Pod requests: 
cpu: 4
memory: 8Gi
But available nodes cannot satisfy the request. The scheduler cannot place the Pod, so it remains Pending.

⭐⭐⭐⭐⭐ 5. CrashLoopBackOff

CrashLoopBackOff means the container repeatedly starts, crashes and Kubernetes backs off before restarting it again. It is a symptom, not the root cause.

Commands

kubectl get pod <pod-name>

kubectl describe pod <pod-name>

kubectl logs <pod-name>

kubectl logs <pod-name> --previous
Possible causes:
  • Application startup failure
  • Wrong environment variable
  • Missing Secret
  • Missing ConfigMap
  • Wrong command/entrypoint
  • Database connection failure
  • Probe configuration problem

⭐⭐⭐⭐⭐ 6. ImagePullBackOff / ErrImagePull

Kubernetes cannot pull the requested container image. 
kubectl describe pod <pod-name>

kubectl get pod <pod-name> -o yaml
Check:
  • Image name
  • Image tag
  • Registry availability
  • ImagePullSecrets
  • Registry credentials
  • Network connectivity
Example: 
image: myregistry/payment:v5
If tag v5 does not exist, the Pod cannot pull it.

⭐⭐⭐⭐⭐ 7. Pod stuck in ContainerCreating

ContainerCreating indicates Kubernetes is still preparing the container. The exact cause is shown through Pod events and description. 
kubectl describe pod <pod-name>

kubectl get events --sort-by=.lastTimestamp
Common causes:
  • Volume mount problems
  • Secret or ConfigMap mount issues
  • Container runtime problems
  • Network setup problems
  • Image pulling

⭐⭐⭐⭐ 8. Pod is Running but application is not working

Running only means the container process is running. It does not guarantee that the application is healthy or reachable.
Pod Running
≠
Application Healthy 
kubectl logs <pod-name>

kubectl describe pod <pod-name>

kubectl get svc

kubectl get endpoints

kubectl get ingress

⭐⭐⭐⭐⭐ 9. Deployment rollout is stuck

kubectl get deployment

kubectl rollout status deployment <deployment-name>

kubectl rollout history deployment <deployment-name>

kubectl describe deployment <deployment-name>
Check whether new Pods are failing because of:
  • Bad image
  • Failed probes
  • Insufficient resources
  • Configuration errors
  • Scheduling problems

⭐⭐⭐⭐⭐ 10. Rollback a failed Deployment

kubectl rollout history deployment myapp

kubectl rollout undo deployment myapp

kubectl rollout status deployment myapp
Real-time scenario: A new application version is deployed and starts returning errors. If the previous version was healthy: 
kubectl rollout undo deployment myapp
Then investigate the new version separately.

⭐⭐⭐⭐⭐ 11. Service not reaching Pods

The Service selects Pods using labels. If the selector does not match Pod labels, the Service can have no backend endpoints. 
kubectl get svc myapp-service -o yaml

kubectl get pods --show-labels

kubectl get endpoints myapp-service
Service selector: 
selector:
  app: frontend
Pod label: 
labels:
  app: backend
No match → no endpoints.

⭐⭐⭐⭐⭐ 12. Service has no endpoints

kubectl get endpoints <service-name>

kubectl get endpointslices

kubectl get pods --show-labels

kubectl describe service <service-name>
If the Service has no endpoints, verify the selector, Pod labels, Pod readiness and namespace.

⭐⭐⭐⭐⭐ 13. Service connection refused

Check the complete path: 
Client
 ↓
Service
 ↓
TargetPort
 ↓
ContainerPort
 ↓
Application Process
Verify: 
kubectl get svc <service-name> -o yaml

kubectl get pod <pod-name> -o yaml

kubectl logs <pod-name>
A common mistake is configuring the Service targetPort differently from the port where the application is actually listening.

⭐⭐⭐⭐⭐ 14. Kubernetes DNS troubleshooting

kubectl get svc

kubectl get pods -n kube-system

kubectl exec -it <pod-name> -- nslookup <service-name>
If: 
backend-service
is in the same namespace, the application can normally resolve it using the Service DNS name. For cross-namespace communication: 
backend-service.backend.svc.cluster.local

⭐⭐⭐⭐⭐ 15. Pod-to-Pod communication fails

kubectl get pods -o wide

kubectl exec -it <pod-name> -- ping <pod-ip>

kubectl exec -it <pod-name> -- curl http://<service-name>:<port>
Check:
  • Pod IPs
  • Services
  • NetworkPolicies
  • DNS
  • Container ports
  • Application listening address

⭐⭐⭐⭐ 16. NetworkPolicy blocking traffic

NetworkPolicies can restrict which Pods are allowed to communicate with other Pods. 
kubectl get networkpolicy

kubectl describe networkpolicy <policy-name>
When troubleshooting networking, do not forget NetworkPolicies. A Pod and Service can appear healthy while traffic is intentionally blocked by policy.

⭐⭐⭐⭐⭐ 17. ConfigMap not found

kubectl get configmap -n <namespace>

kubectl describe pod <pod-name>

kubectl get configmap <configmap-name> -n <namespace>
ConfigMaps are namespace-scoped. Verify the name and namespace.

⭐⭐⭐⭐⭐ 18. Secret not found

kubectl get secrets -n <namespace>

kubectl describe pod <pod-name>

kubectl get secret <secret-name> -n <namespace>
Check:
  • Secret name
  • Namespace
  • Referenced key
  • Workload configuration

⭐⭐⭐⭐⭐ 19. Liveness Probe failure

A liveness probe determines whether the container is still alive. Repeated liveness failure can cause Kubernetes to restart the container. 
kubectl describe pod <pod-name>
Look for events such as probe failures.
Example: Application starts slowly but liveness probe checks too early. The container may repeatedly restart even though the application would eventually become healthy. Use appropriate startup/readiness/liveness probe configuration.

⭐⭐⭐⭐⭐ 20. Readiness Probe failure

Readiness determines whether the Pod should receive traffic. A failed readiness probe normally removes the Pod from Service endpoints while allowing the container to continue running.
Readiness Failure
↓
Pod remains running
↓
Removed from Service traffic
↓
Application recovers
↓
Traffic resumes

⭐⭐⭐⭐ 21. Startup Probe

Startup probes are useful for slow-starting applications. They give the application time to start before liveness/readiness checks become active according to the configured probe behavior.
Examples include:
  • Large Java applications
  • Applications with long initialization
  • Services that load large models or configuration

⭐⭐⭐⭐⭐ 22. OOMKilled

OOMKilled means the container was terminated because it exceeded an available memory limit or otherwise encountered memory pressure leading to an out-of-memory termination. 
kubectl describe pod <pod-name>

kubectl get pod <pod-name> -o yaml

kubectl top pod <pod-name>
If a container has: 
resources:
  limits:
    memory: 256Mi
and the application needs significantly more memory, it may be terminated.

⭐⭐⭐⭐⭐ 23. CPU throttling / high CPU

kubectl top pods

kubectl top nodes

kubectl describe pod <pod-name>
Check:
  • CPU requests
  • CPU limits
  • Application behavior
  • Traffic increase
  • Autoscaling

⭐⭐⭐⭐⭐ 24. Node NotReady

kubectl get nodes

kubectl describe node <node-name>

kubectl get events --sort-by=.lastTimestamp
Possible causes:
  • Kubelet failure
  • Node resource pressure
  • Network problems
  • Disk pressure
  • Container runtime issues
  • Cloud infrastructure failure

⭐⭐⭐⭐⭐ 25. Node memory or disk pressure

kubectl describe node <node-name>
Look for conditions such as: 
MemoryPressure
DiskPressure
PIDPressure
Ready
If a node has insufficient disk space, image pulls, container creation or other workloads may start failing. Investigate node-level disk usage and container runtime storage.

⭐⭐⭐⭐⭐ 26. PVC stuck in Pending

kubectl get pvc

kubectl describe pvc <pvc-name>

kubectl get storageclass

kubectl get pv
Check whether the requested StorageClass exists and whether a suitable volume can be dynamically provisioned.

⭐⭐⭐⭐⭐ 27. Pod cannot mount volume

kubectl describe pod <pod-name>

kubectl describe pvc <pvc-name>

kubectl get pv

kubectl get events --sort-by=.lastTimestamp
Common causes:
  • PVC not bound
  • Wrong volume name
  • StorageClass issue
  • Access mode mismatch
  • CSI driver problem

⭐⭐⭐⭐⭐ 28. Forbidden error

Example: 
Error from server (Forbidden)
This commonly indicates an RBAC authorization problem. Check: 
kubectl auth can-i get pods

kubectl auth can-i create deployments

kubectl get role
kubectl get rolebinding

kubectl get clusterrole
kubectl get clusterrolebinding
The key question is: "Does this identity have permission to perform this action on this resource in this namespace?"

⭐⭐⭐⭐⭐ 29. Ingress returns 404 / 502

kubectl get ingress

kubectl describe ingress <ingress-name>

kubectl get svc

kubectl get endpoints

kubectl get pods
404: Often check host/path/routing configuration.

502/503: Often check backend Service, endpoints, application port and Pod health.

⭐⭐⭐⭐ 30. CoreDNS troubleshooting

kubectl get pods -n kube-system

kubectl get svc -n kube-system

kubectl logs -n kube-system -l k8s-app=kube-dns
If applications cannot resolve Service names, investigate CoreDNS Pods, Service configuration and network connectivity.

⭐⭐⭐⭐⭐ 31. Why are Kubernetes Events important?

Events often provide the fastest clue about scheduling, image pulls, mount failures, probe failures and other resource-level problems. 
kubectl get events --sort-by=.lastTimestamp

kubectl describe pod <pod-name>
When troubleshooting, I usually check Events alongside logs because Events describe what Kubernetes itself observed while logs show what the application process reported.

Do not immediately restart everything. Identify the first broken layer.

🔥 ⭐⭐⭐⭐⭐ 33. Scenario — Pods are running but users get errors

Running Pods do not necessarily mean healthy applications. 
kubectl get pods
kubectl get endpoints
kubectl get svc
kubectl logs <pod-name>
kubectl describe pod <pod-name>
Check:
  • Readiness
  • Application logs
  • Service routing
  • Backend dependencies
  • Database connectivity
  • Ingress

🔥 ⭐⭐⭐⭐⭐ 34. Scenario — New deployment caused outage

First stabilize the service. 
kubectl rollout status deployment myapp

kubectl rollout history deployment myapp

kubectl rollout undo deployment myapp
After recovery:
  • Inspect application logs.
  • Compare old and new configuration.
  • Check image version.
  • Check probes.
  • Check resource changes.
  • Reproduce the issue safely.

  • Database Service name

🎯 If Interviewer Says: "How do you troubleshoot Kubernetes?"

"I follow a systematic approach rather than randomly changing resources. First, I identify the affected resource and check its status using kubectl get. Then I use kubectl describe to inspect conditions and Events. For application-level problems, I check container logs and previous logs if the container restarted. If the problem involves networking, I check Services, endpoints, DNS, NetworkPolicies and Ingress. For scheduling issues, I check nodes, resource requests, taints, tolerations and affinity. For storage problems, I check PVs, PVCs and StorageClasses. For deployment failures, I check rollout status and history and, if necessary, rollback to the last known healthy version. Finally, I verify that the application is healthy and document the root cause and preventive action. My goal is not just to restart the Pod, but to identify and fix the actual root cause."

🚀 60-Second Revision

Pending → Scheduling / resources / constraints

CrashLoopBackOff → Container repeatedly crashing

ImagePullBackOff → Image cannot be pulled

OOMKilled → Memory-related termination

No Endpoints → Selector / labels / readiness

Readiness Failure → Pod removed from traffic

Liveness Failure → Container may be restarted

PVC Pending → Storage provisioning/binding issue

Forbidden → RBAC authorization issue

Node NotReady → Investigate kubelet/node health

Golden Flow → get → describe → events → logs → dependencies → fix → verify
