EKS Security

High-priority Amazon EKS security concepts including IAM, RBAC, Pod security, network security, Secrets and encryption.

⭐⭐⭐⭐⭐ 2. IAM vs Kubernetes RBAC

IAM Kubernetes RBAC
AWS-level identity and permissions. Kubernetes-level authorization.
Controls access to AWS resources. Controls access to Kubernetes resources.
Uses IAM users, roles and policies. Uses Roles, ClusterRoles and bindings.
Interview Answer:
"IAM controls access to AWS resources and EKS access, while Kubernetes RBAC controls what an authenticated identity can do inside the Kubernetes API."

⭐⭐⭐⭐⭐ 3. IAM Role for EKS

EKS commonly uses IAM roles for AWS service and workload access. Using roles avoids embedding long-lived AWS access keys inside applications.

IAM Role
↓
Temporary Credentials
↓
AWS API
↓
AWS Resource

⭐⭐⭐⭐⭐ 4. EKS Access Control

Access to an EKS cluster should be explicitly granted to the identities that need it.

Best Practice:
Give users and automation only the permissions they require. Avoid broad administrative permissions unless genuinely necessary.

⭐⭐⭐⭐⭐ 5. Kubernetes RBAC

RBAC controls which Kubernetes API actions an identity can perform on specific resources.

User / Service Account
↓
Role / ClusterRole
↓
RoleBinding / ClusterRoleBinding
↓
Kubernetes Resources

⭐⭐⭐⭐⭐ 6. Role vs ClusterRole

Role ClusterRole
Namespace-scoped. Can define permissions at cluster scope.
Used for resources within a namespace. Can be used for cluster-scoped resources and can also be bound into namespaces.

⭐⭐⭐⭐⭐ 7. RoleBinding vs ClusterRoleBinding

RoleBinding:
Grants permissions within a namespace.

ClusterRoleBinding:
Grants a ClusterRole across the cluster scope represented by the binding.

⭐⭐⭐⭐⭐ 8. Kubernetes Service Accounts

Service Accounts provide identities for workloads running inside Kubernetes.

Pod
↓
Service Account
↓
Identity
↓
Authorized API / AWS Access
Important:
Do not give every application broad permissions. Create dedicated identities with only the permissions required.

⭐⭐⭐⭐⭐ 9. EKS Pod Access to AWS Services

Applications running in EKS may need to access services such as S3, DynamoDB or Secrets Manager.

Pod
↓
Kubernetes Service Account
↓
IAM Role
↓
AWS API
↓
AWS Service

A common approach is to associate an IAM role with a Kubernetes workload identity mechanism so the application receives controlled AWS permissions without storing static access keys in the Pod.

⭐⭐⭐⭐⭐ 10. Kubernetes Secrets

Kubernetes Secrets are designed to hold sensitive configuration data such as passwords, tokens and keys. 

kubectl get secrets -A

kubectl describe secret <secret-name>
Important:
Kubernetes Secrets should not automatically be treated as a complete secret-management solution. Protect access to them and consider dedicated secret-management services for sensitive production workloads.

⭐⭐⭐⭐⭐ 11. Encryption of Secrets

EKS can integrate with AWS encryption capabilities to protect Kubernetes data at rest.

Kubernetes Secret
↓
Encryption
↓
Encrypted Data
↓
Persistent Storage

⭐⭐⭐⭐⭐ 12. Security Groups

Security Groups provide stateful network access control for AWS resources and network interfaces.

Example:
Allow application traffic only from the expected load balancer or trusted source instead of opening application ports to the entire Internet.

⭐⭐⭐⭐⭐ 13. Network Policies

NetworkPolicy can control allowed network communication between Pods and other endpoints, depending on the networking implementation and policy support.

Frontend Pod
↓
NetworkPolicy
↓
Allowed → Backend Pod
Denied → Untrusted Pod

⭐⭐⭐⭐⭐ 14. Security Groups vs NetworkPolicy

Security Group NetworkPolicy
AWS networking layer. Kubernetes networking layer.
Controls traffic to AWS network interfaces/resources. Controls Pod-level traffic according to supported implementation.
Managed through AWS. Managed through Kubernetes resources.

⭐⭐⭐⭐⭐ 15. Private EKS Cluster Endpoint

EKS cluster endpoint access can be configured to control how the Kubernetes API endpoint is reached.

A private endpoint can reduce exposure of the Kubernetes API to public networks. Access then needs appropriate connectivity from the environments that administer the cluster.

⭐⭐⭐⭐⭐ 16. EKS Security Best Practices

  • Follow least-privilege IAM.
  • Use dedicated IAM roles for workloads.
  • Use Kubernetes RBAC carefully.
  • Avoid unnecessary cluster-admin permissions.
  • Use private subnets where appropriate.
  • Restrict network access with Security Groups.
  • Use NetworkPolicies where appropriate.
  • Protect Kubernetes Secrets.
  • Encrypt sensitive data at rest and in transit.
  • Regularly update Kubernetes and node components.
  • Enable appropriate logging and monitoring.
  • Scan container images for vulnerabilities.

⭐⭐⭐⭐⭐ 17. Scenario: Developer Needs Read-Only Access

Approach:

Create or use an identity with read-only permissions and grant access only to the required namespaces/resources. Do not give the developer cluster-admin access simply because it is easier.

⭐⭐⭐⭐⭐ 18. Scenario: Pod Needs S3 Access

Interview Answer:
"I would create a dedicated workload identity and associate it with an IAM role containing only the required S3 permissions. I would avoid storing AWS access keys directly inside the Pod."

⭐⭐⭐⭐⭐ 19. Scenario: Unauthorized Kubernetes Access

Check

  • Which identity is making the request?
  • Does the identity have EKS access?
  • What Kubernetes RBAC permissions exist?
  • Is the resource namespace correct?
  • Is the requested verb allowed?
kubectl auth can-i get pods

kubectl auth can-i create deployments

kubectl auth can-i delete pods

⭐⭐⭐⭐⭐ 20. Scenario: Secure a Production EKS Cluster

Interview Answer:

"I would use least-privilege IAM and Kubernetes RBAC, dedicated workload identities, private networking where appropriate, Security Groups and NetworkPolicies, protected Secrets, encryption, regular patching, image scanning, logging and continuous monitoring."
