⭐⭐⭐⭐⭐ 3. Scenario: Pod Stuck in Pending

VERY COMMON

A Pending Pod means Kubernetes has not successfully scheduled or started it yet.

Step 1 — Check Pod

kubectl get pod <pod-name>

Step 2 — Describe Pod

kubectl describe pod <pod-name>

Check

  • Insufficient CPU or memory.
  • Node selector mismatch.
  • Affinity / anti-affinity.
  • Taints and tolerations.
  • Persistent volume constraints.
  • Scheduling events.
Interview Answer:
"I would first describe the Pod and inspect the Events section. Then I would check node capacity, taints, tolerations, selectors, affinity rules and storage constraints."

⭐⭐⭐⭐⭐ 4. Scenario: Pod in CrashLoopBackOff

VERY COMMON

CrashLoopBackOff means a container is repeatedly starting and crashing, with Kubernetes applying increasing restart delays.

Commands

kubectl get pod <pod-name>

kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>

Possible Causes

  • Application error.
  • Incorrect environment variables.
  • Missing configuration.
  • Missing Secret or ConfigMap.
  • Wrong command or arguments.
  • Dependency unavailable.
  • Health probe causing restarts.

⭐⭐⭐⭐⭐ 5. Scenario: Pod in ImagePullBackOff

The node cannot successfully pull the container image.

Check

kubectl describe pod <pod-name>

Possible Causes

  • Incorrect image name.
  • Incorrect image tag.
  • Private registry authentication problem.
  • Registry unavailable.
  • Network connectivity problem.
  • Insufficient permissions.
Interview Approach:
"I would inspect Pod events first. I would verify the image repository and tag, registry authentication, node connectivity and required permissions."

⭐⭐⭐⭐⭐ 6. Scenario: Node is NotReady

kubectl get nodes

kubectl describe node <node-name>

Check

  • Node Conditions.
  • MemoryPressure.
  • DiskPressure.
  • PIDPressure.
  • NetworkUnavailable.
  • kubelet health.
  • Node connectivity to the control plane.
  • Instance health.
Interview Answer:
"I would check the node conditions and Events first. Then I would investigate kubelet health, resource pressure, networking, instance health and connectivity with the EKS control plane."

⭐⭐⭐⭐⭐ 7. Scenario: High CPU or Memory

kubectl top nodes

kubectl top pods -A

If Metrics Server or another metrics provider is available, these commands can show resource utilization.

Investigate

  • Which Pod consumes the resources?
  • Are resource requests configured?
  • Are resource limits appropriate?
  • Is HPA configured?
  • Does the node have enough capacity?
  • Should the node group scale?

⭐⭐⭐⭐⭐ 8. Scenario: Service Not Reachable

Client
↓
Service
↓
Endpoints
↓
Pods

Check

kubectl get svc

kubectl describe svc <service-name>

kubectl get endpoints <service-name>

kubectl get endpointslices

kubectl get pods --show-labels

Possible Causes

  • Incorrect Service selector.
  • No healthy Pods.
  • Incorrect targetPort.
  • Application not listening on expected port.
  • NetworkPolicy blocking traffic.
  • DNS problem.

⭐⭐⭐⭐⭐ 9. Scenario: DNS Not Working

Check CoreDNS

kubectl get pods -n kube-system

Check DNS Service

kubectl get svc -n kube-system

Test From a Pod

kubectl exec -it <pod-name> -- nslookup kubernetes.default

Investigate

  • CoreDNS Pods.
  • CoreDNS logs.
  • Service configuration.
  • Pod DNS configuration.
  • Network connectivity.

  • Pod networking.

  • NAT Gateway.
  • Route tables.
  • Security Groups.
  • NACLs where applicable.
  • DNS.
  • VPC CNI health.

⭐⭐⭐⭐⭐ 11. Scenario: Pods Cannot Communicate

Check

  1. Are both Pods Running?
  2. Can you resolve the Service DNS?
  3. Does the Service have endpoints?
  4. Is the correct port being used?
  5. Are NetworkPolicies blocking traffic?
  6. Is the CNI functioning correctly?
  7. Are AWS networking controls involved?
kubectl get pods -o wide

kubectl get svc

kubectl get endpoints

kubectl get networkpolicy -A

⭐⭐⭐⭐⭐ 12. Scenario: Ingress / ALB Not Working

Check

kubectl get ingress -A

kubectl describe ingress <ingress-name>

kubectl get pods -n kube-system

Possible Causes

  • AWS Load Balancer Controller problem.
  • Incorrect Ingress configuration.
  • Wrong target type.
  • Subnet tagging/configuration issue.
  • Security Group issue.
  • IAM permissions issue.
  • Incorrect Service configuration.

⭐⭐⭐⭐⭐ 13. Scenario: EKS Node Cannot Join Cluster

Possible Causes

  • Incorrect node IAM permissions.
  • Incorrect cluster configuration.
  • Network connectivity issue.
  • Security Group rules.
  • Subnet or routing issue.
  • Incorrect bootstrap configuration.
  • Instance or launch configuration issue.

Investigate

aws eks describe-cluster --name <cluster-name>

kubectl get nodes

kubectl get events -A
Interview Approach:
"I would verify the node IAM role, subnet and security-group configuration, cluster endpoint connectivity and node bootstrap logs."

⭐⭐⭐⭐⭐ 14. Scenario: Pod IP Exhaustion

A VPC CNI-based EKS cluster can experience IP capacity constraints when the subnet or node networking capacity is exhausted.

Check

  • Available subnet IP addresses.
  • Number of Pods per node.
  • Node instance networking limits.
  • VPC CNI status and logs.
  • Cluster scaling requirements.

⭐⭐⭐⭐⭐ 15. Scenario: Deployment Has No Available Pods

kubectl get deployment

kubectl describe deployment <deployment-name>

kubectl get replicaset

kubectl get pods

Check

  • Deployment desired replicas.
  • ReplicaSet status.
  • Pod scheduling.
  • Container image.
  • Configuration.
  • Readiness and liveness probes.

⭐⭐⭐⭐⭐ 16. Scenario: Readiness Probe Failing

A failed readiness probe means Kubernetes does not consider the container ready to receive Service traffic.

Check

kubectl describe pod <pod-name>

kubectl logs <pod-name>

Possible Causes

  • Wrong health-check path.
  • Wrong port.
  • Application startup is slow.
  • Application dependency is unavailable.
  • Incorrect probe configuration.

⭐⭐⭐⭐⭐ 17. Scenario: Liveness Probe Causing Restarts

A liveness probe determines whether the container should be restarted. If it repeatedly fails, Kubernetes may restart the container. Check the probe path, port, timing, initial delay and application startup behavior before changing the configuration.

⭐⭐⭐⭐⭐ 18. Scenario: Cannot Access EKS Cluster

Check

aws sts get-caller-identity

aws eks describe-cluster \
--name <cluster-name>

kubectl cluster-info

kubectl get nodes

Possible Causes

  • Wrong AWS identity.
  • Incorrect kubeconfig.
  • Insufficient EKS access permissions.
  • Cluster endpoint access configuration.
  • Network connectivity issue.
  • Expired or invalid authentication.

⭐⭐⭐⭐⭐ 19. Scenario: Check EKS Control Plane Health

EKS manages the Kubernetes control-plane infrastructure, so troubleshooting focuses on API availability, cluster status, access configuration and Kubernetes resources rather than logging into control-plane servers. 

aws eks describe-cluster \
--name <cluster-name>

kubectl cluster-info

kubectl get nodes
