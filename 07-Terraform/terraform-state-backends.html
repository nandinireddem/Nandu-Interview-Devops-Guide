Terraform State & Backends

Interview-focused guide covering Terraform state, remote backends, S3 state, state locking, drift, state commands, collaboration, state security, recovery and real-time production scenarios.

⭐⭐⭐⭐⭐ Core Concept

Terraform state is one of the most important concepts in Terraform. It allows Terraform to keep track of infrastructure resources that it manages and compare the desired configuration with the current managed state.

Terraform Configuration
+
Terraform State
+
Real Infrastructure
↓
terraform plan
↓
Required Changes
Real-time example: A Terraform project creates an AWS VPC and EC2 instance. Later, a developer changes the Terraform code to increase the EC2 instance size. Terraform uses its configuration and state information to determine what resource needs to change rather than blindly creating another instance.

⭐⭐⭐⭐⭐ 1. What is Terraform State?

Terraform state is a record of infrastructure resources managed by Terraform. The default local state file is usually: terraform.tfstate Terraform uses state information to map configuration resources to real infrastructure objects.
Interview answer: "Terraform state stores information about the infrastructure managed by Terraform. Terraform uses it to track resource identities and attributes and to determine what changes are required during plan and apply."

⭐⭐⭐⭐⭐ 2. Why does Terraform need State?

Terraform configuration describes the desired infrastructure, while state helps Terraform understand the resources it is already managing. Without reliable state, Terraform cannot safely perform normal incremental management of the infrastructure.
Desired Configuration
↓
Terraform State
↓
Real Infrastructure
↓
Terraform determines difference

⭐⭐⭐⭐⭐ 3. What is terraform.tfstate?

terraform.tfstate is the default local state file created when Terraform manages resources using the local backend. It contains Terraform's recorded representation of managed resources and their attributes.
Never treat the state file like a normal source-code file. Depending on the infrastructure being managed, state can contain sensitive information. Do not commit it to a public Git repository.

⭐⭐⭐⭐⭐ 4. Local State vs Remote State

Local State Remote State
Stored on the local machine. Stored in a shared remote backend.
Simple for learning and small experiments. Better suited for teams.
Harder to collaborate safely. Centralized access.
Backup is your responsibility. Backend can provide durability and operational controls.
Concurrency is difficult. Can support state locking depending on backend.

⭐⭐⭐⭐⭐ 5. What is a Terraform Backend?

A Terraform backend determines where Terraform stores state and how state-related operations are handled. Terraform supports local state by default and can use remote backends for team environments.
Production example: A DevOps team has five engineers and a CI/CD pipeline. If every engineer stores a separate local state file, Terraform can lose the shared view of infrastructure. A remote backend provides a centralized state location.

⭐⭐⭐⭐⭐ 6. Why use Remote State?

  • Centralized state management.
  • Team collaboration.
  • Better backup and durability options.
  • CI/CD systems can access the same state.
  • State locking may prevent concurrent operations.
  • Access can be controlled using IAM or equivalent permissions.
For production Terraform, remote state is generally preferred over keeping state only on an engineer's laptop.

⭐⭐⭐⭐⭐ 7. AWS S3 Backend

An S3 backend can store Terraform state in an Amazon S3 bucket. A typical design uses:

S3 → state storage
Versioning → recovery from accidental state changes
IAM → access control
Encryption → state protection
Locking → prevent conflicting concurrent operations, using the locking mechanism supported by the Terraform/backend setup

Example

terraform {
  backend "s3" {
    bucket = "company-terraform-state"
    key    = "prod/network/terraform.tfstate"
    region = "ap-south-1"
  }
}

⭐⭐⭐⭐⭐ 8. Why S3 Versioning?

S3 versioning keeps previous versions of objects. For Terraform state, this can help recover from accidental state replacement or corruption when the organization's backend design uses versioning.
Example: A bad state update occurs. If bucket versioning is enabled, the team can investigate previous object versions and recover the state through the organization's approved recovery procedure.

⭐⭐⭐⭐⭐ 9. What is State Locking?

State locking prevents multiple Terraform operations from modifying the same state concurrently when the backend supports locking.
Engineer A
↓
Terraform Operation
↓
State Lock
↓
State Updated
↓
Lock Released

Engineer B waits or is prevented from conflicting operation
Without proper locking, two engineers or CI jobs could attempt conflicting state operations at the same time.

⭐⭐⭐⭐⭐ 10. What happens if two engineers run Terraform simultaneously?

With a properly configured locking-capable remote backend, Terraform can prevent conflicting state operations by acquiring a state lock. The second operation generally waits or fails instead of modifying the same state concurrently.
Never solve a locking problem by blindly deleting or manipulating locking information. First identify the running Terraform operation and verify that no legitimate process is using the state.

⭐⭐⭐⭐⭐ 11. What is State Drift?

Drift occurs when the actual infrastructure changes outside Terraform and no longer matches the configuration and Terraform's managed state expectations.
Example: Terraform creates: 
EC2 instance
type = t3.micro
Someone manually changes the instance to: 
t3.large
Now the infrastructure has changed outside the Terraform workflow. Running: 
terraform plan
can reveal differences that Terraform wants to reconcile.

⭐⭐⭐⭐⭐ 12. How do you detect Drift?

The normal first step is to run: 
terraform plan
Terraform refreshes relevant information from the provider and compares it with the configuration and state to determine proposed changes.
In a production pipeline, drift detection can be performed periodically so the team knows when infrastructure has been changed outside the approved IaC workflow.

⭐⭐⭐⭐⭐ 13. What is terraform state list?

terraform state list
Lists resource addresses currently recorded in Terraform state.

Example output

aws_vpc.main
aws_subnet.public
aws_instance.app

⭐⭐⭐⭐⭐ 14. What is terraform state show?

terraform state show aws_instance.app
Displays detailed state information for a specific resource address.
Useful when troubleshooting what Terraform currently knows about a specific resource.

⭐⭐⭐⭐⭐ 15. What is terraform state rm?

terraform state rm aws_instance.app
Removes a resource address from Terraform state without destroying the actual remote resource.
This is an advanced state operation. Removing a resource from state does not mean Terraform deletes the real infrastructure. Use it only when you understand the desired ownership and recovery impact.

⭐⭐⭐⭐⭐ 16. What is terraform import?

Terraform import associates an existing infrastructure resource with a Terraform resource address so that Terraform can begin managing it.

Example

terraform import aws_instance.app i-0123456789abcdef0
A company has an EC2 instance that was created manually. Instead of deleting it and rebuilding it, the DevOps engineer can import the existing resource and then create matching Terraform configuration.

⭐⭐⭐⭐⭐ 17. What happens if terraform.tfstate is deleted?

If local state is deleted, Terraform loses its local record of the resources it was managing. The real infrastructure may still exist, but Terraform no longer has the expected state mapping.
Do not immediately run terraform apply after losing state. Depending on the configuration and provider, Terraform may propose creating resources that already exist. First recover the correct state or reconstruct/import the resources using a controlled procedure.

⭐⭐⭐⭐⭐ 18. How do you recover lost Terraform State?

  1. Stop automated Terraform runs.
  2. Identify the affected backend and workspace.
  3. Check backend backups or object versions.
  4. Restore the correct state if available.
  5. Verify resource mappings.
  6. Run terraform plan.
  7. Review all proposed changes carefully.
For an S3-backed state design, bucket versioning can provide an important recovery mechanism for previous state object versions.

⭐⭐⭐⭐⭐ 19. State Security

Terraform state can contain sensitive infrastructure information and sometimes sensitive values. Therefore state should be protected like other sensitive infrastructure data.
  • Use a private backend.
  • Restrict access using IAM/RBAC.
  • Enable encryption where appropriate.
  • Enable state-storage versioning when supported and required.
  • Audit access.
  • Do not commit state files to Git.
  • Do not expose state files publicly.
  • Use separate state for appropriate environments.

⭐⭐⭐⭐⭐ 20. Should terraform.tfstate be committed to Git?

Normally, no. Terraform state should generally be stored in an appropriate backend rather than committed to a source-code repository.

.gitignore

*.tfstate
*.tfstate.*
.terraform/
Ignoring state in Git is not a replacement for secure remote state management. The remote backend itself must also be properly protected.

⭐⭐⭐⭐⭐ 21. What is .terraform directory?

The .terraform directory contains Terraform working directory data such as downloaded provider plugins and other initialization-related files. It is not the Terraform state itself. 
.terraform/
Do not confuse:

.terraform/ → working directory data
terraform.tfstate → Terraform state
.terraform.lock.hcl → provider dependency selections/checksums

⭐⭐⭐⭐⭐ 22. terraform state mv

terraform state mv moves a resource address in Terraform state. It is useful when refactoring configuration without wanting Terraform to interpret the resource as a completely new object. 
terraform state mv \
  aws_instance.old \
  aws_instance.app
This can be useful when renaming resources or reorganizing resources into modules, provided the state operation matches the intended configuration refactor.

⭐⭐⭐⭐⭐ 23. State and Modules

When resources are managed inside modules, Terraform state records resource addresses that include the module path. 
module.network.aws_vpc.main

module.compute.aws_instance.app
This allows Terraform to distinguish resources belonging to different module instances.

⭐⭐⭐⭐⭐ 24. Separate State for Dev, QA and Production

Production environments should be isolated from development environments through an appropriate state architecture. One common approach is using separate state files/backend keys for different environments. 
prod/
  network/terraform.tfstate

qa/
  network/terraform.tfstate

dev/
  network/terraform.tfstate
This reduces the risk of a development operation accidentally targeting production state. The exact environment architecture should match the organization's Terraform design.

⭐⭐⭐⭐⭐ 25. Terraform Workspaces

Terraform workspaces allow multiple state instances to be associated with one Terraform configuration. They can be useful for certain environment or workflow designs. 
terraform workspace list

terraform workspace new dev

terraform workspace select dev

terraform workspace show
Workspaces are not automatically a complete security boundary. For critical production environments, separate state/backend architecture is often easier to reason about and control.

⭐⭐⭐⭐⭐ 26. Remote State Data Source

One Terraform configuration can consume outputs from another Terraform-managed state using the terraform_remote_state data source. 
data "terraform_remote_state" "network" {
  backend = "s3"

  config = {
    bucket = "company-terraform-state"
    key    = "prod/network/terraform.tfstate"
    region = "ap-south-1"
  }
}
Example: The networking stack creates a VPC. The application stack consumes the VPC ID from the networking stack's outputs.

⭐⭐⭐⭐⭐ 27. State Refresh Concept

Terraform obtains current information from the provider during normal planning and other operations so that it can evaluate differences between configuration, recorded state and real infrastructure.
Modern Terraform workflows should generally use normal plan/apply behavior rather than relying on the old standalone terraform refresh workflow.

⭐⭐⭐⭐⭐ 28. State Locking Failure

Problem: Terraform reports that it cannot acquire the state lock.

Possible causes:
  • Another Terraform operation is currently running.
  • A previous operation terminated unexpectedly.
  • Backend locking information needs investigation.
  • CI/CD has another active Terraform job.
First verify whether another Terraform operation is actually running. Do not force-unlock state blindly. If the lock is genuinely stale, follow the backend and Terraform recovery procedure carefully.

⭐⭐⭐⭐⭐ 31. Real-Time Scenario: Terraform State Lost

Situation: The local laptop containing terraform.tfstate is lost.

If the project used only local state, the team has lost its local Terraform management record. If the project used a properly configured remote backend, Terraform state remains available through the backend.
This is one of the main reasons production teams use remote state instead of keeping the only state copy on an engineer's machine.

⭐⭐⭐⭐⭐ 32. Real-Time Scenario: Two CI Jobs Run Together

Situation: Two GitHub Actions workflows attempt: 
terraform apply
against the same infrastructure.
A properly configured locking-capable backend prevents conflicting state operations. The pipeline should also be designed so that production Terraform applies are serialized and protected by appropriate approval and concurrency controls.

⭐⭐⭐⭐⭐ 33. State Best Practices

  • Use remote state for team environments.
  • Protect state with strong access controls.
  • Enable encryption where appropriate.
  • Use state versioning/recovery mechanisms.
  • Use state locking when supported.
  • Separate production state from non-production state.
  • Never commit state to public Git repositories.
  • Do not manually edit the state JSON.
  • Use Terraform state commands carefully.
  • Review plan output before production apply.
  • Control CI/CD access to production state.
  • Monitor and audit infrastructure changes.

⭐⭐⭐⭐⭐ 34. Important State Commands

# List resources
terraform state list

# Show a resource
terraform state show aws_instance.app

# Move resource address
terraform state mv aws_instance.old aws_instance.app

# Remove resource from state
terraform state rm aws_instance.app

# Import existing resource
terraform import aws_instance.app i-0123456789abcdef0

# Inspect current plan
terraform plan

# Show state
terraform show
State commands can have significant consequences. Always understand the desired state ownership before using state mv or state rm.

"Terraform state is the record Terraform uses to track the infrastructure resources it manages. It helps Terraform compare the desired configuration with the resources it knows about and determine what changes are required. For local learning, Terraform can store state in terraform.tfstate.
