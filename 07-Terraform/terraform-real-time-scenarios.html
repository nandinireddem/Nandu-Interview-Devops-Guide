⭐⭐⭐⭐⭐ 1. Terraform says Resource Already Exists

Scenario: An AWS S3 bucket was manually created in AWS. Later, you add the same bucket to Terraform. When you run: 
terraform apply
Terraform reports that the resource already exists.

Why?

Terraform does not know that the existing AWS resource should be managed by this Terraform configuration because it is not currently represented in Terraform state.

Solution

terraform import aws_s3_bucket.app existing-bucket-name
Then: 
terraform plan
Interview answer: "I would import the existing resource into Terraform state rather than trying to recreate it. Then I would run terraform plan and align the Terraform configuration with the actual infrastructure."

⭐⭐⭐⭐⭐ 2. Infrastructure was changed manually

A developer manually changes an EC2 instance type from: 
t3.micro
to: 
t3.medium
But the Terraform configuration still contains: 
instance_type = "t3.micro"

What happens?

Terraform refreshes its knowledge of infrastructure and compares the actual infrastructure with the desired configuration. The plan may show a change required to return the instance to the configuration defined in Terraform. 
terraform plan
This is an example of configuration drift.

⭐⭐⭐⭐⭐ 3. What is Terraform Drift?

Drift occurs when the real infrastructure changes outside Terraform and becomes different from what Terraform configuration and state expect.
Terraform Configuration
↓
Desired State
≠
Actual AWS Infrastructure
↓
Drift

How do you detect it?

terraform plan
Real-time example: Someone manually changes a security group rule in AWS Console. Terraform detects the difference during planning and may propose changing the infrastructure back to the desired configuration.

⭐⭐⭐⭐⭐ 4. Terraform Apply Failed Halfway

Suppose Terraform is creating:
  • VPC
  • Subnets
  • Security Groups
  • EC2
  • Load Balancer
The apply fails while creating the Load Balancer.
I would not immediately delete everything. First I would inspect the error and state: 
terraform plan
terraform state list
terraform show
Terraform tracks successfully created resources in state. After fixing the root cause, I would run: 
terraform apply
Terraform should continue toward the desired state.

⭐⭐⭐⭐⭐ 5. Terraform State Lock Error

Two engineers or CI/CD jobs try to run Terraform against the same remote state at the same time. Terraform reports that the state is locked.
The lock protects the state from concurrent modifications. First check whether another legitimate Terraform operation is currently running. Do not blindly force-unlock a state that another process is using. 
terraform plan
terraform apply
Use terraform force-unlock only when you have verified that the lock is stale and no active Terraform operation is using the state.

⭐⭐⭐⭐⭐ 6. Two Engineers Run Terraform Apply

Engineer A runs: 
terraform apply
At the same time Engineer B runs: 
terraform apply
against the same environment.
With a properly configured remote backend that supports state locking, one operation should acquire the lock while the other waits or fails with a lock-related message.
In production, Terraform should generally use a shared remote state with locking rather than independent local state files.

⭐⭐⭐⭐⭐ 7. Terraform AWS Authentication Error

Terraform returns an AWS authentication error such as: 
InvalidClientTokenId

What would you check?

  1. Configured AWS credentials
  2. Environment variables
  3. AWS profile
  4. Credential expiration
  5. IAM permissions
  6. AWS region
  7. STS identity
aws sts get-caller-identity

aws configure list

terraform plan
I would first verify which AWS identity Terraform is using before changing the Terraform configuration.

⭐⭐⭐⭐⭐ 8. Wrong AWS Region

Terraform expects an AMI or resource in: 
ap-south-1
but the data source or provider is configured for another region.

Check provider

provider "aws" {
  region = "ap-south-1"
}

Verify AWS CLI

aws configure get region
AWS resources such as AMIs are often region-specific. A valid AMI ID in one region may not exist in another.

⭐⭐⭐⭐⭐ 9. Terraform Plan Wants to Destroy a Resource

You run: 
terraform plan
and see: 
-/+ resource
or Terraform proposes destroying a production resource.
Do not blindly run terraform apply. First identify why Terraform wants to replace it. Check:
  • Changed immutable argument
  • Resource address changed
  • count / for_each changes
  • State mismatch
  • Manual infrastructure changes
  • Provider behavior
  • Configuration changes
Production destruction should always be reviewed carefully before approval.

⭐⭐⭐⭐⭐ 10. Terraform State File Lost

Suppose a local terraform.tfstate file is accidentally deleted.
If the project uses a remote backend, the state should be retrieved from the backend rather than relying on a local copy. If there is no remote state and no backup, recovery becomes much more difficult because Terraform has lost its record of managed resources.
This is one reason remote state, locking and state backups are important for production Terraform environments.

⭐⭐⭐⭐⭐ 11. Someone Deleted an AWS Resource Manually

Terraform state contains an EC2 instance, but an administrator deleted that EC2 instance manually from AWS.

What happens?

During planning/refresh, Terraform can detect that the object no longer exists and may propose creating it again to satisfy the configuration. 
terraform plan
Terraform's goal is to reconcile infrastructure toward the desired configuration.

⭐⭐⭐⭐⭐ 12. Terraform Resource Was Renamed

Original: 
resource "aws_instance" "web" {
  ...
}
Changed to: 
resource "aws_instance" "frontend" {
  ...
}
Terraform may interpret the change as one resource being removed and another being created.
If the rename is intended to represent the same real infrastructure, use an appropriate state move so Terraform understands the address changed. 
terraform state mv \
  aws_instance.web \
  aws_instance.frontend
Always review the state operation and resulting plan before applying changes to important infrastructure.

⭐⭐⭐⭐⭐ 13. count Changed to for_each

Original resource address: 
aws_instance.app[0]
After changing configuration to for_each: 
aws_instance.app["web"]
Terraform may think the old resource and new resource are different.
The state addresses need to be handled carefully so the existing resource can be associated with the new address rather than unnecessarily recreated. 
terraform plan
terraform state list

⭐⭐⭐⭐ 14. Terraform Module Change

A production environment uses a reusable VPC module. You update the module to change subnet configuration.
Before applying: 
terraform init
terraform validate
terraform plan
Review exactly which resources will change. Module changes can affect many resources, so the plan should be carefully reviewed before production deployment.

⭐⭐⭐⭐⭐ 15. Dev, QA and Production Architecture

A company has three environments:
  • Development
  • QA
  • Production
The infrastructure code should be reusable.
Git Repository
↓
Reusable Terraform Modules
↓
Dev Configuration
↓
QA Configuration
↓
Production Configuration
Common approaches include separate root configurations, separate state per environment and reusable modules. The key requirement is to prevent one environment's state from being accidentally applied to another environment.

⭐⭐⭐⭐⭐ 16. Terraform CI/CD Pipeline

Developer
↓
Git Push
↓
Pull Request
↓
Terraform fmt
↓
Terraform validate
↓
Terraform plan
↓
Review / Approval
↓
Terraform apply
↓
AWS Infrastructure
A production pipeline should separate plan and apply appropriately, protect credentials, use remote state and require approval for sensitive changes.

⭐⭐⭐⭐⭐ 17. Terraform Plan in CI but Apply Locally

A team generates a Terraform plan in CI but then manually runs terraform apply from a laptop.
This creates governance and reproducibility concerns. A better production workflow is to keep the plan/apply process in a controlled CI/CD environment with:
  • Protected credentials
  • Remote state
  • Approvals
  • Auditing
  • Consistent Terraform version

⭐⭐⭐⭐⭐ 18. Terraform Secret Accidentally Committed

An AWS access key or database password is committed to Git.

Immediate response

  1. Assume the credential is compromised.
  2. Revoke or rotate it immediately.
  3. Check where it was exposed.
  4. Remove the secret from active configuration.
  5. Clean repository history when necessary.
  6. Enable secret scanning.
  7. Use a secure secret-management solution.
Deleting the secret from the latest commit is not sufficient if it remains in Git history.

⭐⭐⭐⭐⭐ 19. Terraform State Contains Sensitive Information

Terraform state can contain sensitive infrastructure information and sometimes values that should not be broadly exposed. Therefore state should be protected like sensitive infrastructure data.

Best practices

  • Use a secure remote backend.
  • Restrict access using IAM/RBAC.
  • Enable encryption at rest.
  • Use state locking where supported.
  • Do not commit state files to Git.
  • Restrict CI/CD access.

⭐⭐⭐⭐⭐ 20. Terraform Backend Configuration

A team wants multiple engineers and CI/CD systems to work with the same infrastructure. Instead of local state, they configure a remote backend. 
terraform {
  backend "s3" {
    bucket = "company-terraform-state"
    key    = "prod/network/terraform.tfstate"
    region = "ap-south-1"
  }
}
The exact backend configuration depends on the organization's security, locking and operational requirements. The important design principle is centralized, protected state with controlled access.

⭐⭐⭐⭐ 21. Provider Version Changed

A team updates the AWS provider version. After running: 
terraform init -upgrade
the plan changes unexpectedly.
Provider upgrades can change behavior, schemas or resource handling. Before production rollout:
  1. Review release notes.
  2. Test in a lower environment.
  3. Run terraform validate.
  4. Run terraform plan.
  5. Review the changes carefully.
  6. Promote through environments.

⭐⭐⭐⭐⭐ 22. Terraform Version Mismatch

Developer uses one Terraform version while CI/CD uses another. This can produce inconsistent behavior.
Pin and standardize the Terraform version for the project. Example: 
terraform {
  required_version = ">= 1.6, < 2.0"
}
Teams may use version managers or CI images to keep execution consistent.

⭐⭐⭐⭐ 23. Terraform Destroy in Production

Someone accidentally runs: 
terraform destroy
against the production configuration.
Production Terraform should have strong controls. Examples:
  • Separate production credentials.
  • Restricted permissions.
  • Protected CI/CD workflows.
  • Manual approvals.
  • Clear environment separation.
  • Careful review of plans.
Do not rely only on a human remembering not to run terraform destroy. Production access should be designed to reduce the possibility and impact of mistakes.

⭐⭐⭐⭐⭐ 24. AWS IAM Permission Denied

Terraform returns: 
AccessDenied

Debugging flow

aws sts get-caller-identity

aws configure list

terraform plan

Then identify the AWS API action Terraform attempted and verify that the executing IAM role or user has the required permissions.

Do not solve IAM errors by blindly attaching AdministratorAccess. Grant the minimum required permissions.

⭐⭐⭐⭐⭐ 25. Dependency Problem

Terraform creates an application before a required policy or supporting resource is ready.
First check whether the dependency can be represented naturally by referencing the required resource. Example: 
role = aws_iam_role.app.arn
This creates an implicit dependency. Only if Terraform cannot infer the relationship should you consider: 
depends_on = [
  aws_iam_role_policy.app
]

⭐⭐⭐⭐ 26. Terraform Configuration Works Locally but Fails in CI

Local: 
terraform plan
```

works.

CI:


terraform plan
```

fails.

Check differences

  • Terraform version
  • Provider versions
  • AWS credentials
  • AWS region
  • Environment variables
  • Backend configuration
  • Working directory
  • Variable files
  • IAM permissions
A reliable CI environment should explicitly define its Terraform version, credentials, variables and backend configuration rather than depending on a developer's local machine.

⭐⭐⭐⭐⭐ 28. Disaster Recovery for Terraform

Suppose the Terraform backend or state becomes unavailable.
A production setup should have:
  • Remote state
  • Encryption
  • State versioning / backups where supported
  • Restricted access
  • Documented recovery process
  • Recovery testing
The goal is not merely to keep the Terraform code. The state and backend recovery process must also be understood.

⭐⭐⭐⭐⭐ 29. Large Terraform Project

A company manages networking, security, databases and application infrastructure in one huge Terraform configuration. Planning becomes slow and changes become risky.
I would consider modularization and logical separation. For example: 
terraform/
├── modules/
│   ├── vpc/
│   ├── security/
│   ├── database/
│   └── compute/
│
├── environments/
│   ├── dev/
│   ├── qa/
│   └── prod/
The exact repository structure depends on the team's operational model.

⭐⭐⭐⭐⭐ 30. Interview Scenario: "How would you deploy AWS infrastructure?"

"I would first organize the infrastructure into reusable Terraform modules where appropriate. I would configure a secure remote backend for state and separate state between environments. The code would be stored in Git and changes would go through pull requests. CI would run terraform fmt, validate and plan. After review and approval, the controlled pipeline would run terraform apply. I would protect AWS credentials, use least-privilege IAM, review plans carefully and monitor the resulting infrastructure. For production, I would also have state backup/recovery procedures and strong controls around destructive operations."

Manual Change → Drift → terraform plan

State Lock → Check active operation → never blindly force-unlock

Apply Failed → Fix root cause → plan → apply again

Resource Renamed → Handle state address carefully

🎯 Final Interview Answer: "How do you use Terraform in Production?"

"In production, I treat Terraform as the source of truth for infrastructure and use Git-based workflows for all infrastructure changes. I use reusable modules, environment-specific configurations and a secure remote backend with state protection. For every change, I run formatting and validation, generate a Terraform plan and review the proposed changes before applying them. The apply operation is controlled through CI/CD with appropriate authentication, approvals and auditability. If drift occurs, I investigate the difference between the desired configuration and actual infrastructure before deciding whether to reconcile it. For existing manually created resources, I can import them into Terraform state. I also protect Terraform state, use least-privilege IAM, avoid unnecessary provisioners and have recovery procedures for state and backend failures. The main goal is safe, repeatable and auditable infrastructure automation."
