⭐⭐⭐⭐⭐ 1. What is Terraform?

Terraform is an Infrastructure as Code (IaC) tool used to define, provision and manage infrastructure using declarative configuration files. Instead of manually creating AWS resources through the console, we define the desired infrastructure in code and Terraform creates or updates it.
Terraform Code
↓
Terraform Plan
↓
Review Changes
↓
Terraform Apply
↓
Cloud Infrastructure
Real-time example: Instead of manually creating a VPC, subnets, security groups and EC2 instances in AWS, I can define them in Terraform and create the same architecture repeatedly.

⭐⭐⭐⭐⭐ 2. Why Terraform?

  • Infrastructure as Code
  • Repeatable infrastructure
  • Version control through Git
  • Automation
  • Consistent environments
  • Reusable modules
  • Change preview using plan
  • Works with multiple providers
  • Suitable for CI/CD automation
Interview wording: "Terraform helps us provision and manage infrastructure consistently through code. It provides repeatability, version control, automation and a clear plan of infrastructure changes."

⭐⭐⭐⭐⭐ 3. Declarative vs Imperative

Declarative Imperative
Defines the desired end state. Defines step-by-step instructions.
Terraform Traditional scripts
Terraform determines required actions. User explicitly specifies actions.
Terraform is primarily declarative. You describe what infrastructure should look like and Terraform determines how to reach that state.

⭐⭐⭐⭐⭐ 5. Terraform Files

File Purpose
main.tf Main resources and configuration
variables.tf Input variables
outputs.tf Output values
terraform.tfvars Variable values
providers.tf Provider configuration
versions.tf Terraform/provider version constraints
backend.tf Backend configuration when separated

⭐⭐⭐⭐⭐ 6. Provider

A provider is a Terraform plugin that allows Terraform to interact with an external platform such as AWS, Azure, GCP or Kubernetes. 
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "ap-south-1"
}
The provider translates Terraform resource configuration into API operations for the target platform.

⭐⭐⭐⭐⭐ 7. Resource

resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  tags = {
    Name = "web-server"
  }
}
A resource represents an infrastructure object that Terraform manages. Examples include EC2, S3, VPC, IAM role, security group and load balancer.

⭐⭐⭐⭐⭐ 8. Variables

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t3.micro"
}

Use the variable:

resource "aws_instance" "web" {
  instance_type = var.instance_type
}
Variables make Terraform configurations reusable and reduce hard-coded values.

⭐⭐⭐⭐ 9. Variable Types

variable "name" {
  type = string
}

variable "count" {
  type = number
}

variable "enabled" {
  type = bool
}

variable "ports" {
  type = list(number)
}

variable "tags" {
  type = map(string)
}

variable "config" {
  type = object({
    environment = string
    region      = string
  })
}

⭐⭐⭐⭐⭐ 10. tfvars

instance_type = "t3.medium"
environment   = "production"
Terraform can automatically load: 
terraform.tfvars
*.auto.tfvars
Or explicitly: 
terraform plan -var-file="prod.tfvars"

⭐⭐⭐⭐⭐ 11. Locals

locals {
  project_name = "payment-app"

  common_tags = {
    Project     = local.project_name
    Environment = "production"
  }
}
Locals are useful for calculated or reusable expressions inside a Terraform configuration.

⭐⭐⭐⭐⭐ 12. Outputs

output "instance_id" {
  value = aws_instance.web.id
}

output "public_ip" {
  value = aws_instance.web.public_ip
}
Run: 
terraform output
Outputs expose useful values after Terraform creates infrastructure.

⭐⭐⭐⭐ 13. Data Sources

Data sources allow Terraform to read existing information without creating that resource. 
data "aws_ami" "amazon_linux" {
  most_recent = true

  owners = ["amazon"]
}
Example: Instead of hard-coding an AMI ID, Terraform can query for a suitable AMI dynamically.

⭐⭐⭐⭐⭐ 14. Terraform State

Terraform state is Terraform's record of the infrastructure it manages and the relationship between configuration and real-world resources. Common file: 
terraform.tfstate
Do not commit production Terraform state files to Git. State may contain sensitive infrastructure information.

⭐⭐⭐⭐⭐ 15. Local vs Remote State

Local State Remote State
Stored locally Stored in a shared backend
Suitable mainly for simple/local use Better for teams and CI/CD
Difficult collaboration Centralized access
Limited locking depending on setup Can support state locking depending on backend

⭐⭐⭐⭐⭐ 16. Remote Backend

terraform {
  backend "s3" {
    bucket = "company-terraform-state"
    key    = "prod/network/terraform.tfstate"
    region = "ap-south-1"
  }
}
A remote backend allows a team or CI/CD system to work with centralized Terraform state. The backend should be secured with appropriate access controls, encryption and recovery mechanisms.

⭐⭐⭐⭐⭐ 17. State Locking

State locking prevents multiple Terraform operations from modifying the same state simultaneously when the selected backend supports locking.
If another Terraform process is already using the state, a second operation should not blindly modify it.
Never use force-unlock simply because Terraform reports a lock. First confirm that the lock is stale and no active operation is running.

⭐⭐⭐⭐⭐ 18. Terraform Plan

terraform plan
Plan compares the desired configuration with the current state and provider information and shows proposed changes before apply. Typical symbols: 
+   create
-   destroy
~   update
-/+ replace

⭐⭐⭐⭐⭐ 19. Terraform Apply

terraform apply
Apply executes the approved changes required to make the actual infrastructure match the desired configuration.
In production, apply should normally happen through a controlled workflow with review and appropriate approvals.

⭐⭐⭐⭐⭐ 20. Terraform Destroy

terraform destroy
Destroy removes resources managed by the selected Terraform configuration. Never run it blindly against production.

⭐⭐⭐⭐⭐ 21. Modules

A module is a reusable collection of Terraform configuration. 
module "vpc" {
  source = "./modules/vpc"

  cidr_block = "10.0.0.0/16"
}
Example structure: 
terraform/
├── modules/
│   ├── vpc/
│   ├── ec2/
│   └── security/
│
└── environments/
    ├── dev/
    ├── qa/
    └── prod/

⭐⭐⭐⭐⭐ 22. count vs for_each

count for_each
Good for indexed identical resources. Good for uniquely identified resources.
resource[0] resource["web"] 
resource "aws_instance" "web" {
  count = 2

  ami           = var.ami
  instance_type = "t3.micro"
}
resource "aws_instance" "app" {
  for_each = {
    web = "t3.micro"
    api = "t3.small"
  }

  ami           = var.ami
  instance_type = each.value
}

⭐⭐⭐⭐ 23. depends_on

resource "aws_instance" "app" {

  depends_on = [
    aws_iam_role_policy.app
  ]

}
Terraform normally creates dependencies automatically when one resource references another. depends_on is useful when the dependency cannot be inferred from an expression.

⭐⭐⭐⭐ 24. Lifecycle Rules

resource "aws_instance" "web" {

  lifecycle {
    create_before_destroy = true

    prevent_destroy = true

    ignore_changes = [
      tags
    ]
  }

}
Rule Purpose
create_before_destroy Create replacement before destroying old resource when supported.
prevent_destroy Protect against Terraform destroying the resource.
ignore_changes Ignore selected configuration differences.

⭐⭐⭐ 25. Provisioners

Provisioners allow Terraform to perform actions such as running commands after resource creation. However, they should generally be avoided when a better native resource, cloud-init/user-data, configuration-management tool or other approach exists. 
provisioner "local-exec" {
  command = "echo Instance created"
}
Provisioners can make infrastructure less predictable and harder to maintain.

⭐⭐⭐⭐⭐ 26. Terraform Import

An EC2 instance already exists in AWS but is not managed by Terraform. 
terraform import aws_instance.web i-0123456789abcdef0
Then: 
terraform plan
Import associates an existing real-world resource with a Terraform resource address. Configuration should then be aligned with the actual resource.

⭐⭐⭐⭐⭐ 27. Terraform Drift

Drift occurs when infrastructure is changed outside Terraform. Example: Terraform says: 
instance_type = "t3.micro"
Someone manually changes AWS to: 
t3.medium
Run: 
terraform plan
to identify the difference.

⭐⭐⭐⭐⭐ 28. State Commands

terraform state list

terraform state show <resource>

terraform state mv <old> <new>

terraform state rm <resource>

terraform show
State manipulation is powerful. Always understand the effect before changing production state.

⭐⭐⭐⭐ 29. State Rename

Resource address changes from: 
aws_instance.web
to: 
aws_instance.frontend
terraform state mv \
  aws_instance.web \
  aws_instance.frontend
This tells Terraform that the address changed while the underlying managed object is intended to remain the same.

⭐⭐⭐⭐⭐ 30. Terraform Validation & Formatting

terraform fmt

terraform validate
fmt formats Terraform files. validate checks whether the configuration is syntactically valid and internally consistent for the initialized configuration.

⭐⭐⭐⭐⭐ 32. Terraform Security

  • Do not commit secrets to Git.
  • Protect remote state.
  • Encrypt state at rest where supported.
  • Use least-privilege IAM.
  • Use short-lived credentials where possible.
  • Protect CI/CD credentials.
  • Enable secret scanning.
  • Restrict production access.
  • Review destructive plans.
  • Maintain state backups/recovery mechanisms.

⭐⭐⭐⭐⭐ 33. Terraform State and Secrets

Terraform state can contain sensitive information depending on the resources and expressions being managed. Therefore state should be treated as sensitive infrastructure data.
Do not assume that marking an output as sensitive means the value cannot exist in state. Sensitive values may still be stored in the state required by Terraform.

⭐⭐⭐⭐⭐ 34. Existing Resource Scenario

Problem: Terraform says a resource already exists. Solution: Import the existing resource, inspect the configuration and state, then run a plan. 
terraform import <address> <id>

terraform plan

⭐⭐⭐⭐⭐ 35. Apply Failed Halfway

Never assume everything was rolled back. Check: 
terraform plan
terraform state list
terraform show
Fix the root cause and run the plan again.
Terraform records successful operations in state, so after resolving the error it can usually continue toward the desired state.

⭐⭐⭐⭐⭐ 36. AWS Authentication Troubleshooting

aws sts get-caller-identity

aws configure list

aws configure get region

terraform plan
Check:
  • Credentials
  • IAM role/user
  • Expired credentials
  • Profile
  • Region
  • IAM permissions

⭐⭐⭐⭐⭐ 37. Terraform Works Locally but Fails in CI

I would compare:
  • Terraform version
  • Provider versions
  • AWS credentials
  • AWS profile
  • AWS region
  • Environment variables
  • Variable files
  • Backend
  • Working directory
  • IAM permissions

⭐⭐⭐⭐⭐ 38. Dev / QA / Production

Reusable Modules
↓
Dev State
↓
QA State
↓
Production State
Keep environment state isolated so a Dev operation cannot accidentally modify Production. The exact implementation can use separate root configurations, workspaces or other environment-management approaches depending on the organization's requirements.

⭐⭐⭐⭐⭐ 39. Workspace

terraform workspace list

terraform workspace new dev

terraform workspace select dev

terraform workspace show
Workspaces allow multiple state instances for the same configuration. They can be useful in some scenarios, but teams should not assume workspaces alone provide all environment isolation or security controls required for production.

⭐⭐⭐⭐⭐ 40. Provider Version Locking

Terraform creates a dependency lock file: 
.terraform.lock.hcl
The lock file records selected provider versions and checksums so different machines and CI environments can use consistent provider versions.

⭐⭐⭐⭐⭐ 41. Terraform Version Management

terraform {
  required_version = ">= 1.6, < 2.0"
}
Version constraints help ensure the project is executed with a compatible Terraform version. Teams should also standardize the version used by developers and CI/CD.

🚨 46. Common Terraform Mistakes

  • Running apply without reviewing the plan.
  • Storing state in Git.
  • Hard-coding credentials.
  • Using AdministratorAccess unnecessarily.
  • Ignoring state locking.
  • Blindly using force-unlock.
  • Using provisioners for everything.
  • Creating one huge Terraform configuration.
  • Mixing production and development state.
  • Ignoring provider version changes.
  • Running destructive commands against production.
  • Ignoring drift.

🎯 47. "Explain Terraform" — Interview Answer

"Terraform is an Infrastructure as Code tool that allows us to define and manage infrastructure using declarative configuration. I use Terraform to provision resources such as VPCs, subnets, security groups, EC2 instances, IAM resources and other cloud components. The normal workflow is terraform init, validate, plan and apply. Terraform maintains state to track the relationship between the configuration and real infrastructure. In a team environment I prefer a secure remote backend with appropriate state protection and locking. I use variables, outputs, locals and reusable modules to make the configuration maintainable. For production, infrastructure changes go through Git and CI/CD. The pipeline validates the code, generates a plan and applies approved changes. I also handle real-time situations such as drift, importing existing resources, state issues, authentication failures and failed deployments. The main benefit is repeatable, version-controlled and automated infrastructure management."
