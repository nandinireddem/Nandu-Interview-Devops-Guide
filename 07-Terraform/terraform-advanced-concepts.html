Interview-focused guide covering Data Sources, Locals, Functions, Expressions, count, for_each, depends_on, Dynamic Blocks, Provisioners and real-time Terraform scenarios.

⭐⭐⭐⭐⭐ Why These Concepts Matter

These features help Terraform work with existing infrastructure, reuse values, dynamically create resources and express complex infrastructure logic without unnecessary duplication.

Data Sources → Read Existing Infrastructure

Locals → Reuse Calculated Values

Functions / Expressions → Transform Values

count / for_each → Create Multiple Resources

depends_on → Explicit Dependency

Dynamic Blocks → Generate Nested Blocks

Provisioners → Last-resort Configuration Actions

⭐⭐⭐⭐⭐ 1. What is a Terraform Data Source?

A data source allows Terraform to read information about existing infrastructure or external data without creating that object. The keyword used is: 
data
Real-time example: An AWS VPC already exists. Terraform should use that VPC instead of creating another one. Terraform can retrieve the existing VPC using a data source.

⭐⭐⭐⭐⭐ 2. AWS VPC Data Source

data "aws_vpc" "existing" {

  filter {
    name   = "tag:Name"
    values = ["production-vpc"]
  }
}

Use the VPC ID

resource "aws_subnet" "app" {

  vpc_id = data.aws_vpc.existing.id

  cidr_block = "10.0.10.0/24"

}
Here Terraform reads the existing VPC and uses its ID when creating the subnet.

⭐⭐⭐⭐⭐ 3. Resource vs Data Source

Resource Data Source
Creates or manages infrastructure. Reads existing information.
resource data
Terraform manages its lifecycle. Terraform does not create the object.
Example: create VPC. Example: find existing VPC.
Easy interview answer: "Resource is used to create or manage infrastructure. Data source is used to retrieve information about existing infrastructure."

⭐⭐⭐⭐⭐ 4. Real-Time AWS AMI Data Source

data "aws_ami" "amazon_linux" {

  most_recent = true

  owners = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }

  filter {
    name   = "state"
    values = ["available"]
  }
}

Use it

resource "aws_instance" "app" {

  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

}
Instead of hard-coding an AMI ID that can change between regions, Terraform can dynamically look up a suitable AMI.

⭐⭐⭐⭐⭐ 5. What are Terraform Locals?

Locals allow you to assign reusable names to expressions or computed values inside a module. They help avoid repeating the same expression multiple times. 
locals {

  environment = "production"

  common_tags = {
    Environment = local.environment
    Project     = "payment-app"
    ManagedBy   = "Terraform"
  }

}

Use local value

resource "aws_s3_bucket" "app" {

  bucket = "payment-${local.environment}"

  tags = local.common_tags

}

⭐⭐⭐⭐⭐ 6. Variables vs Locals

Variables Locals
Input supplied to a module. Value calculated or reused inside a module.
Can change between environments. Usually derived from configuration.
var.environment local.environment
Remember: Variable = external input. Local = internal reusable value.

⭐⭐⭐⭐⭐ 7. Terraform Functions

Terraform functions transform or manipulate values. Common functions include:
  • length()
  • join()
  • split()
  • lookup()
  • merge()
  • concat()
  • contains()
  • toset()
  • tolist()
  • tomap()
  • upper()
  • lower()
  • replace()
  • file()
  • templatefile()

⭐⭐⭐⭐⭐ 8. Important Function Examples

length()

locals {
  subnet_count = length(var.subnets)
}

join()

locals {
  name = join("-", ["prod", "web", "01"])
}

merge()

locals {

  tags = merge(
    var.common_tags,
    {
      Environment = "production"
    }
  )

}

contains()

contains(["dev", "qa", "prod"], var.environment)

⭐⭐⭐⭐⭐ 9. Terraform Expressions

Expressions allow Terraform configuration to calculate values, reference resources and make decisions. 
name = "app-${var.environment}"

instance_type = var.environment == "prod"
  ? "t3.medium"
  : "t3.micro"
For Production: 
instance_type = "t3.medium"
For Dev: 
instance_type = "t3.micro"
The conditional expression avoids duplicating the resource.

⭐⭐⭐⭐⭐ 10. Conditional Expression

instance_type = var.environment == "production"
  ? "t3.large"
  : "t3.micro"
Syntax: 
condition ? true_value : false_value
A common real-time use case is selecting different infrastructure sizes or settings based on the environment.

⭐⭐⭐⭐⭐ 11. What is count?

count creates multiple instances of a resource based on a numeric value. 
resource "aws_instance" "app" {

  count = 3

  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

}

Terraform creates three instances: 

aws_instance.app[0]
aws_instance.app[1]
aws_instance.app[2]

⭐⭐⭐⭐⭐ 12. count.index

variable "instance_names" {

  default = [
    "web",
    "api",
    "worker"
  ]

}

resource "aws_instance" "app" {

  count = length(var.instance_names)

  tags = {
    Name = var.instance_names[count.index]
  }

}
count.index gives the numeric index of the current resource instance.

⭐⭐⭐⭐⭐ 13. What is for_each?

for_each creates multiple resource instances from a map or set. It is useful when each instance has a meaningful key. 
variable "instances" {

  default = {
    web    = "t3.micro"
    api    = "t3.small"
    worker = "t3.medium"
  }

}

resource "aws_instance" "app" {

  for_each = var.instances

  ami           = "ami-xxxxxxxx"
  instance_type = each.value

  tags = {
    Name = each.key
  }

}

⭐⭐⭐⭐⭐ 14. count vs for_each

count for_each
Uses a number. Uses map or set.
Uses numeric index. Uses meaningful keys.
count.index each.key / each.value
Good for identical or index-based instances. Good when instances have distinct identities.
Interview answer: "I prefer for_each when resources have meaningful identities because the keys make resource addressing clearer and can reduce unwanted index-related changes."

⭐⭐⭐⭐ 15. for_each with a Set

variable "users" {

  type = set(string)

  default = [
    "dev",
    "qa",
    "admin"
  ]

}

resource "aws_iam_user" "users" {

  for_each = var.users

  name = each.value

}

⭐⭐⭐⭐⭐ 16. What is depends_on?

depends_on explicitly tells Terraform that one resource depends on another resource or module. Terraform normally builds dependencies automatically from references, so depends_on should be used only when the dependency cannot be inferred automatically. 
resource "aws_instance" "app" {

  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  depends_on = [
    aws_iam_role_policy.app
  ]

}

⭐⭐⭐⭐⭐ 17. Implicit vs Explicit Dependency

Implicit dependency

resource "aws_instance" "app" {

  subnet_id = aws_subnet.app.id

}

Terraform automatically knows that the instance depends on the subnet because the instance references its ID.

Explicit dependency

depends_on = [
  aws_iam_role_policy.app
]
Use explicit dependencies only when Terraform cannot determine the relationship from resource references.

⭐⭐⭐⭐ 18. What is a Dynamic Block?

A dynamic block generates repeated nested configuration blocks from a collection. It is useful when a resource contains nested blocks that need to be created dynamically. 
dynamic "ingress" {

  for_each = var.ingress_rules

  content {

    from_port   = ingress.value.from_port
    to_port     = ingress.value.to_port
    protocol    = ingress.value.protocol
    cidr_blocks = ingress.value.cidr_blocks

  }
}

⭐⭐⭐⭐ 19. Dynamic Block Real-Time Example

Suppose a security group has different inbound rules for:

HTTP → 80
HTTPS → 443
SSH → 22

Instead of writing many repeated nested blocks manually, a dynamic block can generate them from a variable. 
variable "ingress_rules" {

  default = {
    http = {
      from_port   = 80
      to_port     = 80
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }

    https = {
      from_port   = 443
      to_port     = 443
      protocol    = "tcp"
      cidr_blocks = ["0.0.0.0/0"]
    }
  }

}

⭐⭐⭐ 20. What are Terraform Provisioners?

Provisioners allow Terraform to perform actions on or after resource creation. Examples include:
  • local-exec
  • remote-exec
  • file
Provisioners are generally considered a last resort. Terraform is designed to manage infrastructure declaratively. Configuration-management tools, cloud-init, images and other mechanisms are often preferable for application setup.

⭐⭐⭐ 21. local-exec Example

resource "aws_instance" "app" {

  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  provisioner "local-exec" {

    command = "echo Instance created"

  }

}
local-exec runs the command on the machine where Terraform is executing. It does not run the command inside the EC2 instance.

⭐⭐⭐ 22. remote-exec Example

provisioner "remote-exec" {

  inline = [
    "sudo apt-get update",
    "sudo apt-get install -y nginx"
  ]

  connection {

    type        = "ssh"
    host        = self.public_ip
    user        = "ubuntu"
    private_key = file("key.pem")

  }

}
For production systems, prefer immutable images, cloud-init, configuration management or other appropriate automation instead of relying heavily on remote-exec.

⭐⭐⭐ 23. What happens if a Provisioner fails?

Provisioner behavior depends on the resource lifecycle and provisioner configuration. By default, a creation-time provisioner failure can cause the resource to be marked as tainted in older Terraform terminology and lead to recreation behavior. Modern Terraform workflows should be designed carefully rather than depending on provisioners for critical configuration.
The important interview point: Provisioners are not the preferred way to configure applications.

⭐⭐⭐⭐ 25. Locals for Common Tags

variable "environment" {
  type = string
}

variable "project" {
  type = string
}

locals {

  common_tags = {
    Environment = var.environment
    Project     = var.project
    ManagedBy   = "Terraform"
    Owner       = "DevOps"
  }

}

resource "aws_s3_bucket" "app" {

  bucket = "${var.project}-${var.environment}"

  tags = local.common_tags

}
This pattern is commonly useful when many AWS resources need the same standard tags.

⭐⭐⭐⭐ 26. Conditional Resource Creation

variable "create_monitoring" {
  type    = bool
  default = true
}

resource "aws_cloudwatch_log_group" "app" {

  count = var.create_monitoring ? 1 : 0

  name = "/app/logs"

}
If create_monitoring = true, Terraform creates one resource. If false, Terraform creates zero instances.

⭐⭐⭐⭐ 27. For Expressions

For expressions transform one collection into another collection. 
variable "names" {

  default = [
    "web",
    "api",
    "database"
  ]

}

output "upper_names" {

  value = [
    for name in var.names : upper(name)
  ]

}

Result: 

[
  "WEB",
  "API",
  "DATABASE"
]

⭐⭐⭐⭐ 29. Troubleshooting count / for_each

Problem: A resource unexpectedly wants to be destroyed and recreated after changing from count to for_each.

Why? The resource addressing model changed. For example: 
aws_instance.app[0]
may become: 
aws_instance.app["web"]
When changing resource addressing, carefully plan state migrations using appropriate Terraform state commands or configuration techniques.

Error: Terraform cannot find the requested AMI, VPC or subnet.

Check:
  • AWS region
  • Account
  • Filters
  • Tags
  • Resource state
  • Permissions

⭐⭐⭐⭐⭐ 31. Advanced Terraform Best Practices

  • Use data sources for existing infrastructure.
  • Use locals for reusable calculated values.
  • Use variables for external inputs.
  • Prefer for_each when resources have meaningful identities.
  • Use count when numeric repetition is appropriate.
  • Prefer implicit dependencies through references.
  • Use depends_on only when necessary.
  • Use dynamic blocks only when they improve maintainability.
  • Treat provisioners as a last resort.
  • Keep expressions readable.
  • Validate inputs where appropriate.
  • Review terraform plan before production apply.

🎯 If Interviewer Says: "Explain Advanced Terraform Concepts"

"Terraform provides several features that help us build reusable and dynamic infrastructure. I use Data Sources when I need to retrieve existing infrastructure, such as an existing VPC or the latest suitable AMI, instead of creating it again. I use locals for reusable calculated values such as common tags, and functions and expressions to transform values or implement conditional logic. For creating multiple resources, I use count when numeric repetition is sufficient and for_each when resources have meaningful keys. Terraform automatically creates dependencies when resources reference each other. I use depends_on only when an explicit dependency cannot be inferred. Dynamic blocks can generate repeated nested configuration, while provisioners are treated as a last resort because Terraform is primarily designed for declarative infrastructure management. These features help make Terraform configurations reusable, maintainable and suitable for real-world DevOps environments."
