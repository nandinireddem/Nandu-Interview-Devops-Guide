Terraform Variables & Modules

Interview-focused guide covering input variables, tfvars, locals, outputs, data sources, types, validation, sensitive values, modules, module inputs and outputs, reusable infrastructure and real-time DevOps scenarios.

⭐⭐⭐⭐⭐ Core Concept

Terraform variables and modules are the foundation of reusable Infrastructure as Code. Variables make configuration flexible, while modules allow infrastructure patterns to be packaged and reused.

Reusable Terraform Code
↓
Variables → Environment-specific values
↓
Modules → Reusable infrastructure
↓
Dev / QA / Production
Real-time example: A company creates the same VPC architecture for Dev, QA and Production. Instead of maintaining three completely different Terraform files, the team creates a reusable VPC module and passes different CIDRs, availability zones and environment values through variables.

⭐⭐⭐⭐⭐ 1. What is a Terraform Variable?

A Terraform input variable allows a configuration to accept values from outside the resource definition. Variables make Terraform configurations reusable and avoid hard-coding environment-specific values.

variables.tf

variable "instance_type" {
  description = "EC2 instance type"
  type        = string
  default     = "t3.micro"
}

Usage

resource "aws_instance" "app" {
  ami           = var.ami_id
  instance_type = var.instance_type
}

⭐⭐⭐⭐⭐ 2. Why use Variables?

  • Avoid hard-coded values.
  • Reuse the same configuration.
  • Support multiple environments.
  • Improve maintainability.
  • Make modules configurable.
  • Allow CI/CD pipelines to supply values.
Example: Instead of changing the resource code: 
instance_type = "t3.micro"
for every environment, define: 
instance_type = var.instance_type
and provide different values for Dev and Production.

⭐⭐⭐⭐⭐ 3. Variable Types

Type Example
string "ap-south-1"
number 2
bool true
list ["a","b","c"]
set toset(["a","b"])
map {env="dev", team="cloud"}
object Structured collection of named attributes
tuple Ordered collection with defined element types

⭐⭐⭐⭐⭐ 4. String, Number and Boolean Variables

variable "project_name" {
  type    = string
  default = "nandu-project"
}

variable "replica_count" {
  type    = number
  default = 2
}

variable "enable_monitoring" {
  type    = bool
  default = true
}

⭐⭐⭐⭐⭐ 5. List and Map Variables

List

variable "availability_zones" {
  type = list(string)

  default = [
    "ap-south-1a",
    "ap-south-1b"
  ]
}

Map

variable "tags" {
  type = map(string)

  default = {
    Environment = "Dev"
    Project     = "Cloud"
  }
}

⭐⭐⭐⭐⭐ 6. What is terraform.tfvars?

A .tfvars file provides values for Terraform input variables. 
aws_region    = "ap-south-1"
instance_type = "t3.micro"
environment   = "dev"
The same Terraform configuration can be used with different .tfvars files for different environments.

⭐⭐⭐⭐⭐ 7. Variable Precedence

Terraform supports multiple ways to provide variable values. Common sources include:
  1. Variable defaults
  2. Environment variables such as TF_VAR_name
  3. Automatically loaded terraform.tfvars and *.auto.tfvars
  4. Explicit -var and -var-file arguments
When multiple sources provide the same variable, Terraform follows its documented precedence rules. Explicit command-line variable arguments have higher precedence than automatic variable files.

⭐⭐⭐⭐⭐ 8. Using -var and -var-file

terraform plan \
  -var="environment=dev"

Using variable file

terraform plan \
  -var-file="dev.tfvars"
This is useful in CI/CD when the pipeline needs to select the appropriate environment configuration.

⭐⭐⭐⭐⭐ 9. What are Locals?

Local values allow you to assign reusable expressions or computed values within a Terraform module. They are useful when the same derived value is used in multiple places. 
locals {
  common_tags = {
    Project     = "Nandu"
    Environment = "Dev"
    ManagedBy   = "Terraform"
  }
}

Usage

resource "aws_s3_bucket" "app" {

  bucket = "nandu-demo-bucket"

  tags = local.common_tags
}

⭐⭐⭐⭐⭐ 10. Variable vs Local

Variable Local
Input supplied to the module. Value calculated or defined inside the module.
Can be changed by the caller. Not directly supplied as module input.
Used for configurable values. Used for reusable internal expressions.
Simple answer: Variable = external input.
Local = internal reusable value.

⭐⭐⭐⭐⭐ 11. Variable Validation

Variable validation allows Terraform to reject invalid input before infrastructure is created. 
variable "environment" {

  type = string

  validation {
    condition = contains(
      ["dev", "qa", "prod"],
      var.environment
    )

    error_message = "Environment must be dev, qa or prod."
  }
}
This prevents someone from accidentally supplying: 
environment = "productionn"
when the module expects only approved values.

⭐⭐⭐⭐⭐ 12. Sensitive Variables

Sensitive variables prevent Terraform CLI output from displaying the value in normal situations. 
variable "db_password" {
  type      = string
  sensitive = true
}
Important: Marking a variable as sensitive does not mean the value is magically encrypted everywhere. Sensitive values can still exist in Terraform state depending on how they are used. Protect the state backend appropriately.

⭐⭐⭐⭐⭐ 13. What are Outputs?

Outputs expose useful values from a Terraform module. 
output "vpc_id" {
  description = "VPC ID"
  value       = aws_vpc.main.id
}
A networking module can output a VPC ID. The application module can consume that output.

⭐⭐⭐⭐⭐ 14. Sensitive Outputs

output "admin_password" {
  value     = var.admin_password
  sensitive = true
}
Sensitive output values should still be treated as sensitive data. The sensitive flag mainly controls how Terraform displays the value.

⭐⭐⭐⭐⭐ 15. What is a Data Source?

A data source allows Terraform to read information from an existing resource or external system without managing that object as a new resource.

AWS AMI Example

data "aws_ami" "amazon_linux" {

  most_recent = true

  owners = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

Use it

resource "aws_instance" "app" {

  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

}

⭐⭐⭐⭐⭐ 16. Resource vs Data Source

Resource Data Source
Creates or manages infrastructure. Reads existing information.
Example: aws_instance Example: aws_ami
Terraform manages lifecycle. Terraform queries existing information.
Resource = "Create/manage this."

Data source = "Find/read this."

⭐⭐⭐⭐⭐ 17. What is a Terraform Module?

A Terraform module is a collection of Terraform configuration files that can be reused as a logical unit. The directory containing Terraform configuration is itself a module; the root configuration is called the root module, and reusable child modules can be called from it.
Instead of writing VPC resources repeatedly for every project, create a reusable VPC module and call it with different inputs.

⭐⭐⭐⭐⭐ 18. Root Module vs Child Module

Root Module Child Module
Configuration where Terraform commands are executed. Module called by another module.
Contains the main environment configuration. Contains reusable infrastructure logic.
Calls child modules. Accepts inputs and exposes outputs.

⭐⭐⭐⭐⭐ 19. Basic Module Structure

terraform-project/
│
├── main.tf
├── variables.tf
├── outputs.tf
│
└── modules/
    └── vpc/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
The module directory contains reusable Terraform configuration. The root module supplies values to it and consumes its outputs.

⭐⭐⭐⭐⭐ 20. Calling a Module

Root module

module "vpc" {

  source = "./modules/vpc"

  vpc_cidr = "10.0.0.0/16"

  environment = "dev"

}
source tells Terraform where the module comes from. The other arguments are values passed to module input variables.

⭐⭐⭐⭐⭐ 21. Module Input Variables

modules/vpc/variables.tf

variable "vpc_cidr" {
  type = string
}

variable "environment" {
  type = string
}

modules/vpc/main.tf

resource "aws_vpc" "main" {

  cidr_block = var.vpc_cidr

  tags = {
    Name        = "${var.environment}-vpc"
    Environment = var.environment
  }

}

⭐⭐⭐⭐⭐ 22. Module Outputs

modules/vpc/outputs.tf

output "vpc_id" {
  value = aws_vpc.main.id
}

Root module

module "vpc" {
  source   = "./modules/vpc"
  vpc_cidr = "10.0.0.0/16"
}

output "application_vpc_id" {
  value = module.vpc.vpc_id
}
Root Module
↓
Module Input
↓
VPC Module
↓
Module Output
↓
Root Module

⭐⭐⭐⭐⭐ 23. Why use Modules?

  • Code reusability.
  • Consistency across environments.
  • Reduced duplication.
  • Standardized infrastructure patterns.
  • Easier maintenance.
  • Clear separation of infrastructure components.
  • Useful for large Terraform codebases.
A company can create standard modules for:

VPC → EKS → RDS → ALB → IAM

Teams consume the approved modules instead of rebuilding the same infrastructure pattern differently.

⭐⭐⭐⭐⭐ 24. Local Module vs Registry Module

Local Module Registry/Remote Module
source = "./modules/vpc" Module downloaded from a registry or remote source.
Maintained inside the project/repository. Can be shared across projects.
Useful for organization-specific modules. Useful for reusable published modules.

⭐⭐⭐⭐⭐ 25. Module Versioning

Remote modules can be versioned so teams can control which module release they use. 
module "vpc" {

  source  = "terraform-aws-modules/vpc/aws"
  version = "x.y.z"

}
In production, pin module versions intentionally and upgrade them through a controlled review process.

⭐⭐⭐⭐⭐ 26. Module Composition

Root Module
↓
VPC Module
+
Security Module
+
EKS Module
+
Monitoring Module
Large Terraform projects are often divided into logical modules instead of putting every resource into one enormous file.

⭐⭐⭐⭐⭐ 27. Passing Module Output to Another Module

module "vpc" {
  source = "./modules/vpc"
}

module "app" {

  source = "./modules/app"

  vpc_id = module.vpc.vpc_id

}
The application module consumes the VPC module's output. Terraform can infer the dependency through this reference.

⭐⭐⭐⭐ 28. for_each with Modules

Modules can be created multiple times using for_each. 
module "environment" {

  for_each = {
    dev  = "10.10.0.0/16"
    prod = "10.20.0.0/16"
  }

  source   = "./modules/vpc"
  vpc_cidr = each.value

}
This can be useful when the same module needs to create multiple similar infrastructure instances.

⭐⭐⭐⭐ 29. count vs for_each with Modules

count for_each
Uses numeric indexes. Uses keys.
Useful for simple repeated instances. Better when instances have meaningful identities.
module.app[0] module.app["dev"]
When individual instances have meaningful names such as dev, qa and prod, I generally prefer for_each because the keys describe the instances.

⭐⭐⭐⭐⭐ 30. Real-Time Multi-Environment Design

Suppose a company has:

Dev → smaller instances
QA → medium instances
Production → larger instances

Reusable module

module "app" {

  source = "./modules/application"

  instance_type = var.instance_type

  environment   = var.environment

}

dev.tfvars

environment   = "dev"
instance_type = "t3.micro"

prod.tfvars

environment   = "prod"
instance_type = "m7i.large"
Same module. Different input values. Different environment infrastructure.

⭐⭐⭐⭐⭐ 32. Common Module Mistakes

  • Creating extremely large modules.
  • Hard-coding environment-specific values.
  • Passing too many unnecessary variables.
  • Not documenting module inputs and outputs.
  • Not validating inputs.
  • Using unpinned remote module versions in production.
  • Exposing sensitive values unnecessarily.
  • Duplicating the same module logic across repositories.

⭐⭐⭐⭐⭐ 33. Variables + Modules + State Relationship

↓

Variables control what values enter the configuration. Modules organize reusable infrastructure. Outputs expose useful results. State records the infrastructure Terraform manages.

⭐⭐⭐⭐⭐ 34. Interview: How do you design reusable Terraform code?

"I separate reusable infrastructure into modules and expose only the configuration values that consumers actually need through input variables. I use validation for important inputs, locals for repeated internal expressions, and outputs for values that other modules need. For different environments, I keep the infrastructure logic reusable and supply environment-specific values through variables or approved environment configuration. For production, I also version reusable modules and review module upgrades before adoption."

🎯 If Interviewer Says: "Explain Terraform Modules"

"Terraform modules are reusable collections of Terraform configuration. I use modules to avoid duplicating infrastructure code and to standardize common components such as VPCs, IAM roles, EKS clusters or application infrastructure. The root module calls a child module and passes values through input variables. The child module creates the required resources and exposes important values through outputs. For example, I can create one reusable VPC module and use it for Dev, QA and Production by passing different CIDRs and environment values. I also use variable validation, locals and versioned modules to make the Terraform code easier to maintain and safer to reuse."
