Linux Advanced Network Troubleshooting

Practical network diagnosis, DNS, ports, routes, traceroute, TCP connectivity, HTTP troubleshooting and real-world DevOps scenarios.

QUESTION 01

Why is Network Troubleshooting Important in DevOps?

⭐⭐⭐⭐⭐ DEVOPS MUST KNOW

Applications in DevOps environments depend heavily on network communication between users, load balancers, containers, Kubernetes services, databases, APIs and cloud resources.

User ↓ DNS ↓ Load Balancer ↓ Application ↓ Database

A failure at any layer can make an application appear unavailable.

🎤 Interview Answer

"Network troubleshooting is important in DevOps because modern applications depend on communication between multiple services. I troubleshoot systematically from DNS and connectivity through ports, routing, firewalls and application-level responses."

QUESTION 02

What is traceroute?

⭐⭐⭐⭐⭐ MUST KNOW

traceroute is used to identify the network hops between the source system and a destination. 

traceroute google.com

On some Linux distributions, the command may need to be installed first.

Why use it?

If a remote server is unreachable, traceroute can help identify where along the network path packets stop receiving expected responses.

🎤 Interview Answer

"Traceroute helps identify the network path and intermediate hops between a source and destination, which can help locate routing or connectivity problems."

QUESTION 03

What is the difference between ping and traceroute?

⭐⭐⭐⭐⭐ VERY COMMON
ping traceroute
Tests basic reachability Shows network path/hops
Measures response time Helps identify path issues
Usually targets one destination Shows intermediate routing hops
🎤 Interview Answer

"Ping checks basic reachability and latency, while traceroute helps identify the path and intermediate hops taken toward the destination."

QUESTION 04

What is curl -v?

⭐⭐⭐⭐⭐ DEVOPS FAVORITE

The -v option makes curl display detailed information about the connection. 

curl -v http://localhost:8080

It can reveal useful details such as connection attempts, request/response headers and TLS-related information for HTTPS.

Useful for:
  • HTTP connection debugging
  • Checking response headers
  • Understanding redirects
  • Troubleshooting TLS/HTTPS
  • Verifying application endpoints
QUESTION 05

How do you check only HTTP response headers?

⭐⭐⭐⭐ 
curl -I https://example.com

This sends a HEAD request when supported and displays response headers without retrieving the normal response body.

Useful headers 
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: ...
Server: ...
QUESTION 06

How do you test a specific TCP port?

⭐⭐⭐⭐⭐ VERY USEFUL

A simple approach is using tools such as nc when available. 

nc -zv server-ip 8080

This can help determine whether a TCP connection to the specified port can be established.

⚠️ Remember

A successful TCP connection only proves that the network path and port are reachable. It does not prove that the application itself is functioning correctly.

QUESTION 07

What is localhost?

⭐⭐⭐⭐⭐ MUST KNOW

localhost refers to the local machine itself. It commonly resolves to loopback addresses such as: 

127.0.0.1
::1
Example 
curl http://localhost:8080

This tests the application from the same machine rather than from another network host.

QUESTION 08

Why test localhost first?

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE

Testing localhost helps separate application problems from external network problems.

curl localhost:8080 ↓ Works? ↓ YES → Investigate external network NO → Investigate application/service
🎤 Interview Answer

"I test the application locally first. If localhost works but remote access fails, I focus on network, firewall, routing or security controls. If localhost itself fails, I investigate the application or service."

QUESTION 09

What is a socket?

⭐⭐⭐⭐

A socket is an endpoint used for network communication. A network connection is commonly associated with an IP address, port and transport protocol.

Example 
192.168.1.10:8080

This identifies an endpoint using an IP address and port.

The ss command is commonly used to inspect sockets. 

ss -tulpn
QUESTION 10

What is a listening port?

⭐⭐⭐⭐⭐ MUST KNOW

A listening port indicates that a service is waiting for incoming network connections. 

ss -lntp
Example

If an application is expected on port 8080 but no process is listening on 8080, remote clients cannot establish a normal TCP connection to that service.

QUESTION 11

What does 0.0.0.0 mean when a service binds to it?

⭐⭐⭐⭐⭐ DEVOPS MUST KNOW

When a service listens on 0.0.0.0 for IPv4, it generally means it is listening on all IPv4 interfaces on that host, subject to firewall and network controls. 

ss -lntp
Compare 
127.0.0.1:8080

Usually accessible only locally. 

0.0.0.0:8080

Generally listening on all IPv4 interfaces.

⚠️ Security Note

Listening on all interfaces does not mean the service should be publicly exposed. Firewall, security groups and network design still matter.

QUESTION 12

How do you check DNS resolution step by step?

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE 
hostname
nslookup example.com
dig example.com
cat /etc/resolv.conf
Hostname ↓ Resolver Configuration ↓ DNS Query ↓ DNS Response ↓ IP Address ↓ Application Connection
🎤 Interview Answer

"I first verify the hostname and use nslookup or dig to check whether DNS returns an expected address. If resolution fails, I inspect resolver configuration and DNS infrastructure."

QUESTION 13

DNS works but application still fails — why?

⭐⭐⭐⭐⭐ IMPORTANT

Successful DNS resolution only proves that the hostname can be resolved. The application can still fail because of:

  • Wrong port
  • Firewall/security-group rules
  • Routing issues
  • Service not running
  • Application errors
  • TLS problems
  • Load balancer health issues
DNS ✓ ↓ IP ✓ ↓ TCP Connection ? ↓ Port ? ↓ Application ? ↓ HTTP Response ?

🔥 TROUBLESHOOTING 15

502 Bad Gateway

⭐⭐⭐⭐⭐ DEVOPS FAVORITE

A 502 response commonly means a gateway or proxy received an invalid or unsuccessful response from an upstream server.

User ↓ Nginx / Load Balancer ↓ Upstream Application ↓ ❌ Failure ↓ 502

Check

  • Is backend application running?
  • Is backend port correct?
  • Can proxy reach backend?
  • Is backend returning a valid response?
  • Check application and proxy logs.
🔥 TROUBLESHOOTING 16

503 Service Unavailable

⭐⭐⭐⭐⭐

503 generally means the service is currently unavailable. Possible causes include overloaded services, unavailable upstreams, maintenance or unhealthy backend instances.

DevOps approach 
systemctl status app
journalctl -u app
ss -lntp
curl localhost:8080

For load-balanced environments, also check backend health and target registration.

🔥 TROUBLESHOOTING 17

504 Gateway Timeout

⭐⭐⭐⭐⭐

A 504 commonly means a gateway or proxy did not receive a timely response from an upstream service.

Client ↓ Proxy / Load Balancer ↓ Backend ↓ No timely response ↓ 504

Investigate backend latency, network connectivity, application performance and timeout configuration.

QUESTION 18

What is TLS/HTTPS troubleshooting?

⭐⭐⭐⭐

HTTPS adds TLS encryption to HTTP. Problems can occur because of certificate validation, hostname mismatch, expired certificates, unsupported protocols or trust-chain issues. 

curl -v https://example.com
Check:
  • Certificate validity
  • Hostname
  • Certificate chain
  • Server configuration
  • Client trust store
  • System time
QUESTION 19

How does system time affect HTTPS?

⭐⭐⭐⭐

TLS certificate validation depends on time validity. If a system clock is significantly incorrect, certificates may appear not yet valid or expired. 

date

On systemd-based systems: 

timedatectl
🔥 REAL-TIME SCENARIO 20

Website is not opening

⭐⭐⭐⭐⭐ MUST PRACTICE
1. DNS ↓ 2. IP Reachability ↓ 3. TCP Port ↓ 4. HTTP Response ↓ 5. Application ↓ 6. Logs

Commands

nslookup app.example.com

ping server-ip

nc -zv server-ip 443

curl -v https://app.example.com

ss -lntp

journalctl -u nginx
🎤 Strong Interview Answer

"I troubleshoot from the outside inward. First I verify DNS, then network reachability, then TCP port connectivity, then the HTTP response. If the request reaches the server but fails, I inspect the proxy, application and system logs."

🔥 REAL-TIME SCENARIO 21

Application works on localhost but not from another machine

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE
localhost works ✓ ↓ Check listening address ↓ Check firewall ↓ Check security group ↓ Check routing ↓ Check client connectivity

First checks

ss -lntp
ip addr
ip route
curl localhost:8080
Common cause

The application may be bound only to 127.0.0.1. In that case, remote systems cannot directly connect to it.

🔥 REAL-TIME SCENARIO 22

Port is listening but connection still fails

⭐⭐⭐⭐⭐

If ss shows the port listening but clients cannot connect, investigate:

  • Listening address
  • Firewall rules
  • Cloud security groups
  • Network ACLs
  • Routing
  • Load balancer configuration
  • Client-side restrictions
🎤 Interview Answer

"A listening socket proves the application has opened the port, but external connectivity can still fail because of binding, firewall, security-group, routing or load-balancer issues."
