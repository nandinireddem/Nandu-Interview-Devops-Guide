⭐⭐⭐⭐⭐ 2. Scenario: Server CPU is 95%

Problem

A production server suddenly shows 95% CPU utilization.

How would you troubleshoot?

  1. Open the Grafana CPU dashboard.
  2. Identify the affected instance.
  3. Check when the CPU increase started.
  4. Check running processes on the server.
  5. Compare CPU with traffic/request rate.
  6. Check recent deployments or configuration changes.
  7. Check memory and disk activity.
  8. Determine whether the workload needs scaling or optimization.
CPU Alert
↓
Grafana
↓
Identify Instance
↓
Linux Process Investigation
↓
Find Root Cause
↓
Fix / Scale
Interview Answer:
"I would first identify the affected instance from Grafana and determine when the CPU spike started. Then I would correlate CPU with traffic, deployments and other system metrics. On the server I would inspect processes and resource usage to identify the process causing the spike. Based on the root cause, I would optimize, restart, rollback or scale the workload."

⭐⭐⭐⭐⭐ 3. Scenario: Memory Usage is Increasing

Memory usage continuously increases and reaches a critical threshold.

Investigation

  1. Check memory dashboard.
  2. Identify affected node or application.
  3. Check whether the increase is gradual or sudden.
  4. Check application memory usage.
  5. Check container memory limits.
  6. Check for OOMKilled events.
  7. Review application logs.
  8. Investigate possible memory leak.
kubectl get pods

kubectl describe pod <pod-name>

kubectl logs <pod-name>

⭐⭐⭐⭐⭐ 5. Scenario: Application Latency is High

Users report that the application is responding slowly.

Metrics to compare

Metric Why check it?
Latency Confirms response-time degradation.
Request Rate Identifies traffic spikes.
Error Rate Identifies failing requests.
CPU Checks resource saturation.
Memory Checks memory pressure.
Database Metrics Checks database bottlenecks.
Interview Answer:
"I would correlate latency with request rate, CPU, memory, errors and database performance. If latency increased together with traffic, I would investigate capacity. If infrastructure metrics are normal, I would investigate the application and downstream dependencies."

⭐⭐⭐⭐⭐ 7. Scenario: Disk Usage is 90%

Investigation

  1. Check Grafana disk dashboard.
  2. Identify affected server.
  3. Check filesystem usage.
  4. Identify large files/directories.
  5. Check application and system logs.
  6. Check log rotation.
  7. Clean unnecessary files if safe.
  8. Increase storage if required.
df -h

du -sh /var/log/*

df -i
Do not blindly delete production files. First determine what is consuming the storage and whether the data is required.

⭐⭐⭐⭐⭐ 8. Scenario: Prometheus Target is DOWN

A target appears as DOWN in Prometheus.

Checklist

  1. Check target URL.
  2. Check target network connectivity.
  3. Check exporter status.
  4. Check metrics endpoint.
  5. Check port.
  6. Check firewall/security rules.
  7. Check service discovery configuration.
  8. Check Prometheus logs.
curl http://target:9100/metrics

⭐⭐⭐⭐⭐ 9. Scenario: Grafana Shows "No Data"

Check in this order

  1. Grafana data source.
  2. Prometheus URL.
  3. Prometheus availability.
  4. PromQL query.
  5. Dashboard time range.
  6. Dashboard variables.
  7. Prometheus target status.
Best interview approach:

"I would isolate whether the problem is in Grafana, the query, Prometheus or the monitored target instead of immediately assuming Grafana is broken."

⭐⭐⭐⭐⭐ 11. Scenario: Too Many Alerts

The monitoring system is generating hundreds of notifications.

How to handle it?

  • Group related alerts.
  • Review alert thresholds.
  • Remove noisy alerts.
  • Use inhibition rules where appropriate.
  • Use silences during planned maintenance.
  • Separate warning and critical alerts.
  • Ensure alerts represent actionable problems.
Interview Point:
A good monitoring system should reduce alert fatigue rather than generate notifications for every small metric fluctuation.

⭐⭐⭐⭐⭐ 16. Scenario: Database is Slow

What would you check?

  • Database latency
  • Connection count
  • CPU
  • Memory
  • Disk I/O
  • Slow queries
  • Application request rate
  • Database errors
Do not immediately blame the database. Correlate application latency, database metrics and traffic to identify the bottleneck.

⭐⭐⭐⭐⭐ 17. Scenario: Monitoring System Itself is Down

If Prometheus or Grafana becomes unavailable, monitoring visibility is affected.

Recovery Approach

  1. Check service/container/Pod status.
  2. Check application logs.
  3. Check resource availability.
  4. Check storage.
  5. Check configuration.
  6. Check network connectivity.
  7. Restore service.
  8. Verify metrics collection after recovery.
Monitoring is itself a production dependency. It should also be designed for reliability and appropriate backup/recovery procedures.

⭐⭐⭐⭐ 18. Scenario: Metrics Suddenly Disappear

Possible Causes

  • Exporter stopped.
  • Target became unreachable.
  • Service discovery stopped finding the target.
  • Prometheus scrape configuration changed.
  • Prometheus is experiencing resource issues.
  • Metric name or labels changed after an application update.

⭐⭐⭐⭐⭐ 20. Golden Signals

Four commonly used service-level monitoring signals are:

Signal Meaning
Latency How long requests take.
Traffic How much demand the system receives.
Errors How many requests are failing.
Saturation How close the system is to its resource limits.
These signals help engineers understand both user impact and system capacity.

⭐⭐⭐⭐⭐ 22. Complete Production Troubleshooting Example

Scenario

Users report slow responses and intermittent errors.

Approach

  1. Check Grafana latency.
  2. Check request rate.
  3. Check error rate.
  4. Check CPU and memory.
  5. Identify affected Pods.
  6. Check application logs.
  7. Check database latency.
  8. Check recent deployments.
  9. Identify root cause.
  10. Apply mitigation.
  11. Verify recovery through monitoring.
Strong Interview Answer:
"I would first quantify the impact using monitoring metrics. Then I would correlate latency and error rate with traffic, infrastructure resources, application logs and downstream dependencies. I would also check recent changes such as deployments. After identifying the most likely root cause, I would mitigate the issue, verify recovery using the same metrics and then work on the permanent fix."

⭐⭐⭐⭐⭐ 23. Monitoring Best Practices

  • Monitor user-facing services.
  • Create actionable alerts.
  • Avoid excessive alerting.
  • Monitor infrastructure and applications.
  • Use meaningful dashboards.
  • Track latency, traffic, errors and saturation.
  • Monitor the monitoring stack itself.
  • Use appropriate retention and storage policies.
  • Document incident response procedures.
  • Correlate metrics with logs and traces when available.
