Project Troubleshooting

Real-time troubleshooting scenarios for an end-to-end Cloud & DevOps project.

⭐⭐⭐⭐⭐ VERY IMPORTANT

1. Your Complete Troubleshooting Method

Identify Failure
↓
Check Logs
↓
Find First Meaningful Error
↓
Identify Failed Layer
↓
Verify Configuration
↓
Fix Root Cause
↓
Retest
↓
Monitor
Interview Answer:

"I don't immediately change multiple configurations. I first identify where the failure occurred, check the logs and isolate the root cause. Then I make the required change, rerun the affected stage and verify the result."

⭐⭐⭐⭐⭐ VERY FREQUENT

2. Jenkins Pipeline Failed

Symptoms

The CI/CD pipeline suddenly fails.

First I open the Jenkins console output and identify the first meaningful error. Then I determine the failed stage:
  • Checkout
  • Build
  • Test
  • Docker build
  • Image push
  • Deployment
I troubleshoot only that layer first.
⭐⭐⭐⭐⭐

3. Git Checkout Failed

git clone <repository-url>
I check:
  • Repository URL
  • Branch
  • Credentials
  • Repository permissions
  • Network connectivity
  • Git installation on the Jenkins agent
If authentication fails, I verify the Jenkins credential and its permissions rather than changing unrelated pipeline stages.
⭐⭐⭐⭐⭐ VERY IMPORTANT

4. Docker Build Failed

docker build -t myapp:1.0 .
I check the Docker build output and inspect:
  • Dockerfile syntax
  • Base image
  • Build context
  • File paths
  • Dependencies
  • Network access
I focus on the first actual error instead of the final generic "build failed" message.
⭐⭐⭐⭐⭐ VERY FREQUENT

5. Docker Container Exits Immediately

docker ps -a

docker logs <container-id>

docker inspect <container-id>
I check the container logs and inspect the configured command. Typical causes include:
  • Application startup failure
  • Incorrect CMD or ENTRYPOINT
  • Missing environment variables
  • Missing dependencies
  • Process exits immediately
⭐⭐⭐⭐⭐

6. Docker Container Is Running but Application Is Not Accessible

docker ps
docker logs <container>
docker inspect <container>
I verify:
  • Application listening port
  • Container port
  • Host port mapping
  • Application listening address
Example: 
docker run -p 8080:8080 myapp
Then test: 
curl http://localhost:8080
⭐⭐⭐⭐⭐ VERY IMPORTANT

7. Docker Image Push Failed

I check:
  • Registry authentication
  • Image name
  • Image tag
  • Repository permissions
  • Network connectivity
I also verify that the image actually exists locally: 
docker images
⭐⭐⭐⭐⭐ VERY FREQUENT

8. Kubernetes Pod Is Pending

kubectl get pods

kubectl describe pod <pod-name>

kubectl get events
I check for:
  • Insufficient CPU or memory
  • Node availability
  • Scheduling constraints
  • Taints and tolerations
  • Node selectors
  • Persistent volume issues
The describe output and events usually provide the most useful clues.
⭐⭐⭐⭐⭐ VERY FREQUENT

9. Kubernetes Pod Is in CrashLoopBackOff

kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>
CrashLoopBackOff means the container repeatedly starts and then fails. I would investigate:
  • Application startup error
  • Incorrect configuration
  • Missing environment variables
  • Secrets
  • Dependency failures
  • Incorrect command
  • Health probe configuration
⭐⭐⭐⭐⭐

10. Kubernetes Shows ImagePullBackOff

I check:
  • Image name
  • Image tag
  • Registry availability
  • Image existence
  • Registry credentials
  • Image pull permissions
Then: 
kubectl describe pod <pod-name>
I look at the Events section for the exact image-pull error.
⭐⭐⭐⭐⭐ VERY IMPORTANT

11. Application Is Running but Service Is Not Working

kubectl get svc

kubectl get endpoints

kubectl get pods --show-labels
I verify that the Service selector matches the Pod labels. Then I verify that the Service port and targetPort match the application configuration. A Service with no healthy endpoints cannot route traffic to the application Pods.
⭐⭐⭐⭐⭐

12. Kubernetes Deployment Rollout Is Stuck

kubectl rollout status deployment/myapp

kubectl get pods

kubectl describe deployment myapp
I check whether new Pods are:
  • Failing to start
  • Unable to pull the image
  • Failing readiness probes
  • Unable to schedule
  • Missing configuration
If the release is confirmed unhealthy, I can consider rolling back to the previous known-good revision.
⭐⭐⭐⭐⭐ VERY IMPORTANT

13. Terraform Apply Failed

terraform plan
terraform apply
I read the exact Terraform error and identify which resource failed. I then check:
  • AWS credentials
  • Region
  • IAM permissions
  • Resource limits
  • Resource dependencies
  • Existing resource conflicts
  • Terraform configuration
I avoid repeatedly running apply without understanding the failure.
⭐⭐⭐⭐⭐

14. Terraform Says Resource Already Exists

I first determine whether the resource was created outside Terraform or already exists in the expected state. Depending on the situation, the resource may need to be imported into Terraform state or the configuration/state relationship may need to be corrected. The correct solution depends on how the resource was originally created.
⭐⭐⭐⭐⭐ VERY IMPORTANT

15. AWS Authentication Error

aws sts get-caller-identity
I verify:
  • AWS credentials
  • Credential expiration
  • Configured profile
  • Region
  • IAM permissions
  • Environment variables
The STS identity command is a useful first check to confirm which AWS identity the environment is actually using.
⭐⭐⭐⭐

16. EKS Cluster Is Working but kubectl Cannot Connect

kubectl get nodes
I check:
  • Kubeconfig
  • AWS identity
  • Cluster endpoint
  • Network connectivity
  • Cluster authentication
  • Authorization / RBAC
I would verify that kubectl is pointing to the correct cluster.
⭐⭐⭐⭐⭐ VERY IMPORTANT

17. Application Became Unhealthy After Deployment

Deployment
↓
Pods Running?
↓
Readiness Probe?
↓
Application Logs?
↓
Service Endpoints?
↓
External Dependencies?
↓
Root Cause
A Pod being in the Running state does not automatically mean the application is ready to receive traffic. I check readiness, logs, dependencies and Service endpoints.
⭐⭐⭐⭐⭐

18. Monitoring Shows High CPU

kubectl top pods
kubectl top nodes
I identify whether the high CPU usage is caused by:
  • Application workload
  • Traffic increase
  • Resource limits
  • Application bug
  • Insufficient capacity
Then I correlate the Kubernetes metrics with application behavior before deciding whether scaling is required.
⭐⭐⭐⭐

19. Grafana Dashboard Shows No Data

I check:
  • Prometheus is running
  • Prometheus is scraping targets
  • Grafana data source configuration
  • Prometheus URL
  • Query correctness
  • Target health
The first thing I verify is whether Prometheus itself has the expected metrics.
⭐⭐⭐⭐⭐ VERY IMPORTANT

20. How Would You Handle a Production Incident?

My approach would be:
  1. Understand the impact.
  2. Identify the affected component.
  3. Check monitoring and logs.
  4. Stop further harmful changes.
  5. Restore service using the safest known solution.
  6. Verify recovery.
  7. Investigate root cause.
  8. Document the incident and preventive action.
The priority during an incident is to restore service safely, then perform deeper root-cause analysis.
⭐⭐⭐⭐⭐ INTERVIEW GOLD

21. One Troubleshooting Example to Remember

Scenario

"After a new deployment, the application became unavailable. What would you do?"

Step 1: Check whether the Pods are running. 

kubectl get pods

Step 2: Check Pod logs. 

kubectl logs <pod-name>

Step 3: Describe the Pod if necessary. 

kubectl describe pod <pod-name>

Step 4: Check Service and endpoints. 

kubectl get svc
kubectl get endpoints

Step 5: Check whether the new image or configuration caused the problem.

Step 6: If the new release is confirmed as the cause, restore the previous known-good version and then investigate the root cause.

kubectl connection failure Kubeconfig → AWS identity → network → RBAC

Grafana no data Prometheus → targets → data source → query
