DevSecOps Real-Time Scenarios

Production-style security situations, troubleshooting approaches and interview-ready answers.

⭐⭐⭐⭐⭐ 1. Trivy Finds a Critical Vulnerability

Scenario:
Your CI/CD pipeline builds a Docker image. Trivy reports a CRITICAL vulnerability. What will you do?

Approach

  1. Check the vulnerability ID and affected package.
  2. Confirm whether the vulnerability actually affects the application.
  3. Check whether a patched package or newer base image is available.
  4. Update the dependency or base image.
  5. Rebuild the Docker image.
  6. Run Trivy again.
  7. Allow promotion only if the organization's security policy is satisfied.
Interview Answer:
"I would first analyze the vulnerability and affected package. If it violates our security policy, I would block the image from promotion, update the vulnerable dependency or base image, rebuild the image and rerun the scan."

⭐⭐⭐⭐⭐ 2. AWS Secret Committed to Git

Scenario:
A developer accidentally commits an AWS access key to GitHub. What do you do?

Immediate Actions

  1. Revoke or rotate the exposed credential immediately.
  2. Check CloudTrail or relevant logs for suspicious usage.
  3. Remove the secret from the source.
  4. Check Git history and clean it if necessary.
  5. Store the replacement credential securely.
  6. Add secret scanning to the CI/CD pipeline.
Important:
Do not assume that deleting the key from the latest commit makes the credential safe. The credential may still exist in Git history or may already have been copied.
Interview Answer:
"My first priority is credential revocation or rotation. Then I would investigate possible usage, remove the secret, clean the repository if required, replace it with a securely managed credential and add secret scanning to prevent recurrence."

⭐⭐⭐⭐⭐ 3. Gitleaks Fails the Pipeline

Scenario:
The Gitleaks stage fails during a deployment pipeline. What do you check?
  1. Read the Gitleaks output.
  2. Identify the detected secret.
  3. Determine whether it is a real secret or false positive.
  4. If real, revoke or rotate the credential.
  5. Remove the secret from the repository.
  6. Use secure secret storage.
  7. Rerun the pipeline.
Interview Answer:
"I would inspect the Gitleaks finding, verify whether it is a true secret, immediately rotate it if necessary, remove it from source control and rerun the pipeline after remediation."

⭐⭐⭐⭐⭐ 4. SonarQube Quality Gate Failed

Scenario:
The build passes, but the SonarQube quality gate fails. Can you deploy?

Normally, if the quality gate is configured as a blocking condition, the pipeline should not promote the artifact until the issue is resolved or an authorized exception is applied.

What to Check?

  • Security vulnerabilities
  • Bugs
  • Code smells
  • Coverage requirements
  • Duplicated code
  • Quality gate configuration
Interview Answer:
"I would inspect the failed quality gate conditions. If the gate is configured as a blocking policy, I would fix the reported issues before promoting the application."

⭐⭐⭐⭐⭐ 5. Developer Says the Security Scan Is a False Positive

Scenario:
A scanner reports a vulnerability, but the developer believes it is a false positive. What do you do?
  1. Verify the finding manually.
  2. Check the vulnerability details and affected component.
  3. Confirm whether the vulnerable code path is actually used.
  4. Review the scanner documentation and evidence.
  5. Document the finding.
  6. Follow the organization's approved exception process if it is genuinely a false positive.
Never simply suppress security findings without validation and documentation.

⭐⭐⭐⭐⭐ 6. Vulnerable Base Image

Scenario:
Your Docker image uses an outdated Ubuntu or Alpine base image and the scanner reports many vulnerabilities.

Solution

  1. Check for a supported newer base image.
  2. Update the Dockerfile.
  3. Rebuild the image.
  4. Run the vulnerability scan again.
  5. Test the application.
  6. Promote the new image after security checks pass.
FROM ubuntu:24.04

The exact base image version should be selected according to the application's compatibility and organizational standards.

⭐⭐⭐⭐⭐ 7. Critical Vulnerability Found in Production

Scenario:
A critical vulnerability is discovered in a production application. What is your response?

Important Actions

  • Assess severity and exposure.
  • Identify affected systems.
  • Apply available patches or mitigations.
  • Restrict exposure if necessary.
  • Deploy the fix safely.
  • Monitor for exploitation.
  • Document the incident.

⭐⭐⭐⭐ 8. Security Scan Makes Pipeline Too Slow

Scenario:
The security team added many scans and now CI/CD takes 45 minutes. Developers are complaining.

Possible Approach

  • Run lightweight checks earlier.
  • Run deeper scans at appropriate pipeline stages.
  • Cache dependencies where appropriate.
  • Run independent security checks in parallel.
  • Avoid duplicate scanning.
  • Optimize scanner configuration.
Interview Answer:
"I would optimize the pipeline rather than simply removing security. Fast checks can run early, independent scans can run in parallel and deeper security testing can run at appropriate stages."

⭐⭐⭐⭐⭐ 9. Security Scan Passes but Production Is Still Compromised

Scenario:
All CI security scans passed, but a production security incident still occurred. Does that mean DevSecOps failed?

Not necessarily. Security scanners cover specific classes of risks; they do not guarantee that an application is completely secure.

Investigate

  • Application vulnerabilities
  • Cloud configuration
  • IAM permissions
  • Network exposure
  • Runtime vulnerabilities
  • Credential compromise
  • Monitoring and detection gaps
Key Point:
"DevSecOps reduces security risk through continuous controls, but security is a continuous process rather than a one-time guarantee."

⭐⭐⭐⭐ 10. How Would You Secure a Jenkins Pipeline?

  • Use Jenkins Credentials instead of hard-coded secrets.
  • Apply least-privilege permissions.
  • Keep Jenkins and plugins updated.
  • Restrict administrative access.
  • Use security scanning stages.
  • Protect production deployment stages.
  • Audit pipeline activity.
  • Secure Jenkins agents.

⭐⭐⭐⭐ 11. How Would You Secure a Kubernetes Deployment?

  • Use RBAC.
  • Follow least privilege.
  • Scan container images.
  • Do not store sensitive credentials directly in manifests.
  • Use NetworkPolicies where appropriate.
  • Apply Pod Security controls.
  • Restrict container privileges.
  • Monitor workloads and cluster activity.

⭐⭐⭐⭐ 12. IaC Scan Finds a Public AWS Resource

Scenario:
An IaC scanner reports that a Terraform resource could expose something publicly. What do you do?
  1. Identify the affected resource.
  2. Understand why public access is configured.
  3. Check whether it is actually required.
  4. Restrict access if unnecessary.
  5. Update the Terraform code.
  6. Run the security scan again.
  7. Apply the infrastructure only after validation.

⭐⭐⭐⭐⭐ 13. Complete Interview Scenario

Question:
"Explain how you would implement DevSecOps for a project from GitHub to production."
Interview Answer:

"I would start by integrating security into the CI/CD pipeline. After a developer pushes code to GitHub, I would run secret scanning and SAST. Then I would scan dependencies for known vulnerabilities. After building the Docker image, I would scan the image using Trivy. Infrastructure definitions can also be scanned before deployment. After deployment to a test environment, I would run appropriate dynamic security testing. Security gates would prevent artifacts that violate the organization's defined policies from progressing to production. Finally, I would monitor the production environment and continuously remediate vulnerabilities."
