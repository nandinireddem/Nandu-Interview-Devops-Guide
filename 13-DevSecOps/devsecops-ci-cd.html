DevSecOps in CI/CD

How security checks are integrated into automated CI/CD pipelines using practical stages, security gates and real-time examples.

⭐⭐⭐⭐⭐ 1. Why Integrate Security into CI/CD?

CI/CD automates building, testing and deploying applications. DevSecOps extends this automation by adding security checks into the same delivery process.

This allows security issues to be detected before an insecure artifact reaches production.

Interview Answer:
"We integrate security into CI/CD so that security checks become automated and repeatable. The pipeline can scan source code, dependencies, secrets, container images and infrastructure before deployment."

⭐⭐⭐⭐⭐ 4. Security Gates

A security gate determines whether the pipeline can continue after a security check.

Example Policy

  • Critical vulnerabilities → Block deployment
  • High vulnerabilities → Block or require approval
  • Medium vulnerabilities → Track and remediate
  • Low vulnerabilities → Track according to policy
The exact thresholds should be defined by the organization's security policy. Do not assume that every vulnerability should automatically fail every pipeline.

⭐⭐⭐⭐⭐ 5. Example Jenkins Pipeline

pipeline {

    agent any

    stages {

        stage('Checkout') {
            steps {
                git 'https://github.com/example/project.git'
            }
        }

        stage('SAST') {
            steps {
                echo 'Run SonarQube analysis'
            }
        }

        stage('Secret Scan') {
            steps {
                echo 'Run Gitleaks'
            }
        }

        stage('Dependency Scan') {
            steps {
                echo 'Run dependency scanner'
            }
        }

        stage('Build') {
            steps {
                echo 'Build application'
            }
        }

        stage('Docker Build') {
            steps {
                sh 'docker build -t myapp:latest .'
            }
        }

        stage('Container Scan') {
            steps {
                sh 'trivy image myapp:latest'
            }
        }

        stage('Deploy') {
            steps {
                echo 'Deploy application'
            }
        }
    }
}
Interview Point:
"The commands are examples. In a real project, I would configure credentials, scanners, severity thresholds and quality gates based on the organization's security requirements."

⭐⭐⭐⭐⭐ 6. Example GitHub Actions Flow

name: DevSecOps Pipeline

on:
  push:

jobs:

  security:
    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Secret Scan
        run: |
          gitleaks detect --source .

      - name: Build Docker Image
        run: |
          docker build -t myapp:${{ github.sha }} .

      - name: Container Scan
        run: |
          trivy image myapp:${{ github.sha }}

In production, scanners should be pinned and configured according to the organization's security and CI/CD standards.

⭐⭐⭐⭐⭐ 7. What If Trivy Finds a Critical Vulnerability?

  1. Trivy scans the image.
  2. A critical vulnerability is detected.
  3. The configured security policy evaluates the result.
  4. If critical vulnerabilities are blocking conditions, the pipeline fails.
  5. The image is not promoted to the next environment.
  6. The vulnerable package or base image is updated.
  7. The image is rebuilt and scanned again.
Interview Answer:
"If Trivy finds a critical vulnerability, I would check the affected package and severity, apply the organization's policy, block the image from promotion if it violates the policy, remediate the vulnerability and rerun the pipeline."

⭐⭐⭐⭐⭐ 8. What If Gitleaks Finds an AWS Credential?

First priority: revoke or rotate the exposed credential.
  1. Stop the pipeline.
  2. Identify the exposed credential.
  3. Revoke or rotate it immediately.
  4. Remove the secret from the source.
  5. Clean repository history if required.
  6. Store the replacement credential securely.
  7. Run the pipeline again.

Deleting the secret from the current file alone may not remove it from Git history.

⭐⭐⭐⭐⭐ 9. How Do You Store Secrets in CI/CD?

Never hard-code production credentials directly inside pipeline files.

Common Options

  • GitHub Secrets
  • Jenkins Credentials
  • AWS Secrets Manager
  • HashiCorp Vault
  • Cloud-specific secret management services
Interview Answer:
"I store sensitive credentials in a dedicated secrets-management solution or the CI/CD platform's protected credential store and inject them only when required."

⭐⭐⭐⭐⭐ 10. How Do You Prevent Insecure Deployment?

  • Run automated security scans.
  • Configure security gates.
  • Use least-privilege credentials.
  • Protect production environments.
  • Require approvals where appropriate.
  • Scan container images.
  • Scan infrastructure definitions.
  • Monitor deployed applications.

⭐⭐⭐⭐ 11. Security vs Pipeline Speed

Security checks should be designed so they provide strong protection without unnecessarily slowing development.

Fast Checks Slower Checks
Secret scanning Full DAST scans
Basic SAST Large dependency analysis
Dockerfile linting Deep security testing

A common approach is to run fast checks early and deeper tests at appropriate later stages.

⭐⭐⭐⭐ 12. Security Pipeline Failure Troubleshooting

Scenario

"The deployment failed because the security stage failed."

Approach

  1. Identify which security tool failed.
  2. Read the scanner output.
  3. Identify severity and affected component.
  4. Determine whether the failure is expected.
  5. Fix the vulnerability or configuration.
  6. Rerun the scan.
  7. Continue deployment only when policy requirements are satisfied.
