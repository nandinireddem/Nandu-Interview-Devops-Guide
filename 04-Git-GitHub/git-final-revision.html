⭐⭐⭐⭐⭐ 1. Git Fundamentals

Q1. What is Git?

Git is a distributed version control system used to track changes in source code and enable developers to collaborate safely.

Q2. Why is Git distributed?

Each developer normally has a complete local repository containing the project history, so many Git operations can be performed locally.

Q3. Git vs GitHub?

Git GitHub
Version control system Hosting and collaboration platform
Runs locally Provides remote repositories
Tracks project history Provides PRs, reviews, issues and CI integrations

Q4. What is a Git repository?

A Git repository contains project files together with Git metadata and version history.

Q5. What are Working Tree, Staging Area and Repository?

Area Meaning
Working Tree Current files and modifications
Staging Area Changes selected for the next commit
Repository Committed project history

⭐⭐⭐⭐⭐ 3. Branches & Branching

What is a branch?

A branch is a movable reference to a commit that allows independent development without directly changing another branch.

Why use branches?

  • Feature isolation
  • Parallel development
  • Bug fixes
  • Code review
  • Production protection
main
 ├── feature/login
 ├── feature/payment
 └── bugfix/api-error
git branch
git switch main
git switch -c feature/login
git branch -d feature/login

⭐⭐⭐⭐⭐ 4. Merge vs Rebase

Merge Rebase
Combines histories Replays commits onto another base
Can create merge commit Usually creates linear history
Does not rewrite existing commits Rewrites commit history
Safer for shared branches Use carefully on shared branches 
git switch main
git merge feature/login

git switch feature/login
git rebase main
Avoid rebasing shared commits when other developers depend on them.

⭐⭐⭐⭐⭐ 5. Merge Conflict

What is a merge conflict?

A merge conflict occurs when Git cannot automatically determine which changes should be kept. 
git merge feature/login

# Resolve conflicting files

git add .
git commit

During rebase

git rebase main

# Resolve conflict

git add .
git rebase --continue

Abort

git merge --abort
git rebase --abort
Interview answer: I inspect the conflicting files, understand both changes, resolve the conflict carefully, stage the resolved files and complete the merge or rebase.

⭐⭐⭐⭐⭐ 6. Reset vs Revert

Reset Revert
Moves HEAD / branch reference Creates a new reversing commit
Can rewrite local history Preserves existing history
Useful for local work Preferred for shared history

Reset modes

git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1

Revert

git revert <commit-id>
Be careful with git reset --hard because uncommitted changes can be lost.

⭐⭐⭐⭐⭐ 7. Git Stash

Why use stash?

Git stash temporarily stores uncommitted changes so you can switch to another task without creating an unfinished commit. 
git stash
git stash list
git stash pop
git stash apply
git stash drop
You are working on a feature when an urgent production bug arrives. Stash the unfinished work, switch to the bugfix branch, fix the issue, then restore your previous work.

⭐⭐⭐⭐⭐ 8. Remote, Fetch, Pull & Push

What is origin?

origin is the conventional default name for a remote repository. 
git remote -v
git remote add origin <URL>

git fetch origin
git pull origin main
git push origin main
Fetch Pull
Downloads remote updates Downloads and integrates changes
Does not merge into current branch Can update current branch

⭐⭐⭐⭐⭐ 10. Branch Protection

  • Require Pull Requests
  • Require approvals
  • Require CI checks
  • Restrict direct pushes
  • Protect production branches
A developer accidentally pushes untested code to main. Branch protection with PR reviews and required CI checks can prevent unsafe direct changes.

⭐⭐⭐⭐⭐ 11. Git Tags & Releases

Tags identify specific versions or release points in Git history. 
git tag

git tag -a v1.0.0 -m "Release v1.0.0"

git push origin v1.0.0

git push origin --tags

git show v1.0.0

Semantic Versioning

MAJOR.MINOR.PATCH

1.4.2

1 = breaking change
4 = new feature
2 = bug fix
CI/CD pipelines can use release tags such as v2.0.0 to trigger controlled production deployments.

⭐⭐⭐⭐⭐ 12. Cherry-Pick

Cherry-pick applies the changes from a specific commit onto the current branch. 
git cherry-pick <commit-id>
A bug fix exists in development, but production needs only that specific fix. Cherry-pick the required commit instead of merging all development changes. 
git cherry-pick <commit-id>

# Resolve conflict
git add .
git cherry-pick --continue

# Abort
git cherry-pick --abort

⭐⭐⭐⭐⭐ 13. Reflog & Recovery

Reflog records local movements of references such as HEAD and branch pointers. 
git reflog
If a developer accidentally resets a branch and appears to lose a commit, reflog can often help locate the previous commit reference. 
git reflog

git reset --hard <recovered-commit>
Reflog is primarily local and is not a permanent remote backup.

⭐⭐⭐⭐ 15. .gitignore

.gitignore specifies files and directories that Git should normally ignore when detecting untracked files. 
.env
*.log
node_modules/
.terraform/
*.tfstate
*.pem
Adding a file to .gitignore does not automatically remove a file that is already tracked.

⭐⭐⭐⭐ 16. Git Clean

git clean removes untracked files from the working tree. 
git clean -n
git clean -f
Always use git clean -n first to inspect what would be removed.

⭐⭐⭐⭐ 17. Git Hooks

Git hooks are scripts that execute automatically at specific Git lifecycle events.
  • pre-commit
  • commit-msg
  • pre-push
  • post-merge
A pre-commit hook can run formatting, linting or validation before allowing a commit.

⭐⭐⭐⭐ 18. Git Bisect

Git bisect uses binary search through commit history to identify the commit that introduced a bug. 
git bisect start
git bisect bad
git bisect good <known-good-commit>

# Continue marking commits good/bad

git bisect reset

⭐⭐⭐ 19. Git Submodules

A Git submodule allows one repository to include another repository at a specific commit. 
git submodule add <repository-url>
git submodule update --init --recursive

⭐⭐⭐ 20. Git LFS

Git LFS is designed for large files by keeping pointers in Git while large objects are managed separately.

It is useful for large binaries, media and other files that are not ideal for normal Git object storage.

⭐⭐⭐⭐⭐ 21. Git Security

Should secrets be committed?

No. Passwords, API keys, AWS credentials, tokens and private keys should never be committed to Git.

Best practices

  • Environment variables
  • Secret managers
  • GitHub encrypted secrets
  • Secret scanning
  • Credential rotation
  • Never commit private keys
If a secret is accidentally pushed, deleting the file is not enough. Treat the credential as compromised and rotate it immediately.

⭐⭐⭐⭐⭐ 24. Most Important Real-Time Scenarios

Scenario 1 — Bad code pushed to main

Use git revert for a shared branch because it preserves history through a new reversing commit. 
git revert <bad-commit>
git push origin main

Scenario 2 — Accidentally deleted commit

Use git reflog to locate the previous commit and recover it. 
git reflog
git reset --hard <commit-id>

Scenario 3 — Only one production fix is required

Use git cherry-pick instead of merging an entire development branch. 
git switch production
git cherry-pick <fix-commit>

Scenario 4 — Branch is behind main

git fetch origin

# Merge approach
git merge origin/main

# Rebase approach
git rebase origin/main

Scenario 5 — Push rejected

The remote contains commits that your local branch does not have. Fetch and integrate the remote changes before pushing again. 
git fetch origin
git pull --rebase origin main
git push origin main
Do not blindly use git push --force on a shared branch.

⭐⭐⭐⭐⭐ 25. Production Rollback Scenario

A production deployment failed. First identify the currently deployed version and the last known-good release. If releases are tagged, redeploy the known-good version or immutable artifact instead of rewriting production Git history. 
git tag
git show v1.4.0
Known-Good Tag
↓
Known-Good Artifact
↓
Redeploy
↓
Verify

⭐⭐⭐⭐ 26. Common Git Interview Traps

Question Correct Answer
Is GitHub Git? No. Git is the version control system; GitHub is a hosting and collaboration platform.
Does git fetch merge? No. It downloads remote updates without merging them.
Does git pull only download? No. It fetches and integrates changes.
Is reset the same as revert? No. Reset moves references; revert creates a reversing commit.
Is rebase always better than merge? No. It depends on the workflow and shared-history requirements.
Does .gitignore remove tracked files? No.
Can deleting a secret remove it completely? No. Rotate the secret and clean history when appropriate.
Can reflog recover everything? No. It is local and entries can expire.

🎯 Explain Git in 1 Minute

Git is a distributed version control system used to track source code changes and enable collaboration. Developers normally work on feature branches, commit their changes and push them to a remote repository such as GitHub. A Pull Request is then used for code review and automated CI checks before merging changes into the main branch. Git provides commands such as merge, rebase, reset, revert, stash, cherry-pick and reflog for handling different development scenarios. In DevOps, Git acts as the source of truth for application code and CI/CD configuration. Tags can identify releases and commits or tags can trigger automated build, test, security scanning and deployment pipelines. For production safety, I would use protected branches, code review, CI validation, secure secret management and controlled releases.
