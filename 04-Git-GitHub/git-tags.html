Git Tags & Releases

Git tags, annotated tags, versioning, releases, rollback strategies and practical DevOps deployment workflows.

⭐⭐⭐⭐ GIT TAGS — IMPORTANT FOR DEVOPS

Git tags are used to mark specific points in Git history, commonly for software releases such as v1.0.0, v2.0.0 or v2.1.3.

In DevOps, tags are especially useful for identifying exactly which version of source code was built and deployed.

1. What is a Git Tag?

A Git tag is a reference that points to a specific Git object, commonly a commit.

Example

v1.0.0
v1.1.0
v2.0.0

Instead of remembering a commit hash, teams can use a meaningful version name to identify a release.

Interview-ready answer:

"Git tags are used to mark specific points in the repository history. They are commonly used to identify software releases and stable versions."

2. Why are Git Tags important in DevOps?

Tags provide a stable reference to the exact source-code version used for a release or deployment.
Code Changes
↓
Commit
↓
Git Tag v1.0.0
↓
CI Build
↓
Docker Image
↓
Production Deployment

This makes releases traceable and helps teams identify exactly which version is running in an environment.

3. How do you list Git tags?

git tag

Example

v1.0.0
v1.1.0
v1.2.0
v2.0.0

4. How do you create a lightweight tag?

git tag v1.0.0

This creates a lightweight tag pointing to the current commit.

Tag a specific commit

git tag v1.0.0 abc1234

5. What is an annotated tag?

An annotated tag is a full Git object containing metadata such as the tagger, date and message.

Create one

git tag -a v1.0.0 -m "Release version 1.0.0"

Annotated tags are generally preferred for official releases because they contain release metadata.

6. Lightweight Tag vs Annotated Tag

Lightweight Tag Annotated Tag
Simple reference Full Git object
Minimal metadata Contains tagger, date and message
Useful for simple references Preferred for official releases
git tag v1.0.0 git tag -a v1.0.0 -m "Release"
Interview answer:

"A lightweight tag is a simple pointer to a commit. An annotated tag is a Git object containing metadata such as the tagger, date and message. Annotated tags are commonly preferred for releases."

7. How do you view information about a tag?

git show v1.0.0

This displays information about the tag and the referenced commit.

8. How do you push a tag to GitHub?

Push one tag

git push origin v1.0.0

Push all tags

git push origin --tags
Creating a tag locally does not automatically make it available on the remote repository. You need to push it.

9. How do you delete a local tag?

git tag -d v1.0.0

This removes the tag from your local repository.

10. How do you delete a remote tag?

git push origin --delete v1.0.0

This removes the tag from the remote repository.

Alternative syntax

git push origin :refs/tags/v1.0.0

11. How do you checkout a tag?

git checkout v1.0.0

This places you at the commit referenced by the tag.

If you make new commits from a tag without creating a branch, you can end up in a detached HEAD state.

12. What is detached HEAD when checking out a tag?

A detached HEAD means HEAD points directly to a commit instead of pointing to a local branch.

Example

git checkout v1.0.0

You can inspect or test that version safely. If you need to develop from that point, create a branch. 

git switch -c hotfix-from-v1.0.0

13. How do you create a tag on a specific commit?

git tag -a v1.0.0 abc1234 -m "Release v1.0.0"

The tag will point to the specified commit instead of the current HEAD.

14. How do you list tags matching a pattern?

git tag -l "v1.*"

Example

v1.0.0
v1.1.0
v1.2.0

15. What is semantic versioning?

Semantic Versioning commonly follows the format:

MAJOR.MINOR.PATCH
Part Meaning
MAJOR Breaking or incompatible changes
MINOR Backward-compatible new functionality
PATCH Backward-compatible bug fixes

Example

1.4.2

1 → Major
4 → Minor
2 → Patch

16. What is a GitHub Release?

A GitHub Release is a published release associated with a Git tag, providing a convenient way to distribute and document a specific version of a project.

A release can include:

  • Version number
  • Release notes
  • Changelog
  • Links to source code
  • Build artifacts
  • Binary files

17. Git Tag vs GitHub Release

Git Tag GitHub Release
Git reference GitHub publishing feature
Points to a Git object Usually associated with a tag
Can exist without GitHub Requires GitHub platform
Used for version identification Used for publishing/documenting a release

19. How can CI/CD use Git tags?

A CI/CD pipeline can be configured to trigger when a version tag is pushed.

Example concept

git push origin v2.0.0

        ↓

CI/CD detects tag

        ↓

Build application

        ↓

Run tests

        ↓

Build Docker image

        ↓

Push image

        ↓

Deploy version 2.0.0

This creates a clear relationship between source-code versions and deployments.

20. Why are immutable version tags useful in DevOps?

A release tag provides a stable identifier for the source version that was intended for a particular release.

This improves:

  • Traceability
  • Rollback planning
  • Release auditing
  • Deployment tracking
  • Incident investigation
In production workflows, teams should establish a policy for protecting release tags and avoiding accidental tag movement.

21. How would you rollback to an earlier tagged version?

First identify the desired stable tag. 

git tag

git show v1.3.0

For inspection or creating a branch from that version: 

git switch -c rollback-v1.3.0 v1.3.0

In a real production environment, rollback is usually handled through the deployment system rather than rewriting the main branch history.

DevOps interview point:

"I would prefer redeploying a known-good version such as a release tag or corresponding immutable artifact rather than rewriting production Git history."

22. Can you move an existing tag?

Yes, technically a tag can be deleted and recreated at another commit, but moving an already-published release tag is generally discouraged.

Example

git tag -d v1.0.0

git tag v1.0.0 <new-commit>

git push origin v1.0.0 --force
Avoid moving published production tags unless your team's release policy explicitly allows it. Prefer creating a new version such as v1.0.1.

23. Real-Time Scenario: Production is running v2.1.0

An incident occurs and you discover that v2.0.5 was the last known-good release.

Production
↓
v2.1.0 ❌
↓
Known-good release
↓
v2.0.5 ✅
↓
Redeploy

The tag provides a reliable reference for locating the source version associated with the earlier release.

24. How do you find which commit a tag points to?

git rev-list -n 1 v1.0.0

You can also inspect the tag with: 

git show v1.0.0
