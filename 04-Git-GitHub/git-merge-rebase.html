Git Merge & Rebase

Understand merge, fast-forward merge, three-way merge, rebase, conflicts, interactive rebase and real-time DevOps scenarios.

⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

1. What is Git Merge?

Interview Answer:

Git merge is used to combine the changes from one branch into another branch.

For example, after completing a feature, we can merge the feature branch into the main branch. 

git switch main

git merge feature-login
Remember:

The branch you are currently on is the branch that receives the changes.

⭐⭐⭐⭐⭐ MUST KNOW

2. How does Git Merge work?

Git examines the commit history of both branches and determines how the histories can be combined.

Depending on the commit structure, Git may perform a fast-forward merge or a three-way merge.

main
↓
Common Ancestor
↙ ↘
Feature
Main
⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

3. What is a Fast-Forward Merge?

Interview Answer:

A fast-forward merge happens when the target branch has not diverged from the branch being merged.

Git simply moves the target branch pointer forward. No additional merge commit is required. 

Before:

A --- B --- C
      \
       feature


After:

A --- B --- C
           ↑
          main
          feature
Example:

If main has no new commits after the feature branch was created, Git can simply move main forward to the latest feature commit.

⭐⭐⭐⭐⭐ MUST KNOW

4. What is a Three-Way Merge?

Interview Answer:

A three-way merge is used when both branches have new commits after their common ancestor.

Git uses three points:

  • Common ancestor
  • Current branch tip
  • Incoming branch tip
        C --- D
       /
A --- B
       \
        E --- F

B = Common Ancestor

C,D = Feature branch

E,F = Main branch

Because both branches changed independently, Git may create a new merge commit.

⭐⭐⭐⭐⭐ INTERVIEW FAVORITE

5. What is a Merge Commit?

Interview Answer:

A merge commit is a special commit created when Git combines two diverged branch histories. 

        C
       / \
A --- B   M
       \ /
        D

M = Merge Commit

A merge commit normally has two parent commits.

⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

6. What is Git Rebase?

Interview Answer:

Git rebase moves or replays commits from one branch on top of another base commit.

It is commonly used to create a cleaner, more linear commit history. 

Before:

A --- B --- C
       \
        D --- E
             feature


After rebase:

A --- B --- C --- D' --- E'
                       feature
Important:

The rebased commits are recreated, so their commit IDs change.

⭐⭐⭐⭐⭐ MUST KNOW

7. How do you rebase a feature branch onto main?

git switch feature-login

git rebase main

Git takes the feature commits and replays them on top of the latest main branch. 

Before:

A --- B --- C       main
       \
        D --- E     feature


After:

A --- B --- C --- D' --- E'
                          feature
⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

8. What is the difference between Merge and Rebase?

Merge Rebase
Combines histories Replays commits
Can create a merge commit Usually creates a linear history
Preserves existing commit history Rewrites commit history
Does not normally change existing commit IDs Rebased commits receive new IDs
Safer for shared branches Needs caution on shared branches
Interview Shortcut:

Merge = preserve and combine histories.

Rebase = replay commits onto a new base.

⭐⭐⭐⭐⭐ DEVOPS FAVORITE

9. Why does rebase create a cleaner history?

Rebase removes unnecessary merge commits from the feature development history and creates a more linear sequence of commits. 

Merge:

A --- B -------- M
       \        /
        C --- D


Rebase:

A --- B --- C' --- D'

A linear history can make it easier to understand when changes were introduced and troubleshoot commit history.

⭐⭐⭐⭐⭐ VERY IMPORTANT

10. Why should you be careful when rebasing a shared branch?

Interview Answer:

Rebase rewrites commit history. Because commit IDs can change, rebasing a branch that other developers are already using can cause synchronization problems.

⚠️ Important Interview Point:

Avoid rebasing shared/public branches unless the team has specifically agreed on that workflow.

⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

11. What is a Merge Conflict?

Interview Answer:

A merge conflict occurs when Git cannot automatically determine which changes should be kept.

This commonly happens when two branches modify the same lines of the same file differently. 

<<<<<<< HEAD
version from main
=======
version from feature
>>>>>>> feature-login
⭐⭐⭐⭐⭐ MUST KNOW

12. How do you resolve a merge conflict?

  1. Run git status.
  2. Identify the conflicted files.
  3. Open the files.
  4. Understand both versions.
  5. Choose or combine the correct changes.
  6. Remove conflict markers.
  7. Stage the resolved files.
  8. Complete the merge.
git status

# Fix the file manually

git add app.py

git commit -m "Resolve merge conflict"
⭐⭐⭐⭐⭐ REBASE CONFLICT

13. How do you resolve a conflict during rebase?

When a conflict occurs during rebase, Git pauses the rebase. We resolve the file manually and then continue the rebase. 

git status

# Fix the conflicted file

git add app.py

git rebase --continue
⭐⭐⭐⭐ IMPORTANT

14. How do you abort a rebase?

git rebase --abort

This cancels the current rebase operation and returns the branch to the state it was in before the rebase started.

⭐⭐⭐⭐ IMPORTANT

15. How do you skip a problematic commit during rebase?

git rebase --skip

This tells Git to skip the current commit being replayed.

Use carefully:

Only skip a commit when you understand why that commit is no longer required.

⭐⭐⭐⭐⭐ MUST KNOW

16. What is Interactive Rebase?

Interview Answer:

Interactive rebase allows us to modify, reorder, combine or remove commits before sharing the history. 

git rebase -i HEAD~3

This opens the last three commits for interactive editing.

⭐⭐⭐⭐ INTERVIEW FOLLOW-UP

17. What can you do with interactive rebase?

  • Reorder commits
  • Squash commits
  • Change commit messages
  • Edit commits
  • Drop commits
  • Combine multiple commits
pick   abc123 Add login page
squash def456 Fix login page
pick   ghi789 Add validation

The squash operation combines commits.

⭐⭐⭐⭐⭐ VERY FREQUENTLY ASKED

18. What is git merge --no-ff?

Interview Answer:

The --no-ff option forces Git to create a merge commit even when a fast-forward merge is possible. 

git merge --no-ff feature-login

Teams may use this when they want the history to clearly show that a feature branch was merged.

⭐⭐⭐⭐⭐ DEVOPS SCENARIO

19. Your feature branch is behind main. What would you do?

Interview Answer:

I would first update my local main branch and then bring the latest main changes into my feature branch.

Depending on the team's workflow, I can use merge or rebase. 

git switch main

git pull origin main

git switch feature-login

git rebase main

If the team does not allow rebasing shared branches, I would use merge instead.

⭐⭐⭐⭐⭐ REAL-TIME DEVOPS SCENARIO

20. You have local commits and main has new commits. How do you update your feature branch?

One approach is to rebase the feature branch onto the latest main: 

git switch main
git pull origin main

git switch feature-login
git rebase main

This keeps the feature commits on top of the latest main history.

⭐⭐⭐⭐⭐ PRODUCTION SCENARIO

21. Would you rebase main in production?

Interview Answer:

Normally, I would avoid rewriting history on a shared production or main branch.

For shared branches, merge is generally safer because it preserves the existing history.

Key Point:

Do not treat rebase as simply a "better merge". They solve different workflow needs.

⭐⭐⭐⭐⭐ CI/CD SCENARIO

22. How does merge/rebase affect CI/CD?

CI pipelines commonly run when branches are pushed or when Pull Requests are created or updated.

If a branch is rebased, the commit IDs change, so the CI system may see the rebased commits as new commits.

After resolving conflicts or rebasing, the branch should be tested again before merging.

⭐⭐⭐⭐⭐ INTERVIEW TRAP

23. Is rebase safer than merge?

No. It depends on the situation.

Rebase provides a cleaner history but rewrites commits. Merge preserves the existing history and is generally safer for shared branches.

Good interview answer:

"I would use rebase for keeping my private feature branch up to date and maintaining a linear history, but I would avoid rewriting history on shared branches."

⭐⭐⭐⭐⭐ SCENARIO

24. You started a rebase and got many conflicts. What would you do?

  1. Check the current rebase state.
  2. Review the conflicted files.
  3. Resolve each conflict carefully.
  4. Stage the resolved files.
  5. Run git rebase --continue.
  6. Repeat until the rebase completes.
  7. If the rebase is no longer appropriate, use git rebase --abort.
git status

# Resolve conflict

git add .

git rebase --continue

# If necessary:
git rebase --abort
⭐⭐⭐⭐⭐ REAL-TIME DEVOPS

25. A developer force-pushed after rebasing. What should the team be careful about?

Because rebase rewrites history, a force push can replace the remote branch history.

Other developers who already based work on the old history may need to reconcile their local branches.

Important:

Force-pushing shared branches can disrupt other developers. It should be done only when the team workflow permits it.

🧠 QUICK COMMAND REVISION

Git Merge & Rebase Commands

# Merge
git switch main
git merge feature

# Force merge commit
git merge --no-ff feature

# Rebase
git switch feature
git rebase main

# Continue rebase
git rebase --continue

# Abort rebase
git rebase --abort

# Skip current commit
git rebase --skip

# Interactive rebase
git rebase -i HEAD~3

# Check status
git status

# View history
git log --oneline --graph --all
