GitHub Actions Security

Secrets, GITHUB_TOKEN, permissions, OIDC, AWS IAM, least privilege, environments and real-time security scenarios.

⭐⭐⭐⭐⭐ 1. Why is GitHub Actions Security Important?

GitHub Actions can access source code, cloud resources, deployment systems and secrets. A poorly secured workflow can therefore become an entry point into the infrastructure. The main security goals are:

• Protect credentials
• Limit permissions
• Secure workflow execution
• Prevent secret exposure
• Control production deployments
• Use short-lived credentials where possible
GitHub Repository
↓
Workflow
↓
Credentials / Permissions
↓
Cloud Resources
↓
Production

⭐⭐⭐⭐⭐ 2. What are GitHub Secrets?

GitHub Secrets are encrypted values used to store sensitive information such as API tokens, passwords, private credentials and other secrets required by workflows. They should not be hard-coded directly into workflow files. 
- name: Deploy

  env:
    API_TOKEN: ${{ secrets.API_TOKEN }}

  run: ./deploy.sh
Never commit passwords, access keys, private keys or tokens directly into the repository.

⭐⭐⭐⭐⭐ 3. Where Can Secrets Be Stored?

Scope Use
Repository Secret Used by workflows in a repository.
Environment Secret Used for a specific environment such as production.
Organization Secret Can be shared across selected repositories.
For production deployments, environment-level controls can be useful because production credentials can be isolated from development workflows.

⭐⭐⭐⭐⭐ 4. How Do You Use Secrets?

name: Deploy

on:
  workflow_dispatch:

jobs:

  deploy:

    runs-on: ubuntu-latest

    steps:

      - name: Deploy Application
        env:
          DEPLOY_TOKEN: ${{ secrets.DEPLOY_TOKEN }}

        run: |
          ./deploy.sh
Do not use commands such as: 
echo "${{ secrets.DEPLOY_TOKEN }}"
because exposing secrets in logs is dangerous.

⭐⭐⭐⭐⭐ 5. What is GITHUB_TOKEN?

GITHUB_TOKEN is a token automatically provided to a GitHub Actions workflow for interacting with GitHub resources. Its permissions should be restricted to only what the workflow needs. 
permissions:
  contents: read

⭐⭐⭐⭐⭐ 6. What are Workflow Permissions?

Permissions control what the workflow's GitHub token is allowed to access. A secure workflow should follow the principle of least privilege. 
permissions:
  contents: read

For example, if the workflow only needs to read repository files, do not give it unnecessary write permissions.

⭐⭐⭐⭐⭐ 7. Least Privilege

Least privilege means giving a workflow, user or service only the minimum permissions required to perform its task.
Required Permission
↓
Minimum Access
↓
Perform Task
↓
No Unnecessary Privileges
Interview answer:
"I follow least privilege by restricting GitHub token permissions, limiting AWS IAM permissions and using separate roles for different environments."

⭐⭐⭐⭐⭐ 8. What is GitHub OIDC?

OpenID Connect allows GitHub Actions to authenticate with supported cloud providers using short-lived identity credentials instead of storing long-lived cloud access keys in GitHub Secrets.
GitHub Actions
↓
OIDC Identity Token
↓
Cloud Identity Provider
↓
IAM Role
↓
Temporary Credentials
↓
Cloud Resources

⭐⭐⭐⭐⭐ 9. Why Use OIDC with AWS?

Without OIDC, teams may store long-lived AWS access keys in GitHub Secrets. With OIDC, GitHub Actions can request temporary credentials by assuming an AWS IAM role. This reduces the risk associated with long-lived credentials.
Long-Lived Access Keys OIDC
Credentials stored and rotated Short-lived credentials
Higher credential exposure risk Reduced credential storage
Manual credential management Federated identity

⭐⭐⭐⭐⭐ 10. AWS OIDC Workflow

permissions:
  id-token: write
  contents: read

steps:

  - name: Configure AWS Credentials
    uses: aws-actions/configure-aws-credentials@v4
    with:
      role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
      aws-region: ap-south-1
The workflow requests an OIDC token and uses it to assume the configured AWS IAM role. The IAM role's trust policy determines which GitHub identities are allowed to assume it.

⭐⭐⭐⭐⭐ 11. AWS IAM Role

The AWS IAM role defines what actions the GitHub Actions workflow can perform after authentication. For example, a deployment role may be allowed to push images to ECR or interact with specific deployment resources.
GitHub Identity
↓
IAM Trust Policy
↓
IAM Role
↓
IAM Permissions Policy
↓
AWS Resources

⭐⭐⭐⭐⭐ 12. Trust Policy vs Permissions Policy

Trust Policy Permissions Policy
Defines who can assume the role. Defines what the role can do.
Controls trusted identities. Controls allowed AWS actions.
Authentication relationship. Authorization permissions.
Easy way to remember:

Trust Policy → "Who can use this role?"
Permissions Policy → "What can this role do?"

⭐⭐⭐⭐⭐ 13. Example: Restrict AWS Permissions

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecr:GetAuthorizationToken",
        "ecr:BatchCheckLayerAvailability",
        "ecr:PutImage",
        "ecr:InitiateLayerUpload",
        "ecr:UploadLayerPart",
        "ecr:CompleteLayerUpload"
      ],
      "Resource": "*"
    }
  ]
}
In a real environment, permissions should be designed according to the exact workflow requirements and resource scope. Avoid giving a CI workflow unrestricted administrator permissions.

⭐⭐⭐⭐⭐ 14. Production Environment Protection

Production deployments should have additional controls such as:

• Required reviewers
• Environment-specific secrets
• Deployment restrictions
• Branch protection
• Approval gates
• Least-privilege credentials

⭐⭐⭐⭐⭐ 15. Branch Protection

Branch protection helps prevent unsafe changes from being directly merged into important branches such as main. Typical controls include:

• Pull request requirement
• Required approvals
• Required status checks
• Restrict direct pushes
• Code review requirements

⭐⭐⭐⭐⭐ 16. Pull Request Security

Be careful when workflows execute code from untrusted pull requests, especially when those workflows have access to secrets or elevated permissions.
A malicious change in a pull request should not be able to freely access production credentials or sensitive infrastructure. Use appropriate workflow triggers, permissions and approval controls.

⭐⭐⭐⭐⭐ 17. Why is pull_request_target Sensitive?

pull_request_target runs in the context of the base repository and can have access to repository-level resources that ordinary pull request workflows may not have. Because of this, it must be used carefully when executing code or processing untrusted pull request content.
Interview point:
Never blindly execute untrusted pull request code with elevated permissions or access to sensitive secrets.

⭐⭐⭐⭐⭐ 18. Third-Party Actions Security

GitHub Actions can use third-party actions from the marketplace or other repositories. However, an action executes code in the workflow environment, so its source and permissions should be reviewed.
Best practice:

• Prefer trusted actions.
• Review action source.
• Pin versions carefully.
• Minimize workflow permissions.
• Keep actions updated through a controlled process.

⭐⭐⭐⭐ 19. Why Pin Action Versions?

- uses: actions/checkout@v4
Pinning an action version provides more predictable workflow behavior than blindly tracking an unknown moving version. For highly controlled environments, organizations may pin actions to specific commit SHAs according to their security policy.

⭐⭐⭐⭐⭐ 20. Secret Leakage Prevention

To reduce accidental secret exposure:

1. Never hard-code secrets.
2. Use GitHub Secrets or an external secret manager.
3. Do not print secrets in logs.
4. Restrict workflow permissions.
5. Avoid unnecessary secret access.
6. Rotate compromised credentials immediately.
7. Prefer short-lived credentials where possible.

⭐⭐⭐⭐⭐ 21. Secret Scanning

Secret scanning tools detect credentials or sensitive patterns that may have accidentally been committed to source control. Examples include:

GitHub Secret Scanning Gitleaks 
gitleaks detect --source .

⭐⭐⭐⭐⭐ 24. Real-Time Scenario: AWS Authentication Failed

Problem: GitHub Actions cannot assume the AWS IAM role.

Check: 1. OIDC provider configuration.
2. id-token: write permission.
3. IAM trust policy.
4. Repository/branch restrictions.
5. Role ARN.
6. AWS account.
7. Region.
8. GitHub workflow claims.

⭐⭐⭐⭐⭐ 25. Real-Time Scenario: Secret Not Available

Possible causes:

• Incorrect secret name
• Secret belongs to another repository
• Environment not selected
• Workflow is running from an untrusted context
• Secret was deleted or renamed
• Incorrect expression syntax 
${{ secrets.MY_SECRET }}

⭐⭐⭐⭐⭐ 26. Real-Time Scenario: Secret Accidentally Committed

If a credential is committed to Git:

1. Revoke or rotate the credential immediately.

2. Remove it from the repository.

3. Check whether it was used maliciously.

4. Update the application/workflow to use secure storage.

5. Review repository history and access.

6. Add secret scanning/prevention controls.
Deleting the secret from the latest commit alone does not make a previously exposed credential safe. Rotate it.

⭐⭐⭐⭐⭐ 27. Secure GitHub Actions Workflow

name: Secure CI

on:
  pull_request:
    branches:
      - main

permissions:
  contents: read

jobs:

  test:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Install
        run: npm ci

      - name: Test
        run: npm test

      - name: Secret Scan
        run: |
          echo "Run secret scanning here"
The important ideas are:

• Read-only permissions by default
• No unnecessary secrets
• Automated validation
• Security scanning
• Controlled deployment

⭐⭐⭐⭐⭐ 28. Security Checklist

  • Use least-privilege workflow permissions.
  • Never hard-code credentials.
  • Use GitHub Secrets for required sensitive values.
  • Prefer OIDC for cloud authentication where supported.
  • Use restricted AWS IAM roles.
  • Protect production environments.
  • Use branch protection.
  • Review third-party actions.
  • Use secret scanning.
  • Scan dependencies and container images.
  • Do not expose secrets in logs.
  • Rotate credentials immediately after exposure.
  • Be careful with untrusted pull requests.

🎯 Interview-Ready Answer

"To secure GitHub Actions, I start with least-privilege permissions for the GITHUB_TOKEN and avoid hard-coding credentials. For sensitive values, I use GitHub Secrets or an appropriate external secret-management solution. For AWS deployments, I prefer GitHub OIDC with an IAM role so the workflow receives temporary credentials instead of storing long-lived AWS access keys. I also protect production environments with approvals and branch protection, review third-party Actions, scan repositories for leaked secrets, and perform dependency and container security scans. For pull requests from untrusted sources, I make sure sensitive secrets and elevated permissions are not exposed unnecessarily."
