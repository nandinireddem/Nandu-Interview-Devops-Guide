⭐⭐⭐⭐⭐ Scenario 1 — Workflow Does Not Start

Interviewer:
"You pushed code to the main branch, but your GitHub Actions workflow did not start. What will you check?"
Step 1: Check whether the workflow file exists under: 
.github/workflows/
Step 2: Check the YAML syntax.

Step 3: Check the trigger. 
on:
  push:
    branches:
      - main
Step 4: Confirm that the push actually targeted the expected branch.

Step 5: Check whether the workflow is disabled or restricted by repository settings.

⭐⭐⭐⭐⭐ Scenario 2 — Workflow YAML Error

Problem:
"GitHub reports that the workflow file is invalid."
Check:

• YAML indentation
• Incorrect key names
• Missing colon
• Incorrect expressions
• Invalid workflow syntax
• Incorrect on configuration
• Unsupported action configuration 
jobs:

  build:
    runs-on: ubuntu-latest

    steps:
      - name: Build
        run: echo "Building..."

↓ Docker Tag
↓ Docker Push
Then verify:
• Registry URL

"GitHub Actions cannot push an image to Amazon ECR."
Check:

1. AWS authentication.
2. OIDC configuration.
3. IAM role trust policy.
4. IAM permissions.
5. ECR repository.
6. AWS region.
7. ECR login.
8. Image tag.

⭐⭐⭐⭐⭐ Scenario 9 — AWS OIDC Authentication Failed

Problem:
"GitHub Actions says it cannot assume the AWS IAM role."
Check the following in order:

1. Workflow permission 
permissions:
  id-token: write
  contents: read
2. AWS OIDC provider Confirm the GitHub OIDC provider exists in AWS.

3. IAM trust policy Verify that the correct GitHub repository/branch or other intended claims are trusted.

4. Role ARN Verify that the workflow references the correct role.

⭐⭐⭐⭐⭐ Scenario 10 — Secret Is Empty or Unavailable

Problem:
"A GitHub Secret appears to be unavailable inside the workflow."
Check:

• Exact secret name
• Repository vs environment secret
• Correct environment
• Workflow context
• Repository permissions
• Whether the secret actually exists Example: 
${{ secrets.AWS_ROLE_ARN }}
Do not print the secret value while troubleshooting.

GitHub permission: Check:

⭐⭐⭐⭐⭐ Scenario 13 — ImagePullBackOff

Interviewer:
"Kubernetes shows ImagePullBackOff after your GitHub Actions deployment. How do you troubleshoot?"
First inspect the pod: 
kubectl describe pod <pod-name>
Check:
• Image repository
• Image tag
• ECR/registry access
• ImagePullSecrets
• Node network connectivity
• Registry permissions

⭐⭐⭐⭐⭐ Scenario 14 — CrashLoopBackOff

Problem:
"The deployment succeeds but the application enters CrashLoopBackOff."
Check: 
kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>
Possible causes:

• Application startup failure
• Incorrect environment variables
• Missing Secret/ConfigMap
• Incorrect command
• Port/configuration issue
• Dependency unavailable
• Failed health checks

⭐⭐⭐⭐⭐ Scenario 15 — Pipeline Succeeds but Deployment Is Wrong

Problem:
"GitHub Actions is green, but Kubernetes is still running the old image."
Check:

1. Image tag generated by CI.
2. Image actually pushed to registry.
3. Deployment manifest.
4. Deployment rollout.
5. Kubernetes image field.
6. GitOps repository if ArgoCD is used.
7. ArgoCD sync status.

⭐⭐⭐⭐⭐ Scenario 16 — ArgoCD Is Not Deploying the New Image

Problem:
"GitHub Actions pushed the image, but ArgoCD did not deploy it."
Check:

• Did CI update the GitOps repository?
• Did the commit reach the correct branch?
• Is ArgoCD tracking the correct repository?
• Is ArgoCD tracking the correct path?
• Is the application OutOfSync?
• Are there manifest errors?
• Is auto-sync enabled?

⭐⭐⭐⭐⭐ Scenario 17 — Job Is Stuck

• Runner labels
• Concurrency restrictions
• Organization/repository limits
• Workflow queue For self-hosted runners, verify that the runner is online and has matching labels.

⭐⭐⭐⭐⭐ Scenario 21 — Production Deployment Failed

Problem:
"Production deployment completed but the application is unhealthy."
Immediate priorities:

1. Check application health.
2. Check monitoring and logs.
3. Determine blast radius.
4. Roll back if required.
5. Investigate root cause.
6. Prevent recurrence. 
kubectl rollout status deployment/myapp

kubectl rollout history deployment/myapp

kubectl rollout undo deployment/myapp

⭐⭐⭐⭐⭐ Scenario 22 — Security Scan Failed

Problem:
"A Trivy/security scan failed the pipeline."
Do not immediately bypass the scan. First determine:

• Vulnerability severity
• Affected package/image layer
• Whether a fixed version exists
• Whether the issue is actually exploitable
• Organization's security policy Then update the vulnerable dependency/base image or handle an approved exception through the security process.

⭐⭐⭐⭐⭐ Scenario 23 — Secret Accidentally Committed

Interviewer:
"A developer accidentally committed an AWS access key. What do you do?"
1. Immediately disable/rotate the exposed credential.

2. Check CloudTrail or relevant logs for suspicious usage.

3. Remove the secret from source/history according to the incident procedure.

4. Move credentials into secure storage.

5. Enable secret scanning/prevention.

6. Review why the control failed.
The most important first action is credential rotation/revocation, not simply deleting the file from Git.

⭐⭐⭐⭐⭐ Scenario 24 — PR Workflow Security Issue

Problem:
"A pull request from an untrusted contributor needs to run tests, but the workflow also has access to production secrets."
Do not expose production secrets unnecessarily. Separate untrusted PR validation from privileged deployment workflows. Use:

• Minimal permissions
• Appropriate PR triggers
• Environment protection
• Approval gates
• Separate deployment workflow

jobs:

6. Check Recent Changes

↓

Interview answer:
"I start from the failed workflow run and identify the exact job and step. I read the logs, compare the failed run with the last successful run, verify configuration, secrets and permissions, fix the root cause and rerun the workflow. After it succeeds, I verify the deployed application rather than assuming a green pipeline means the release is healthy."

⭐⭐⭐⭐⭐ Scenario 27 — CI Green but Application Down

A successful CI/CD workflow only confirms that the defined pipeline steps completed successfully. It does not automatically prove that the application is healthy. Check:

• Application logs
• Kubernetes pods
• Service endpoints
• Ingress/load balancer
• Health probes
• Metrics
• Alerts
• Recent deployment
Pipeline Success
≠
Application Health

⭐⭐⭐⭐ Scenario 28 — Need Rollback After Bad Release

If the application is unhealthy after deployment, first stabilize the service. For Kubernetes: 
kubectl rollout undo deployment/myapp
Then verify: 
kubectl rollout status deployment/myapp

kubectl get pods
After recovery, investigate the failed release.

⭐⭐⭐⭐ Scenario 29 — Multiple Jobs Should Run in Parallel

jobs:

  unit-tests:
    runs-on: ubuntu-latest
    steps:
      - run: npm test

  security:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Security scan"

  lint:
    runs-on: ubuntu-latest
    steps:
      - run: npm run lint
Because these jobs have no dependency on each other, they can execute independently. If a deployment requires all three, a later job can use: 
needs:
  - unit-tests
  - security
  - lint

⚠️ Common Interview Mistakes

Mistake Better Approach
"I will rerun the pipeline." First identify and fix the root cause.
"I will add admin permissions." Use least privilege.
"I will print the secret to debug." Never expose secrets.
"Green pipeline means deployment is healthy." Verify application health.
"Delete the leaked secret from Git." Rotate/revoke it immediately.
"Give AWS access keys to GitHub." Prefer OIDC and short-lived credentials.

🎯 Master Interview Answer

"When troubleshooting a GitHub Actions pipeline, I first identify whether the issue is with the trigger, workflow syntax, runner, application build, test, security scan, registry authentication, cloud authentication or deployment. I start from the failed workflow run, identify the failed job and step, and inspect the logs. Then I compare the failed run with the last successful run and check recent code or configuration changes. For cloud-related failures, I verify authentication and permissions. For AWS, I would check the OIDC configuration, IAM trust policy and role permissions. For Kubernetes failures, I check the deployment, pods, events, logs, image configuration and RBAC. After identifying the root cause, I make the smallest appropriate fix, rerun the workflow and verify the actual application health. If a production deployment causes an incident, I prioritize stabilization and rollback when necessary, followed by root-cause analysis and preventive actions."
