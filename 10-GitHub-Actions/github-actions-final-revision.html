Last-minute interview revision covering the most important concepts, workflow syntax, CI/CD flow, security, AWS, Docker, Kubernetes and real-time troubleshooting.

⭐⭐⭐⭐⭐ 1. What is GitHub Actions?

GitHub Actions is a CI/CD automation platform integrated with GitHub. It allows us to automatically build, test, scan and deploy applications based on events such as code pushes, pull requests or manual triggers.

⭐⭐⭐⭐⭐ 2. GitHub Actions Architecture

The most important components are:

Workflow → YAML automation definition

Event → Trigger that starts workflow

Job → Group of steps executed on a runner

Step → Individual command or action

Runner → Machine that executes the job

Action → Reusable automation component

⭐⭐⭐⭐⭐ 3. Workflow → Job → Step

name: CI

on:
  push:
    branches:
      - main

jobs:

  build:

    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Build
        run: echo "Building application"

      - name: Test
        run: echo "Running tests"
Workflow
↓
Job
↓
Steps

⭐⭐⭐⭐⭐ 6. What is a Runner?

A runner is the machine where a GitHub Actions job actually executes. GitHub-hosted runners are managed by GitHub. Self-hosted runners are machines managed by the organization.
GitHub-Hosted Self-Hosted
Managed by GitHub Managed by organization
Easy setup More control
Temporary environments Can use custom infrastructure

⭐⭐⭐⭐⭐ 7. What is an Action?

An Action is a reusable unit of automation. Example: 
- uses: actions/checkout@v4
Instead of writing checkout logic manually, we use the existing action.

⭐⭐⭐⭐⭐ 8. run vs uses

run uses
Executes shell commands. Executes a reusable Action.
run: npm test uses: actions/checkout@v4

⭐⭐⭐⭐⭐ 9. Job Dependencies with needs

jobs:

  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Testing"

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploying"
needs creates a dependency between jobs. Here, deployment starts only after the test job succeeds.

⭐⭐⭐⭐⭐ 10. Environment Variables

env:
  APP_ENV: production

jobs:

  build:

    runs-on: ubuntu-latest

    steps:

      - run: echo "$APP_ENV"
Environment variables store non-secret configuration values. Sensitive information should be stored as secrets instead.

⭐⭐⭐⭐⭐ 11. GitHub Secrets

GitHub Secrets are encrypted values used for sensitive information such as tokens, passwords and credentials. Example: 
env:
  API_TOKEN: ${{ secrets.API_TOKEN }}
Never hard-code credentials inside workflow files.

⭐⭐⭐⭐⭐ 12. GITHUB_TOKEN

GitHub automatically provides GITHUB_TOKEN to workflows for interacting with GitHub resources. Its permissions should be restricted according to the workflow's requirements. 
permissions:
  contents: read

⭐⭐⭐⭐⭐ 13. GitHub OIDC

GitHub OIDC allows a workflow to authenticate with cloud providers using short-lived identity credentials instead of storing long-lived cloud access keys.
GitHub Actions
↓
OIDC Token
↓
AWS IAM
↓
IAM Role
↓
Temporary Credentials
↓
AWS Resources

⭐⭐⭐⭐⭐ 14. AWS OIDC Permissions

permissions:
  id-token: write
  contents: read
id-token: write allows the workflow to request an OIDC identity token. The AWS IAM role trust policy then determines whether the GitHub identity is allowed to assume the role.

⭐⭐⭐⭐⭐ 15. Trust Policy vs Permissions Policy

Trust Policy Permissions Policy
Who can assume the role? What can the role do?
Controls trusted identities. Controls AWS actions/resources.
Easy memory:

Trust = WHO
Permissions = WHAT

⭐⭐⭐⭐⭐ 21. Matrix Strategy

strategy:

  matrix:
    node: [18, 20, 22]

steps:

  - uses: actions/setup-node@v4
    with:
      node-version: ${{ matrix.node }}
Matrix strategy allows the same job to run against multiple configurations such as operating systems, language versions or runtime versions.

⭐⭐⭐⭐⭐ 24. How Do You Secure GitHub Actions?

  • Use least-privilege permissions.
  • Never hard-code credentials.
  • Use GitHub Secrets.
  • Prefer OIDC for cloud authentication.
  • Restrict AWS IAM permissions.
  • Protect production environments.
  • Use branch protection.
  • Review third-party Actions.
  • Use secret scanning.
  • Scan dependencies and container images.
  • Be careful with untrusted pull requests.

⭐⭐⭐⭐⭐ 26. Scenario — Workflow Not Triggering

"My workflow is not running after I push code. What will you check?"
I would first verify the workflow file location and YAML syntax. Then I would check the configured trigger and branch filters. After that I would check whether the workflow is disabled or whether repository settings are preventing the expected execution.

⭐⭐⭐⭐⭐ 27. Scenario — Tests Fail Only in CI

I would compare the local and CI environments. I would check:

• Runtime versions
• Dependencies
• Environment variables
• Operating system
• Database/service dependencies
• Test configuration Then I would reproduce the failure as closely as possible.

⭐⭐⭐⭐⭐ 28. Scenario — Docker Push Failed

I would verify the image was built successfully, then check registry login, credentials, repository name, image tag and registry permissions. For AWS ECR, I would additionally verify AWS authentication, OIDC, IAM permissions and region.

⭐⭐⭐⭐⭐ 29. Scenario — AWS OIDC Failed

I would check:

1. id-token: write permission.
2. AWS OIDC provider.
3. IAM trust policy.
4. Repository/branch conditions.
5. IAM role ARN.
6. Role permissions.

⭐⭐⭐⭐⭐ 30. Scenario — Kubernetes ImagePullBackOff

I would run: 
kubectl describe pod <pod-name>
Then check the image name, image tag, registry access, authentication and ImagePullSecrets.

⭐⭐⭐⭐⭐ 31. Scenario — CrashLoopBackOff

I would inspect the current and previous container logs and describe the pod. 
kubectl logs <pod-name>

kubectl logs <pod-name> --previous

kubectl describe pod <pod-name>
Then check application startup, environment variables, Secrets, ConfigMaps, commands and health probes.

⭐⭐⭐⭐⭐ 32. Scenario — Bad Production Deployment

My priority would be to stabilize production. I would check application health and logs, determine the impact and rollback if required. After recovery, I would investigate the root cause and add preventive controls. 
kubectl rollout undo deployment/myapp

kubectl rollout status deployment/myapp

⭐⭐⭐⭐⭐ 33. Secret Accidentally Committed

The first priority is to revoke or rotate the exposed credential. Then I would investigate possible usage, remove the secret from the repository according to the organization's procedure, move it to secure storage and enable preventive scanning.
Never assume that deleting the file from the latest commit makes the credential safe.

⭐⭐⭐⭐⭐ 34. Green Pipeline but Application Is Down

A green pipeline only means the configured workflow steps succeeded. I would verify the actual application using:

• Pod status
• Application logs
• Health probes
• Service
• Ingress/load balancer
• Metrics
• Alerts
CI Success
≠
Application Health

🎤 Final Interview Answer

"GitHub Actions is a CI/CD automation platform integrated with GitHub. I use workflows defined in YAML to automate stages such as checkout, build, testing, security scanning, Docker image creation and deployment. A workflow contains jobs, and jobs contain steps that execute on runners. For security, I use least-privilege permissions, GitHub Secrets and prefer OIDC for AWS authentication instead of long-lived access keys. The GitHub identity assumes a restricted IAM role through its trust policy. In a production CI/CD pipeline, I would build and test the application, scan it, build and scan the container image, push it to a registry and deploy it to the target environment. For Kubernetes and GitOps, GitHub Actions can update the image or GitOps repository while ArgoCD synchronizes the desired state to the cluster. For troubleshooting, I start from the failed workflow, identify the failed job and step, read the logs, check configuration and permissions, fix the root cause, rerun the workflow and finally verify application health."
