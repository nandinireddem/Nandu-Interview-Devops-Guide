GitHub Actions Core Concepts

Important concepts, YAML structure, workflows, events, jobs, steps, actions, runners, variables, artifacts and interview questions.

⭐⭐⭐⭐⭐ 1. What is GitHub Actions?

GitHub Actions is a CI/CD and automation platform integrated with GitHub. It allows us to automatically build, test, scan and deploy applications based on repository events.
Developer
↓
Git Push
↓
GitHub Actions
↓
Build → Test → Scan
↓
Deploy
Interview answer:
"GitHub Actions is GitHub's automation and CI/CD platform. We define workflows using YAML files inside the repository, and those workflows execute jobs on runners when specified events occur."

⭐⭐⭐⭐⭐ 2. Where are GitHub Actions workflows stored?

Workflow YAML files are stored inside the repository under: 
.github/workflows/

Example:

project/
├── src/
├── Dockerfile
└── .github/
    └── workflows/
        └── ci.yml

⭐⭐⭐⭐⭐ 3. What is a Workflow?

A workflow is an automated process defined in a YAML file. It specifies when automation should run and what jobs should be executed. 
name: CI Pipeline

on:
  push:
    branches:
      - main

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - run: echo "Build application"

⭐⭐⭐⭐⭐ 4. What is an Event?

An event is something that triggers a workflow.
EventUse
pushRun when code is pushed.
pull_requestRun when a pull request changes.
workflow_dispatchRun manually.
scheduleRun on a schedule.
workflow_callCall a reusable workflow.
on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main

⭐⭐⭐⭐⭐ 5. What is a Job?

A job is a collection of steps that runs on a runner. A workflow can contain one or multiple jobs. 
jobs:

  build:
    runs-on: ubuntu-latest

    steps:
      - run: echo "Build"

  test:
    runs-on: ubuntu-latest

    steps:
      - run: echo "Test"

Jobs can run independently or can be connected using needs.

⭐⭐⭐⭐⭐ 6. What is a Step?

A step is an individual operation inside a job. A step can execute a shell command or use an action. 
steps:

  - name: Checkout
    uses: actions/checkout@v4

  - name: Install
    run: npm install

  - name: Test
    run: npm test

⭐⭐⭐⭐⭐ 7. What is an Action?

An Action is a reusable component that performs a specific task. Actions prevent us from repeatedly writing common automation logic. 
- name: Checkout repository
  uses: actions/checkout@v4

Here actions/checkout@v4 is a reusable action used to checkout repository code.

⭐⭐⭐⭐⭐ 8. What is a Runner?

A runner is the machine that executes a GitHub Actions job.
Runner Description
GitHub-hosted Machine managed by GitHub.
Self-hosted Machine managed by the organization. 
runs-on: ubuntu-latest
Interview point:
GitHub-hosted runners are convenient because GitHub manages the execution environment. Self-hosted runners provide greater control over the environment and infrastructure.

⭐⭐⭐⭐⭐ 9. GitHub-Hosted vs Self-Hosted Runner

GitHub-Hosted Self-Hosted
Managed by GitHub Managed by organization
Easy to configure Requires infrastructure management
Fresh environment generally provided for each job Organization controls environment
Less maintenance More control/customization

⭐⭐⭐⭐⭐ 10. Complete Basic Workflow

name: Basic CI

on:
  push:
    branches:
      - main

jobs:

  build:
    runs-on: ubuntu-latest

    steps:

      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Install Dependencies
        run: npm install

      - name: Run Tests
        run: npm test

      - name: Build
        run: npm run build

Job
↓
Runner
↓
Checkout
↓

⭐⭐⭐⭐⭐ 11. What is runs-on?

runs-on specifies the runner environment where the job will execute. 
runs-on: ubuntu-latest

Other examples can include Windows or macOS runners:

runs-on: windows-latest

runs-on: macos-latest

⭐⭐⭐⭐⭐ 12. What is run vs uses?

run uses
Executes shell commands. Uses a reusable Action.
run: npm test uses: actions/checkout@v4 
- name: Test
  run: npm test

- name: Checkout
  uses: actions/checkout@v4

⭐⭐⭐⭐⭐ 13. Job Dependencies using needs

The needs keyword makes one job wait for another job to complete successfully. 
jobs:

  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build"

  test:
    needs: build
    runs-on: ubuntu-latest
    steps:
      - run: echo "Test"

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - run: echo "Deploy"
Build
↓
Test
↓
Deploy

⭐⭐⭐⭐ 14. Parallel Jobs

If jobs do not depend on each other, they can execute independently and potentially in parallel. 
jobs:

  build:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Build"

  security:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Security Scan"

  test:
    runs-on: ubuntu-latest
    steps:
      - run: echo "Tests"
Build ↘
Security → Independent Jobs
Test ↗

⭐⭐⭐⭐⭐ 15. Environment Variables

Environment variables store configuration values used during workflow execution. 
env:
  APP_ENV: production

jobs:

  build:
    runs-on: ubuntu-latest

    steps:
      - run: echo "$APP_ENV"

Variables can be defined at workflow, job or step level.

⭐⭐⭐⭐⭐ 16. GitHub Secrets

Secrets are encrypted values used to store sensitive information such as tokens, passwords and credentials. 
steps:

  - name: Deploy
    env:
      API_TOKEN: ${{ secrets.API_TOKEN }}

    run: ./deploy.sh
Never hard-code passwords, private keys or cloud credentials inside workflow YAML files.

⭐⭐⭐⭐ 17. Artifacts

Artifacts allow files produced during a workflow to be stored and downloaded after the workflow or job completes. 
- name: Upload Build
  uses: actions/upload-artifact@v4
  with:
    name: build-output
    path: dist/

Examples: test reports, compiled packages, logs and build outputs.

⭐⭐⭐⭐ 18. Matrix Strategy

A matrix allows the same job to run against multiple combinations, such as different language versions or operating systems. 
strategy:
  matrix:
    node: [18, 20, 22]

steps:
  - run: echo "Node ${{ matrix.node }}"
Node 18    Node 20    Node 22
↓        ↓        ↓
Tests

⭐⭐⭐⭐ 19. Manual Workflow

workflow_dispatch allows users to manually start a workflow. 
on:
  workflow_dispatch:

Useful for controlled deployments and operational tasks.

⭐⭐⭐⭐ 20. Scheduled Workflow

on:
  schedule:
    - cron: "0 2 * * *"
Scheduled workflows run according to cron expressions.

⭐⭐⭐⭐⭐ 21. Permissions

The permissions section controls what the workflow's GITHUB_TOKEN can access. 
permissions:
  contents: read
Use least privilege. Give the workflow only the permissions it actually requires.

⭐⭐⭐⭐⭐ 23. Real-Time Scenario: Workflow Failed

Question:
"Your GitHub Actions pipeline failed. How will you troubleshoot it?"

Answer: 1. Open the failed workflow run.
2. Identify the failed job.
3. Identify the failed step.
4. Read the logs.
5. Compare with the last successful run.
6. Check recent code/configuration changes.
7. Check dependencies, secrets and permissions.
8. Fix the root cause.
9. Rerun and verify.

⭐⭐⭐⭐⭐ 24. Real-Time Scenario: Secret Error

If a secret is not working, check:

• Secret name
• Repository/environment scope
• Workflow permissions
• Event restrictions
• Cloud-side permissions
• Target account or role
Never print the secret value into workflow logs while troubleshooting.

⭐⭐⭐⭐⭐ 25. GitHub Actions + Docker

name: Docker CI

on:
  push:
    branches:
      - main

jobs:

  docker:
    runs-on: ubuntu-latest

    steps:

      - name: Checkout
        uses: actions/checkout@v4

      - name: Build Docker Image
        run: docker build -t myapp:${{ github.sha }} .

      - name: List Images
        run: docker images
Using the commit SHA as an image identifier helps connect the image to the exact source revision.

🎯 Interview-Ready Answer

"GitHub Actions is a CI/CD automation platform integrated with GitHub. Workflows are written in YAML and stored under the .github/workflows directory. A workflow is triggered by events such as push or pull request. It contains jobs, jobs contain steps, and steps can execute shell commands or reusable Actions. Each job runs on a runner. We can use GitHub-hosted or self-hosted runners depending on the requirement. For a production pipeline, I would use GitHub Actions to checkout code, build and test the application, perform security checks, build a Docker image, push it to a registry and deploy it to the target environment. For security, I would use Secrets or short-lived federated credentials where supported, apply least-privilege permissions and avoid exposing sensitive values in logs."
