Jenkins Git + Docker + CI/CD

Interview-focused guide covering Git integration, GitHub Webhooks, SCM triggers, Docker builds, container registries, image tagging, Jenkins credentials and an end-to-end production-style CI/CD flow.

⭐⭐⭐⭐⭐ Core Concept

A common Jenkins CI/CD workflow starts with a Git push and ends with a tested application artifact or Docker image being deployed.

Developer

GitHub

↓
Jenkins
↓

↓
Build
↓
Test

↓
Container Registry
↓
Deploy
↓

Real-time example: A developer pushes a Java application to GitHub. Jenkins is triggered through a webhook, checks out the code, runs Maven tests, builds a Docker image, pushes it to Amazon ECR and deploys the new image to Kubernetes.

⭐⭐⭐⭐⭐ 1. How does Jenkins integrate with Git?

Jenkins can connect to Git repositories and automatically checkout source code before executing build and test stages. The repository can be GitHub, GitLab, Bitbucket or another supported SCM system.

Typical flow

git push
    ↓
GitHub Repository
    ↓
Webhook
    ↓
Jenkins
    ↓
Checkout Source
    ↓
Build / Test

⭐⭐⭐⭐⭐ 2. Webhook vs Poll SCM

Webhook Poll SCM
Git provider notifies Jenkins when an event occurs. Jenkins periodically checks the repository.
Event-driven. Polling-based.
Usually faster reaction to changes. Can generate unnecessary repository checks.
Interview answer: "For modern CI/CD, I generally prefer webhooks because the Git provider can notify Jenkins immediately when a relevant event occurs, instead of Jenkins repeatedly polling the repository."

⭐⭐⭐⭐⭐ 3. What happens when a developer pushes code?

The important point is that Jenkins does not magically know that code changed. A trigger such as a webhook, polling mechanism or manual/API trigger starts the job.

⭐⭐⭐⭐⭐ 4. Jenkins Git Checkout

Simple checkout

stage('Checkout') {

    steps {
        checkout scm
    }
}

For a Pipeline job configured with SCM, checkout scm checks out the source configured for that job.

Explicit Git checkout

stage('Checkout') {

    steps {

        git branch: 'main',
            url: 'https://github.com/example/app.git'
    }
}
For private repositories, credentials should be configured securely through Jenkins Credentials rather than putting usernames or tokens directly into the Jenkinsfile.

⭐⭐⭐⭐⭐ 5. Why do we use Docker with Jenkins?

Docker packages an application together with its runtime dependencies into a portable container image. Jenkins can automate building, testing and publishing that image.
Without containerization, an application may behave differently between build and deployment environments. With Docker: Source Code → Docker Image → Same Image → Deployment This improves consistency between environments.

⭐⭐⭐⭐⭐ 6. Docker Build in Jenkins

stage('Docker Build') {

    steps {

        sh '''
        docker build \
          -t payment-app:${BUILD_NUMBER} .
        '''
    }
}
BUILD_NUMBER is a Jenkins-provided build identifier. Using a unique tag helps identify which Jenkins build produced an image.

⭐⭐⭐⭐⭐ 7. Docker Image Tagging Strategy

Avoid using only latest for production deployments. Use identifiable immutable or versioned tags where possible. 

payment-app:42
payment-app:1.4.2
payment-app:git-a8f32c1
Real-time example: Jenkins Build #42 creates: 
123456789.dkr.ecr.ap-south-1.amazonaws.com/payment-app:42
If deployment fails, you can identify exactly which build/image was used.

⭐⭐⭐⭐⭐ 8. Push Docker Image to Registry

A container registry stores Docker images so deployment systems can pull them later. Examples include Amazon ECR, Docker Hub, GitHub Container Registry and other OCI-compatible registries.

Generic example

docker login <registry>

docker tag payment-app:42 \
  <registry>/payment-app:42

docker push \
  <registry>/payment-app:42
Registry credentials should not be written directly into the Jenkinsfile or shell commands. Use Jenkins Credentials or an appropriate workload identity mechanism.

⭐⭐⭐⭐⭐ 9. Jenkins + Docker + ECR

A common AWS workflow:
GitHub
↓
Jenkins
↓
Docker Build
↓
Amazon ECR
↓
EKS / ECS
↓
Application
Jenkins builds the image and pushes it to ECR. The deployment platform then pulls the image from ECR.

Conceptual commands

docker build -t payment-app:${BUILD_NUMBER} .

docker tag payment-app:${BUILD_NUMBER} \
  ${ECR_REPOSITORY}:${BUILD_NUMBER}

docker push ${ECR_REPOSITORY}:${BUILD_NUMBER}

⭐⭐⭐⭐⭐ 10. Complete Jenkins Git + Docker Pipeline

pipeline {

    agent any

    environment {

        IMAGE_NAME = 'payment-app'
        REGISTRY = '123456789.dkr.ecr.ap-south-1.amazonaws.com'
        IMAGE_TAG = "${BUILD_NUMBER}"
    }

    stages {

        stage('Checkout') {

            steps {
                checkout scm
            }
        }

        stage('Build') {

            steps {
                sh 'mvn clean package'
            }
        }

        stage('Test') {

            steps {
                sh 'mvn test'
            }
        }

        stage('Docker Build') {

            steps {

                sh '''
                docker build \
                  -t ${IMAGE_NAME}:${IMAGE_TAG} .
                '''
            }
        }

        stage('Docker Tag') {

            steps {

                sh '''
                docker tag \
                  ${IMAGE_NAME}:${IMAGE_TAG} \
                  ${REGISTRY}/${IMAGE_NAME}:${IMAGE_TAG}
                '''
            }
        }

        stage('Push Image') {

            steps {

                sh '''
                docker push \
                  ${REGISTRY}/${IMAGE_NAME}:${IMAGE_TAG}
                '''
            }
        }
    }

    post {

        success {
            echo 'CI pipeline completed successfully'
        }

        failure {
            echo 'CI pipeline failed'
        }
    }
}
This demonstrates the pipeline flow. Authentication to ECR and other external systems should be implemented through secure Jenkins credentials or AWS identity mechanisms rather than hard-coded credentials.

⭐⭐⭐⭐⭐ 11. Docker Build vs Docker Push

docker build docker push
Creates an image locally/on the build agent. Uploads an image to a registry.
Uses Dockerfile and build context. Requires access to the target registry.
Example: docker build -t app:42 . Example: docker push registry/app:42

⭐⭐⭐⭐⭐ 12. How do you securely authenticate to Docker Registry?

Credentials should be stored in Jenkins Credentials or supplied through a secure identity mechanism. The pipeline should reference the credential rather than embedding the password or token in source code.

Conceptual Jenkins example

withCredentials([
    usernamePassword(
        credentialsId: 'docker-registry',
        usernameVariable: 'REGISTRY_USER',
        passwordVariable: 'REGISTRY_PASS'
    )
]) {

    sh '''
    echo "$REGISTRY_PASS" | \
      docker login \
      --username "$REGISTRY_USER" \
      --password-stdin registry.example.com
    '''
}
Never commit: 
docker login -u admin -p MyPassword
into a Jenkinsfile or Git repository.

⭐⭐⭐⭐⭐ 13. What if Docker build fails?

Check:

1. Dockerfile syntax.
2. Build context.
3. Required files.
4. Base image availability.
5. Network connectivity.
6. Docker daemon access.
7. Disk space.
8. CPU/memory resources.

Useful commands

docker version
docker info
docker images
docker ps
df -h

⭐⭐⭐⭐⭐ 14. What if Docker Push fails?

Common causes:
  • Registry authentication failure.
  • Wrong repository name.
  • Wrong image tag.
  • Repository does not exist.
  • Insufficient registry permissions.
  • Network connectivity problems.
  • Registry service issue.

Debugging approach

docker images

docker login <registry>

docker push <registry>/app:42

Then inspect the exact error and verify credentials and repository permissions.

⭐⭐⭐⭐⭐ 15. What if Jenkins cannot access Docker?

Problem: Pipeline reports that the Docker command cannot connect to the Docker daemon.

Check: 1. Is Docker installed on the Jenkins agent?
2. Is Docker running?
3. Does the Jenkins execution user have permission?
4. Is the correct Docker socket/runtime available?
5. Is the agent containerized?
6. Are security restrictions blocking Docker access?

Commands

docker version
docker info
docker ps

⭐⭐⭐⭐⭐ 16. Git Branch-based Deployment

A common strategy is: develop → Dev
release/* → QA/Staging
main → Production

Jenkins condition

stage('Production Deploy') {

    when {
        branch 'main'
    }

    steps {
        sh './deploy-production.sh'
    }
}
The exact branch strategy depends on the organization's Git workflow. The important concept is that deployment rules should be explicit and controlled.

⭐⭐⭐⭐⭐ 18. Real-Time Scenario: Jenkins Build Works but Deployment Fails

Suppose:

Git checkout → SUCCESS
Maven build → SUCCESS
Tests → SUCCESS
Docker build → SUCCESS
Docker push → SUCCESS
Deployment → FAILURE

Do not rebuild everything immediately. First inspect the deployment layer:
  • Image name/tag.
  • Registry availability.
  • Deployment manifest.
  • Kubernetes credentials.
  • Cluster connectivity.
  • Namespace.
  • Pod events and logs.

⭐⭐⭐⭐⭐ 19. Real-Time Scenario: Wrong Docker Image Deployed

Problem: Production is running an unexpected image. Likely cause: The pipeline uses a mutable tag such as latest or deployment configuration was not updated correctly. Better approach: Use unique version/build/commit-based tags. 
payment-app:105
payment-app:git-a8f32c1
This improves traceability because you can map a deployed image back to a specific source revision and Jenkins build.

⭐⭐⭐⭐⭐ 20. CI vs CD

CI CD
Continuous Integration Continuous Delivery / Deployment
Build and test code changes. Release and deploy validated artifacts.
Find integration issues early. Automate software delivery.
CI
Git → Build → Test → Scan → Package

CD
Artifact/Image → Deploy → Verify

⭐⭐⭐⭐⭐ 21. Jenkins + Git + Docker Best Practices

  • Keep Jenkinsfile in Git.
  • Use webhooks for event-driven triggering where appropriate.
  • Use unique image tags.
  • Avoid relying only on latest.
  • Never hard-code credentials.
  • Use Jenkins Credentials or workload identity.
  • Scan images before deployment.
  • Keep Docker images small and reproducible.
  • Use immutable artifacts where possible.
  • Promote the same tested image across environments rather than rebuilding different images unnecessarily.

🎯 If Interviewer Says: "Explain Jenkins CI/CD with Git and Docker"

"In a typical CI/CD workflow, a developer pushes code to GitHub. A webhook triggers the Jenkins pipeline. Jenkins checks out the source code and runs the build and automated tests. If the tests pass, Jenkins builds a Docker image and tags it with a unique build or source revision identifier. The image is then pushed to a container registry such as Amazon ECR. The deployment stage updates the target environment, for example Kubernetes or EKS, to use that image. For security, I don't hard-code Git, registry or cloud credentials inside the Jenkinsfile. I use Jenkins Credentials or appropriate cloud identity mechanisms. For production, I also prefer immutable/versioned image tags, security scanning and traceability between the Git commit, Jenkins build and deployed container image."
